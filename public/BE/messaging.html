Message Queues & Event-Driven

Tách rời service bằng messaging bất đồng bộ. RabbitMQ vs Kafka, pub/sub vs queue, đảm bảo at-least-once + idempotent consumer, Outbox pattern, Saga (orchestration vs choreography), ordering & dead-letter. Ví dụ MassTransit thực chiến trên .NET.

1. Vì sao dùng messaging?

Gọi HTTP đồng bộ giữa các service tạo coupling thời gian: A phải chờ B, B sập thì A sập. Messaging cho phép tách rời (decoupling) và chịu tải (buffering).

⏱️ Bất đồng bộ

Producer gửi rồi đi tiếp, không chờ consumer xử lý xong. Giảm độ trễ phản hồi user.

🔌 Decoupling

Producer không biết ai consume. Thêm consumer mới không sửa producer.

🌊 Buffering / spike

Tải đột biến được queue hấp thụ; consumer xử lý theo nhịp của mình.

2. Queue vs Pub/Sub

📥 Point-to-Point (Queue)

Một message → đúng một consumer xử lý (competing consumers để scale). Dùng cho "công việc cần làm": gửi email, xử lý đơn.

Command vs Event (đặt tên đúng): Command (SendEmailCommand) gửi tới một queue, kỳ vọng được xử lý — mệnh lệnh. Event (OrderPlacedEvent) publish, ai quan tâm thì nghe — thông báo quá khứ. Đừng publish command, đừng "ra lệnh" bằng event.

3. RabbitMQ vs Kafka

Hai công cụ giải hai bài toán khác nhau. Đừng hỏi "cái nào tốt hơn" mà hỏi "bài toán của tôi là gì".

Tiêu chíRabbitMQApache Kafka
Mô hìnhMessage broker (smart broker, dumb consumer)Distributed log (dumb broker, smart consumer)
RoutingLinh hoạt: exchange (direct/topic/fanout/headers)Topic + partition, đơn giản
Lưu trữ messageXoá sau khi ack (thường)Giữ theo retention (giờ/ngày/vô hạn) — replay được
ThroughputCao (chục nghìn/s)Rất cao (triệu/s), thiết kế cho stream lớn
OrderingTheo queueĐảm bảo trong 1 partition (theo key)
Consumer modelPush, broker theo dõi ackPull, consumer giữ offset
Use case lý tưởngTask queue, RPC, routing phức tạp, microservice commandsEvent streaming, log, analytics, event sourcing, replay
💡 Tóm gọn: Cần task queue + routing linh hoạt → RabbitMQ. Cần stream khối lượng lớn, replay, nhiều consumer độc lập đọc cùng dữ liệu → Kafka. Nhiều hệ thống lớn dùng cả hai cho từng phần.

4. Delivery guarantees & Idempotent Consumer

Trong hệ phân tán, exactly-once delivery gần như không khả thi end-to-end. Thực tế ta dùng at-least-once + consumer idempotent để đạt hiệu ứng "exactly-once processing".

MứcÝ nghĩaRủi ro
At-most-onceGửi tối đa 1 lần, ack trước khi xử lýCó thể mất message
At-least-onceGửi lại đến khi ack, ack sau khi xử lýCó thể xử lý trùng (duplicate)
Exactly-once (processing)At-least-once + dedup/idempotentPhức tạp, cần lưu trạng thái đã xử lý

Idempotent consumer — chống xử lý trùng

// Lưu MessageId đã xử lý; nếu thấy lại thì bỏ qua
public class PaymentConsumer : IConsumer<OrderPlaced>
{
    private readonly AppDbContext _db;
    public PaymentConsumer(AppDbContext db) => _db = db;

    public async Task Consume(ConsumeContext<OrderPlaced> ctx)
    {
        var msgId = ctx.MessageId!.Value;

        // Dedup check — unique constraint trên ProcessedMessageId
        if (await _db.ProcessedMessages.AnyAsync(p => p.Id == msgId))
            return;  // đã xử lý rồi → idempotent, bỏ qua

        // Xử lý nghiệp vụ + ghi dấu đã xử lý TRONG CÙNG transaction
        await ChargeAsync(ctx.Message);
        _db.ProcessedMessages.Add(new(msgId, DateTime.UtcNow));
        await _db.SaveChangesAsync();
    }
}
⚠️ Idempotency là trách nhiệm của consumer. Đừng giả định broker đảm bảo "đúng một lần". Mọi consumer phải an toàn khi nhận lại cùng message (retry, redelivery sau crash). Dùng natural key (orderId) hoặc messageId làm khoá dedup.

5. Outbox Pattern — dual-write problem

Vấn đề: cần (1) lưu order vào DB và (2) publish event ra broker. Nếu DB commit xong rồi broker chết → mất event. Nếu publish xong rồi DB rollback → event ma. Hai hệ thống, không có transaction chung.

// Trong CÙNG transaction với business data
using var tx = await _db.Database.BeginTransactionAsync(ct);

_db.Orders.Add(order);
_db.OutboxMessages.Add(new OutboxMessage
{
    Id = Guid.NewGuid(),
    Type = nameof(OrderPlaced),
    Payload = JsonSerializer.Serialize(new OrderPlaced(order.Id, order.Total)),
    OccurredOn = DateTime.UtcNow,
    ProcessedOn = null
});

await _db.SaveChangesAsync(ct);  // order + outbox commit cùng nhau — nguyên tử
await tx.CommitAsync(ct);

// Background relay (hoặc CDC như Debezium) đọc outbox chưa gửi:
var pending = await _db.OutboxMessages
    .Where(m => m.ProcessedOn == null)
    .OrderBy(m => m.OccurredOn).Take(100).ToListAsync(ct);

foreach (var msg in pending)
{
    await _bus.Publish(Deserialize(msg), ct);  // at-least-once
    msg.ProcessedOn = DateTime.UtcNow;
}
await _db.SaveChangesAsync(ct);
💡 MassTransit có Outbox tích hợp: AddEntityFrameworkOutbox tự lo bảng outbox/inbox + relay. Inbox đồng thời cho idempotency phía consumer. Khỏi tự viết relay.

6. Saga — giao dịch phân tán dài hạn

Không có distributed transaction (2PC) cho microservice. Saga chia một giao dịch dài thành chuỗi bước cục bộ, mỗi bước có compensating action để hoàn tác khi lỗi.

🎭 Choreography

Không có điều phối viên trung tâm. Mỗi service nghe event và phát event tiếp theo.

  • Ưu: tách rời cao, không single point
  • Nhược: khó theo dõi luồng, "ai gọi ai" rối khi nhiều bước
  • Hợp: luồng đơn giản, ít bước
Order →OrderPlaced
Payment →Paid
Shipping →Shipped

🎬 Orchestration

Một orchestrator (state machine) ra lệnh từng bước và nhận kết quả.

  • Ưu: luồng tập trung, dễ theo dõi/sửa, dễ compensate
  • Nhược: orchestrator là điểm phụ thuộc
  • Hợp: luồng phức tạp, nhiều nhánh lỗi

Saga state machine với MassTransit

public class OrderState : SagaStateMachineInstance
{
    public Guid CorrelationId { get; set; }
    public string CurrentState { get; set; } = null!;
    public decimal Total { get; set; }
}

public class OrderSaga : MassTransitStateMachine<OrderState>
{
    public State AwaitingPayment { get; } = null!;
    public State AwaitingShipment { get; } = null!;
    public Event<OrderPlaced> OrderPlaced { get; } = null!;
    public Event<PaymentSucceeded> PaymentSucceeded { get; } = null!;
    public Event<PaymentFailed> PaymentFailed { get; } = null!;

    public OrderSaga()
    {
        InstanceState(x => x.CurrentState);

        Initially(
            When(OrderPlaced)
                .Then(ctx => ctx.Saga.Total = ctx.Message.Total)
                .Send(new Uri("queue:charge-payment"),
                      ctx => new ChargePayment(ctx.Saga.CorrelationId, ctx.Saga.Total))
                .TransitionTo(AwaitingPayment));

        During(AwaitingPayment,
            When(PaymentSucceeded)
                .Send(new Uri("queue:ship-order"),
                      ctx => new ShipOrder(ctx.Saga.CorrelationId))
                .TransitionTo(AwaitingShipment),
            When(PaymentFailed)
                .Publish(ctx => new OrderCancelled(ctx.Saga.CorrelationId, "Thanh toán thất bại"))
                .Finalize());  // compensate: huỷ đơn
    }
}

8. Ordering & Dead-Letter Queue

🔢 Message ordering

Ordering toàn cục rất tốn kém. Chiến lược thực tế:

  • Partition theo key (Kafka): cùng orderId → cùng partition → có thứ tự
  • Single consumer / không concurrency cho queue cần thứ tự
  • Thiết kế để không cần ordering: dùng version/timestamp, bỏ qua event cũ

💀 Dead-Letter Queue (DLQ)

Message lỗi mãi (poison message) sau khi hết retry → chuyển vào DLQ để không chặn queue chính.

  • Retry có giới hạn (exponential backoff)
  • Hết retry → _error / _skipped queue (MassTransit tự tạo)
  • Có alert + công cụ replay DLQ sau khi fix bug
Poison message chặn cả hệ thống: Không có DLQ + retry vô hạn → một message lỗi loop mãi, chiếm consumer, message sau ùn tắc. Luôn giới hạn retry và có DLQ.

🎯 Checklist Event-Driven

  • ✅ Phân biệt đúng Command (1 consumer) vs Event (pub/sub)
  • ✅ Chọn broker theo bài toán: RabbitMQ (task/routing) vs Kafka (stream/replay)
  • ✅ Mọi consumer idempotent — an toàn khi nhận lại message
  • ✅ Outbox pattern khi cần "save DB + publish" nguyên tử
  • ✅ Saga cho giao dịch dài; chọn choreography (đơn giản) vs orchestration (phức tạp)
  • ✅ Mỗi bước Saga có compensating action
  • ✅ Retry có backoff + giới hạn lần
  • ✅ Có DLQ + alert + khả năng replay message lỗi
  • ✅ Thiết kế giảm phụ thuộc ordering; nếu cần thì partition theo key
