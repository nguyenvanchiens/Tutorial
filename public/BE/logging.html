Logging & Observability

Quan sát hệ thống (observability) qua ba trụ cột logs, metrics, traces. Nắm vững ILogger<T>, structured logging, Serilog, correlation ID, OpenTelemetry, health checks và metrics/traces cơ bản. Code chính xác cho ASP.NET Core .NET 8/9 — để khi production cháy, bạn biết chính xác chuyện gì đang xảy ra.

1. Ba trụ cột của Observability

Observability = khả năng suy ra trạng thái bên trong hệ thống từ dữ liệu nó phát ra. Khác với monitoring (theo dõi cái đã biết), observability giúp trả lời cả những câu hỏi chưa từng nghĩ tới khi sự cố lạ xảy ra. Ba trụ cột bổ sung cho nhau.

Trụ cộtTrả lời câu hỏiVí dụCông cụ phổ biến
Logs (nhật ký)Chuyện gì đã xảy ra tại 1 thời điểm?"User 42 đăng nhập thất bại lúc 10:03"Serilog + Seq, ELK, Loki
Metrics (số liệu)Hệ thống đang khoẻ cỡ nào? (số liệu tổng hợp theo thời gian)RPS, p99 latency, CPU, error ratePrometheus, Grafana
Traces (dấu vết)1 request đi qua đâu và tốn thời gian ở đâu?API → service → DB → cache (span thời gian từng bước)Jaeger, Tempo, Zipkin
Mối liên kết: một traceId duy nhất nên xuyên suốt cả ba. Từ một metric bất thường (p99 tăng vọt) → nhảy sang trace của request chậm → đọc logs gắn cùng traceId để biết nguyên nhân. OpenTelemetry chính là chuẩn thống nhất ba trụ cột này.

2. ILogger<T> — nền tảng logging của .NET

ASP.NET Core có sẵn abstraction logging trong Microsoft.Extensions.Logging. Inject ILogger<T> qua DI — T là class hiện tại, dùng làm category name (giúp lọc log theo namespace).

public class OrderService
{
    private readonly ILogger<OrderService> _logger;

    public OrderService(ILogger<OrderService> logger) // DI tự inject
        => _logger = logger;

    public async Task CreateAsync(Order order)
    {
        // ✅ STRUCTURED logging: message template + named params
        // {OrderId}, {Amount} là PROPERTY, không phải string interpolation
        _logger.LogInformation(
            "Đang tạo đơn hàng {OrderId} cho khách {CustomerId}, tổng {Amount}",
            order.Id, order.CustomerId, order.Total);

        // ❌ KHÔNG dùng interpolation $"..." — mất structured properties
        // _logger.LogInformation($"Tạo đơn {order.Id}"); // SAI
    }
}
⚠️ Message template, KHÔNG interpolation: truyền "... {OrderId} ..." kèm tham số, đừng dùng $"... {order.Id} ...". Template giữ nguyên thông điệp gốc (gom nhóm log cùng loại) và lưu các giá trị thành property có thể query. Interpolation nối chuỗi ngay → mất cấu trúc, mất khả năng tìm kiếm, và luôn tốn chi phí format kể cả khi log level bị tắt.

LoggerMessage source generator — high performance

Với hot path, dùng attribute [LoggerMessage] (source generator). Nó sinh code log không allocate, kiểm tra log level trước khi format, và mạnh về kiểu (compile-time). Đây là cách log nhanh nhất trong .NET hiện đại.

public static partial class OrderLogs
{
    [LoggerMessage(
        EventId = 1001,
        Level = LogLevel.Information,
        Message = "Tạo đơn {OrderId} cho khách {CustomerId} thành công")]
    public static partial void OrderCreated(
        this ILogger logger, int orderId, int customerId);

    [LoggerMessage(
        EventId = 1002,
        Level = LogLevel.Warning,
        Message = "Đơn {OrderId} bị từ chối: {Reason}")]
    public static partial void OrderRejected(
        this ILogger logger, int orderId, string reason);
}

// Sử dụng — ngắn gọn, không allocate, nhanh hơn LogInformation thường
_logger.OrderCreated(order.Id, order.CustomerId);
_logger.OrderRejected(order.Id, "hết hàng");
💡 Khi nào dùng [LoggerMessage]? Cho các log gọi thường xuyên (mỗi request, vòng lặp). Cho log thưa thớt, _logger.LogInformation(...) bình thường là đủ. class phải là partial và static (hoặc method partial trong class instance) để generator hoạt động.

3. Log Levels — khi nào dùng cái nào

Chọn đúng level là kỹ năng quan trọng. Sai level → hoặc spam noise (mọi thứ Error), hoặc bỏ sót sự cố (mọi thứ Debug bị tắt ở prod).

LevelÝ nghĩaKhi dùngProd?
Trace (0)Chi tiết nhất, có thể chứa dữ liệu nhạy cảmDebug sâu nội bộ, dò từng bướcTắt
Debug (1)Thông tin gỡ lỗi cho devGiá trị biến, luồng xử lý khi devTắt
Information (2)Sự kiện nghiệp vụ bình thường"Đơn đã tạo", "User đăng nhập", app khởi độngBật (vừa phải)
Warning (3)Bất thường nhưng app vẫn chạyRetry, fallback, config thiếu, deprecated APIBật
Error (4)Một thao tác thất bạiException trong xử lý request, gọi service lỗiBật
Critical (5)Lỗi nghiêm trọng, app/dữ liệu nguy hiểmMất kết nối DB toàn cục, hết bộ nhớ, cần báo động ngayBật + alert

Cấu hình minimum level theo từng category trong appsettings.json — giảm noise từ framework, giữ chi tiết cho code của bạn:

{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning",
      "Microsoft.EntityFrameworkCore.Database.Command": "Warning",
      "MyApp.OrderService": "Debug"
    }
  }
}
Quy tắc category: log level áp dụng theo tiền tố namespace dài nhất khớp. MyApp.OrderService ở Debug trong khi Default chỉ Information → bạn xem được chi tiết của riêng service đó mà không bị ngập log từ chỗ khác.

4. Structured Logging với Serilog

Serilog là thư viện structured logging phổ biến nhất. Thay vì ghi dòng text phẳng, nó ghi event có cấu trúc (properties dạng key-value) — xuất ra JSON, query được như database. Cài đặt cho ASP.NET Core qua Serilog.AspNetCore.

// dotnet add package Serilog.AspNetCore
// dotnet add package Serilog.Sinks.Seq

using Serilog;

var builder = WebApplication.CreateBuilder(args);

// Cấu hình Serilog: đọc từ appsettings + enrichers + sinks
builder.Host.UseSerilog((context, services, config) => config
    .ReadFrom.Configuration(context.Configuration)
    .ReadFrom.Services(services)
    .Enrich.FromLogContext()                 // gắn property từ LogContext (correlation id)
    .Enrich.WithMachineName()
    .Enrich.WithEnvironmentName()
    .WriteTo.Console(new Serilog.Formatting.Compact.CompactJsonFormatter())
    .WriteTo.File("logs/app-.json", rollingInterval: RollingInterval.Day,
        formatter: new Serilog.Formatting.Compact.CompactJsonFormatter())
    .WriteTo.Seq("http://localhost:5341"));     // sink Seq để query log

var app = builder.Build();

// Middleware ghi 1 dòng log gọn cho mỗi HTTP request (thay log ồn ào mặc định)
app.UseSerilogRequestLogging();

app.Run();

💡 Vì sao structured > plain text? Khi sự cố xảy ra lúc 2h sáng, bạn cần truy vấn: "tất cả Error của CustomerId=7 trong 10 phút qua" hay "đơn nào có Amount > 1 triệu mà thất bại". Với log JSON trong Seq/ELK, đó là một câu query. Với text phẳng, đó là cơn ác mộng grep.

5. Correlation ID — lần theo request xuyên service

Trong hệ microservice, một request đi qua nhiều service. Để nối tất cả log của cùng một request lại, cần một correlation/trace ID chung. Chuẩn hiện đại là W3C Trace Context — header traceparent, được .NET tự sinh và truyền đi qua Activity.

// .NET tự tạo Activity cho mỗi request. TraceId nằm ở đây:
var traceId = Activity.Current?.TraceId.ToString();

// header traceparent (W3C) tự được truyền qua HttpClient sang service khác:
// traceparent: 00-{traceId}-{spanId}-{flags}

Dùng middleware tuỳ biến để đảm bảo mọi log trong phạm vi request đều mang correlation id. Kết hợp với BeginScope để gắn property vào tất cả log bên trong scope (không phải lặp lại từng dòng):

public class CorrelationIdMiddleware
{
    private const string HeaderName = "X-Correlation-ID";
    private readonly RequestDelegate _next;
    private readonly ILogger<CorrelationIdMiddleware> _logger;

    public CorrelationIdMiddleware(RequestDelegate next, ILogger<CorrelationIdMiddleware> logger)
        => (_next, _logger) = (next, logger);

    public async Task InvokeAsync(HttpContext ctx)
    {
        // Lấy correlation id từ header, hoặc dùng TraceId của Activity
        var correlationId = ctx.Request.Headers[HeaderName].FirstOrDefault()
            ?? Activity.Current?.TraceId.ToString()
            ?? Guid.NewGuid().ToString("n");

        ctx.Response.Headers[HeaderName] = correlationId; // trả lại cho client

        // BeginScope: mọi log trong request này tự động có {CorrelationId}
        using (_logger.BeginScope(new Dictionary<string, object>
        {
            ["CorrelationId"] = correlationId
        }))
        {
            await _next(ctx);
        }
    }
}

// Đăng ký SỚM trong pipeline (Program.cs)
app.UseMiddleware<CorrelationIdMiddleware>();
BeginScope + Serilog: nhờ .Enrich.FromLogContext(), các property trong scope được Serilog gắn vào mọi log event tự động. Một dòng _logger.LogInformation("Xử lý đơn {OrderId}", id) sâu trong service vẫn mang theo CorrelationId mà không cần truyền tay.

6. OpenTelemetry — chuẩn quan sát hiện đại

OpenTelemetry (OTel) là chuẩn mở, vendor-neutral để thu thập traces & metrics. .NET 8/9 hỗ trợ first-class. Bạn instrument một lần, export tới bất kỳ backend nào (Jaeger, Tempo, Prometheus, Grafana, Datadog...) qua giao thức OTLP.

// dotnet add package OpenTelemetry.Extensions.Hosting
// dotnet add package OpenTelemetry.Instrumentation.AspNetCore
// dotnet add package OpenTelemetry.Instrumentation.Http
// dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol
// dotnet add package OpenTelemetry.Instrumentation.EntityFrameworkCore

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService(serviceName: "OrderApi"))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()      // trace request đến
        .AddHttpClientInstrumentation()      // trace HttpClient đi ra
        .AddEntityFrameworkCoreInstrumentation() // trace query EF Core
        .AddSource("OrderApi.Orders")      // custom ActivitySource
        .AddOtlpExporter())                  // export sang Jaeger/Tempo (OTLP)
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddRuntimeInstrumentation()         // GC, thread pool...
        .AddMeter("OrderApi.Metrics")
        .AddOtlpExporter());                 // hoặc AddPrometheusExporter()

var app = builder.Build();
💡 Distributed tracing miễn phí: chỉ với AddAspNetCoreInstrumentation() + AddHttpClientInstrumentation(), mọi request qua service và mọi cuộc gọi HttpClient ra ngoài đều tự sinh span, tự truyền traceparent. Mở Jaeger lên là thấy waterfall toàn bộ hành trình request qua các service.

7. Health Checks

Health check cho phép load balancer, Kubernetes, hoặc monitoring biết app có khoẻ không. ASP.NET Core có sẵn AddHealthChecks(). Phân biệt liveness (app còn sống không — nếu chết thì restart) và readiness (app sẵn sàng nhận traffic chưa — DB/cache đã kết nối).

// dotnet add package AspNetCore.HealthChecks.SqlServer
// dotnet add package AspNetCore.HealthChecks.Redis

builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString, name: "sql", tags: new[] { "ready" })
    .AddRedis(redisConnection, name: "redis", tags: new[] { "ready" })
    .AddCheck<OrderQueueHealthCheck>("order-queue", tags: new[] { "ready" });

var app = builder.Build();

// /health — tổng quát; /health/live — liveness; /health/ready — readiness
app.MapHealthChecks("/health");
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false   // không chạy check nào → chỉ xác nhận process còn sống
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready") // chỉ check phụ thuộc
});
// Custom health check: kiểm tra logic nghiệp vụ của bạn
public class OrderQueueHealthCheck : IHealthCheck
{
    private readonly IOrderQueue _queue;
    public OrderQueueHealthCheck(IOrderQueue queue) => _queue = queue;

    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct = default)
    {
        var depth = await _queue.GetDepthAsync(ct);
        if (depth > 10_000)
            return HealthCheckResult.Degraded($"Hàng đợi quá tải: {depth}");
        return HealthCheckResult.Healthy($"Độ sâu hàng đợi: {depth}");
    }
}
Liveness vs Readiness: Kubernetes dùng /health/live để quyết định restart pod (đừng cho DB vào đây — DB chết tạm thời không nên gây restart loop). Dùng /health/ready để quyết định có gửi traffic vào pod không (DB chưa sẵn sàng → tạm ngừng nhận request).

8. Metrics & Traces cơ bản

Ngoài instrumentation tự động, bạn tự phát số liệu nghiệp vụ qua System.Diagnostics.Metrics (Meter, Counter, Histogram) và tự tạo span nghiệp vụ qua Activity.

Metrics — Meter / Counter / Histogram

public class OrderMetrics
{
    private readonly Counter<long> _ordersCreated;
    private readonly Histogram<double> _orderValue;

    public OrderMetrics(IMeterFactory meterFactory)
    {
        // Tên meter "OrderApi.Metrics" khớp với AddMeter() ở phần 6
        var meter = meterFactory.Create("OrderApi.Metrics");
        _ordersCreated = meter.CreateCounter<long>(
            "orders.created", unit: "{orders}", description: "Số đơn đã tạo");
        _orderValue = meter.CreateHistogram<double>(
            "orders.value", unit: "VND", description: "Phân bố giá trị đơn");
    }

    public void RecordOrder(Order order)
    {
        // Counter: chỉ tăng (đếm tổng). Tag để phân nhóm.
        _ordersCreated.Add(1, new KeyValuePair<string, object?>("region", order.Region));
        // Histogram: phân bố giá trị (p50/p95/p99 latency, kích thước...)
        _orderValue.Record(order.Total);
    }
}

Traces — Activity & Span

// ActivitySource là "nguồn" sinh span. Tên khớp AddSource() ở phần 6.
public static class Telemetry
{
    public static readonly ActivitySource Source = new("OrderApi.Orders");
}

public async Task ProcessAsync(Order order)
{
    // StartActivity tạo 1 span con trong trace hiện tại
    using var activity = Telemetry.Source.StartActivity("ProcessOrder");
    activity?.SetTag("order.id", order.Id);
    activity?.SetTag("order.region", order.Region);

    try
    {
        await _payment.ChargeAsync(order);  // span con tự nối vào đây
        activity?.SetStatus(ActivityStatusCode.Ok);
    }
    catch (Exception ex)
    {
        activity?.SetStatus(ActivityStatusCode.Error, ex.Message);
        throw;
    }
}
Loại instrumentĐặc tínhVí dụ
Counter<T>Chỉ tăng, đếm tích luỹSố request, số đơn, số lỗi
UpDownCounter<T>Tăng/giảm, giá trị hiện tạiSố kết nối đang mở, item trong queue
Histogram<T>Phân bố giá trị (percentile)Latency, kích thước payload
Activity (span)Khoảng thời gian + tag của 1 thao tác1 bước xử lý trong trace

9. Do / Don't khi làm Logging & Observability

❌ Log secrets / PII

_logger.LogInformation("Login {User} pass {Password}", u, pwd); // 💀 rò mật khẩu

Không bao giờ log mật khẩu, token, số thẻ, CCCD, email/điện thoại đầy đủ. Vi phạm bảo mật & GDPR/nghị định bảo vệ dữ liệu. Mask hoặc loại bỏ trước khi log.

❌ Log trong vòng lặp nóng ở mức Information

foreach (var row in millionRows)
    _logger.LogInformation("Xử lý {Id}", row.Id); // triệu dòng log → ngập, tốn I/O

Log hot loop ở Information làm sink quá tải, tốn đĩa & tiền (log SaaS tính theo dung lượng). Dùng Debug/Trace, hoặc log tổng hợp ("đã xử lý N dòng"), hoặc dùng metric thay vì log.

❌ String interpolation thay vì structured

_logger.LogInformation($"Đơn {order.Id} lỗi"); // mất property, không query được

Mất structured properties, không filter/aggregate được, và luôn tốn chi phí format kể cả khi level bị tắt. Dùng message template + named params.

❌ Nuốt exception trong im lặng

try { await DoAsync(); } catch { } // 💀 lỗi biến mất không dấu vết

Catch rỗng làm lỗi tan biến — không log, không metric, không alert. Khi prod sai bạn sẽ mù hoàn toàn. Tối thiểu phải _logger.LogError(ex, "...") rồi xử lý/rethrow.

✅ Log exception đúng cách

catch (Exception ex)
{
    // exception là tham số ĐẦU TIÊN → giữ nguyên stack trace
    _logger.LogError(ex, "Tạo đơn {OrderId} thất bại", order.Id);
    throw; // rethrow giữ stack (đừng throw ex;)
}

Truyền exception làm tham số đầu để giữ stack trace; dùng template cho thông điệp; throw; chứ không throw ex;.

✅ Dùng metric cho dữ liệu tần suất cao

_ordersCreated.Add(1); // đếm bằng counter, rẻ hơn log triệu dòng

Thứ cần đếm/đo theo thời gian → dùng metric (rẻ, tổng hợp sẵn). Log để giải thích sự kiện cụ thể, metric để theo dõi xu hướng.

🎯 Checklist Logging & Observability

  • ✅ Dùng ILogger<T> inject qua DI; hot path dùng [LoggerMessage]
  • ✅ Structured logging: message template + named params, KHÔNG interpolation
  • ✅ Chọn đúng log level; cấu hình minimum level theo category trong appsettings
  • ✅ Serilog xuất JSON, có enrichers, sink Console/File/Seq để query được
  • ✅ Correlation/Trace ID gắn vào mọi log qua middleware + BeginScope
  • ✅ OpenTelemetry instrument ASP.NET Core + HttpClient + EF Core, export OTLP
  • ✅ Health checks tách /health/live và /health/ready; có check DB/Redis
  • ✅ Metric (Counter/Histogram) cho số liệu tần suất cao thay vì log
  • ✅ Activity/span cho các bước nghiệp vụ quan trọng trong trace
  • ✅ KHÔNG log secrets/PII, KHÔNG log hot loop ở Information, KHÔNG nuốt exception
  • ✅ Log exception với LogError(ex, ...) và throw; giữ stack trace
