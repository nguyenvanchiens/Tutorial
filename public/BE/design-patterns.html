SOLID & Design Patterns

Năm nguyên lý SOLID và các mẫu thiết kế kinh điển (Repository, Strategy, Factory, Decorator, Mediator, Options) áp dụng đúng cách trong C# / .NET 8/9. Mỗi nguyên lý và pattern đều có ví dụ "xấu vs tốt", code thật chạy được, và lời khuyên "khi nào nên dùng — khi nào đừng". Pattern là công cụ, không phải mục tiêu.

Tổng quan

SOLID là 5 nguyên lý thiết kế hướng đối tượng (Robert C. Martin) giúp code dễ mở rộng, dễ test, dễ bảo trì. Design Patterns là những lời giải đã được kiểm chứng cho các vấn đề lặp đi lặp lại. Mục tiêu cuối cùng không phải "dùng nhiều pattern", mà là code thay đổi rẻ và ít coupling.

SOLID

SRP, OCP, LSP, ISP, DIP — nền tảng để viết class/interface tốt trước khi nghĩ tới pattern.

Patterns

Repository, Strategy, Factory, Decorator, Mediator — giải pháp tái sử dụng được cho coupling và mở rộng.

.NET built-in

Options pattern, DI container, keyed services — nhiều pattern đã có sẵn trong framework, đừng tự dựng lại.

Triết lý xuyên suốt: Áp dụng SOLID/pattern để giải quyết một vấn đề cụ thể (coupling cao, khó test, switch khổng lồ...). Đừng over-engineer. Code đơn giản giải đúng bài toán luôn thắng abstraction thừa.

PHẦN 1 — SOLID

1. S — Single Responsibility Principle (SRP)

Một class chỉ nên có một lý do để thay đổi. Nói cách khác: một class phục vụ một "actor" / một mục đích. Khi logic nghiệp vụ và việc gửi email trộn vào nhau, mỗi lần đổi template email lại phải sửa class xử lý đơn hàng — sai.

❌ Vi phạm SRP

public class OrderService
{
    public void PlaceOrder(Order order)
    {
        // 1. Logic nghiệp vụ
        _db.Orders.Add(order);
        _db.SaveChanges();

        // 2. Gửi email — trách nhiệm KHÁC
        var smtp = new SmtpClient("smtp.local");
        smtp.Send(new MailMessage(
            "shop@x.com", order.Email,
            "Đặt hàng thành công", "..."));
    }
}

Đổi cách lưu DB hoặc đổi nhà cung cấp email đều phải sửa class này → 2 lý do thay đổi.

✅ Tách trách nhiệm

public interface IEmailSender
{
    Task SendAsync(string to, string subject, string body);
}

public class OrderService
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _email;

    public OrderService(AppDbContext db, IEmailSender email)
        => (_db, _email) = (db, email);

    public async Task PlaceOrderAsync(Order order, CancellationToken ct)
    {
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
        await _email.SendAsync(order.Email,
            "Đặt hàng thành công", "...");
    }
}

Nghiệp vụ đơn hàng và việc gửi email tách rời. Đổi SMTP → SendGrid chỉ cần thay implement IEmailSender.

💡 Mẹo nhận biết: nếu mô tả class phải dùng chữ "và" ("lưu đơn và gửi mail và xuất PDF"), nhiều khả năng đang vi phạm SRP. Nhưng đừng cực đoan chẻ nhỏ tới mức mỗi class 1 dòng — SRP là về "lý do thay đổi", không phải "số dòng code".

2. O — Open/Closed Principle (OCP)

Class nên mở để mở rộng, đóng để sửa đổi. Khi thêm loại mới mà phải đụng vào một switch khổng lồ ở khắp nơi → vi phạm OCP. Giải pháp: đa hình (polymorphism) / Strategy.

❌ Switch phình to mỗi khi thêm loại

public decimal Calc(Customer c, decimal total)
{
    switch (c.Tier)
    {
        case Tier.Regular: return total;
        case Tier.Silver:  return total * 0.95m;
        case Tier.Gold:    return total * 0.90m;
        // Thêm Platinum => phải SỬA method này
        default: return total;
    }
}

Mỗi tier mới buộc sửa lại method đã test xong → rủi ro hồi quy.

✅ Đa hình — thêm loại không sửa code cũ

public abstract class CustomerTier
{
    public abstract decimal ApplyDiscount(decimal total);
}

public class GoldTier : CustomerTier
{
    public override decimal ApplyDiscount(decimal t)
        => t * 0.90m;
}
// Thêm PlatinumTier = thêm class MỚI, không sửa cái cũ
public class PlatinumTier : CustomerTier
{
    public override decimal ApplyDiscount(decimal t)
        => t * 0.80m;
}

Logic tính tiền chỉ gọi tier.ApplyDiscount(total). Thêm hạng mới = thêm class, không động vào code đã ổn định.

⚠️ Đừng cực đoan: không phải mọi switch đều xấu. Với enum cố định, ít thay đổi, một switch rõ ràng dễ đọc hơn 5 class. Chỉ trừu tượng hóa khi loại thực sự hay thêm/sửa.

3. L — Liskov Substitution Principle (LSP)

Đối tượng của lớp con phải thay thế được cho lớp cha mà không phá vỡ tính đúng đắn của chương trình. Nếu subtype "ném exception" hoặc "đổi nghĩa" hành vi base → vi phạm LSP. Ví dụ kinh điển: Penguin là Bird nhưng không bay được.

❌ Vi phạm LSP (Penguin không bay)

public class Bird
{
    public virtual void Fly() { /* bay */ }
}

public class Penguin : Bird
{
    public override void Fly()
        => throw new NotSupportedException(); // 💥
}

// Code dùng List<Bird> gọi .Fly() sẽ nổ với Penguin

Penguin "là" Bird về mặt phân loại, nhưng phá hợp đồng Fly() của base → người dùng base bị bất ngờ.

✅ Tách khả năng bằng abstraction đúng

public abstract class Bird
{
    public abstract void Eat();
}

public interface IFlying
{
    void Fly();
}

public class Sparrow : Bird, IFlying
{
    public override void Eat() { }
    public void Fly() { /* bay */ }
}

public class Penguin : Bird // không implement IFlying
{
    public override void Eat() { }
}

Chỉ con vật biết bay mới implement IFlying. Không có chỗ nào gọi Fly() trên Penguin được nữa.

Square/Rectangle: ví dụ khác — Square kế thừa Rectangle rồi override setter Width/Height để luôn bằng nhau, làm test rect.Width=5; rect.Height=4; Assert(Area==20) sai. Bài học: kế thừa phải giữ nguyên hợp đồng hành vi (precondition không mạnh hơn, postcondition không yếu hơn).

4. I — Interface Segregation Principle (ISP)

Client không nên bị buộc phụ thuộc vào method nó không dùng. Thay vì một interface "béo" IMachine ép mọi máy phải implement cả in, scan, fax → tách thành các interface nhỏ chuyên biệt.

❌ Interface béo (fat interface)

public interface IMachine
{
    void Print(Document d);
    void Scan(Document d);
    void Fax(Document d);
}

// Máy in thường buộc phải implement Scan/Fax vô nghĩa
public class SimplePrinter : IMachine
{
    public void Print(Document d) { }
    public void Scan(Document d)
        => throw new NotSupportedException(); // 💥
    public void Fax(Document d)
        => throw new NotSupportedException();
}

✅ Interface nhỏ, chuyên biệt

public interface IPrinter { void Print(Document d); }
public interface IScanner { void Scan(Document d); }

// Máy in chỉ cần IPrinter
public class SimplePrinter : IPrinter
{
    public void Print(Document d) { }
}

// Máy đa năng implement nhiều interface
public class AllInOne : IPrinter, IScanner
{
    public void Print(Document d) { }
    public void Scan(Document d) { }
}

Client chỉ phụ thuộc đúng thứ nó cần. Không còn method "ném exception cho có".

💡 ISP và DI: interface nhỏ giúp mock dễ hơn khi unit test, và đăng ký DI rõ ràng hơn. Nhưng đừng tạo interface 1 method cho mọi class — chỉ tách khi có nhiều implement hoặc cần ranh giới rõ ràng.

5. D — Dependency Inversion Principle (DIP)

Module cấp cao không phụ thuộc module cấp thấp; cả hai phụ thuộc vào abstraction. Cụ thể: service không new trực tiếp SqlRepository, mà nhận IRepository qua constructor; DI container lo việc cung cấp implement.

❌ Phụ thuộc cụ thể (new trực tiếp)

public class ReportService
{
    private readonly SqlUserRepository _repo
        = new SqlUserRepository(); // cứng nhắc

    public Report Build()
        => new(_repo.GetAll());
}

Không thể test với fake repo, không đổi được sang Mongo/in-memory, coupling chặt với SQL.

✅ Inject abstraction qua constructor

public interface IUserRepository
{
    Task<IReadOnlyList<User>> GetAllAsync(CancellationToken ct);
}

public class ReportService
{
    private readonly IUserRepository _repo;
    public ReportService(IUserRepository repo) => _repo = repo;

    public async Task<Report> BuildAsync(CancellationToken ct)
        => new(await _repo.GetAllAsync(ct));
}
// Program.cs (.NET 8/9) — đăng ký abstraction => implement
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IUserRepository, SqlUserRepository>();
builder.Services.AddScoped<ReportService>();

// DI container tự "inject" SqlUserRepository vào ReportService.
// Khi test: đăng ký FakeUserRepository thay thế.
DIP ≠ "luôn tạo interface": DIP nói về chiều phụ thuộc. DI container (Microsoft.Extensions.DependencyInjection) là cơ chế hiện thực DIP phổ biến nhất trong .NET. Lifetime đúng (Singleton / Scoped / Transient) cũng quan trọng như chính việc inject.

PHẦN 2 — DESIGN PATTERNS

6. Repository Pattern

Mục đích: trừu tượng hóa lớp truy cập dữ liệu, để nghiệp vụ không phụ thuộc trực tiếp vào EF Core / SQL. Tách persistence khỏi domain, dễ test, dễ đổi nguồn dữ liệu.

public interface IRepository<T> where T : class
{
    Task<T?> GetByIdAsync(int id, CancellationToken ct);
    Task<IReadOnlyList<T>> ListAsync(CancellationToken ct);
    Task AddAsync(T entity, CancellationToken ct);
    void Remove(T entity);
}

public class EfRepository<T> : IRepository<T> where T : class
{
    private readonly AppDbContext _db;
    public EfRepository(AppDbContext db) => _db = db;

    public Task<T?> GetByIdAsync(int id, CancellationToken ct)
        => _db.Set<T>().FindAsync(new object[] { id }, ct).AsTask();

    public async Task<IReadOnlyList<T>> ListAsync(CancellationToken ct)
        => await _db.Set<T>().ToListAsync(ct);

    public async Task AddAsync(T e, CancellationToken ct)
        => await _db.Set<T>().AddAsync(e, ct);

    public void Remove(T e) => _db.Set<T>().Remove(e);
}
⚠️ Cảnh báo quan trọng: DbContext của EF Core đã là Unit of Work + Repository (mỗi DbSet<T> là một repository, SaveChanges là UoW). Bọc một lớp IRepository<T> mỏng dính chỉ chuyển tiếp gọi sang DbContext thường là abstraction vô nghĩa: bạn mất sức mạnh của LINQ/IQueryable, Include, projection... mà chẳng được gì. Chỉ dùng Repository khi thật sự cần ẩn EF khỏi domain hoặc gom query phức tạp lại một chỗ.
💡 Khi nào dùng: khi muốn domain layer không biết tới EF Core (Clean Architecture), khi cần tập trung query phức tạp/đặc tả (Specification pattern), hoặc khi có nhiều nguồn dữ liệu. Nếu app CRUD đơn giản → dùng thẳng DbContext trong service cũng hoàn toàn ổn.

7. Strategy Pattern

Mục đích: đóng gói một họ thuật toán có thể hoán đổi cho nhau và chọn lúc runtime. Đây chính là cách hiện thực OCP. Ví dụ: chọn cách tính phí ship theo loại vận chuyển.

public interface IShippingCostStrategy
{
    decimal Calculate(Order order);
}

public class StandardShipping : IShippingCostStrategy
{
    public decimal Calculate(Order o) => o.Weight * 1.0m;
}

public class ExpressShipping : IShippingCostStrategy
{
    public decimal Calculate(Order o) => o.Weight * 2.5m + 10m;
}

// Context chọn strategy lúc runtime
public class CheckoutService
{
    public decimal GetShipping(Order o, IShippingCostStrategy strategy)
        => strategy.Calculate(o);
}
💡 Khi nào dùng: khi có nhiều cách làm cùng một việc và muốn chọn động (theo cấu hình, theo input người dùng), hoặc để thay if/switch phình to. Trong .NET, Strategy thường kết hợp với DI + keyed services (xem phần Factory) để resolve đúng implement theo key.

8. Factory Pattern

Mục đích: tách việc tạo đối tượng ra khỏi nơi dùng nó. Factory Method để lớp con quyết định tạo gì; Abstract Factory tạo cả họ sản phẩm. Trong .NET 8/9, thường thay bằng keyed services rất gọn.

Cách cổ điển: INotificationFactory

public interface INotificationSender { Task SendAsync(string msg); }
public class EmailSender : INotificationSender { public Task SendAsync(string m) => Task.CompletedTask; }
public class SmsSender   : INotificationSender { public Task SendAsync(string m) => Task.CompletedTask; }

public interface INotificationFactory
{
    INotificationSender Create(NotificationChannel channel);
}

public class NotificationFactory : INotificationFactory
{
    private readonly IServiceProvider _sp;
    public NotificationFactory(IServiceProvider sp) => _sp = sp;

    public INotificationSender Create(NotificationChannel c) => c switch
    {
        NotificationChannel.Email => _sp.GetRequiredService<EmailSender>(),
        NotificationChannel.Sms   => _sp.GetRequiredService<SmsSender>(),
        _ => throw new ArgumentOutOfRangeException(nameof(c))
    };
}

Cách .NET 8+: Keyed Services (gọn hơn)

// Program.cs — đăng ký theo key
builder.Services.AddKeyedScoped<INotificationSender, EmailSender>("email");
builder.Services.AddKeyedScoped<INotificationSender, SmsSender>("sms");

// Resolve theo key — không cần tự viết factory
public class AlertService
{
    private readonly IServiceProvider _sp;
    public AlertService(IServiceProvider sp) => _sp = sp;

    public Task NotifyAsync(string channel, string msg)
    {
        var sender = _sp.GetRequiredKeyedService<INotificationSender>(channel);
        return sender.SendAsync(msg);
    }
}

// Hoặc inject thẳng bằng attribute [FromKeyedServices]
public SomeCtor([FromKeyedServices("email")] INotificationSender email) { }
💡 Khi nào dùng: khi loại đối tượng tạo ra phụ thuộc runtime (kênh gửi, loại file, nhà cung cấp thanh toán). Ưu tiên keyed services của .NET 8/9 thay vì tự viết factory thủ công — ít code, tận dụng DI lifetime.

9. Decorator Pattern

Mục đích: bọc thêm hành vi (caching, logging, retry, validation) quanh một object mà không sửa object gốc, bằng cách implement cùng interface và "ôm" instance gốc bên trong. Tuân thủ OCP tuyệt đối.

// Implement gốc
public class ProductRepository : IProductRepository
{
    private readonly AppDbContext _db;
    public ProductRepository(AppDbContext db) => _db = db;
    public Task<Product?> GetAsync(int id, CancellationToken ct)
        => _db.Products.FindAsync(new object[] { id }, ct).AsTask();
}

// Decorator: thêm cache mà KHÔNG sửa ProductRepository
public class CachedProductRepository : IProductRepository
{
    private readonly IProductRepository _inner;   // object gốc
    private readonly IMemoryCache _cache;

    public CachedProductRepository(IProductRepository inner, IMemoryCache cache)
        => (_inner, _cache) = (inner, cache);

    public async Task<Product?> GetAsync(int id, CancellationToken ct)
    {
        if (_cache.TryGetValue(id, out Product? p)) return p;
        p = await _inner.GetAsync(id, ct);   // gọi xuống gốc
        _cache.Set(id, p, TimeSpan.FromMinutes(5));
        return p;
    }
}
// Đăng ký decorator bằng Scrutor (gói NuGet phổ biến)
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.Decorate<IProductRepository, CachedProductRepository>();
// Có thể chồng nhiều lớp: Decorate logging rồi Decorate cache...
Scrutor: DI container mặc định của .NET không có Decorate() sẵn. Gói Scrutor bổ sung method này (và scan assembly tự đăng ký). Không có Scrutor thì phải tự đăng ký factory bọc tay. Khi nào dùng: thêm cross-cutting concern (cache, log, retry, đo thời gian) mà không làm bẩn class nghiệp vụ.

10. Mediator Pattern (MediatR + CQRS)

Mục đích: giảm coupling giữa các thành phần — chúng không gọi trực tiếp nhau mà gửi message qua một "mediator". Trong .NET, thư viện MediatR hiện thực pattern này, rất hợp với CQRS: mỗi thao tác là một IRequest có một IRequestHandler riêng.

// 1. Command (request) — là một thao tác có ý định rõ ràng
public record CreateOrderCommand(int CustomerId, decimal Total)
    : IRequest<Guid>;   // trả về Guid (Id đơn mới)

// 2. Handler — chứa logic xử lý command đó
public class CreateOrderHandler
    : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly AppDbContext _db;
    public CreateOrderHandler(AppDbContext db) => _db = db;

    public async Task<Guid> Handle(
        CreateOrderCommand cmd, CancellationToken ct)
    {
        var order = new Order(cmd.CustomerId, cmd.Total);
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
        return order.Id;
    }
}

// 3. Controller chỉ gửi command, KHÔNG biết handler nào xử lý
[ApiController, Route("orders")]
public class OrdersController : ControllerBase
{
    private readonly IMediator _mediator;
    public OrdersController(IMediator m) => _mediator = m;

    [HttpPost]
    public async Task<IActionResult> Create(
        CreateOrderCommand cmd, CancellationToken ct)
    {
        Guid id = await _mediator.Send(cmd, ct);
        return CreatedAtAction(nameof(Create), new { id }, id);
    }
}
// Program.cs — đăng ký MediatR (quét assembly tìm handler)
builder.Services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssembly(typeof(CreateOrderHandler).Assembly));
💡 Khi nào dùng: app có nhiều use-case rõ ràng, muốn tách handler nhỏ gọn, cần pipeline behavior (validation, logging, transaction) chung. Lưu ý: MediatR thêm một lớp gián tiếp — với CRUD nhỏ thì gọi service trực tiếp đơn giản hơn. Đừng dùng MediatR chỉ để "cho giống kiến trúc xịn".

11. Options Pattern (.NET native)

Mục đích: bind cấu hình (appsettings.json, env vars, secrets) vào class strongly-typed thay vì đọc IConfiguration["key"] rải rác. Là pattern có sẵn trong .NET — không cần thư viện ngoài.

// appsettings.json
// "Email": { "From": "shop@x.com", "SmtpHost": "smtp.local", "Port": 587 }

// 1. Class options + validation bằng DataAnnotations
public class EmailOptions
{
    public const string SectionName = "Email";

    [Required, EmailAddress]
    public string From { get; set; } = "";

    [Required]
    public string SmtpHost { get; set; } = "";

    [Range(1, 65535)]
    public int Port { get; set; }
}
// 2. Program.cs — bind + validate khi khởi động
builder.Services
    .AddOptions<EmailOptions>()
    .Bind(builder.Configuration.GetSection(EmailOptions.SectionName))
    .ValidateDataAnnotations()
    .ValidateOnStart();   // app fail ngay lúc start nếu config sai

// Cách ngắn gọn tương đương (không ValidateOnStart):
// builder.Services.Configure<EmailOptions>(
//     builder.Configuration.GetSection(EmailOptions.SectionName));
// 3. Inject vào service
public class SmtpEmailSender : IEmailSender
{
    private readonly EmailOptions _opt;

    // IOptions<T>: giá trị cố định suốt vòng đời app (Singleton)
    public SmtpEmailSender(IOptions<EmailOptions> options)
        => _opt = options.Value;

    public Task SendAsync(string to, string subject, string body)
    {
        // dùng _opt.SmtpHost, _opt.Port, _opt.From...
        return Task.CompletedTask;
    }
}
Kiểu injectHành viKhi dùng
IOptions<T>Đọc 1 lần, cache mãi mãi (Singleton)Config không đổi khi runtime; mọi lifetime
IOptionsSnapshot<T>Tính lại mỗi request (Scoped)Config reload theo request; chỉ Scoped/Transient
IOptionsMonitor<T>Theo dõi thay đổi liên tục + OnChangeSingleton cần config nóng (hot reload appsettings)
💡 ValidateOnStart(): luôn bật cho config quan trọng — bạn muốn app không khởi động nếu thiếu connection string hay SMTP host, thay vì chết giữa giờ cao điểm vì NullReferenceException.

12. Do / Don't — dùng pattern đúng cách

✅ Bắt đầu từ vấn đề, không từ pattern

Nhận diện "đau" cụ thể (coupling chặt, switch khổng lồ, khó test) rồi mới chọn pattern giải đúng cái đau đó. Pattern là phương tiện, không phải đích đến.

✅ Ưu tiên cơ chế built-in của .NET

DI container, keyed services, Options pattern, IHttpClientFactory, BackgroundService... đã giải nhiều bài toán pattern cổ điển. Dùng chúng trước khi tự dựng.

✅ Giữ abstraction "vừa đủ"

Một interface có ít nhất 2 implement (hoặc một fake để test) thì xứng đáng tồn tại. Interface 1-1 chỉ để "cho có" thường là noise.

❌ Áp pattern bừa khi không cần

Repository bọc DbContext mỏng, Factory cho thứ chỉ có 1 loại, MediatR cho CRUD 3 endpoint... tạo gián tiếp vô ích, làm code khó đọc hơn.

❌ Over-abstraction / kiến trúc vũ trụ

Wrap mọi thứ sau interface, 7 lớp gián tiếp cho một lời gọi DB. "Generic repository + service + manager + facade" cho app nhỏ là phản tác dụng.

❌ Dùng pattern để "trông pro"

Chọn pattern vì nó nổi tiếng chứ không vì nó giải vấn đề của bạn. Đồng nghiệp sẽ trả giá khi bảo trì. YAGNI (You Aren't Gonna Need It) luôn đúng.

🎯 Checklist SOLID & Patterns

  • ✅ Mỗi class có một lý do thay đổi rõ ràng (SRP)
  • ✅ Thêm loại mới không phải sửa code đã ổn định (OCP) — dùng đa hình / Strategy
  • ✅ Lớp con thay được lớp cha mà không phá hợp đồng (LSP) — không "ném NotSupported"
  • ✅ Interface nhỏ, chuyên biệt, client không phụ thuộc method thừa (ISP)
  • ✅ Phụ thuộc abstraction, inject qua constructor + DI container (DIP)
  • ✅ Không bọc Repository mỏng dính lên DbContext nếu không cần ẩn EF
  • ✅ Strategy + keyed services để chọn thuật toán/implement runtime
  • ✅ Ưu tiên keyed services (AddKeyedScoped) thay vì factory thủ công
  • ✅ Decorator (qua Scrutor) cho cross-cutting concern: cache, log, retry
  • ✅ MediatR + CQRS chỉ khi app đủ lớn để hưởng lợi từ handler/pipeline
  • ✅ Options pattern + ValidateOnStart() cho mọi config quan trọng
  • ✅ Bắt đầu từ vấn đề, không over-engineer — pattern là công cụ, không phải mục tiêu
