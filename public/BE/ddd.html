Domain-Driven Design cho .NET

Mô hình hoá phần mềm theo nghiệp vụ thực. Strategic Design (bounded context, ubiquitous language, context mapping) định hình kiến trúc lớn; Tactical Design (entity, value object, aggregate, domain event, repository, ACL) cho code sạch. Kèm ví dụ C# hoàn chỉnh.

1. Vì sao DDD?

DDD giải quyết vấn đề độ phức tạp nghiệp vụ, không phải phức tạp kỹ thuật. Nó đặt domain (nghiệp vụ) làm trung tâm, code phản ánh đúng cách chuyên gia nghiệp vụ nói chuyện.

✅ Hợp với DDD

  • Domain phức tạp, nhiều rule, nhiều thay đổi
  • Cần cộng tác chặt với chuyên gia nghiệp vụ
  • Hệ thống sống lâu, nhiều team
  • VD: banking, logistics, insurance, e-commerce lớn

❌ Không cần DDD đầy đủ

  • CRUD đơn giản, data-entry app
  • Prototype/MVP cần ra nhanh
  • Domain mỏng, chủ yếu là kỹ thuật (ETL, reporting)
  • Team chưa quen — chỉ lấy tactical patterns hữu ích

2. Strategic Design

Ubiquitous Language

Ngôn ngữ chung giữa dev và domain expert. Cùng một từ, cùng một nghĩa, dùng trong cả hội thoại lẫn code. Tránh "translation layer" trong đầu lập trình viên.

Ví dụ: Trong context Vận chuyển, "Cargo" được "routed" theo một "Itinerary" gồm nhiều "Leg". Code dùng đúng class Cargo, Itinerary, Leg — không phải ShipmentData, RouteInfo.

Bounded Context

Ranh giới rõ ràng trong đó một model + ubiquitous language có hiệu lực. Cùng một từ "Customer" có thể có nghĩa khác nhau giữa các context.

Sales Context

Customer = lead, có credit limit, sales rep.

Billing Context

Customer = bên thanh toán, có invoice, payment terms.

Support Context

Customer = người mở ticket, có SLA, lịch sử liên hệ.

⚠️ Cạm bẫy "Shared Model": Cố ép một class Customer khổng lồ dùng chung mọi context → god object, coupling cao. Mỗi context có model riêng của "Customer" là điều bình thường và đúng đắn.

Context Mapping

Mô tả quan hệ giữa các bounded context khi chúng phải tích hợp.

PatternÝ nghĩa

3. Tactical Design — building blocks

Entity

Có identity kéo dài theo thời gian. Hai entity bằng nhau khi cùng Id, dù thuộc tính khác.

Value Object

Không có identity, định nghĩa bằng giá trị. Bất biến. VD: Money, Address, DateRange.

Aggregate

Cụm entity + VO được coi là một đơn vị nhất quán. Có một Aggregate Root làm cổng vào.

Domain Event

Sự kiện có ý nghĩa nghiệp vụ vừa xảy ra. VD: OrderPlaced. Quá khứ, bất biến.

Repository

Abstraction lưu/lấy aggregate. Một repository cho mỗi aggregate root.

Domain Service

Logic không thuộc về entity/VO nào cụ thể. Stateless. VD: PricingService.

Value Object — ví dụ Money

// VO bất biến, equality theo giá trị (record cho free Equals/GetHashCode)
public record Money
{
    public decimal Amount { get; }
    public Currency Currency { get; }

    public Money(decimal amount, Currency currency)
    {
        if (amount < 0) throw new ArgumentException("Amount không âm");
        Amount = amount;
        Currency = currency;
    }

    public Money Add(Money other)
    {
        if (Currency != other.Currency)
            throw new DomainException("Không thể cộng tiền khác loại");
        return new(Amount + other.Amount, Currency);  // trả VO mới, không mutate
    }

    public static Money Zero(Currency c) => new(0, c);
}

4. Aggregate & Aggregate Root

Aggregate là biên giới của tính nhất quán (consistency boundary). Mọi thay đổi đi qua Root; Root bảo vệ invariant. Tham chiếu giữa aggregate chỉ bằng Id, không bằng object.

Order (Aggregate Root)
OrderLine (entity nội bộ) OrderLine Money Total (VO) CustomerId (chỉ Id, không object) OrderStatus (enum) 
public class Order : AggregateRoot<Guid>
{
    private readonly List<OrderLine> _lines = new();
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();  // không expose List để sửa ngoài

    public Guid CustomerId { get; private set; }   // ref aggregate khác = Id
    public OrderStatus Status { get; private set; }
    public Money Total => _lines.Aggregate(
        Money.Zero(Currency.VND), (acc, l) => acc.Add(l.LineTotal));

    private Order() { }  // cho EF Core

    // Factory method — đặt tên theo ubiquitous language
    public static Order Place(Guid customerId)
    {
        var order = new Order { Id = Guid.NewGuid(), CustomerId = customerId, Status = OrderStatus.Draft };
        order.Raise(new OrderPlacedEvent(order.Id, customerId));  // domain event
        return order;
    }

    // Mọi thay đổi qua method bảo vệ invariant
    public void AddLine(Guid productId, int qty, Money unitPrice)
    {
        if (Status != OrderStatus.Draft)
            throw new DomainException("Chỉ thêm dòng khi đơn ở Draft");
        if (qty <= 0)
            throw new DomainException("Số lượng phải > 0");

        var existing = _lines.FirstOrDefault(l => l.ProductId == productId);
        if (existing is not null) existing.IncreaseQty(qty);
        else _lines.Add(new OrderLine(productId, qty, unitPrice));
    }

    public void Confirm()
    {
        if (_lines.Count == 0)
            throw new DomainException("Không thể xác nhận đơn rỗng");  // invariant
        Status = OrderStatus.Confirmed;
        Raise(new OrderConfirmedEvent(Id, Total.Amount));
    }
}
💡 Quy tắc thiết kế aggregate (Vaughn Vernon): (1) Bảo vệ invariant trong một aggregate. (2) Aggregate nhỏ. (3) Tham chiếu aggregate khác bằng Id. (4) Cập nhật aggregate khác qua eventual consistency (domain event), không trong cùng transaction.

5. Domain Events

Aggregate raise event khi có sự kiện nghiệp vụ. Event được dispatch sau khi persist thành công — thường ngay trước/sau SaveChanges.

public abstract class AggregateRoot<TId>
{
    public TId Id { get; protected set; } = default!;
    private readonly List<IDomainEvent> _events = new();
    public IReadOnlyList<IDomainEvent> DomainEvents => _events.AsReadOnly();
    protected void Raise(IDomainEvent e) => _events.Add(e);
    public void ClearEvents() => _events.Clear();
}

public record OrderConfirmedEvent(Guid OrderId, decimal Total) : IDomainEvent;
// Dispatch events trong SaveChanges override (EF Core + MediatR)
public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    var entities = ChangeTracker.Entries<AggregateRoot<Guid>>()
        .Where(e => e.Entity.DomainEvents.Any())
        .Select(e => e.Entity).ToList();

    var events = entities.SelectMany(e => e.DomainEvents).ToList();
    var result = await base.SaveChangesAsync(ct);  // persist trước

    entities.ForEach(e => e.ClearEvents());
    foreach (var e in events)
        await _mediator.Publish(e, ct);          // rồi mới publish

    return result;
}
⚠️ In-process domain event vs integration event: Domain event ở trên là trong cùng process. Để thông báo sang bounded context/service khác, chuyển thành integration event publish qua message bus (xem trang Messaging) — thường kèm Outbox pattern để đảm bảo nhất quán.

6. Repository

Một repository cho mỗi aggregate root. Interface sống ở tầng Domain; implementation ở Infrastructure (EF Core). Repository load/save nguyên cụm aggregate.

// Domain layer — interface, không biết EF Core
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(Guid id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
    void Remove(Order order);
}

// Infrastructure layer — implement bằng EF Core
public class OrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public OrderRepository(AppDbContext db) => _db = db;

    public Task<Order?> GetByIdAsync(Guid id, CancellationToken ct)
        => _db.Orders
            .Include(o => o.Lines)   // load nguyên aggregate
            .FirstOrDefaultAsync(o => o.Id == id, ct);

    public async Task AddAsync(Order o, CancellationToken ct) => await _db.Orders.AddAsync(o, ct);
    public void Remove(Order o) => _db.Orders.Remove(o);
}
❌ Anti-pattern: Repository "generic" IRepository<T> expose IQueryable ra ngoài → query logic rò rỉ khắp nơi, không còn aggregate boundary. Dùng repository chuyên biệt theo aggregate, hoặc tách hẳn read sang CQRS query.

7. Anti-Corruption Layer (ACL)

Khi tích hợp hệ thống legacy/bên thứ ba có model "bẩn", ACL dịch sang model sạch của domain bạn — cách ly domain khỏi sự lộn xộn bên ngoài.

// Model "bẩn" từ ERP legacy (SOAP, field viết tắt khó hiểu)
public class LegacyCustomerDto
{
    public string CUST_NM { get; set; }     // tên
    public string CR_LMT { get; set; }      // credit limit dạng string "1.000.000"
    public string ST_CD { get; set; }       // "A"=active, "I"=inactive
}

// ACL: translator dịch sang domain model sạch
public class CustomerAcl : ICustomerProvider
{
    private readonly ILegacyErpClient _erp;
    public CustomerAcl(ILegacyErpClient erp) => _erp = erp;

    public async Task<Customer> GetAsync(string code, CancellationToken ct)
    {
        var dto = await _erp.FetchCustomerAsync(code, ct);

        // Dịch sang ubiquitous language của domain mình
        return new Customer(
            name: dto.CUST_NM.Trim(),
            creditLimit: new Money(decimal.Parse(dto.CR_LMT, CultureInfo.GetCultureInfo("vi-VN")), Currency.VND),
            isActive: dto.ST_CD == "A");
    }
}
💡 Lợi ích ACL: Khi ERP đổi field/format, chỉ ACL phải sửa; domain không đụng tới. Domain luôn nói "ngôn ngữ của mình".

8. Kiến trúc tầng (Clean / Onion)

DDD thường đi với Clean Architecture: dependency hướng vào trong, Domain ở lõi không phụ thuộc gì.

┌─────────────────────────────────────────┐
│  API / UI         (Controllers, Minimal API)   │  ← phụ thuộc vào trong
│  ┌───────────────────────────────────┐  │
│  │  Application   (Command/Query handlers,  │  │
│  │                use cases, MediatR)       │  │
│  │  ┌─────────────────────────────┐  │  │
│  │  │  Domain  (Entity, VO, Aggregate, │  │  │  ← LÕI, không ref ra ngoài
│  │  │          Domain Event, interface)│  │  │
│  │  └─────────────────────────────┘  │  │
│  └───────────────────────────────────┘  │
│  Infrastructure (EF Core, repos, ACL, MQ)      │  ← implement interface của Domain
└─────────────────────────────────────────┘
Dependency Inversion: Domain định nghĩa interface IOrderRepository; Infrastructure implement. Domain không bao giờ using Microsoft.EntityFrameworkCore. Đây là điều giúp domain test được và bền với thay đổi hạ tầng.

🎯 Checklist DDD

  • ✅ Có ubiquitous language — code dùng đúng từ nghiệp vụ
  • ✅ Mỗi bounded context có model riêng, không share god-object
  • ✅ Vẽ context map, xác định quan hệ (ACL/Conformist/...)
  • ✅ Value object bất biến, equality theo giá trị (dùng record)
  • ✅ Aggregate nhỏ; ref aggregate khác bằng Id, không object
  • ✅ Mọi thay đổi qua method của Root, bảo vệ invariant
  • ✅ Constructor private + factory method đặt tên nghiệp vụ
  • ✅ Domain event dispatch sau khi persist thành công
  • ✅ Một repository / aggregate root; interface ở Domain
  • ✅ ACL cách ly hệ thống ngoài; Domain không phụ thuộc Infrastructure
