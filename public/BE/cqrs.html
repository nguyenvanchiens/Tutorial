CQRS + MediatR — Tách Command & Query

Command Query Responsibility Segregation: tách rõ write-model và read-model, dùng MediatR làm in-process bus, pipeline behaviors cho validation/logging/transaction. Kèm phân tích khi NÊN và khi KHÔNG nên dùng, quan hệ với Event Sourcing, và các pitfall thực chiến.

1. CQRS là gì — và không phải là gì

CQRS chỉ là một nguyên tắc đơn giản: thao tác thay đổi state (Command) tách khỏi thao tác đọc state (Query). Mỗi bên có model, code path, và đôi khi database riêng.

✍️ Command (write)

Thể hiện ý định thay đổi. Trả về void hoặc id/ack, không trả về data đọc.

  • CreateOrderCommand
  • CancelOrderCommand
  • Validate → thay đổi aggregate → persist
  • Đi qua business rules, transaction

🔍 Query (read)

Chỉ đọc, không side-effect. Trả về DTO/ViewModel tối ưu cho UI.

  • GetOrderByIdQuery
  • SearchOrdersQuery
  • Có thể bypass domain model, query thẳng
  • Dùng Dapper/projection cho tốc độ
⚠️ Hiểu nhầm phổ biến: CQRS không bắt buộc 2 database, không bắt buộc Event Sourcing, không bắt buộc message bus. Ở mức cơ bản nhất nó chỉ là tách interface read/write trên cùng một DB. Đừng "over-engineer".

2. Setup MediatR

MediatR là in-process mediator: decouple sender khỏi handler. Lưu ý license: từ v12.4 (cuối 2024) MediatR chuyển sang commercial license cho công ty > 5M USD doanh thu; OSS thay thế là Mediator (source-generator) hoặc tự viết.

  1. Cài package 
    dotnet add package MediatR
dotnet add package FluentValidation
dotnet add package FluentValidation.DependencyInjectionExtensions
  2. Đăng ký DI 
    // Program.cs
builder.Services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssembly(typeof(Program).Assembly);

    // Pipeline behaviors chạy theo thứ tự đăng ký
    cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));
    cfg.AddOpenBehavior(typeof(ValidationBehavior<,>));
    cfg.AddOpenBehavior(typeof(TransactionBehavior<,>));
});

builder.Services.AddValidatorsFromAssembly(typeof(Program).Assembly);

3. Command end-to-end

Một command đầy đủ: record bất biến, validator, handler. Handler là nơi duy nhất orchestrate domain + persistence.

// 1. Command — record bất biến, implement IRequest<TResult>
public record CreateOrderCommand(
    Guid CustomerId,
    IReadOnlyList<OrderLineDto> Lines) : IRequest<Guid>;

// 2. Validator — tách rule khỏi handler
public class CreateOrderValidator : AbstractValidator<CreateOrderCommand>
{
    public CreateOrderValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty();
        RuleFor(x => x.Lines).NotEmpty().WithMessage("Đơn hàng phải có ít nhất 1 dòng");
        RuleForEach(x => x.Lines).ChildRules(l =>
            l.RuleFor(x => x.Quantity).GreaterThan(0));
    }
}

// 3. Handler — orchestrate domain, KHÔNG chứa business rule sâu
public class CreateOrderHandler : IRequestHandler<CreateOrderCommand, Guid>
{
    private readonly IOrderRepository _repo;
    private readonly IUnitOfWork _uow;

    public CreateOrderHandler(IOrderRepository repo, IUnitOfWork uow)
        => (_repo, _uow) = (repo, uow);

    public async Task<Guid> Handle(CreateOrderCommand cmd, CancellationToken ct)
    {
        // Business rule sống trong aggregate, không ở đây
        var order = Order.Create(cmd.CustomerId);
        foreach (var line in cmd.Lines)
            order.AddLine(line.ProductId, line.Quantity, line.UnitPrice);

        await _repo.AddAsync(order, ct);
        await _uow.SaveChangesAsync(ct);  // commit + dispatch domain events
        return order.Id;
    }
}
💡 Controller mỏng: Controller chỉ map HTTP → command rồi _mediator.Send(cmd). Toàn bộ logic nằm trong handler — dễ test, dễ tái dùng từ background job/gRPC. 
[ApiController, Route("api/orders")]
public class OrdersController(ISender mediator) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Create(CreateOrderCommand cmd)
    {
        var id = await mediator.Send(cmd);
        return CreatedAtAction(nameof(GetById), new { id }, null);
    }
}

4. Query — read-model tối ưu

Query không cần đi qua domain model. Project thẳng ra DTO, hoặc dùng Dapper cho query nặng. Đây là điểm CQRS phát huy: read và write tối ưu độc lập.

public record GetOrderByIdQuery(Guid Id) : IRequest<OrderDetailDto?>;

public class GetOrderByIdHandler
    : IRequestHandler<GetOrderByIdQuery, OrderDetailDto?>
{
    private readonly AppDbContext _db;
    public GetOrderByIdHandler(AppDbContext db) => _db = db;

    public async Task<OrderDetailDto?> Handle(GetOrderByIdQuery q, CancellationToken ct)
        => await _db.Orders
            .AsNoTracking()                       // read-only, nhanh hơn
            .Where(o => o.Id == q.Id)
            .Select(o => new OrderDetailDto(   // projection, chỉ lấy field cần
                o.Id,
                o.Customer.Name,
                o.Lines.Sum(l => l.Quantity * l.UnitPrice),
                o.Status.ToString()))
            .FirstOrDefaultAsync(ct);
}
Read-model có thể khác hẳn write-model: write dùng aggregate Order với invariant nghiêm ngặt; read dùng OrderDetailDto phẳng, denormalized, join sẵn tên khách hàng. Hai mô hình phục vụ hai mục đích khác nhau.

5. Pipeline Behaviors — cross-cutting concerns

Behavior bọc quanh mỗi handler giống middleware. Đây là sức mạnh thật của MediatR: validation, logging, transaction, caching tập trung một chỗ.

LoggingBehavior — log request + thời gian
ValidationBehavior — chạy FluentValidation, throw nếu fail
TransactionBehavior — mở transaction quanh command
➤ Handler (CreateOrderHandler) chạy ở giữa
TransactionBehavior — commit / rollback
LoggingBehavior — log kết quả + elapsed

Validation behavior

public class ValidationBehavior<TRequest, TResponse>
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : IRequest<TResponse>
{
    private readonly IEnumerable<IValidator<TRequest>> _validators;
    public ValidationBehavior(IEnumerable<IValidator<TRequest>> v) => _validators = v;

    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        if (_validators.Any())
        {
            var ctx = new ValidationContext<TRequest>(request);
            var failures = (await Task.WhenAll(
                    _validators.Select(v => v.ValidateAsync(ctx, ct))))
                .SelectMany(r => r.Errors)
                .Where(f => f is not null)
                .ToList();

            if (failures.Count != 0)
                throw new ValidationException(failures);
        }
        return await next();  // gọi handler tiếp theo trong chain
    }
}

Logging behavior

public class LoggingBehavior<TReq, TRes> : IPipelineBehavior<TReq, TRes>
    where TReq : IRequest<TRes>
{
    private readonly ILogger<LoggingBehavior<TReq, TRes>> _log;
    public LoggingBehavior(ILogger<LoggingBehavior<TReq, TRes>> log) => _log = log;

    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        var name = typeof(TReq).Name;
        var sw = Stopwatch.StartNew();
        _log.LogInformation("➤ Handling {Request}", name);
        try
        {
            var res = await next();
            _log.LogInformation("✔ {Request} done in {Ms}ms", name, sw.ElapsedMilliseconds);
            return res;
        }
        catch (Exception ex)
        {
            _log.LogError(ex, "✘ {Request} failed in {Ms}ms", name, sw.ElapsedMilliseconds);
            throw;
        }
    }
}

Transaction behavior (chỉ cho Command)

// Marker interface để phân biệt command cần transaction
public interface ITransactionalRequest { }

public class TransactionBehavior<TReq, TRes> : IPipelineBehavior<TReq, TRes>
    where TReq : ITransactionalRequest
{
    private readonly AppDbContext _db;
    public TransactionBehavior(AppDbContext db) => _db = db;

    public async Task<TRes> Handle(TReq req, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);
        try
        {
            var res = await next();
            await tx.CommitAsync(ct);
            return res;
        }
        catch
        {
            await tx.RollbackAsync(ct);
            throw;
        }
    }
}
⚠️ Thứ tự behavior quan trọng: Logging ngoài cùng (đo cả validation), Validation trước Transaction (đừng mở tx khi input đã sai), Transaction sát handler nhất. Đăng ký đúng thứ tự bạn muốn chúng bọc.

6. Khi NÊN và khi KHÔNG nên dùng CQRS

✅ Nên dùng khi

  • Read và write có tải/scale rất khác nhau (đọc nhiều gấp 100×)
  • Read-model phức tạp, cần denormalize cho nhiều màn hình khác nhau
  • Business logic write phức tạp (nhiều invariant, domain rules)
  • Cần audit/event log từng thay đổi
  • Nhiều team làm chung, muốn tách rõ trách nhiệm

❌ Không nên khi

  • CRUD đơn giản, đọc = ghi cùng shape — thêm CQRS chỉ là boilerplate
  • Team nhỏ, chưa quen pattern — tăng độ phức tạp vô ích
  • App nhỏ, ít domain logic
  • Bạn nghĩ "CQRS = phải có 2 DB + event sourcing" (sai và đắt)
Áp dụng theo bounded context: Không phải toàn app dùng CQRS. Một context phức tạp (Ordering) dùng CQRS đầy đủ; context CRUD đơn giản (Settings) chỉ cần repository thường.

7. Quan hệ với Event Sourcing

CQRS và Event Sourcing (ES) thường đi cùng nhưng độc lập. Bạn có thể dùng CQRS mà không ES, và ngược lại.

Khía cạnhCQRS thườngCQRS + Event Sourcing
Lưu stateState hiện tại (row trong table)Chuỗi sự kiện bất biến (event store)
Read-modelQuery thẳng write-DB hoặc replicaProjection build từ event stream
Audit / lịch sửPhải tự thêm audit logMiễn phí — mọi thay đổi là event
Time-travel / replayKhôngReplay event để rebuild bất kỳ state nào
Độ phức tạpTrung bìnhCao (eventual consistency, versioning event)
// Với ES, aggregate sinh ra events thay vì sửa state trực tiếp
public class Order : AggregateRoot
{
    public void Cancel(string reason)
    {
        if (Status == OrderStatus.Shipped)
            throw new DomainException("Không thể huỷ đơn đã giao");

        // Apply event — state thay đổi qua When(), event được lưu vào store
        Raise(new OrderCancelledEvent(Id, reason, DateTime.UtcNow));
    }

    private void When(OrderCancelledEvent e)
    {
        Status = OrderStatus.Cancelled;
        CancelReason = e.Reason;
    }
}
Đừng nhảy thẳng vào Event Sourcing. ES là công cụ mạnh nhưng chi phí lớn: versioning event schema, snapshot, eventual consistency. Chỉ dùng khi domain thật sự cần lịch sử/replay (finance, audit). Phần lớn app dùng CQRS thường là đủ.

8. Pitfalls thực chiến

❌ Query có side-effect

Query "ghi log lần truy cập" vào DB → phá nguyên tắc đọc thuần. Khó cache, khó scale read.

Fix: side-effect thành command/event riêng, fire-and-forget.

❌ Handler chứa business logic

Nhồi rule vào handler → anemic domain, logic rải rác, khó test.

Fix: logic sống trong aggregate/domain service, handler chỉ orchestrate.

❌ Command trả về data đọc

CreateOrderCommand trả về full DTO order → mờ ranh giới read/write.

Fix: trả id/ack thôi; muốn data thì gọi query sau.

❌ Một validator khổng lồ

Validate cả business rule (số dư đủ tiền) trong FluentValidation → cần DB call.

Fix: validator chỉ validate input format; business rule ở domain.

❌ Read-model cập nhật trễ mà không lường

Read replica/projection eventual consistency → user tạo xong không thấy ngay.

Fix: read-your-write từ write-DB cho user vừa thao tác, hoặc thông báo UI.

❌ Lạm dụng MediatR cho mọi method call

Dùng Send thay cho gọi service trực tiếp ở mọi nơi → khó trace, overhead.

Fix: MediatR cho use-case boundary, không cho mọi internal call.

🎯 Checklist áp dụng CQRS

  • ✅ Command là record bất biến, trả về void/id/ack — không trả read-data
  • ✅ Query AsNoTracking() + projection, không side-effect
  • ✅ Business logic ở aggregate/domain, handler chỉ orchestrate
  • ✅ ValidationBehavior validate input; business rule ở domain
  • ✅ TransactionBehavior chỉ bọc command (marker interface)
  • ✅ Behavior đăng ký đúng thứ tự: Logging → Validation → Transaction → Handler
  • ✅ Chỉ áp CQRS cho context phức tạp, CRUD đơn giản giữ repository thường
  • ✅ Cân nhắc license MediatR — hoặc dùng Mediator source-gen
  • ✅ Event Sourcing chỉ thêm khi domain thật sự cần lịch sử/replay
  • ✅ Lường trước eventual consistency của read-model
