Hiểu sâu Dependency Injection trong .NET

Dependency Injection (DI) là xương sống của mọi ứng dụng ASP.NET Core hiện đại. Bài này đi từ "tại sao cần DI", 3 lifetime (Singleton/Scoped/Transient), cách đăng ký service, thiết kế theo interface, đến cái bẫy captive dependency nguy hiểm nhất. Code mẫu chuẩn .NET 8/9 (2026).

1. Dependency Injection là gì & tại sao cần?

DI là một dạng triển khai của nguyên tắc Inversion of Control (IoC): thay vì class tự tạo dependency của mình bằng new, nó nhận dependency từ bên ngoài (thường qua constructor).

🔄 Inversion of Control

Quyền "quyết định dùng implementation nào" được đảo ngược — không nằm trong class mà nằm ở composition root (nơi đăng ký service).

🔗 Loose Coupling

Class chỉ phụ thuộc vào abstraction (interface), không phụ thuộc vào class cụ thể. Đổi implementation không cần sửa class dùng nó.

🧪 Testability

Vì dependency được inject vào, ta dễ dàng thay bằng mock/fake khi viết unit test — không phải đụng tới hạ tầng thật (DB, HTTP, email...).

Định nghĩa ngắn gọn: DI = "đừng tự đi tìm thứ bạn cần, hãy để nó được trao cho bạn". .NET có sẵn một IoC Container (gọi là IServiceProvider) lo việc tạo và trao dependency theo cấu hình bạn khai báo.

So sánh: tự new vs được inject

❌ Tight coupling — tự new dependency

public class OrderService
{
    private readonly SmtpEmailSender _email;
    private readonly SqlOrderRepository _repo;

    public OrderService()
    {
        // Tự tạo — phụ thuộc cứng vào class cụ thể
        _email = new SmtpEmailSender("smtp.gmail.com", 587);
        _repo  = new SqlOrderRepository("Server=...;Db=prod");
    }

    public async Task PlaceAsync(Order o)
    {
        await _repo.SaveAsync(o);
        await _email.SendAsync(o.Email, "Đặt hàng OK");
    }
}

Không test được: muốn unit test phải gửi email thật + connect SQL thật. Đổi sang SendGrid? Phải sửa code OrderService.

✅ Loose coupling — inject abstraction

public class OrderService
{
    private readonly IEmailSender _email;
    private readonly IOrderRepository _repo;

    // Dependency được trao qua constructor
    public OrderService(IEmailSender email, IOrderRepository repo)
    {
        _email = email;
        _repo  = repo;
    }

    public async Task PlaceAsync(Order o)
    {
        await _repo.SaveAsync(o);
        await _email.SendAsync(o.Email, "Đặt hàng OK");
    }
}

Test: inject Mock<IEmailSender> + Mock<IOrderRepository>. Đổi sang SendGrid? Chỉ đăng ký implementation khác — không đụng OrderService.

💡 Dependency Inversion Principle (chữ "D" trong SOLID): module cấp cao không nên phụ thuộc module cấp thấp — cả hai nên phụ thuộc vào abstraction. DI là công cụ giúp bạn thực thi nguyên tắc này một cách tự nhiên.

2. Container DI built-in của .NET

Từ .NET Core trở đi, framework có sẵn một IoC container nhẹ. Bạn cấu hình nó qua builder.Services (kiểu IServiceCollection) ở Program.cs.

// Program.cs (.NET 8/9 — top-level statements)
var builder = WebApplication.CreateBuilder(args);

// 1. Đăng ký service vào container
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddSingleton<IEmailSender, SmtpEmailSender>();
builder.Services.AddTransient<IOrderService, OrderService>();

builder.Services.AddControllers();

var app = builder.Build();   // container được "đóng băng" tại đây

app.MapControllers();
app.Run();
  1. Đăng ký (register) — khai báo "khi ai cần IFoo, hãy đưa cho họ Foo", kèm lifetime.
  2. Resolve — framework tự tạo object và truyền dependency vào (qua constructor) khi cần. Bạn hiếm khi gọi tay.
  3. Dispose — container tự gọi Dispose() cho service IDisposable đúng thời điểm theo lifetime của nó.
⚠️ Composition Root: mọi đăng ký nên tập trung ở Program.cs (hoặc các extension method AddXxx()). Đừng rải provider.GetService() khắp nơi — đó là anti-pattern Service Locator, làm mất hết lợi ích của DI.

3. Ba Lifetime: Singleton · Scoped · Transient

Khi đăng ký, bạn chọn vòng đời (lifetime) — quyết định container tái sử dụng instance hay tạo mới. Đây là phần dễ sai nhất, hiểu kỹ sẽ tránh được rất nhiều bug.

Lifetime Một instance cho mỗi... Dùng khi Nguy hiểm
Singleton Toàn bộ vòng đời ứng dụng (1 instance duy nhất) Service không state / state chia sẻ an toàn: cache, config, logger, HttpClient factory Phải thread-safe. Không được giữ Scoped/Transient (captive dependency)
Scoped Mỗi HTTP request (mỗi scope) Phổ biến nhất cho web: DbContext, Unit of Work, repository, service per-request Không inject vào Singleton. Không dùng ở BackgroundService nếu không tạo scope thủ công
Transient Mỗi lần được resolve (luôn tạo mới) Service nhẹ, stateless, không cần chia sẻ: validator, mapper, formatter Nếu nắm tài nguyên nặng → tốn bộ nhớ. Vẫn bị "captured" nếu nhét vào Singleton
Quy tắc vàng về cấp bậc lifetime: service được inject vào phải có lifetime bằng hoặc dài hơn service chứa nó. Singleton chỉ được giữ Singleton. Scoped được giữ Scoped + Singleton. Transient được giữ tất cả.

Service demo — đếm số & sinh GUID

Để "nhìn thấy" sự khác nhau giữa 3 lifetime, ta tạo một service lưu một Guid cố định lúc khởi tạo. Cùng một instance → cùng Guid.

// IOperation: mỗi instance có 1 Guid sinh lúc constructor chạy
public interface IOperation
{
    Guid OperationId { get; }
}

public class Operation : IOperation
{
    public Operation() => OperationId = Guid.NewGuid();
    public Guid OperationId { get; }
}

// 3 interface kế thừa để đăng ký 3 lifetime khác nhau cùng 1 class
public interface ISingletonOp : IOperation { }
public interface IScopedOp    : IOperation { }
public interface ITransientOp : IOperation { }

public class Operation : ISingletonOp, IScopedOp, ITransientOp
{
    public Operation() => OperationId = Guid.NewGuid();
    public Guid OperationId { get; }
}
// Đăng ký mỗi interface một lifetime khác nhau
builder.Services.AddSingleton<ISingletonOp, Operation>();
builder.Services.AddScoped<IScopedOp, Operation>();
builder.Services.AddTransient<ITransientOp, Operation>();

Endpoint in ra Guid để quan sát

app.MapGet("/ops", (
    ISingletonOp s1, ISingletonOp s2,
    IScopedOp    sc1, IScopedOp    sc2,
    ITransientOp t1, ITransientOp t2) => new
{
    Singleton1 = s1.OperationId,
    Singleton2 = s2.OperationId,   // == Singleton1 (mọi request)
    Scoped1    = sc1.OperationId,
    Scoped2    = sc2.OperationId,  // == Scoped1 (trong 1 request)
    Transient1 = t1.OperationId,
    Transient2 = t2.OperationId    // != Transient1 (luôn khác)
});

Kết quả qua 2 request liên tiếp

Biến Request #1 Request #2 Nhận xét
Singleton1 / Singleton2 AAA / AAA AAA / AAA Giống nhau ở cả 2 request — 1 instance toàn app
Scoped1 / Scoped2 BBB / BBB CCC / CCC Giống nhau trong 1 request, đổi giữa các request
Transient1 / Transient2 DDD / EEE FFF / GGG Luôn khác nhau — mỗi lần resolve tạo mới

Ví dụ thực tế: counter Singleton dùng chung

// Đếm tổng số request — phải thread-safe vì Singleton chia sẻ giữa nhiều thread
public interface IRequestCounter
{
    long Increment();
}

public class RequestCounter : IRequestCounter
{
    private long _count;
    // Interlocked đảm bảo an toàn khi nhiều request chạy song song
    public long Increment() => Interlocked.Increment(ref _count);
}

// Đăng ký Singleton vì cần đếm chung cho cả app
builder.Services.AddSingleton<IRequestCounter, RequestCounter>();

app.MapGet("/count", (IRequestCounter c) => new { Total = c.Increment() });
// /count gọi 3 lần → 1, 2, 3 (state được giữ vì cùng 1 instance)
🚫 Singleton phải thread-safe: vì nhiều request (nhiều thread) cùng dùng chung 1 instance, mọi state mutable phải bảo vệ bằng lock, Interlocked, hoặc dùng cấu trúc Concurrent*. Một List<T> thường trong Singleton = bug khó tái hiện.

4. Constructor Injection (và 2 dạng còn lại)

.NET DI container chỉ hỗ trợ constructor injection một cách native. Đây cũng là dạng được khuyên dùng tuyệt đại đa số trường hợp.

public class InvoiceService
{
    private readonly IOrderRepository _repo;
    private readonly ILogger<InvoiceService> _logger;

    // Container tự nhìn constructor và truyền đủ dependency vào
    public InvoiceService(IOrderRepository repo, ILogger<InvoiceService> logger)
    {
        _repo = repo;
        _logger = logger;
    }
}

// .NET 8/9 — primary constructor gọn hơn
public class InvoiceService(IOrderRepository repo, ILogger<InvoiceService> logger)
{
    public async Task RunAsync()
    {
        logger.LogInformation("Bắt đầu tạo hoá đơn");
        var orders = await repo.GetPendingAsync();
        // ...
    }
}
Dạng injection Cách dùng Nên dùng?
Constructor Truyền dependency qua tham số constructor ✅ Mặc định. Dependency bắt buộc, immutable (readonly), rõ ràng
Method Truyền vào tham số method (vd handler Minimal API, [FromServices]) ⚠️ Chỉ cho dependency dùng 1 chỗ, hoặc trong action/endpoint
Property Gán qua public property (không native — cần thư viện bên thứ 3) ❌ Tránh. Dependency "ẩn", dễ NullReferenceException 
// Method injection trong controller action bằng [FromServices]
[HttpGet("export")]
public IActionResult Export([FromServices] IPdfExporter exporter)
{
    // exporter chỉ cần ở action này → không nhét vào constructor
    return File(exporter.Render(), "application/pdf");
}
💡 Vì sao ưu tiên constructor injection? Dependency hiện rõ ngay ở chữ ký constructor (không "ẩn"), có thể đánh readonly nên không bị đổi sau khi tạo, và nếu thiếu đăng ký thì lỗi nổ ngay lúc resolve thay vì âm thầm null. Constructor "phình to" nhiều tham số là dấu hiệu class vi phạm Single Responsibility — nên tách nhỏ.

5. Các cách đăng ký Service

Ngoài Add{Lifetime}<IFoo, Foo>() cơ bản, container .NET hỗ trợ nhiều kiểu đăng ký linh hoạt.

5.1 Cú pháp cơ bản

// Map interface → implementation
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddTransient<IGuidFactory, GuidFactory>();

// Đăng ký concrete type không có interface
builder.Services.AddScoped<PricingCalculator>();

// Đăng ký một instance có sẵn (luôn là Singleton)
builder.Services.AddSingleton<IAppConfig>(new AppConfig { Region = "vn" });

5.2 Factory registration (lambda)

Khi việc tạo object cần logic, hoặc cần lấy service khác từ provider để build.

builder.Services.AddScoped<IPaymentGateway>(sp =>
{
    // Lấy dependency khác từ IServiceProvider (sp)
    var cfg = sp.GetRequiredService<IOptions<PayConfig>>().Value;
    var http = sp.GetRequiredService<IHttpClientFactory>();

    return cfg.Provider switch
    {
        "stripe" => new StripeGateway(http, cfg.ApiKey),
        "vnpay"  => new VnpayGateway(http, cfg.ApiKey),
        _        => throw new InvalidOperationException("Unknown gateway")
    };
});

5.3 TryAdd — chỉ thêm nếu chưa có

Hữu ích khi viết thư viện: cho phép người dùng override implementation của bạn bằng cách đăng ký trước.

using Microsoft.Extensions.DependencyInjection.Extensions;

// Chỉ đăng ký nếu IClock chưa được đăng ký trước đó
services.TryAddSingleton<IClock, SystemClock>();

// AddX thường thì SẼ thêm bản trùng — resolve IFoo lấy bản CUỐI cùng
services.AddSingleton<IClock, SystemClock>();
services.AddSingleton<IClock, FakeClock>();
// GetRequiredService<IClock>() → trả về FakeClock

5.4 Nhiều implementation + IEnumerable<T>

Đăng ký nhiều bản cho cùng interface → inject IEnumerable<T> để lấy tất cả. Pattern hữu ích cho validator chain, notification channels.

builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();
builder.Services.AddScoped<INotifier, PushNotifier>();

public class NotificationService(IEnumerable<INotifier> notifiers)
{
    public async Task NotifyAllAsync(string msg)
    {
        // Lặp qua TẤT CẢ implementation đã đăng ký
        foreach (var n in notifiers)
            await n.SendAsync(msg);
    }
}
⚠️ TryAddEnumerable: nếu dùng TryAdd với nhiều implementation, nó coi cùng service type là "đã có" và bỏ qua. Khi muốn thêm nhiều bản mà không trùng lặp chính xác, dùng services.TryAddEnumerable(ServiceDescriptor.Scoped<INotifier, SmsNotifier>()).

5.5 Keyed Services (.NET 8+)

Từ .NET 8, có thể đăng ký nhiều implementation gắn key và chọn đúng bản theo key khi resolve.

// Đăng ký theo key
builder.Services.AddKeyedScoped<INotifier, EmailNotifier>("email");
builder.Services.AddKeyedScoped<INotifier, SmsNotifier>("sms");

// Inject bằng [FromKeyedServices]
public class AlertService(
    [FromKeyedServices("sms")] INotifier sms,
    [FromKeyedServices("email")] INotifier email)
{
    public INotifier Sms { get; } = sms;
    public INotifier Email { get; } = email;
}

// Hoặc lấy trực tiếp từ provider
var sms = sp.GetRequiredKeyedService<INotifier>("sms");
Keyed vs IEnumerable: dùng IEnumerable<T> khi cần chạy tất cả implementation; dùng keyed khi cần chọn đúng một implementation theo điều kiện (vd theo tenant, theo config).

6. Thiết kế hướng Interface (Program to Abstraction)

DI phát huy sức mạnh khi class phụ thuộc vào interface chứ không phải class cụ thể. Đây là nền tảng cho việc test và thay thế implementation.

// Abstraction — định nghĩa "cần gì", không nói "làm thế nào"
public interface IAppLogger
{
    void Info(string message);
    void Error(string message, Exception? ex = null);
}

// Implementation cho production — ghi ra console/file
public class ConsoleAppLogger : IAppLogger
{
    public void Info(string m)  => Console.WriteLine($"[INFO]  {m}");
    public void Error(string m, Exception? ex = null)
        => Console.Error.WriteLine($"[ERROR] {m} {ex}");
}

// Implementation cho test — chỉ lưu vào list để assert
public class FakeAppLogger : IAppLogger
{
    public List<string> Messages { get; } = new();
    public void Info(string m)  => Messages.Add($"INFO:{m}");
    public void Error(string m, Exception? ex = null) => Messages.Add($"ERROR:{m}");
}
// Class chỉ phụ thuộc IAppLogger — không biết Console hay Fake
public class CheckoutService(IAppLogger log)
{
    public bool Checkout(Cart cart)
    {
        if (cart.IsEmpty)
        {
            log.Error("Giỏ hàng rỗng");
            return false;
        }
        log.Info($"Checkout {cart.Items.Count} sản phẩm");
        return true;
    }
}
// Unit test — inject FakeAppLogger để assert log đã được gọi
[Fact]
public void Checkout_EmptyCart_LogsError()
{
    var fakeLog = new FakeAppLogger();
    var sut = new CheckoutService(fakeLog);

    var ok = sut.Checkout(new Cart());   // giỏ rỗng

    ok.Should().BeFalse();
    fakeLog.Messages.Should().Contain("ERROR:Giỏ hàng rỗng");
}
💡 Lợi ích của interface: (1) Test — thay bằng fake/mock dễ dàng; (2) Swap — đổi SQL → Mongo, SMTP → SendGrid chỉ bằng đổi đăng ký; (3) Decorator — bọc thêm logging/caching/retry quanh implementation gốc mà không sửa nó.
⚠️ Đừng lạm dụng interface: không phải class nào cũng cần interface. Nếu chỉ có 1 implementation và không bao giờ mock (vd DTO, value object, model), tạo interface chỉ thêm rác. Tạo abstraction khi thực sự cần test/swap.

7. ⚠️ Captive Dependency — cái bẫy chết người

Đây là lỗi DI phổ biến và nguy hiểm nhất: khi một service lifetime dài (Singleton) giữ tham chiếu tới service lifetime ngắn (Scoped/Transient). Service ngắn bị "bắt giữ" (captured) suốt vòng đời của service dài.

🚫 Hậu quả: một DbContext (Scoped) bị Singleton giữ → nó sống mãi mãi → không bao giờ được dispose đúng cách, ôm connection, tích luỹ change tracker, và không thread-safe nên crash khi nhiều request dùng song song. Dữ liệu stale, lỗi "A second operation started on this context...".

❌ Singleton giữ Scoped (captive dependency)

// CacheWarmer được đăng ký SINGLETON
public class CacheWarmer
{
    private readonly AppDbContext _db;  // Scoped! bị bắt giữ

    // DbContext (Scoped) bị inject vào Singleton → captured
    public CacheWarmer(AppDbContext db) => _db = db;

    public async Task WarmAsync()
    {
        // _db này là instance từ request ĐẦU TIÊN, dùng mãi mãi
        var products = await _db.Products.ToListAsync();
        // → stale data + crash khi nhiều thread dùng cùng _db
    }
}

builder.Services.AddSingleton<CacheWarmer>();   // 💥
builder.Services.AddDbContext<AppDbContext>();    // Scoped (mặc định)

DbContext sống suốt đời app → ôm connection, change tracker phình to, không thread-safe → lỗi ngẫu nhiên dưới tải.

✅ Fix 1: Inject IServiceScopeFactory, tự tạo scope

public class CacheWarmer(IServiceScopeFactory scopeFactory)
{
    public async Task WarmAsync()
    {
        // Tạo scope NGẮN HẠN, lấy DbContext tươi, dispose sau khi xong
        using var scope = scopeFactory.CreateScope();
        var db = scope.ServiceProvider
                       .GetRequiredService<AppDbContext>();

        var products = await db.Products.ToListAsync();
        // scope dispose ở cuối using → DbContext được dispose đúng
    }
}

Mỗi lần warm tạo scope riêng → DbContext tươi, dùng xong dispose ngay. An toàn thread.

✅ Fix 2: Inject factory cho dependency Transient

// Cần Transient trong Singleton? Inject Func<T> hoặc factory
public class ReportEngine(Func<IPdfRenderer> rendererFactory)
{
    public byte[] Build()
    {
        // Tạo renderer MỚI mỗi lần cần, không giữ tham chiếu lâu dài
        var renderer = rendererFactory();
        return renderer.Render();
    }
}

// Đăng ký factory
builder.Services.AddTransient<IPdfRenderer, PdfRenderer>();
builder.Services.AddSingleton<Func<IPdfRenderer>>(sp =>
    () => sp.GetRequiredService<IPdfRenderer>());
builder.Services.AddSingleton<ReportEngine>();

Singleton chỉ giữ một factory (delegate), không giữ instance Transient → tạo mới khi cần.

BackgroundService cũng là Singleton trá hình

IHostedService / BackgroundService được resolve một lần lúc startup → bản chất là Singleton. Inject thẳng Scoped vào nó = captive dependency.

public class CleanupWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            // Tạo scope mới cho MỖI vòng lặp — DbContext tươi mỗi lần
            using (var scope = scopeFactory.CreateScope())
            {
                var db = scope.ServiceProvider
                               .GetRequiredService<AppDbContext>();
                await db.Database.ExecuteSqlRawAsync(
                    "DELETE FROM Sessions WHERE ExpiresAt < NOW()", ct);
            }
            await Task.Delay(TimeSpan.FromMinutes(10), ct);
        }
    }
}

Bật Scope Validation để bắt lỗi sớm

.NET tự động bật scope validation ở môi trường Development. Nó sẽ ném exception ngay lúc startup nếu phát hiện Singleton giữ Scoped — bắt bug trước khi lên production.

// Ép bật validation ở MỌI môi trường (khuyên cho test)
var builder = WebApplication.CreateBuilder(args);

builder.Host.UseDefaultServiceProvider((context, options) =>
{
    options.ValidateScopes = true;   // chặn captive dependency
    options.ValidateOnBuild = true;  // kiểm tra toàn bộ lúc Build()
});
Lỗi bạn sẽ thấy: "Cannot consume scoped service 'AppDbContext' from singleton 'CacheWarmer'." — đây là scope validation đang cứu bạn. Đừng tắt nó đi, hãy sửa thiết kế.

8. Mẹo & thực hành tốt

✅ DbContext luôn là Scoped

AddDbContext<T>() mặc định đăng ký Scoped. Đừng đổi sang Singleton. Cần dùng ngoài request → tự tạo scope.

✅ Gom đăng ký vào extension method

Tạo AddApplicationServices(), AddInfrastructure() để Program.cs gọn và module hoá theo layer.

❌ Dùng Service Locator

Inject IServiceProvider rồi GetService() tứ tung làm dependency "ẩn", phá vỡ DI. Chỉ chấp nhận trong composition root/factory.

❌ Singleton chứa state mutable không khoá

Một List<T> hay Dictionary thường trong Singleton = race condition. Dùng Concurrent* hoặc lock.

Đăng ký gọn bằng extension method

// ServiceCollectionExtensions.cs
public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddApplicationServices(
        this IServiceCollection services)
    {
        services.AddScoped<IOrderService, OrderService>();
        services.AddScoped<ICheckoutService, CheckoutService>();
        services.AddSingleton<IClock, SystemClock>();
        return services;
    }
}

// Program.cs gọn gàng
builder.Services.AddApplicationServices();
builder.Services.AddInfrastructure(builder.Configuration);

🎯 Checklist Dependency Injection

  • ✅ Class nhận dependency qua constructor injection, gán readonly
  • ✅ Phụ thuộc vào interface/abstraction khi cần test hoặc swap implementation
  • ✅ Chọn đúng lifetime: DbContext + repository = Scoped; cache/logger/config = Singleton
  • ✅ Singleton là thread-safe — mọi state mutable được khoá hoặc dùng Concurrent* / Interlocked
  • ✅ KHÔNG inject Scoped/Transient trực tiếp vào Singleton (captive dependency)
  • ✅ Trong BackgroundService / Singleton: dùng IServiceScopeFactory.CreateScope() để lấy Scoped service
  • ✅ Bật ValidateScopes + ValidateOnBuild để bắt lỗi DI lúc startup
  • ✅ Mọi đăng ký tập trung ở composition root (Program.cs / extension method) — KHÔNG Service Locator
  • ✅ Nhiều implementation? Dùng IEnumerable<T> (chạy tất cả) hoặc keyed services (.NET 8) để chọn một
  • ✅ Viết thư viện? Dùng TryAdd / TryAddEnumerable để cho phép người dùng override
