Authentication & JWT

Hiểu sâu cách xác thực trong ASP.NET Core .NET 8/9: phân biệt Authentication vs Authorization, cấu trúc JWT (header.payload.signature), access token vs refresh token, cấu hình JwtBearer & TokenValidationParameters, policy/role authorization, đọc claims, refresh token rotation và những lỗi bảo mật chết người. Code C# chính xác, dùng được ngay.

1. Authentication vs Authorization

Hai khái niệm thường bị nhầm lẫn. Authentication (AuthN — xác thực) trả lời câu hỏi "Bạn là ai?". Authorization (AuthZ — phân quyền) trả lời "Bạn được phép làm gì?". Luôn xác thực TRƯỚC, phân quyền SAU.

🪪 Authentication (AuthN)

Chứng minh danh tính: kiểm tra username/password, validate JWT, kiểm tra API key, OAuth/OpenID. Kết quả: một ClaimsPrincipal đại diện cho người dùng (đã đăng nhập hay anonymous).

🔐 Authorization (AuthZ)

Quyết định người đã xác thực có được truy cập tài nguyên không, dựa trên role, claim, policy. Trong ASP.NET Core: middleware UseAuthorization(), attribute [Authorize], policy.

Tiêu chíAuthenticationAuthorization
Câu hỏi"Bạn là ai?""Bạn được làm gì?"
Thực hiện khiTrước (xác định danh tính)Sau (kiểm tra quyền)
Dữ liệu dùngCredentials, token, cookieRoles, claims, policies
Lỗi trả về401 Unauthorized403 Forbidden
MiddlewareUseAuthentication()UseAuthorization()
Thứ tự middleware quan trọng: trong pipeline phải đặt app.UseAuthentication(); TRƯỚC app.UseAuthorization();. Sai thứ tự thì HttpContext.User chưa được dựng khi authorization chạy → mọi request đều bị 401/403.

2. Cấu trúc JWT (JSON Web Token)

JWT là chuỗi gồm 3 phần ngăn cách bằng dấu chấm: header.payload.signature. Mỗi phần được mã hoá Base64Url (không phải mã hoá bảo mật — chỉ là encoding).

// Một JWT trông như thế này (3 phần ngăn bởi dấu chấm):
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   // HEADER  (base64url)
.eyJzdWIiOiIxMjMiLCJuYW1lIjoiQ2hpZW4iLCJleHAiOjE3MTg0MDAwMDB9  // PAYLOAD
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   // SIGNATURE

1. Header

Khai báo thuật toán ký và loại token.

{
  "alg": "HS256",
  "typ": "JWT"
}

2. Payload (Claims)

Chứa các claim mô tả người dùng & metadata token.

{
  "sub": "123",
  "name": "Chien",
  "role": "Admin",
  "iss": "devhub",
  "aud": "devhub-api",
  "exp": 1718400000
}

3. Signature

Ký base64url(header) + "." + base64url(payload) bằng secret key → đảm bảo token không bị sửa.

HMACSHA256(
  base64Url(header) + "." +
  base64Url(payload),
  secret
)
Claim chuẩnÝ nghĩa
sub (subject)ID định danh người dùng
iss (issuer)Bên phát hành token (server của bạn)
aud (audience)Bên được phép dùng token (API đích)
exp (expiration)Thời điểm hết hạn (Unix timestamp)
iat (issued at)Thời điểm phát hành
nbf (not before)Token chỉ hợp lệ sau thời điểm này
jti (JWT ID)ID duy nhất của token (dùng để revoke)
⚠️ Payload KHÔNG được mã hoá: phần payload chỉ encode Base64Url, không phải encrypt. Ai cũng có thể giải mã và đọc nội dung claim (dán vào jwt.io là thấy hết). Tuyệt đối KHÔNG để dữ liệu nhạy cảm (mật khẩu, số thẻ, secret) trong payload. Signature chỉ chống sửa đổi, không chống đọc.

3. Access Token vs Refresh Token

Mô hình hai token là nền tảng của xác thực hiện đại: access token sống ngắn, refresh token sống dài. Tách ra để cân bằng giữa bảo mật và trải nghiệm.

Tiêu chíAccess TokenRefresh Token
Tuổi thọNgắn (~5–15 phút)Dài (vài ngày → vài tuần)
Mục đíchGọi API, truy cập tài nguyênLấy access token mới khi hết hạn
Định dạngJWT (self-contained)Chuỗi opaque ngẫu nhiên (thường lưu DB)
Gửi kèmMỗi request (Authorization: Bearer)Chỉ khi refresh
Thu hồi (revoke)Khó (stateless) → để hết hạn nhanhDễ (xoá/đánh dấu trong DB)
Lưu ở clientMemory (an toàn nhất)HttpOnly cookie (khuyến nghị)
Vì sao tách hai token? Nếu access token bị lộ, nó hết hạn nhanh (vài phút) nên thiệt hại giới hạn. Refresh token sống lâu nhưng được giữ kín hơn, ít gửi đi, và có thể thu hồi trong DB. Người dùng không phải đăng nhập lại liên tục — UX tốt mà vẫn an toàn.
Đánh đổi: access token là stateless — server không thể "huỷ" nó trước khi hết hạn. Vì thế access token PHẢI sống ngắn. Nếu cần huỷ tức thì (logout ngay, ban user), dùng cơ chế bổ sung: blacklist jti, kiểm tra version token, hoặc rút ngắn exp.

4. Cấu hình & phát hành token trong ASP.NET Core

Luồng dựng JWT authentication đầy đủ cho .NET 8/9. Cài package Microsoft.AspNetCore.Authentication.JwtBearer. Thư viện tạo/đọc token: Microsoft.IdentityModel.JsonWebTokens (mới, khuyến nghị) hoặc System.IdentityModel.Tokens.Jwt (cũ hơn).

  1. Cấu hình settings trong appsettings.json — secret thật phải lấy từ User Secrets / Key Vault, không hardcode. 
    {
  "Jwt": {
    "Issuer": "https://devhub.local",
    "Audience": "devhub-api",
    "Key": "<lay-tu-secret-store-toi-thieu-32-bytes>",
    "AccessTokenMinutes": 15,
    "RefreshTokenDays": 7
  }
}
  2. Đăng ký authentication với AddJwtBearer trong Program.cs. 
    var jwt = builder.Configuration.GetSection("Jwt");
var key = new SymmetricSecurityKey(
    Encoding.UTF8.GetBytes(jwt["Key"]!));

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = jwt["Issuer"],
            ValidateAudience = true,
            ValidAudience = jwt["Audience"],
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = key,
            ClockSkew = TimeSpan.Zero   // bỏ 5 phút mặc định để exp chính xác
        };
    });

builder.Services.AddAuthorization();
  3. Bật middleware đúng thứ tự trong pipeline. 
    var app = builder.Build();

app.UseAuthentication();   // dựng HttpContext.User trước
app.UseAuthorization();    // rồi mới kiểm tra quyền

app.MapControllers();
app.Run();
  4. Sinh access token bằng JsonWebTokenHandler (API mới của Microsoft.IdentityModel). 
    public class TokenService(IConfiguration config)
{
    public string CreateAccessToken(User user)
    {
        var jwt = config.GetSection("Jwt");
        var key = new SymmetricSecurityKey(
            Encoding.UTF8.GetBytes(jwt["Key"]!));

        var descriptor = new SecurityTokenDescriptor
        {
            Issuer = jwt["Issuer"],
            Audience = jwt["Audience"],
            Expires = DateTime.UtcNow.AddMinutes(
                int.Parse(jwt["AccessTokenMinutes"]!)),
            Subject = new ClaimsIdentity(new[]
            {
                new Claim(JwtRegisteredClaimNames.Sub, user.Id.ToString()),
                new Claim(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
                new Claim(ClaimTypes.Name, user.UserName),
                new Claim(ClaimTypes.Role, user.Role)
            }),
            SigningCredentials = new SigningCredentials(
                key, SecurityAlgorithms.HmacSha256)
        };

        var handler = new JsonWebTokenHandler();
        return handler.CreateToken(descriptor);
    }

    // Refresh token: chuỗi ngẫu nhiên mạnh, KHÔNG phải JWT
    public string CreateRefreshToken() =>
        Convert.ToBase64String(RandomNumberGenerator.GetBytes(64));
}
  5. Endpoint /auth/login — xác thực credential, trả về access + refresh token. 
    [ApiController]
[Route("auth")]
public class AuthController(
    IUserService users,
    TokenService tokens,
    IRefreshTokenStore store) : ControllerBase
{
    [HttpPost("login")]
    [AllowAnonymous]
    public async Task<IActionResult> Login(
        LoginRequest req, CancellationToken ct)
    {
        var user = await users.ValidateCredentialsAsync(
            req.UserName, req.Password, ct);
        if (user is null)
            return Unauthorized(new { error = "Sai tài khoản hoặc mật khẩu" });

        var access = tokens.CreateAccessToken(user);
        var refresh = tokens.CreateRefreshToken();

        // Lưu refresh token đã HASH vào DB (xem mục 8)
        await store.SaveAsync(user.Id, refresh, ct);

        return Ok(new
        {
            accessToken = access,
            refreshToken = refresh,
            expiresIn = 900   // 15 phút (giây)
        });
    }
}
💡 JsonWebTokenHandler vs JwtSecurityTokenHandler: Microsoft khuyến nghị JsonWebTokenHandler (namespace Microsoft.IdentityModel.JsonWebTokens) cho code mới — nhanh hơn, ít allocation hơn. JwtSecurityTokenHandler (System.IdentityModel.Tokens.Jwt) là API cũ, vẫn dùng được nhưng đang dần bị thay thế.

5. Token Validation — kiểm tra gì?

Mỗi request có Authorization: Bearer <token>, middleware JwtBearer tự động validate dựa trên TokenValidationParameters. Validate ĐẦY ĐỦ là tuyến phòng thủ then chốt.

Tham sốKiểm traVì sao quan trọng
ValidateIssuerSigningKeyChữ ký hợp lệ với keyChống token giả mạo / tự ký
ValidateIssueriss đúng server phát hànhChống token từ hệ thống khác
ValidateAudienceaud đúng API đíchChống dùng token của service khác
ValidateLifetimeexp/nbf còn hiệu lựcChống token hết hạn
ClockSkewĐộ lệch đồng hồ cho phépMặc định 5 phút; set Zero để exp chính xác
// Validate thủ công (vd khi refresh, đọc token đã hết hạn)
var handler = new JsonWebTokenHandler();
var result = await handler.ValidateTokenAsync(token, new TokenValidationParameters
{
    ValidateIssuer = true,  ValidIssuer = jwt["Issuer"],
    ValidateAudience = true, ValidAudience = jwt["Audience"],
    ValidateLifetime = true,
    ValidateIssuerSigningKey = true,
    IssuerSigningKey = key,
    ClockSkew = TimeSpan.Zero
});

if (!result.IsValid)
    throw new SecurityTokenException("Token không hợp lệ", result.Exception);

ClaimsIdentity identity = result.ClaimsIdentity; // claims đã parse
⚠️ Symmetric key phải đủ mạnh: với HS256, key tối thiểu 256-bit (32 bytes). Key yếu/ngắn dễ bị brute-force để giả token. Lấy key từ dotnet user-secrets (dev) hoặc Azure Key Vault / biến môi trường (prod) — KHÔNG commit vào appsettings.json. Nếu nhiều service chia sẻ key, cân nhắc dùng RSA (asymmetric, RS256): server ký bằng private key, các service validate bằng public key.

6. [Authorize] — Policies & Roles

Sau khi xác thực, dùng [Authorize] để phân quyền. Có hai cách: role-based (đơn giản) và policy-based (linh hoạt, khuyến nghị cho logic phức tạp).

// Đăng ký policies trong Program.cs
builder.Services.AddAuthorization(options =>
{
    // Policy theo role
    options.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));

    // Policy theo claim
    options.AddPolicy("CanPublish", p =>
        p.RequireClaim("permission", "articles:publish"));

    // Policy gộp nhiều điều kiện
    options.AddPolicy("SeniorEditor", p => p
        .RequireRole("Editor")
        .RequireClaim("level", "senior")
        .RequireAuthenticatedUser());
});
// Áp dụng trên controller / action
[Authorize]                              // chỉ cần đã đăng nhập
[Authorize(Roles = "Admin,Manager")]      // role-based
[Authorize(Policy = "AdminOnly")]          // policy-based
[AllowAnonymous]                        // mở public dù controller có [Authorize]
public class ArticlesController : ControllerBase
{
    [HttpPost("publish")]
    [Authorize(Policy = "CanPublish")]
    public IActionResult Publish() => Ok();
}
Tiêu chíRole-basedPolicy-based
Cách dùng[Authorize(Roles="...")][Authorize(Policy="...")]
LogicChỉ kiểm tra roleRole + claim + handler tùy biến
Linh hoạtThấpCao (logic phức tạp, requirement)
Bảo trìRải rác string role khắp nơiTập trung khi khai báo policy
Khuyến nghịApp nhỏ, role cố địnhApp thật, cần mở rộng
💡 Ưu tiên policy-based: role thực chất chỉ là một loại claim. Policy gom logic phân quyền vào một chỗ, dễ test và đổi yêu cầu mà không phải sửa string rải rác. Với logic rất phức tạp (vd resource-based: "chỉ chủ sở hữu mới sửa được bài"), viết IAuthorizationHandler tùy biến.

7. Claims & ClaimsPrincipal

Sau xác thực, danh tính người dùng nằm trong HttpContext.User (kiểu ClaimsPrincipal). Mỗi mẩu thông tin là một Claim (cặp type/value), được nạp từ payload JWT.

// Đọc claims trong controller (User = ClaimsPrincipal)
[Authorize]
[HttpGet("me")]
public IActionResult Me()
{
    // sub được map sang NameIdentifier
    var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value
                 ?? User.FindFirstValue(JwtRegisteredClaimNames.Sub);

    var name  = User.Identity?.Name;            // ClaimTypes.Name
    var isAdmin = User.IsInRole("Admin");        // kiểm tra role
    var perms = User.FindAll("permission")       // nhiều claim cùng type
                    .Select(c => c.Value).ToArray();

    return Ok(new { userId, name, isAdmin, perms });
}
Lưu ý mapping claim: mặc định JwtBearer ánh xạ vài claim chuẩn sang URI dài của ClaimTypes (vd sub → ClaimTypes.NameIdentifier). Nếu muốn giữ tên claim gốc (sub, role...), tắt mapping: JsonWebTokenHandler.DefaultInboundClaimTypeMap.Clear(); hoặc set options.MapInboundClaims = false; trong AddJwtBearer.
⚠️ Claim không phải nguồn chân lý tuyệt đối: claim được "đóng băng" vào token lúc đăng nhập. Nếu bạn thu hồi quyền của user, các token cũ vẫn mang claim cũ cho tới khi hết hạn. Đây là lý do access token phải sống ngắn. Dữ liệu nhạy cảm/biến động nên kiểm tra lại từ DB, đừng tin mù vào claim.

8. Refresh Token Rotation

Rotation là pattern bảo mật: mỗi lần dùng refresh token để lấy access token mới, refresh token cũ bị vô hiệu hoá và phát hành refresh token MỚI. Nếu một refresh token đã dùng lại xuất hiện lần nữa → dấu hiệu bị đánh cắp → thu hồi cả chuỗi (token family).

  1. Lưu refresh token đã HASH trong DB (không lưu plaintext) — kèm UserId, ExpiresAt, IsRevoked, và ReplacedByToken để truy vết chuỗi.
  2. Khi client gọi /auth/refresh: hash token nhận được, tra DB tìm bản ghi khớp còn hiệu lực.
  3. Nếu token đã bị revoke (reuse detection): thu hồi TOÀN BỘ token của user (token family) → buộc đăng nhập lại. Đây là dấu hiệu token bị lộ.
  4. Nếu hợp lệ: đánh dấu token cũ là revoked, sinh access + refresh MỚI, lưu refresh mới (hash), trả về cho client.
[HttpPost("refresh")]
[AllowAnonymous]
public async Task<IActionResult> Refresh(
    RefreshRequest req, CancellationToken ct)
{
    // 1. Hash token để so với DB (so sánh hash, không lưu plaintext)
    var hash = Sha256(req.RefreshToken);
    var stored = await store.FindByHashAsync(hash, ct);

    if (stored is null || stored.ExpiresAt < DateTime.UtcNow)
        return Unauthorized();

    // 2. Reuse detection: token đã bị revoke mà còn dùng lại → bị lộ
    if (stored.IsRevoked)
    {
        await store.RevokeAllForUserAsync(stored.UserId, ct); // thu hồi cả family
        return Unauthorized(new { error = "Token reuse detected" });
    }

    // 3. Rotate: revoke token cũ, phát hành cặp mới
    var user = await users.GetByIdAsync(stored.UserId, ct);
    var newAccess  = tokens.CreateAccessToken(user);
    var newRefresh = tokens.CreateRefreshToken();

    stored.IsRevoked = true;
    stored.ReplacedByToken = Sha256(newRefresh);   // nối chuỗi để truy vết
    await store.SaveAsync(user.Id, newRefresh, ct);
    await store.UpdateAsync(stored, ct);

    return Ok(new { accessToken = newAccess, refreshToken = newRefresh });
}

private static string Sha256(string input) =>
    Convert.ToHexString(
        SHA256.HashData(Encoding.UTF8.GetBytes(input)));
💡 Vì sao hash refresh token trong DB? Giống lưu mật khẩu: nếu DB bị lộ, attacker không có token plaintext để dùng. So sánh bằng hash khi xác thực. Với refresh token (entropy cao, ngẫu nhiên 64 bytes), SHA-256 là đủ — không cần bcrypt như mật khẩu người dùng.

9. Cạm bẫy bảo mật (Do / Don't)

❌ Lưu JWT trong localStorage

localStorage.setItem("token", accessToken); // 💀 dễ bị XSS đánh cắp

Bất kỳ script độc nào (XSS) đều đọc được localStorage và lấy token. Nguy hiểm hơn nữa với refresh token sống lâu.

✅ Refresh token trong HttpOnly Secure cookie

Response.Cookies.Append("refreshToken", refresh, new CookieOptions
{
    HttpOnly = true,   // JS không đọc được → chống XSS
    Secure   = true,   // chỉ gửi qua HTTPS
    SameSite = SameSiteMode.Strict // chống CSRF
});

Giữ access token ngắn hạn trong memory (biến JS), refresh token trong HttpOnly cookie. JS không chạm được cookie → an toàn trước XSS.

❌ Signing key yếu / hardcode

var key = "secret123"; // quá ngắn, lại còn commit vào git

Key yếu bị brute-force để giả token. Key trong source code = lộ ngay. Dùng key ngẫu nhiên ≥ 32 bytes, lấy từ Key Vault / User Secrets / env var.

❌ Tắt bớt validation cho "nhanh"

ValidateIssuer = false;
ValidateAudience = false;
ValidateLifetime = false; // 💀 token hết hạn vẫn xài được

Mỗi cờ tắt là một lỗ hổng. Luôn validate đầy đủ: issuer, audience, lifetime, signing key.

❌ Để secret/PII trong claim

new Claim("password", user.Password); // 💀 ai cũng decode đọc được

Payload chỉ encode chứ không mã hoá. Đừng để mật khẩu, số CMND/thẻ, secret nội bộ vào claim. Chỉ để ID & metadata cần cho authz.

✅ Buộc HTTPS + access token sống ngắn

app.UseHttpsRedirection();        // token chỉ đi qua kênh mã hoá
// AccessTokenMinutes = 15 → thiệt hại giới hạn nếu lộ

Luôn HTTPS để token không bị nghe lén. Access token ngắn (5–15 phút) giới hạn cửa sổ tấn công; cần phiên dài thì dùng refresh token rotation.

🎯 Checklist Auth & JWT

  • ✅ UseAuthentication() đặt TRƯỚC UseAuthorization() trong pipeline
  • ✅ Validate đầy đủ: Issuer, Audience, Lifetime, IssuerSigningKey; cân nhắc ClockSkew = Zero
  • ✅ Signing key ≥ 32 bytes, lấy từ User Secrets / Key Vault / env — KHÔNG hardcode
  • ✅ Access token sống ngắn (5–15 phút), refresh token sống dài & thu hồi được
  • ✅ Refresh token lưu DẠNG HASH trong DB, áp dụng rotation + reuse detection
  • ✅ KHÔNG để mật khẩu / PII / secret trong claim (payload chỉ encode, không mã hoá)
  • ✅ Refresh token trong HttpOnly + Secure + SameSite cookie; access token giữ trong memory
  • ✅ Bật UseHttpsRedirection() — token chỉ truyền qua HTTPS
  • ✅ Ưu tiên policy-based authorization cho logic phức tạp; dùng IsInRole/FindFirst để đọc claim
  • ✅ Dùng JsonWebTokenHandler (Microsoft.IdentityModel.JsonWebTokens) cho code mới
