Làm chủ EF Core nền tảng

Entity Framework Core là ORM chính thức của .NET. Bài học đi từ khái niệm ORM, cấu hình DbContext, mapping entity, migrations, quan hệ (1-1, 1-n, n-n), loading dữ liệu liên quan, query LINQ → SQL, change tracking, cho tới vấn đề kinh điển N+1. Cập nhật EF Core 8/9 trên .NET 8/9 (2026).

1. EF Core là gì? Khái niệm ORM

EF Core (Entity Framework Core) là một ORM (Object-Relational Mapper) — lớp trung gian ánh xạ giữa class C# và bảng trong database. Bạn làm việc với object, EF Core dịch ra SQL.

🧠 ORM giải quyết gì?

  • Không phải viết SQL chuỗi tay → giảm lỗi typo, SQL injection
  • Class C# ↔ bảng, property ↔ cột tự động
  • Query bằng LINQ, EF Core dịch sang SQL của provider
  • Theo dõi thay đổi (change tracking) và sinh INSERT/UPDATE/DELETE
  • Quản lý schema qua migrations

⚙️ Mô hình hoạt động

  • Entity — class POCO ánh xạ tới 1 bảng
  • DbContext — đại diện 1 phiên làm việc với DB
  • DbSet<T> — đại diện 1 bảng / tập entity
  • Provider — thư viện dịch LINQ sang SQL cụ thể
  • Migration — bản ghi tiến hoá schema

2. DbContext — trái tim của EF Core

DbContext đại diện cho một phiên làm việc với database: nó chứa các DbSet<T> (bảng), cấu hình model, và quản lý change tracking + lưu thay đổi.

// AppDbContext.cs
using Microsoft.EntityFrameworkCore;

public class AppDbContext : DbContext
{
    public AppDbContext(DbContextOptions<AppDbContext> options)
        : base(options) { }

    // Mỗi DbSet đại diện 1 bảng
    public DbSet<Blog> Blogs => Set<Blog>();
    public DbSet<Post> Posts => Set<Post>();
    public DbSet<Author> Authors => Set<Author>();

    // Cấu hình model bằng Fluent API
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Blog>(b =>
        {
            b.HasKey(x => x.Id);
            b.Property(x => x.Title).HasMaxLength(200).IsRequired();
            b.HasIndex(x => x.Url).IsUnique();
        });

        // Áp dụng tất cả config trong assembly (khuyên dùng khi model lớn)
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
    }
}

Đăng ký DbContext qua DI + connection string

Trong ASP.NET Core, đăng ký DbContext trong container DI bằng AddDbContext. Connection string đặt ở appsettings.json.

// appsettings.json
{
  "ConnectionStrings": {
    "Default": "Host=localhost;Database=blogdb;Username=app;Password=secret"
  }
}
// Program.cs (.NET 8/9 minimal hosting)
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(
        builder.Configuration.GetConnectionString("Default")));

// EF Core 8+: có thể dùng AddDbContextPool để tái sử dụng instance (perf)
builder.Services.AddDbContextPool<AppDbContext>(o =>
    o.UseNpgsql(builder.Configuration.GetConnectionString("Default")));

var app = builder.Build();
⚠️ Lifetime của DbContext: AddDbContext đăng ký lifetime Scoped (1 instance / 1 request HTTP). KHÔNG bao giờ dùng DbContext như Singleton hay chia sẻ giữa nhiều thread — nó không thread-safe. Mỗi đơn vị công việc nên có context riêng và sống ngắn. 
// Inject DbContext vào service / controller
public class BlogService
{
    private readonly AppDbContext _db;
    public BlogService(AppDbContext db) => _db = db;

    public Task<List<Blog>> GetAllAsync() =>
        _db.Blogs.ToListAsync();
}

3. Entities — Conventions, Annotations & Fluent API

Entity là class POCO (Plain Old CLR Object). EF Core ánh xạ chúng theo 3 lớp ưu tiên: convention (quy ước mặc định) → data annotations (attribute) → Fluent API (mạnh nhất, ghi đè tất cả).

🪄 Conventions — EF Core tự suy ra

  • Property tên Id hoặc <Tên>Id → khoá chính (primary key)
  • Property kiểu reference tới entity khác + <Tên>Id → khoá ngoại (foreign key)
  • Tên class → tên bảng (số nhiều qua DbSet); tên property → tên cột
  • Kiểu C# → kiểu cột tương ứng (int→int, string→nvarchar, DateTime→timestamp...)
  • string? → cột nullable; string (non-nullable) → cột NOT NULL (nếu bật nullable reference types)
// Entity dựa hoàn toàn vào convention
public class Blog
{
    public int Id { get; set; }            // PK theo convention
    public string Title { get; set; } = "";  // NOT NULL
    public string? Url { get; set; }         // nullable
    public DateTime CreatedAt { get; set; }

    // Navigation property — quan hệ 1-n
    public List<Post> Posts { get; set; } = [];
}

Data Annotations vs Fluent API

Cùng một cấu hình, hai cách viết. Annotations ngắn gọn cho rule đơn giản; Fluent API mạnh hơn, tách config ra khỏi entity.

Mục đíchData AnnotationFluent API

Độ dài tối đa[MaxLength(200)].Property(x => x.Title).HasMaxLength(200)

Tên bảng[Table("blogs")].ToTable("blogs")

// Cách A — Data Annotations (gắn trực tiếp trên entity)
using System.ComponentModel.DataAnnotations;
using System.ComponentModel.DataAnnotations.Schema;

[Table("posts")]
public class Post
{
    [Key]
    public int Id { get; set; }

    [Required, MaxLength(300)]
    public string Title { get; set; } = "";

    [Column("body", TypeName = "text")]
    public string? Content { get; set; }

    [NotMapped]
    public int WordCount => Content?.Split(' ').Length ?? 0;
}
// Cách B — Fluent API trong IEntityTypeConfiguration (khuyên cho dự án lớn)
public class PostConfig : IEntityTypeConfiguration<Post>
{
    public void Configure(EntityTypeBuilder<Post> b)
    {
        b.ToTable("posts");
        b.HasKey(x => x.Id);
        b.Property(x => x.Title).HasMaxLength(300).IsRequired();
        b.Property(x => x.Content).HasColumnName("body").HasColumnType("text");
        b.Ignore(x => x.WordCount);
        b.HasIndex(x => x.Title);
    }
}
// Được nạp tự động bởi ApplyConfigurationsFromAssembly(...) trong OnModelCreating
💡 Khoá chính (Primary Key): Convention nhận diện Id / <Type>Id. Muốn khoá kép (composite) thì BẮT BUỘC dùng Fluent API: b.HasKey(x => new { x.OrderId, x.ProductId }). EF Core mặc định sinh khoá int identity (auto-increment); muốn GUID dùng b.Property(x => x.Id).HasDefaultValueSql("gen_random_uuid()").

4. Migrations — quản lý tiến hoá schema

Migration là cơ chế version-control cho database schema. Mỗi lần model thay đổi, bạn tạo một migration ghi lại diff, rồi áp lên database.

  1. Tạo migration đầu tiên — EF Core so sánh model hiện tại với migration trước đó (lần đầu là rỗng) và sinh code. 
    # Tên migration nên mô tả ý nghĩa thay đổi
dotnet ef migrations add InitialCreate

# Nếu DbContext nằm ở project khác project khởi động:
dotnet ef migrations add InitialCreate \
    --project src/MyApp.Infrastructure \
    --startup-project src/MyApp.Api
  2. Áp migration lên database — tạo bảng / sửa cột thật sự. 
    dotnet ef database update            # áp tới migration mới nhất
dotnet ef database update InitialCreate  # áp tới 1 migration cụ thể
  3. Thêm thay đổi tiếp theo — sửa entity (vd thêm cột Slug), rồi tạo migration mới. 
    # Sau khi sửa entity Post thêm property Slug
dotnet ef migrations add AddPostSlug
dotnet ef database update
  4. Hoàn tác (revert) — quay về một migration trước đó, EF chạy phần Down(). 
    # Quay DB về trạng thái sau InitialCreate (undo AddPostSlug)
dotnet ef database update InitialCreate

# Gỡ migration cuối CHƯA áp (xoá file)
dotnet ef migrations remove

# Sinh script SQL để DBA review / chạy trên prod
dotnet ef migrations script --idempotent -o migrate.sql

Một file migration chứa gì?

// Migrations/20260615_AddPostSlug.cs
public partial class AddPostSlug : Migration
{
    // Up: áp dụng thay đổi (forward)
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AddColumn<string>(
            name: "Slug",
            table: "posts",
            type: "character varying(150)",
            maxLength: 150,
            nullable: true);
    }

    // Down: hoàn tác (rollback)
    protected override void Down(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.DropColumn(name: "Slug", table: "posts");
    }
}
Thành phầnVai trò

Bảng __EFMigrationsHistoryEF tạo trong DB để ghi migration nào đã áp
⚠️ Đừng sửa migration đã chạy trên prod. Migration là bất biến sau khi đã apply. Cần đổi thì tạo migration MỚI. Trên production nên dùng migrations script --idempotent (an toàn chạy lại nhiều lần) hoặc CI/CD apply tự động — tránh gọi EnsureCreated() (nó bỏ qua hệ thống migration hoàn toàn).
EnsureCreated vs Migrate: Database.EnsureCreated() tạo schema một phát từ model, KHÔNG dùng migration — chỉ hợp cho test/prototype. Database.Migrate() áp các migration còn thiếu — dùng cho app thật.

5. Relationships — quan hệ giữa các bảng

EF Core dựng quan hệ qua navigation property + foreign key. Có 3 dạng chính: 1-1, 1-n, n-n.

📐 One-to-Many (1-n) — phổ biến nhất

Schema: Blog (1) ⟶ nhiều Post. Bảng posts có cột FK BlogId trỏ về blogs.Id.

public class Blog
{
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public List<Post> Posts { get; set; } = [];   // nav: nhiều con
}

public class Post
{
    public int Id { get; set; }
    public string Title { get; set; } = "";
    public int BlogId { get; set; }        // FK theo convention
    public Blog Blog { get; set; } = null!;  // nav: cha
}
// Fluent API (tường minh, ghi đè convention)
modelBuilder.Entity<Post>()
    .HasOne(p => p.Blog)
    .WithMany(b => b.Posts)
    .HasForeignKey(p => p.BlogId)
    .OnDelete(DeleteBehavior.Cascade);   // xoá blog → xoá post con

📐 One-to-One (1-1)

Schema: mỗi Author có đúng 1 AuthorProfile. Bảng author_profiles giữ FK AuthorId đồng thời là khoá chính của nó.

public class Author
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public AuthorProfile? Profile { get; set; }
}

public class AuthorProfile
{
    public int Id { get; set; }
    public string Bio { get; set; } = "";
    public int AuthorId { get; set; }      // FK
    public Author Author { get; set; } = null!;
}
modelBuilder.Entity<Author>()
    .HasOne(a => a.Profile)
    .WithOne(p => p.Author)
    .HasForeignKey<AuthorProfile>(p => p.AuthorId);  // chỉ rõ bên giữ FK

📐 Many-to-Many (n-n) — skip navigation (EF Core 5+)

Schema: 1 Post có nhiều Tag, 1 Tag gắn nhiều Post. Từ EF Core 5, bạn KHÔNG cần khai báo entity join — EF tự tạo bảng nối PostTag ngầm.

public class Post
{
    public int Id { get; set; }
    public List<Tag> Tags { get; set; } = [];   // skip navigation
}

public class Tag
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Post> Posts { get; set; } = [];
}
// Convention tự xử lý. Muốn tuỳ biến bảng nối:
modelBuilder.Entity<Post>()
    .HasMany(p => p.Tags)
    .WithMany(t => t.Posts)
    .UsingEntity<PostTag>(
        j => j.HasOne<Tag>().WithMany().HasForeignKey("TagId"),
        j => j.HasOne<Post>().WithMany().HasForeignKey("PostId"),
        j =>
        {
            j.ToTable("post_tags");
            j.Property<DateTime>("AddedAt").HasDefaultValueSql("now()");
        });
Quan hệNav phía 1Nav phía 2FK nằm ở
1-11 reference1 reference1 bảng (bên phụ thuộc)
1-ncollection1 referencebảng "nhiều"
n-ncollectioncollectionbảng nối (ngầm hoặc tường minh)
💡 OnDelete behavior: Cascade (xoá cha → xoá con), Restrict (chặn xoá nếu còn con), SetNull (set FK = null). Chọn đúng để tránh xoá nhầm dữ liệu hoặc lỗi ràng buộc khoá ngoại.

6. Loading Related Data — nạp dữ liệu liên quan

Khi query Blog, navigation Posts KHÔNG tự động được nạp. EF Core có 3 chiến lược nạp dữ liệu liên quan.

① Eager Loading — Include / ThenInclude

Nạp dữ liệu liên quan ngay trong query gốc bằng JOIN. Rõ ràng, dễ kiểm soát.

var blogs = await _db.Blogs
    .Include(b => b.Posts)                  // nạp các Post
        .ThenInclude(p => p.Comments)       // rồi nạp Comment của mỗi Post
    .Include(b => b.Owner)                  // nạp thêm 1 nhánh khác
    .ToListAsync();

// Filtered Include (EF Core 5+): lọc/sắp xếp collection được nạp
var blog = await _db.Blogs
    .Include(b => b.Posts.Where(p => p.IsPublished)
                        .OrderByDescending(p => p.CreatedAt))
    .FirstOrDefaultAsync(b => b.Id == 1);

② Explicit Loading — .Entry().Collection().Load()

Nạp dữ liệu liên quan SAU, khi đã có entity, bằng lệnh tường minh. Hữu ích khi không phải lúc nào cũng cần dữ liệu con.

var blog = await _db.Blogs.FirstAsync(b => b.Id == 1);

// Nạp collection sau
await _db.Entry(blog)
    .Collection(b => b.Posts)
    .LoadAsync();

// Nạp 1 reference sau
await _db.Entry(blog)
    .Reference(b => b.Owner)
    .LoadAsync();

// Có thể truy vấn thêm trên collection thay vì load hết
var publishedCount = await _db.Entry(blog)
    .Collection(b => b.Posts)
    .Query()
    .CountAsync(p => p.IsPublished);

③ Lazy Loading — proxies + virtual

Tự động nạp khi truy cập navigation lần đầu. Tiện nhưng RẤT dễ gây N+1 (xem mục 9). Phải cài package proxies + đánh dấu navigation là virtual.

# Cài package
dotnet add package Microsoft.EntityFrameworkCore.Proxies
// Bật proxies khi cấu hình
builder.Services.AddDbContext<AppDbContext>(o => o
    .UseLazyLoadingProxies()
    .UseNpgsql(connectionString));

// Navigation PHẢI là virtual để EF tạo proxy override
public class Blog
{
    public int Id { get; set; }
    public virtual List<Post> Posts { get; set; } = [];
}

// Truy cập blog.Posts lần đầu → EF tự bắn thêm 1 query
foreach (var p in blog.Posts) { ... }  // query ngầm xảy ra ở đây!
Chiến lượcKhi nạpSố queryDùng khi
Eager (Include)Cùng query gốc (JOIN)1 (hoặc vài với SplitQuery)Biết chắc cần dữ liệu con
Explicit (.Load())Gọi tay sau đó1 thêm / lần LoadĐôi khi mới cần dữ liệu con
Lazy (proxies)Tự động khi truy cập nav1 thêm / mỗi lần chạm (⚠️ N+1)Prototype — tránh ở prod
🚫 Cẩn thận Lazy Loading: tiện lợi nhưng âm thầm sinh hàng loạt query trong vòng lặp. Phần lớn team production TẮT lazy loading và dùng Eager (Include) hoặc projection để kiểm soát số query.

7. Querying — LINQ dịch sang SQL

Bạn viết LINQ trên DbSet; EF Core dịch sang SQL của provider và thực thi trên server (không kéo cả bảng về RAM). Query chỉ chạy khi được "materialize" (ToListAsync, FirstOrDefaultAsync, ...).

// Where + OrderBy + paging → dịch thành WHERE / ORDER BY / LIMIT OFFSET
var posts = await _db.Posts
    .Where(p => p.IsPublished && p.BlogId == 1)
    .OrderByDescending(p => p.CreatedAt)
    .Skip(20).Take(10)
    .ToListAsync();

// FirstOrDefault — lấy 1 hoặc null
var post = await _db.Posts
    .FirstOrDefaultAsync(p => p.Id == 42);

// SingleOrDefault — kỳ vọng 0 hoặc 1, ném lỗi nếu >1
var bySlug = await _db.Posts.SingleOrDefaultAsync(p => p.Slug == "hello");

// Aggregate dịch thẳng xuống SQL — không kéo dữ liệu về
int count = await _db.Posts.CountAsync(p => p.IsPublished);
bool any  = await _db.Posts.AnyAsync(p => p.BlogId == 1);

Projection — chỉ lấy cột cần (Select)

Dùng Select tạo DTO → SQL chỉ SELECT các cột cần, không nạp toàn entity, không cần tracking. Rất hiệu quả cho màn hình đọc.

var summaries = await _db.Posts
    .Where(p => p.IsPublished)
    .Select(p => new PostSummaryDto
    {
        Id = p.Id,
        Title = p.Title,
        BlogTitle = p.Blog.Title,          // JOIN tự động, không cần Include
        CommentCount = p.Comments.Count()   // dịch thành sub-query COUNT
    })
    .ToListAsync();

AsNoTracking — query chỉ đọc

// Read-only → tắt change tracking → nhanh hơn, ít RAM hơn
var posts = await _db.Posts
    .AsNoTracking()
    .Where(p => p.IsPublished)
    .ToListAsync();

// Bật mặc định no-tracking cho cả context (nếu phần lớn là đọc)
_db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking;
💡 AsNoTracking() cho mọi query chỉ đọc. Khi không cần update entity, no-tracking bỏ qua việc tạo snapshot theo dõi → giảm bộ nhớ và CPU đáng kể trên list lớn. Còn với Select ra DTO thì EF không tracking sẵn rồi.
⚠️ Client vs Server evaluation: EF Core cố dịch toàn bộ LINQ xuống SQL. Nếu dùng method C# mà SQL không hiểu (vd hàm tự viết) trong Where, EF Core 3+ sẽ NÉM lỗi thay vì âm thầm kéo dữ liệu về lọc ở client. Hãy đẩy logic lọc xuống dạng SQL-dịch-được, hoặc .AsEnumerable() tường minh trước khi xử lý ở client.

8. Change Tracking & SaveChanges

Khi query entity (có tracking), EF Core giữ một snapshot. Khi bạn sửa property, EF so sánh với snapshot để biết cần UPDATE cột nào. SaveChanges gom tất cả thay đổi thành lệnh SQL trong 1 transaction.

EntityStateÝ nghĩaSaveChanges sinh
AddedMới Add(), chưa có trong DBINSERT
ModifiedĐang tracked và có property đổiUPDATE (chỉ cột đổi)
DeletedĐã gọi Remove()DELETE
UnchangedTracked nhưng không đổi gì(không sinh lệnh)
DetachedKhông được context theo dõi(không sinh lệnh)
// INSERT
var blog = new Blog { Title = "EF Core" };
_db.Blogs.Add(blog);                 // state = Added

// UPDATE — chỉ cần sửa property trên entity đã tracked
var post = await _db.Posts.FirstAsync(p => p.Id == 1);
post.Title = "Tiêu đề mới";       // state tự thành Modified

// DELETE
var old = await _db.Posts.FindAsync(99);
_db.Posts.Remove(old);               // state = Deleted

// Tất cả gom trong 1 transaction
await _db.SaveChangesAsync();

// Kiểm tra state tường minh
var state = _db.Entry(post).State;  // EntityState.Modified
SaveChanges là atomic: EF Core gói toàn bộ INSERT/UPDATE/DELETE của một lần SaveChanges vào MỘT transaction. Nếu một lệnh fail → rollback tất cả. EF Core còn batch nhiều lệnh thành ít round-trip để tối ưu hiệu năng.
⚠️ Khi tracking gây hại perf: query trả về hàng chục nghìn entity chỉ để hiển thị (đọc) mà vẫn tracking → tốn RAM tạo snapshot + chậm. Dùng AsNoTracking() hoặc projection. Ngoài ra giữ DbContext sống quá lâu khiến change tracker phình to → memory leak; hãy giữ context sống ngắn (scoped per request).

9. Vấn đề N+1 — bug hiệu năng kinh điển

N+1 xảy ra khi bạn chạy 1 query lấy danh sách, rồi trong vòng lặp lại bắn THÊM 1 query cho mỗi phần tử để nạp dữ liệu con. 1 + N query thay vì 1.

❌ SAI — lazy/explicit load trong vòng lặp

Lấy 100 blog (1 query) rồi với mỗi blog lại truy cập blog.Posts (lazy) → 100 query con. Tổng 101 query, kéo theo nghẽn DB.

var blogs = await _db.Blogs.ToListAsync();   // 1 query lấy 100 blog

foreach (var blog in blogs)
{
    // MỖI lần chạm blog.Posts (lazy) bắn 1 query → +100 query!
    Console.WriteLine($"{blog.Title}: {blog.Posts.Count} bài");
}
// Tổng cộng: 1 + 100 = 101 query (N+1)

✅ ĐÚNG — Eager Include hoặc projection (1 query)

Gộp dữ liệu con vào query gốc bằng Include, hoặc tốt hơn là Select ra đúng dữ liệu cần (DTO + COUNT dịch thẳng sang SQL).

// Cách 1: Eager loading — 1 query có JOIN
var blogs = await _db.Blogs
    .Include(b => b.Posts)
    .ToListAsync();

// Cách 2 (tốt nhất cho màn hình đọc): projection — chỉ lấy số đếm
var data = await _db.Blogs
    .Select(b => new { b.Title, PostCount = b.Posts.Count() })
    .ToListAsync();   // 1 query, COUNT chạy trên SQL server

AsSplitQuery — tránh "cartesian explosion"

Khi Include nhiều collection cùng lúc, JOIN sinh tích Descartes → dữ liệu trùng lặp phình to. AsSplitQuery tách thành nhiều query nhỏ thay vì 1 JOIN khổng lồ.

var blogs = await _db.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Contributors)
    .AsSplitQuery()        // nhiều query nhỏ thay vì 1 JOIN bùng nổ
    .AsNoTracking()        // đọc thuần → bỏ tracking
    .ToListAsync();
💡 Phát hiện N+1: bật logging EF Core (.LogTo(Console.WriteLine, LogLevel.Information)) hoặc .EnableSensitiveDataLogging() ở môi trường dev để thấy SQL thực tế. Nếu một màn hình bắn hàng chục query giống nhau → gần như chắc chắn là N+1. Fix bằng Include / projection; với nhiều collection thêm AsSplitQuery; query đọc luôn kèm AsNoTracking.

10. Một số tính năng đáng dùng (EF Core 8/9)

⚡ Bulk update / delete (EF Core 7+)

Update/Delete hàng loạt thẳng trên SQL, không cần load entity về tracking.

// 1 lệnh UPDATE, không kéo entity về
await _db.Posts
    .Where(p => p.CreatedAt < cutoff)
    .ExecuteUpdateAsync(s => s
        .SetProperty(p => p.IsArchived, true));

await _db.Posts
    .Where(p => p.IsSpam)
    .ExecuteDeleteAsync();

🧱 Complex types & raw SQL

EF Core 8 thêm ComplexProperty; raw SQL khi LINQ không đủ.

// Raw SQL an toàn (tham số hoá)
var posts = await _db.Posts
    .FromSql($"SELECT * FROM posts WHERE title = {term}")
    .ToListAsync();

// SQL không trả entity
await _db.Database.ExecuteSqlAsync(
    $"REFRESH MATERIALIZED VIEW post_stats");
Transaction tường minh: mặc định mỗi SaveChanges đã là 1 transaction. Cần gói nhiều SaveChanges hoặc nhiều thao tác lại với nhau → dùng await using var tx = await _db.Database.BeginTransactionAsync(); rồi await tx.CommitAsync();.

🎯 Checklist EF Core nền tảng

  • ✅ Cài đúng provider (SqlServer / Npgsql / Sqlite) khớp database
  • ✅ DbContext đăng ký Scoped qua AddDbContext, connection string ở appsettings.json
  • ✅ KHÔNG chia sẻ DbContext giữa thread; giữ context sống ngắn
  • ✅ Entity có khoá chính rõ ràng (convention hoặc HasKey)
  • ✅ Cấu hình phức tạp dùng Fluent API trong IEntityTypeConfiguration
  • ✅ Quản lý schema bằng migrations (migrations add + database update), không sửa migration đã apply
  • ✅ Prod dùng migrations script --idempotent hoặc Database.Migrate(), không EnsureCreated()
  • ✅ Định nghĩa quan hệ 1-1 / 1-n / n-n + chọn đúng OnDelete
  • ✅ Nạp dữ liệu liên quan có chủ đích — ưu tiên Include / projection, tránh Lazy ở prod
  • ✅ Query chỉ đọc luôn thêm AsNoTracking()
  • ✅ Dùng Select ra DTO để lấy đúng cột cần thay vì cả entity
  • ✅ Tránh N+1 — không lazy/explicit load trong vòng lặp; thêm AsSplitQuery khi Include nhiều collection
  • ✅ Bật EF Core logging ở dev để soi SQL thực tế và phát hiện query thừa
