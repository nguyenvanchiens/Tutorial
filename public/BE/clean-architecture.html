Clean / Onion Architecture

Hiểu sâu kiến trúc Clean/Onion trong .NET 8/9: vì sao kiến trúc tầng truyền thống thất bại, The Dependency Rule (dependency luôn hướng vào trong), bốn layer Domain / Application / Infrastructure / API, Ports & Adapters (Hexagonal), Dependency Inversion, mapping DTO ở boundary, và quan trọng nhất — khi nào đừng dùng nó vì over-engineer.

1. Vấn đề của kiến trúc tầng truyền thống

Kiến trúc N-tier kinh điển (Presentation → Business → Data Access) xếp các tầng chồng lên nhau, mỗi tầng phụ thuộc tầng dưới. Vấn đề: business logic phụ thuộc vào data access, mà data access lại phụ thuộc database/EF Core. Khi đổi DB, đổi ORM hay muốn unit test, logic nghiệp vụ bị kéo theo cả thế giới hạ tầng.

🚫 N-tier truyền thống

Dependency hướng xuống dưới: Business → Data Access → Database. Core nghiệp vụ "biết" về EF Core, connection string, SQL. Muốn test logic phải dựng cả database. Đổi ORM = sửa khắp nơi.

✅ Clean / Onion

Đảo ngược: dependency hướng vào trong, về phía Domain. Hạ tầng (DB, HTTP, file) nằm ở vòng ngoài và phụ thuộc vào core, không phải ngược lại. Core thuần nghiệp vụ, test được không cần DB.

Clean Architecture (Robert C. Martin) và Onion Architecture (Jeffrey Palermo) cùng một ý tưởng cốt lõi: vẽ hệ thống thành các vòng tròn đồng tâm. Càng vào trong càng trừu tượng và ổn định (business rules), càng ra ngoài càng cụ thể và dễ thay đổi (UI, DB, framework). Quy tắc duy nhất: dependency chỉ được hướng vào trong.

         ┌─────────────────────────────────────────┐
         │  API / Presentation  (controllers, DI)    │
         │   ┌───────────────────────────────────┐   │
         │   │  Infrastructure (EF Core, SMTP…)  │   │
         │   │   ┌───────────────────────────┐   │   │
         │   │   │  Application (use cases)  │   │   │
         │   │   │   ┌───────────────────┐   │   │   │
         │   │   │   │  Domain (entity)  │   │   │   │  ← trung tâm
         │   │   │   └───────────────────┘   │   │   │
         │   │   └───────────────────────────┘   │   │
         │   └───────────────────────────────────┘   │
         └─────────────────────────────────────────┘
                  ▲ dependency luôn hướng VÀO TRONG ▲
Cùng một triết lý: Clean, Onion và Hexagonal (Ports & Adapters) khác tên gọi nhưng chung một nguyên tắc — tách business logic khỏi chi tiết kỹ thuật bằng cách đảo ngược chiều phụ thuộc. Dưới đây ta dùng cách phân layer phổ biến nhất trong cộng đồng .NET.

2. The Dependency Rule

Luật quan trọng nhất, chi phối toàn bộ kiến trúc: "Source code dependencies chỉ được hướng vào trong." Vòng trong không bao giờ biết gì về vòng ngoài.

Hướng vào trong

API biết Infrastructure + Application + Domain. Infrastructure biết Application + Domain. Application biết Domain. Domain không biết gì.

Vòng trong "mù"

Domain không tham chiếu EF Core, ASP.NET, JSON, HttpClient. Nó không biết dữ liệu được lưu ở đâu hay UI là gì.

Vượt biên qua interface

Khi vòng trong cần "gọi ra ngoài" (gửi email, lưu DB), nó định nghĩa interface; vòng ngoài hiện thực interface đó.

💡 Mẹo kiểm tra nhanh: nhìn vào using trên đầu file Domain. Nếu thấy using Microsoft.EntityFrameworkCore; hay using Microsoft.AspNetCore...; → bạn đã vi phạm Dependency Rule. Domain chỉ được dùng BCL thuần (System.*) và types của chính nó.

Hệ quả thực tế: bạn có thể đổi SQL Server sang PostgreSQL, đổi REST sang gRPC, đổi EF Core sang Dapper — mà không phải đụng một dòng nào trong Domain và Application. Đó chính là giá trị của việc đảo ngược phụ thuộc.

3. Bốn layer giải thích kỹ

🟣 Domain — trái tim hệ thống

Chứa Entities, Value Objects, Domain Events, business rules / invariants, và exception nghiệp vụ. KHÔNG có dependency ngoài nào — không EF Core, không attribute của framework. Đây là kiến thức nghiệp vụ thuần.

// Domain/Entities/Order.cs — không tham chiếu hạ tầng nào
namespace Shop.Domain.Entities;

public sealed class Order
{
    private readonly List<OrderLine> _lines = new();

    public Guid Id { get; private set; }
    public Money Total { get; private set; } = Money.Zero;
    public IReadOnlyList<OrderLine> Lines => _lines.AsReadOnly();
    public OrderStatus Status { get; private set; }

    private Order() { } // cho ORM materialize

    public static Order Create(Guid customerId)
        => new() { Id = Guid.NewGuid(), Status = OrderStatus.Draft };

    public void AddLine(Product product, int qty)
    {
        if (Status != OrderStatus.Draft)            // invariant nghiệp vụ
            throw new DomainException("Đơn đã chốt, không thể thêm dòng.");
        if (qty <= 0)
            throw new DomainException("Số lượng phải > 0.");

        _lines.Add(new OrderLine(product.Id, product.Price, qty));
        Total = _lines.Aggregate(Money.Zero, (acc, l) => acc + l.LineTotal);
    }
}
// Value Object: bất biến, so sánh theo giá trị (record rất hợp)
public readonly record struct Money(decimal Amount, string Currency = "VND")
{
    public static Money Zero => new(0);
    public static Money operator +(Money a, Money b)
    {
        if (a.Currency != b.Currency)
            throw new DomainException("Không cộng được hai loại tiền khác nhau.");
        return a with { Amount = a.Amount + b.Amount };
    }
}

🔵 Application — use cases

Điều phối nghiệp vụ: use cases (thường dạng CQRS Command/Query + handler), DTOs, và quan trọng nhất là các interface (ports) như IOrderRepository, IEmailSender, IUnitOfWork. Application khai báo những gì nó cần ở vòng ngoài, chứ không tự hiện thực. Chỉ tham chiếu Domain.

// Application/Orders/Commands/PlaceOrderCommand.cs
public record PlaceOrderCommand(Guid CustomerId, List<OrderItemDto> Items)
    : IRequest<OrderResultDto>;   // dùng MediatR (tuỳ chọn)

// Handler điều phối use case — phụ thuộc INTERFACE, không phải EF Core
public sealed class PlaceOrderHandler
    : IRequestHandler<PlaceOrderCommand, OrderResultDto>
{
    private readonly IOrderRepository _orders;
    private readonly IProductRepository _products;
    private readonly IUnitOfWork _uow;
    private readonly IEmailSender _email;

    public PlaceOrderHandler(IOrderRepository orders, IProductRepository products,
        IUnitOfWork uow, IEmailSender email)
        => (_orders, _products, _uow, _email) = (orders, products, uow, email);

    public async Task<OrderResultDto> Handle(
        PlaceOrderCommand cmd, CancellationToken ct)
    {
        var order = Order.Create(cmd.CustomerId);
        foreach (var item in cmd.Items)
        {
            var product = await _products.GetByIdAsync(item.ProductId, ct)
                ?? throw new NotFoundException("Sản phẩm không tồn tại.");
            order.AddLine(product, item.Quantity);   // rule nằm trong Domain
        }

        await _orders.AddAsync(order, ct);
        await _uow.SaveChangesAsync(ct);                // commit transaction
        await _email.SendOrderConfirmationAsync(order.Id, ct);

        return new OrderResultDto(order.Id, order.Total.Amount);
    }
}

🟢 Infrastructure — chi tiết kỹ thuật

Nơi "bẩn": EF Core DbContext, hiện thực repository, gọi service ngoài (SMTP, payment gateway, blob storage), cache, message bus. Infrastructure hiện thực các interface mà Application/Domain đã khai báo. Tham chiếu Application + Domain.

// Infrastructure/Persistence/OrderRepository.cs — adapter cụ thể
using Microsoft.EntityFrameworkCore;   // EF Core CHỈ xuất hiện ở đây

public sealed class OrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public OrderRepository(AppDbContext db) => _db = db;

    public async Task<Order?> GetByIdAsync(Guid id, CancellationToken ct)
        => await _db.Orders
            .Include(o => o.Lines)
            .FirstOrDefaultAsync(o => o.Id == id, ct);

    public async Task AddAsync(Order order, CancellationToken ct)
        => await _db.Orders.AddAsync(order, ct);
}

// EF Core config tách rời Domain — entity Domain KHÔNG có attribute EF
public sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> b)
    {
        b.HasKey(o => o.Id);
        b.OwnsMany(o => o.Lines, l => l.WithOwner());
        b.OwnsOne(o => o.Total);   // map Value Object Money
    }
}

🟠 API / Presentation — composition root

Điểm vào: controllers hoặc Minimal API, model binding, mapping request → command, và composition root — nơi DI container ráp interface với implementation. API tham chiếu tất cả để đăng ký DI, nhưng code nghiệp vụ thì gọi qua abstraction.

// Api/Program.cs — composition root, ráp port với adapter
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseNpgsql(builder.Configuration.GetConnectionString("Default")));

// Đăng ký: interface (Application)  →  implementation (Infrastructure)
builder.Services.AddScoped<IOrderRepository, OrderRepository>();
builder.Services.AddScoped<IProductRepository, ProductRepository>();
builder.Services.AddScoped<IUnitOfWork, EfUnitOfWork>();
builder.Services.AddScoped<IEmailSender, SmtpEmailSender>();
builder.Services.AddMediatR(c =>
    c.RegisterServicesFromAssembly(typeof(PlaceOrderHandler).Assembly));

var app = builder.Build();

// Minimal API endpoint — chỉ điều hướng, không chứa logic
app.MapPost("/orders", async (PlaceOrderRequest req, ISender sender, CancellationToken ct) =>
{
    var result = await sender.Send(req.ToCommand(), ct);
    return Results.Created($"/orders/{result.Id}", result);
});

app.Run();

Mỗi layer là một project riêng trong solution. Quy tắc tham chiếu (project reference) thực thi Dependency Rule ở mức compiler — bạn không thể vô tình để Domain dùng EF Core nếu Domain không reference nó.

⚠️ Cẩn thận với reference "tiện tay": Lý tưởng nhất là API chỉ ref Application, còn Infrastructure được nạp qua một extension method AddInfrastructure() để API không cần biết chi tiết. Nhưng thực tế, vì composition root nằm ở API nên API thường phải ref Infrastructure để đăng ký DI. Điều cấm tuyệt đối là chiều ngược: Infrastructure hay Application không bao giờ ref API.

5. Ports & Adapters (Hexagonal)

Đây là cơ chế kỹ thuật làm cho Dependency Rule khả thi: Dependency Inversion Principle. Port là interface định nghĩa ở vòng trong (Application/Domain). Adapter là implementation cụ thể ở vòng ngoài (Infrastructure). Vòng trong phụ thuộc vào abstraction nó tự sở hữu, không phụ thuộc chi tiết.

// === PORT: định nghĩa ở Application — nó "sở hữu" hợp đồng này ===
namespace Shop.Application.Common.Interfaces;

public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(Guid id, CancellationToken ct);
    Task AddAsync(Order order, CancellationToken ct);
}

public interface IEmailSender
{
    Task SendOrderConfirmationAsync(Guid orderId, CancellationToken ct);
}
// === ADAPTER: hiện thực ở Infrastructure — chi tiết kỹ thuật ===
namespace Shop.Infrastructure.Services;

public sealed class SmtpEmailSender : IEmailSender
{
    private readonly SmtpClient _smtp;
    public SmtpEmailSender(SmtpClient smtp) => _smtp = smtp;

    public async Task SendOrderConfirmationAsync(Guid orderId, CancellationToken ct)
    {
        var msg = new MailMessage("shop@demo.vn", "khach@demo.vn")
        {
            Subject = "Xác nhận đơn hàng",
            Body = $"Đơn {orderId} đã được tạo thành công."
        };
        await _smtp.SendMailAsync(msg, ct);
    }
}
Đảo ngược dòng chảy: Lúc runtime, Application gọi SmtpEmailSender (chiều thực thi hướng ra ngoài). Nhưng lúc compile, source dependency lại hướng vào trong: Infrastructure phụ thuộc interface ở Application, chứ Application không hề biết SMTP tồn tại. Đó chính là "đảo ngược phụ thuộc" — và là lý do bạn thay SmtpEmailSender bằng SendGridEmailSender mà không sửa Application.

6. Mapping với DTOs ở boundary

Entity Domain không được leak ra API. Lý do: entity chứa logic, invariant, có thể có navigation property gây vòng lặp serialize, và nếu expose trực tiếp thì hợp đồng API của bạn bị khoá cứng vào cấu trúc nội bộ. Thay vào đó, map Domain ↔ DTO ở ranh giới.

Vì sao phải tách DTO?

  • API contract ổn định, đổi entity không vỡ client
  • Tránh over-posting / mass assignment
  • Không leak field nhạy cảm (password hash, internal flag)
  • Tránh vòng lặp serialize của navigation property
  • Shape dữ liệu đúng nhu cầu màn hình

Manual vs Mapper

  • Manual mapping: rõ ràng, dễ debug, không "magic", không reflection runtime — khuyến nghị cho dự án vừa
  • Mapster: nhanh, có source generator (compile-time, AOT-friendly)
  • AutoMapper: tiện cho dự án lớn nhưng dễ giấu lỗi mapping, khó trace
// Manual mapping — minh bạch, không phụ thuộc thư viện ngoài
public static class OrderMappings
{
    public static OrderResultDto ToDto(this Order o) => new(
        Id: o.Id,
        Total: o.Total.Amount,
        Status: o.Status.ToString(),
        Lines: o.Lines.Select(l => new OrderLineDto(l.ProductId, l.Quantity)).ToList());
}

// DTO là record phẳng, chỉ chứa data — không logic
public record OrderResultDto(Guid Id, decimal Total, string Status, List<OrderLineDto> Lines);
💡 Nhiều "loại" DTO: phân biệt Request DTO (input, ở API: PlaceOrderRequest), Command/Query (ở Application), và Response DTO (output: OrderResultDto). Đừng dùng chung một class cho cả input lẫn output — chúng tiến hoá theo hướng khác nhau.

7. Khi nào Clean Architecture là overkill?

Sự thật phũ phàng: phần lớn dự án nhỏ không cần 4 project, CQRS và hàng đống interface. Clean Architecture đánh đổi nhiều boilerplate để lấy khả năng bảo trì lâu dài. Nếu dự án không sống đủ lâu hoặc không đủ phức tạp, bạn chỉ tốn công.

❌ Đừng dùng khi…

  • App CRUD thuần, ít business rule (admin panel, form nhập liệu)
  • Prototype / MVP / hackathon cần ship nhanh
  • Microservice nhỏ chỉ vài endpoint
  • Team nhỏ, dự án ngắn hạn, ít người maintain
  • Đội chưa quen — over-engineer làm chậm cả nhóm

✅ Hợp lý khi…

  • Domain phức tạp, nhiều quy tắc nghiệp vụ thay đổi
  • Dự án dài hạn, nhiều người, sống nhiều năm
  • Cần thay đổi hạ tầng độc lập (DB, message bus, gateway)
  • Yêu cầu test nghiệp vụ cao, cô lập khỏi I/O
  • Nhiều entry point (REST + gRPC + background worker)
⚠️ Over-engineering là một chi phí thật: mỗi interface một implementation duy nhất, mỗi command một handler một dòng, mỗi map qua 3 tầng DTO — tất cả đều là code phải đọc, viết, maintain. Với app nhỏ, chi phí này lớn hơn lợi ích. Đừng thêm abstraction "phòng khi cần"; thêm khi thật sự cần (YAGNI).
Giải pháp trung gian: Vertical Slice Architecture — gom tất cả code của một tính năng (request, handler, validation, DB access) vào một thư mục/file theo feature thay vì theo layer. Ít boilerplate hơn Clean, vẫn tách biệt tốt. Hoặc đơn giản là layered architecture truyền thống cho CRUD. Chọn kiến trúc theo độ phức tạp của bài toán, không theo trào lưu.

8. Lợi ích khi dùng đúng chỗ

🧪 Testability

Domain test thuần không cần mock. Application test bằng cách mock interface (in-memory repo), không cần dựng DB — test nhanh, ổn định, chạy hàng nghìn lần/giây.

🔌 Độc lập framework / DB

EF Core, ASP.NET, SMTP đều là chi tiết ở vòng ngoài. Đổi PostgreSQL→SQL Server, REST→gRPC, SMTP→SendGrid mà core không đổi.

🔧 Dễ thay đổi & mở rộng

Business rule tập trung ở Domain — sửa một chỗ. Thêm adapter mới (gateway thanh toán mới) chỉ là thêm class hiện thực interface có sẵn.

💡 Điểm mấu chốt: giá trị không nằm ở "nhiều layer" mà ở chỗ business logic được bảo vệ khỏi sự thay đổi của hạ tầng. Nếu kiến trúc của bạn không đạt được điều đó (vd Domain vẫn ref EF Core), thì dù có 10 project cũng vô nghĩa.

🎯 Checklist Clean / Onion Architecture

  • ✅ Domain không tham chiếu EF Core, ASP.NET, hay bất kỳ framework hạ tầng nào
  • ✅ Tất cả interface (port) như IRepository, IEmailSender nằm ở Application (hoặc Domain)
  • ✅ Implementation (adapter) của các interface nằm ở Infrastructure
  • ✅ Chiều tham chiếu: Api → Infrastructure/Application → Domain — không có circular dependency
  • ✅ Infrastructure và Application không bao giờ ref API/Presentation
  • ✅ Entity Domain không leak ra API — luôn map qua DTO ở boundary
  • ✅ Business rule & invariant nằm trong Domain, không rò rỉ ra handler hay controller
  • ✅ DI composition root nằm ở API (Program.cs), ráp interface với implementation
  • ✅ CancellationToken truyền xuyên suốt qua các port async
  • ✅ Đã cân nhắc: bài toán có đủ phức tạp để xứng đáng kiến trúc này chưa? (tránh over-engineer)
