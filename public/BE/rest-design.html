Thiết kế REST API

Thiết kế REST API chuẩn mực cho ASP.NET Core .NET 8/9: mô hình hoá resource (danh từ, sub-resource), HTTP verb & status code đúng ngữ nghĩa, idempotency & Idempotency-Key, versioning với Asp.Versioning, phân trang offset vs keyset, ProblemDetails RFC 7807, HATEOAS và các best practice về hợp đồng API (camelCase, ISO 8601 UTC, OpenAPI). Tất cả code chính xác cho .NET 8/9.

1. Mô hình hoá Resource (Resource Modeling)

REST xoay quanh resource (tài nguyên) — là danh từ, không phải hành động. URL định danh resource; HTTP verb mới thể hiện hành động. Đừng nhét động từ vào URL (/getOrder, /createUser là sai).

✅ Danh từ số nhiều cho collection

  • GET /api/orders — danh sách đơn hàng
  • GET /api/orders/42 — đơn hàng cụ thể
  • POST /api/orders — tạo đơn mới
  • GET /api/orders/42/items — sub-resource

🚫 Động từ trong URL (RPC trá hình)

  • POST /api/getOrder?id=42
  • POST /api/createOrder
  • GET /api/orders/deleteAll
  • POST /api/order/42/markAsPaid
Loại resourceMẫu URLÝ nghĩa
Collection/api/ordersTập hợp nhiều resource
Phần tử (item)/api/orders/{id}Một resource trong collection
Sub-resource (lồng nhau)/api/orders/{id}/itemsResource thuộc về resource cha
Sub-resource item/api/orders/{id}/items/{itemId}Một item trong đơn hàng
Singleton/api/users/me/profileResource đơn nhất (không phải collection)
// Minimal API .NET 8/9 — nhóm route theo resource
var orders = app.MapGroup("/api/orders");

orders.MapGet("/", GetOrders);            // collection
orders.MapGet("/{id:int}", GetOrderById);  // item
orders.MapPost("/", CreateOrder);          // tạo trong collection

// Sub-resource: items thuộc về order
orders.MapGet("/{id:int}/items", GetOrderItems);
orders.MapPost("/{id:int}/items", AddOrderItem);
⚠️ Đừng lồng quá sâu: tối đa nên dừng ở /orders/{id}/items/{itemId}. Lồng 3-4 cấp (/users/1/orders/2/items/3/reviews/4) làm URL khó hiểu và khó cache. Khi đã có ID duy nhất của item, hãy truy cập phẳng: /api/order-items/{itemId}.
💡 Hành động không-CRUD: với thao tác không map vào CRUD (vd "thanh toán đơn"), coi nó như tạo một sub-resource hành động: POST /api/orders/42/payments thay vì POST /api/orders/42/pay. Vẫn giữ danh từ.

2. HTTP Verb & Status Code

Verb thể hiện ý định; status code thể hiện kết quả. Dùng đúng cặp này là cốt lõi của REST.

VerbNgữ nghĩaIdempotent?Có body?Success code
GETĐọc resource, không có side-effectCóKhông200 OK
POSTTạo mới / hành động không idempotentKhôngCó201 Created
PUTThay thế toàn bộ resourceCóCó200 / 204
PATCHCập nhật một phần resourceTuỳ (nên thiết kế idempotent)Có200 / 204
DELETEXoá resourceCóKhông204 No Content

Status code thường gặp

CodeTênKhi nào dùng

201CreatedPOST tạo mới thành công — kèm header Location
204No ContentDELETE / PUT thành công nhưng không trả body
400Bad RequestRequest sai cú pháp / không parse được / thiếu field
401UnauthorizedChưa xác thực (chưa đăng nhập / token sai)
403ForbiddenĐã xác thực nhưng không đủ quyền

409ConflictXung đột trạng thái (trùng key, optimistic concurrency)

// POST trả 201 Created + Location trỏ tới resource vừa tạo
orders.MapPost("/", async (CreateOrderDto dto, IOrderService svc, CancellationToken ct) =>
{
    var created = await svc.CreateAsync(dto, ct);
    // Results.Created tự set header Location: /api/orders/{id}
    return Results.Created($"/api/orders/{created.Id}", created);
});

// DELETE trả 204 No Content khi thành công, 404 khi không thấy
orders.MapDelete("/{id:int}", async (int id, IOrderService svc, CancellationToken ct) =>
{
    var deleted = await svc.DeleteAsync(id, ct);
    return deleted ? Results.NoContent() : Results.NotFound();
});
400 vs 422: dùng 400 khi request không hợp lệ về cú pháp (JSON hỏng, thiếu field bắt buộc, sai kiểu). Dùng 422 khi request đọc được nhưng vi phạm luật nghiệp vụ (vd email đúng format nhưng đã tồn tại, ngày kết thúc trước ngày bắt đầu). Nhiều team dùng 400 cho cả hai cũng chấp nhận được — quan trọng là nhất quán toàn API.

3. Idempotency (Tính bất biến khi lặp)

Một thao tác idempotent nếu gọi 1 lần hay N lần đều cho cùng trạng thái cuối. Đây là tính chất sống còn cho retry an toàn (mạng lỗi, client gửi lại).

VerbIdempotent?Giải thích
GET✅ CóĐọc nhiều lần không thay đổi gì (an toàn + idempotent)
PUT✅ CóThay thế toàn bộ — PUT 5 lần cùng body = 1 lần
DELETE✅ CóXoá rồi xoá lại → vẫn "đã xoá" (lần sau trả 404)
POST🚫 KhôngGọi 2 lần → tạo 2 resource. Retry nguy hiểm (double charge!)
PATCH⚠️ Tuỳ{"status":"paid"} idempotent; {"qty":"+1"} thì không
⚠️ POST không idempotent: nếu client gửi POST /payments, mạng timeout rồi retry → có thể trừ tiền 2 lần. Giải pháp chuẩn công nghiệp (Stripe, PayPal) là Idempotency-Key: client gửi 1 key duy nhất; server lưu kết quả lần đầu và trả lại đúng kết quả đó cho các lần lặp. 
// Pattern Idempotency-Key cho POST không-idempotent
// Client gửi header: Idempotency-Key: 7c2f...-unique-per-attempt
orders.MapPost("/", async (
    CreateOrderDto dto,
    [FromHeader(Name = "Idempotency-Key")] string? idempotencyKey,
    IOrderService svc,
    IIdempotencyStore store,
    CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(idempotencyKey))
        return Results.BadRequest("Thiếu header Idempotency-Key.");

    // Đã xử lý key này trước đó? Trả lại kết quả cũ, KHÔNG tạo mới.
    var cached = await store.TryGetAsync(idempotencyKey, ct);
    if (cached is not null)
        return Results.Created($"/api/orders/{cached.Id}", cached);

    var created = await svc.CreateAsync(dto, ct);

    // Lưu (key -> kết quả) với TTL, lý tưởng trong cùng transaction
    await store.SaveAsync(idempotencyKey, created, TimeSpan.FromHours(24), ct);

    return Results.Created($"/api/orders/{created.Id}", created);
});
💡 Lưu key ở đâu: Redis (TTL tự động) hoặc bảng DB với unique constraint trên key. Nên gắn key với cả hash của request body để tránh client tái dùng key cho payload khác. RFC draft "The Idempotency-Key HTTP Header Field" mô tả pattern này.

4. Versioning (Quản lý phiên bản API)

Khi API đã public, bạn không được phá vỡ client cũ. Versioning cho phép tiến hoá API mà không "đập" người dùng hiện tại. Có 4 chiến lược chính.

Chiến lượcVí dụƯuNhược
URL path/api/v1/ordersRõ ràng, dễ cache, dễ test trên browserKhông "thuần REST" (URL nên định danh resource, không version)
Query string/api/orders?api-version=1.0Dễ dùng, không đổi pathDễ bị bỏ quên, làm rối URL
HeaderX-Api-Version: 1.0URL sạchKhó test bằng browser, ít rõ ràng
Media-typeAccept: application/json;v=1"Thuần REST" nhất (content negotiation)Phức tạp, client hay làm sai
Thực tế phổ biến: URL path versioning (/v1/) thắng thế trong đa số API public vì rõ ràng và dễ debug. Dùng thư viện chính thức Asp.Versioning.Http / Asp.Versioning.Mvc (kế thừa từ Microsoft.AspNetCore.Mvc.Versioning). 
// dotnet add package Asp.Versioning.Http        (Minimal API)
// dotnet add package Asp.Versioning.Mvc.ApiExplorer  (Swagger)
using Asp.Versioning;

builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1.0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true; // trả header api-supported-versions
    // Đọc version từ URL segment; có thể combine nhiều reader
    options.ApiVersionReader = ApiVersionReader.Combine(
        new UrlSegmentApiVersionReader(),
        new HeaderApiVersionReader("X-Api-Version"),
        new QueryStringApiVersionReader("api-version"));
})
.AddApiExplorer(o =>
{
    o.GroupNameFormat = "'v'VVV";       // v1, v1.1, v2
    o.SubstituteApiVersionInUrl = true;
});
// Minimal API: khai báo version set rồi gắn cho từng endpoint
var versions = app.NewApiVersionSet()
    .HasApiVersion(new ApiVersion(1.0))
    .HasApiVersion(new ApiVersion(2.0))
    .Build();

var orders = app.MapGroup("/api/v{version:apiVersion}/orders")
    .WithApiVersionSet(versions);

orders.MapGet("/", GetOrdersV1).MapToApiVersion(1.0);
orders.MapGet("/", GetOrdersV2).MapToApiVersion(2.0); // shape mới
// Controller-based: attribute routing với version trong URL
[ApiController]
[ApiVersion(1.0)]
[ApiVersion(2.0)]
[Route("api/v{version:apiVersion}/orders")]
public class OrdersController : ControllerBase
{
    [HttpGet, MapToApiVersion(1.0)]
    public Task<IActionResult> GetV1() => ...;

    [HttpGet, MapToApiVersion(2.0)]
    public Task<IActionResult> GetV2() => ...;
}
💡 Deprecation: dùng [ApiVersion(1.0, Deprecated = true)] để báo client một version sắp ngừng hỗ trợ — framework sẽ trả header api-deprecated-versions. Cho client thời gian di trú trước khi gỡ.

5. Phân trang, Lọc & Sắp xếp

Không bao giờ trả về toàn bộ collection không giới hạn. Luôn phân trang. Có 2 kiểu chính: offset (dễ) và keyset/cursor (chuẩn cho dữ liệu lớn / real-time).

Offset pagination

?page=2&pageSize=20 → SKIP 20 TAKE 20.

  • ✅ Đơn giản, nhảy tới trang bất kỳ
  • ✅ Hiển thị tổng số trang dễ dàng
  • 🚫 Chậm khi offset lớn (DB phải skip hàng triệu dòng)
  • 🚫 Dữ liệu thay đổi giữa các trang → bị trùng/sót item

Keyset / Cursor pagination

?after=eyJpZCI6MTIzfQ&pageSize=20 → WHERE id > lastId.

  • ✅ Nhanh ổn định dù dữ liệu lớn (dùng index)
  • ✅ Không trùng/sót khi insert/delete đồng thời
  • 🚫 Không nhảy tới trang N tuỳ ý
  • 🚫 Phức tạp hơn khi sort nhiều cột
// Envelope phân trang chuẩn: data + metadata
public record PagedResult<T>(
    IReadOnlyList<T> Items,
    int Page,
    int PageSize,
    long TotalCount)
{
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
    public bool HasNext => Page * PageSize < TotalCount;
}
// OFFSET pagination với EF Core — lọc + sort + phân trang
public async Task<PagedResult<OrderDto>> GetOrdersAsync(
    string? status, string? sort,
    int page = 1, int pageSize = 20,
    CancellationToken ct = default)
{
    page = Math.Max(1, page);
    pageSize = Math.Clamp(pageSize, 1, 100); // chặn pageSize quá lớn

    IQueryable<Order> query = _db.Orders.AsNoTracking();

    // Lọc (filter)
    if (!string.IsNullOrWhiteSpace(status))
        query = query.Where(o => o.Status == status);

    // Sắp xếp: ?sort=-createdAt nghĩa là createdAt giảm dần
    query = sort switch
    {
        "-createdAt" => query.OrderByDescending(o => o.CreatedAt),
        "createdAt"  => query.OrderBy(o => o.CreatedAt),
        "total"      => query.OrderBy(o => o.Total),
        _            => query.OrderByDescending(o => o.Id) // mặc định ổn định
    };

    var total = await query.LongCountAsync(ct);

    var items = await query
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(o => new OrderDto(o.Id, o.Status, o.Total, o.CreatedAt))
        .ToListAsync(ct);

    return new PagedResult<OrderDto>(items, page, pageSize, total);
}
// KEYSET pagination — nhanh & ổn định cho dataset lớn
// Cursor là Id của phần tử cuối trang trước (mã hoá base64)
public async Task<(List<OrderDto> Items, int? NextCursor)> GetOrdersKeysetAsync(
    int? afterId, int pageSize = 20, CancellationToken ct = default)
{
    pageSize = Math.Clamp(pageSize, 1, 100);

    IQueryable<Order> query = _db.Orders.AsNoTracking().OrderBy(o => o.Id);

    if (afterId is not null)
        query = query.Where(o => o.Id > afterId); // dùng index trên Id

    var rows = await query
        .Take(pageSize + 1) // lấy dư 1 để biết còn trang sau không
        .ToListAsync(ct);

    var hasMore = rows.Count > pageSize;
    var page = rows.Take(pageSize).Select(MapToDto).ToList();
    int? next = hasMore ? page[^1].Id : null;

    return (page, next);
}
💡 Trả metadata phân trang ở đâu: đặt trong body (envelope như trên) là phổ biến và dễ dùng nhất. Cách "thuần HTTP" là dùng header Link (RFC 8288) với rel="next"/rel="prev" và header X-Total-Count. Chọn 1 kiểu và nhất quán toàn API.

6. ProblemDetails — RFC 7807

Đừng trả lỗi với mỗi API mỗi kiểu ({ "error": "..." }, { "message": "..." }). RFC 7807 (cập nhật bởi RFC 9457) định nghĩa định dạng lỗi chuẩn application/problem+json — ASP.NET Core hỗ trợ sẵn qua ProblemDetails.

// Cấu trúc problem+json chuẩn
{
  "type": "https://example.com/errors/insufficient-funds",
  "title": "Số dư không đủ",
  "status": 422,
  "detail": "Tài khoản thiếu 50.000đ để hoàn tất giao dịch.",
  "instance": "/api/orders/42/payments",
  "traceId": "00-8fa...-01"
}
// Program.cs — bật ProblemDetails toàn cục (.NET 8/9)
builder.Services.AddProblemDetails(options =>
{
    // Bổ sung field tuỳ biến vào mọi problem response
    options.CustomizeProblemDetails = ctx =>
    {
        ctx.ProblemDetails.Instance = ctx.HttpContext.Request.Path;
        ctx.ProblemDetails.Extensions["traceId"] =
            Activity.Current?.Id ?? ctx.HttpContext.TraceIdentifier;
    };
});

var app = builder.Build();
app.UseExceptionHandler();   // kích hoạt IExceptionHandler
app.UseStatusCodePages();    // 404/405... cũng trả problem+json
// IExceptionHandler (.NET 8+) — biến exception thành ProblemDetails
public sealed class GlobalExceptionHandler(IProblemDetailsService problemDetails)
    : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext http, Exception ex, CancellationToken ct)
    {
        var (status, title) = ex switch
        {
            NotFoundException        => (StatusCodes.Status404NotFound, "Không tìm thấy"),
            ValidationException      => (StatusCodes.Status422UnprocessableEntity, "Dữ liệu không hợp lệ"),
            ConcurrencyException     => (StatusCodes.Status409Conflict, "Xung đột phiên bản"),
            UnauthorizedAccessException => (StatusCodes.Status403Forbidden, "Không có quyền"),
            _                        => (StatusCodes.Status500InternalServerError, "Lỗi hệ thống")
        };

        http.Response.StatusCode = status;

        return await problemDetails.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = http,
            Exception = ex,
            ProblemDetails = new ProblemDetails
            {
                Status = status,
                Title = title,
                // KHÔNG lộ ex.Message thô ở 500 trong production
                Detail = status == 500 ? "Đã xảy ra lỗi không mong muốn." : ex.Message
            }
        });
    }
}

// Đăng ký
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();
// ValidationProblemDetails: gom nhiều lỗi field theo RFC 7807
if (errors.Count > 0)
{
    return Results.ValidationProblem(
        errors,                       // IDictionary<string, string[]>
        statusCode: StatusCodes.Status422UnprocessableEntity,
        title: "Một hoặc nhiều trường không hợp lệ");
}
// => { "title": "...", "status": 422, "errors": { "email": ["..."] } }
Tự động cho [ApiController]: controller gắn [ApiController] tự trả ValidationProblemDetails (400) khi model state không hợp lệ — không cần tự check ModelState.IsValid. Đây cũng là application/problem+json.

7. HATEOAS — Liên kết trong response

HATEOAS (Hypermedia As The Engine Of Application State) là cấp cao nhất của mô hình Richardson Maturity. Ý tưởng: response không chỉ chứa dữ liệu mà còn chứa các link hành động tiếp theo client có thể thực hiện, để client không phải hardcode URL.

// Response có HATEOAS links
{
  "id": 42,
  "status": "pending",
  "total": 250000,
  "_links": {
    "self":   { "href": "/api/orders/42", "method": "GET" },
    "pay":    { "href": "/api/orders/42/payments", "method": "POST" },
    "cancel": { "href": "/api/orders/42", "method": "DELETE" },
    "items":  { "href": "/api/orders/42/items", "method": "GET" }
  }
}

✅ Khi nào đáng dùng

  • API public dài hạn, nhiều client đa dạng
  • Workflow phức tạp với nhiều trạng thái (link phụ thuộc state)
  • Muốn client tách rời (decouple) khỏi cấu trúc URL

🚫 Khi nào thường thừa

  • API nội bộ, client do chính team viết
  • Frontend SPA đơn giản, biết trước route
  • Đa số CRUD API thông thường — chi phí cao, lợi ích thấp
⚠️ Thực tế: HATEOAS đẹp về lý thuyết nhưng phần lớn API sản xuất không dùng đầy đủ vì client hiếm khi tự "khám phá" link động — họ vẫn đọc tài liệu. Đừng over-engineer. Nếu cần định dạng chuẩn, tham khảo HAL (application/hal+json) hoặc JSON:API.

8. Best Practice cho Hợp đồng API (Contract)

Hợp đồng (contract) là lời hứa với client. Một khi đã public, phá vỡ contract là phá vỡ ứng dụng người khác. Dưới đây là các quy ước cần nhất quán.

camelCase cho JSON

Property JSON dùng camelCase (createdAt, không CreatedAt). System.Text.Json mặc định đã camelCase trong ASP.NET Core.

Ngày giờ: ISO 8601 UTC

Luôn 2026-06-15T08:30:00Z (UTC, hậu tố Z). Không gửi giờ local mơ hồ. Client tự đổi sang giờ địa phương.

Nhất quán số nhiều/đặt tên

Collection luôn số nhiều. Trường boolean dạng isActive, hasItems. Tránh viết tắt khó hiểu.

// Cấu hình JSON nhất quán toàn ứng dụng
builder.Services.ConfigureHttpJsonOptions(o =>        // Minimal API
{
    o.SerializerOptions.PropertyNamingPolicy = JsonNamingPolicy.CamelCase;
    o.SerializerOptions.DefaultIgnoreCondition =
        JsonIgnoreCondition.WhenWritingNull;          // bỏ null cho gọn
});

// DTO dùng DateTimeOffset/DateTime UTC -> serialize ra ISO 8601 "...Z"
public record OrderDto(
    int Id,
    string Status,
    decimal Total,
    DateTimeOffset CreatedAt); // "2026-06-15T08:30:00+00:00"
⚠️ Không bao giờ phá vỡ contract: được phép thêm field mới (optional), thêm endpoint mới. KHÔNG được đổi tên/xoá field, đổi kiểu dữ liệu, đổi ngữ nghĩa của field cũ, đổi status code đã hứa. Những thay đổi phá vỡ phải đi qua một version mới. 
// OpenAPI/Swagger — .NET 9 có built-in Microsoft.AspNetCore.OpenApi
builder.Services.AddOpenApi(); // .NET 9
// ...
app.MapOpenApi();              // /openapi/v1.json

// Mô tả response để contract rõ ràng trong tài liệu
orders.MapGet("/{id:int}", GetOrderById)
    .Produces<OrderDto>(StatusCodes.Status200OK)
    .Produces<ProblemDetails>(StatusCodes.Status404NotFound)
    .WithName("GetOrderById")
    .WithSummary("Lấy chi tiết một đơn hàng theo Id");
💡 Nullability rõ ràng: tận dụng nullable reference types (string? vs string) trong DTO để OpenAPI sinh schema chính xác field nào optional. Client codegen sẽ phản ánh đúng — giảm bug "thiếu null check".

9. Do / Don't

❌ Động từ trong URL

POST /api/orders/42/markAsShipped
GET  /api/getOrdersByUser?userId=7

URL nên là danh từ. Dùng verb HTTP + sub-resource: POST /api/orders/42/shipments, GET /api/users/7/orders.

❌ Luôn trả 200 OK kể cả khi lỗi

HTTP/1.1 200 OK
{ "success": false, "error": "Not found" }

Client/proxy/cache dựa vào status code. Trả đúng 404/422/500 với problem+json.

❌ Trả entity DB thẳng ra ngoài

return Ok(_db.Users.Find(id)); // lộ PasswordHash, navigation...

Lộ field nhạy cảm, lộ schema, dễ over-posting. Luôn map sang DTO/record riêng cho response.

❌ Trả collection không phân trang

GET /api/orders => trả về cả 2 triệu dòng

Sập memory + chậm. Luôn phân trang với pageSize có giới hạn (clamp tối đa 100).

✅ Resource danh từ + verb đúng + status đúng

POST /api/orders        => 201 + Location
DELETE /api/orders/42   => 204

Ngữ nghĩa rõ ràng, dễ cache, dễ test, tương thích chuẩn HTTP.

✅ Lỗi chuẩn ProblemDetails + version hoá thay đổi phá vỡ

Content-Type: application/problem+json
GET /api/v2/orders   // shape mới ở v2, v1 vẫn sống

Client xử lý lỗi nhất quán; thay đổi breaking đi qua version mới, không đập client cũ.

🎯 Checklist Thiết kế REST API

  • ✅ URL là danh từ số nhiều (/api/orders), không có động từ
  • ✅ Sub-resource lồng tối đa 2 cấp (/orders/{id}/items)
  • ✅ Verb đúng ngữ nghĩa: GET đọc, POST tạo, PUT thay thế, PATCH sửa phần, DELETE xoá
  • ✅ Status code đúng: 201+Location khi tạo, 204 khi xoá, 4xx/5xx khi lỗi
  • ✅ POST không-idempotent có Idempotency-Key để retry an toàn
  • ✅ Versioning bằng Asp.Versioning (URL /v1/), deprecation rõ ràng
  • ✅ Mọi collection đều phân trang, có clamp pageSize, hỗ trợ filter & sort
  • ✅ Dataset lớn dùng keyset/cursor pagination thay vì offset
  • ✅ Lỗi trả ProblemDetails (RFC 7807) qua AddProblemDetails + IExceptionHandler
  • ✅ JSON camelCase, ngày giờ ISO 8601 UTC, không lộ entity DB (dùng DTO)
  • ✅ Không phá vỡ contract — thay đổi breaking đi qua version mới
  • ✅ Có OpenAPI/Swagger, mô tả .Produces response cho từng endpoint
  • ✅ HATEOAS chỉ dùng khi thực sự cần — đừng over-engineer
