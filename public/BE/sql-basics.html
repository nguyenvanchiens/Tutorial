SQL & Database nền tảng

Toàn bộ kiến thức SQL nền tảng cho backend developer: SELECT & lọc dữ liệu, các loại JOIN, GROUP BY & hàm tổng hợp, khóa & ràng buộc, index, chuẩn hóa (normalization), transaction & ACID, và bảo mật chống SQL Injection. Ví dụ chuẩn ANSI SQL, ghi chú khác biệt SQL Server / PostgreSQL / MySQL.

1. Database quan hệ & bảng mẫu

Database quan hệ (RDBMS) lưu dữ liệu trong các bảng (table) gồm cột (column) và hàng (row). Các bảng liên kết với nhau qua khóa. Toàn bộ lesson dùng schema bán hàng đơn giản dưới đây.

🗂️ Bảng (Table)

Tập hợp dữ liệu cùng loại — như một "sheet" Excel. Ví dụ: Customers, Orders, Products.

📊 Cột (Column)

Thuộc tính có kiểu dữ liệu cố định: INT, VARCHAR, DECIMAL, DATE... Mỗi cột có tên duy nhất trong bảng.

📑 Hàng (Row)

Một bản ghi cụ thể — một khách hàng, một đơn hàng. Còn gọi là record hoặc tuple.

📐 Schema mẫu dùng xuyên suốt

-- Bảng khách hàng
Customers ( Id, Name, City, CreatedAt )

-- Bảng đơn hàng — mỗi đơn thuộc về 1 khách hàng
Orders ( Id, CustomerId, Total, Status, OrderDate )

-- Bảng sản phẩm
Products ( Id, Name, CategoryId, Price, Stock )

-- Bảng chi tiết đơn — nối Orders <-> Products (quan hệ nhiều-nhiều)
OrderItems ( OrderId, ProductId, Quantity, UnitPrice )
SQL là ngôn ngữ khai báo (declarative): bạn mô tả cái gì muốn lấy, không mô tả làm thế nào. Bộ tối ưu (query optimizer) của database tự quyết định cách thực thi nhanh nhất.

2. SELECT — Truy vấn & chiếu cột

Lệnh SELECT là trái tim của SQL. Nó đọc dữ liệu từ bảng và trả về một tập kết quả (result set).

-- Lấy tất cả cột (tránh dùng * trong production)
SELECT * FROM Customers;

-- Chiếu (projection): chỉ lấy cột cần thiết
SELECT Id, Name, City FROM Customers;

-- Alias cột (AS) và alias bảng — đặt tên ngắn gọn, dễ đọc
SELECT c.Name AS CustomerName,
       c.City AS Location
FROM Customers c;

-- Cột tính toán (computed column)
SELECT Name,
       Price,
       Price * 1.1 AS PriceWithTax
FROM Products;

DISTINCT — loại bỏ trùng lặp

-- Danh sách thành phố duy nhất khách hàng đang ở
SELECT DISTINCT City FROM Customers;

-- DISTINCT áp dụng cho TỔ HỢP cột, không phải từng cột riêng
SELECT DISTINCT City, Status FROM Customers c
JOIN Orders o ON o.CustomerId = c.Id;
⚠️ Tránh SELECT * trong code production: lấy thừa cột → tốn băng thông, phá vỡ covering index, và code dễ vỡ khi schema thay đổi. Luôn liệt kê cột cụ thể.

3. WHERE — Lọc dữ liệu

Mệnh đề WHERE lọc các hàng theo điều kiện. Chỉ những hàng thỏa điều kiện mới đi vào kết quả.

Toán tử so sánh & logic

-- So sánh cơ bản: = <> < > <= >=
SELECT * FROM Orders WHERE Total >= 1000;

-- Kết hợp AND / OR / NOT — chú ý độ ưu tiên, dùng ngoặc cho rõ
SELECT * FROM Orders
WHERE Status = 'Paid'
  AND (Total > 500 OR CustomerId = 7);

LIKE — khớp mẫu chuỗi

-- % = nhiều ký tự bất kỳ ; _ = đúng 1 ký tự
SELECT * FROM Customers WHERE Name LIKE 'Nguyen%';   -- bắt đầu bằng Nguyen
SELECT * FROM Customers WHERE Name LIKE '%an%';       -- chứa "an"
SELECT * FROM Customers WHERE City LIKE 'Ha _oi';     -- Ha + 1 ký tự + oi

IN, BETWEEN, IS NULL

-- IN: thuộc một danh sách giá trị (gọn hơn nhiều OR)
SELECT * FROM Orders WHERE Status IN ('Paid', 'Shipped', 'Done');

-- BETWEEN: trong khoảng (bao gồm 2 đầu mút)
SELECT * FROM Orders WHERE Total BETWEEN 100 AND 500;
SELECT * FROM Orders
WHERE OrderDate BETWEEN '2026-01-01' AND '2026-06-30';

-- IS NULL / IS NOT NULL — KHÔNG dùng = NULL (luôn trả về UNKNOWN!)
SELECT * FROM Customers WHERE City IS NULL;
SELECT * FROM Customers WHERE City IS NOT NULL;
🚫 NULL không bằng bất cứ thứ gì — kể cả chính nó. NULL = NULL trả về UNKNOWN, không phải TRUE. Vì vậy WHERE City = NULL không bao giờ khớp hàng nào. Luôn dùng IS NULL / IS NOT NULL.

4. ORDER BY & phân trang (LIMIT / TOP / OFFSET-FETCH)

ORDER BY sắp xếp kết quả. Phân trang giúp lấy từng "trang" dữ liệu — cú pháp khác nhau giữa các hệ DB.

-- Sắp xếp tăng dần (ASC, mặc định) / giảm dần (DESC)
SELECT Name, Total FROM Orders
ORDER BY Total DESC, OrderDate ASC;   -- sắp nhiều cột
Hệ DBLấy N hàng đầuPhân trang (bỏ qua + lấy)
SQL ServerSELECT TOP 10 ...OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY
PostgreSQL / MySQL / SQLite... LIMIT 10LIMIT 10 OFFSET 20
Oracle (12c+)FETCH FIRST 10 ROWS ONLYOFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY
-- ANSI chuẩn (SQL Server 2012+, Postgres, Oracle): OFFSET-FETCH
-- Trang 3, mỗi trang 10 dòng -> bỏ qua (3-1)*10 = 20 dòng
SELECT Id, Total FROM Orders
ORDER BY OrderDate DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;

-- MySQL / PostgreSQL: LIMIT ... OFFSET
SELECT Id, Total FROM Orders
ORDER BY OrderDate DESC
LIMIT 10 OFFSET 20;
⚠️ Phân trang luôn cần ORDER BY: không có ORDER BY thì thứ tự hàng không xác định → trang 2 có thể lặp/bỏ sót dữ liệu của trang 1. Với dataset lớn, cân nhắc keyset pagination (WHERE Id > lastId) thay vì OFFSET lớn vì OFFSET phải quét bỏ qua nhiều hàng.

5. JOIN — Kết hợp nhiều bảng

JOIN ghép các hàng từ nhiều bảng dựa trên điều kiện liên kết (thường là khóa). Đây là kỹ năng quan trọng bậc nhất khi truy vấn dữ liệu quan hệ.

Loại JOINTrả vềKhi nào dùng
INNER JOINChỉ các hàng khớp ở CẢ hai bảngLấy đơn hàng có khách hàng tồn tại
LEFT JOINTất cả hàng bảng trái + khớp bên phải (NULL nếu không khớp)Tất cả khách, kể cả người chưa mua
RIGHT JOINTất cả hàng bảng phải + khớp bên tráiHiếm dùng — thường viết lại thành LEFT
FULL OUTER JOINTất cả hàng cả hai bảng, NULL chỗ không khớpĐối chiếu 2 tập, tìm chênh lệch
CROSS JOINTích Descartes — mọi cặp tổ hợpSinh ma trận, lịch, kết hợp size×color
SELF JOINBảng tự nối với chính nóQuan hệ phân cấp: nhân viên ↔ quản lý

INNER JOIN — giao của hai bảng

-- Đơn hàng kèm tên khách. Chỉ đơn có CustomerId khớp Customers.Id
SELECT o.Id, o.Total, c.Name
FROM Orders o
INNER JOIN Customers c ON o.CustomerId = c.Id;

LEFT JOIN — giữ hết bảng trái

-- Tất cả khách hàng, kèm đơn hàng nếu có. Khách chưa mua -> cột đơn = NULL
SELECT c.Name, o.Id AS OrderId, o.Total
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id;

-- Mẹo: tìm khách CHƯA từng mua hàng
SELECT c.Name
FROM Customers c
LEFT JOIN Orders o ON o.CustomerId = c.Id
WHERE o.Id IS NULL;

RIGHT JOIN — giữ hết bảng phải

-- Tương đương LEFT JOIN nhưng đảo vai trò. Hiếm dùng trong thực tế.
SELECT c.Name, o.Total
FROM Orders o
RIGHT JOIN Customers c ON o.CustomerId = c.Id;

FULL OUTER JOIN — giữ hết cả hai

-- Cả khách không đơn LẪN đơn mồ côi (CustomerId không khớp khách nào)
SELECT c.Name, o.Id AS OrderId
FROM Customers c
FULL OUTER JOIN Orders o ON o.CustomerId = c.Id;
-- Lưu ý: MySQL không hỗ trợ FULL OUTER JOIN -> phải UNION LEFT + RIGHT

CROSS JOIN — tích Descartes

-- Mọi tổ hợp size x color (3 size x 4 color = 12 hàng)
SELECT s.SizeName, cl.ColorName
FROM Sizes s
CROSS JOIN Colors cl;

SELF JOIN — nối bảng với chính nó

-- Bảng Employees(Id, Name, ManagerId). Lấy nhân viên kèm tên quản lý
SELECT e.Name AS Employee,
       m.Name AS Manager
FROM Employees e
LEFT JOIN Employees m ON e.ManagerId = m.Id;
💡 Quy tắc vàng: điều kiện lọc bảng phải trong LEFT JOIN nên đặt trong mệnh đề ON, không phải WHERE — nếu để ở WHERE, NULL sẽ bị loại và LEFT JOIN âm thầm biến thành INNER JOIN.

6. GROUP BY & hàm tổng hợp

Hàm tổng hợp (aggregate) gom nhiều hàng thành một giá trị. GROUP BY chia dữ liệu thành các nhóm rồi tính tổng hợp cho từng nhóm.

HàmÝ nghĩaGhi chú NULL
COUNT(*)Đếm số hàngĐếm cả hàng có NULL
COUNT(col)Đếm giá trị không NULL của cộtBỏ qua NULL
SUM(col)Tổng các giá trịBỏ qua NULL
AVG(col)Trung bìnhBỏ qua NULL (mẫu số không tính NULL)
MIN / MAX(col)Giá trị nhỏ nhất / lớn nhấtBỏ qua NULL
-- Tổng quan toàn bảng (không GROUP BY -> 1 hàng kết quả)
SELECT COUNT(*)   AS TotalOrders,
       SUM(Total) AS Revenue,
       AVG(Total) AS AvgOrder,
       MIN(Total) AS Smallest,
       MAX(Total) AS Biggest
FROM Orders;

-- Doanh thu theo từng khách hàng
SELECT CustomerId,
       COUNT(*)   AS NumOrders,
       SUM(Total) AS TotalSpent
FROM Orders
GROUP BY CustomerId;

HAVING vs WHERE

-- WHERE lọc TRƯỚC khi gom nhóm (trên hàng đơn lẻ)
-- HAVING lọc SAU khi gom nhóm (trên kết quả tổng hợp)
SELECT CustomerId, SUM(Total) AS TotalSpent
FROM Orders
WHERE Status = 'Paid'          -- chỉ tính đơn đã thanh toán
GROUP BY CustomerId
HAVING SUM(Total) > 10000     -- chỉ giữ khách chi tiêu > 10000
ORDER BY TotalSpent DESC;
WHERE vs HAVING — khác biệt cốt lõi: WHERE không dùng được hàm tổng hợp (SUM, COUNT...) vì nó chạy trước khi gom nhóm. Muốn lọc theo kết quả tổng hợp phải dùng HAVING. Thứ tự thực thi logic: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. 
-- Ví dụ phức hợp: top sản phẩm bán chạy
SELECT p.Name,
       SUM(oi.Quantity)              AS UnitsSold,
       SUM(oi.Quantity * oi.UnitPrice) AS Revenue
FROM OrderItems oi
JOIN Products p ON p.Id = oi.ProductId
GROUP BY p.Name
HAVING SUM(oi.Quantity) > 100
ORDER BY Revenue DESC;

7. Khóa & ràng buộc (Keys & Constraints)

Khóa định danh và liên kết dữ liệu, đảm bảo tính toàn vẹn (integrity). Ràng buộc (constraint) là luật database tự bắt buộc.

🔑 Primary Key (PK)

Định danh duy nhất mỗi hàng. Không NULL, không trùng. Mỗi bảng chỉ có 1 PK (có thể gồm nhiều cột).

🔗 Foreign Key (FK)

Cột tham chiếu PK của bảng khác → tạo quan hệ. Đảm bảo không có "đơn hàng mồ côi" trỏ tới khách không tồn tại.

✨ UNIQUE

Giá trị không trùng nhau (vd: email, username). Khác PK: cho phép NULL và bảng có nhiều UNIQUE.

🧩 Composite Key

Khóa gồm nhiều cột ghép lại. Thường dùng cho bảng nối nhiều-nhiều như OrderItems(OrderId, ProductId).

CREATE TABLE Customers (
    Id        INT          IDENTITY(1,1) PRIMARY KEY,
    Name      NVARCHAR(100) NOT NULL,
    Email     NVARCHAR(150) NOT NULL UNIQUE,        -- không trùng email
    City      NVARCHAR(80)  NULL,
    CreatedAt DATETIME2     NOT NULL DEFAULT SYSUTCDATETIME()
);

CREATE TABLE Orders (
    Id         INT           IDENTITY(1,1) PRIMARY KEY,
    CustomerId INT           NOT NULL,
    Total      DECIMAL(12,2) NOT NULL CHECK (Total >= 0),  -- CHECK constraint
    Status     NVARCHAR(20)  NOT NULL DEFAULT 'Pending',
    OrderDate  DATETIME2     NOT NULL,

    -- Foreign Key: mỗi đơn phải trỏ tới khách có thật
    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerId) REFERENCES Customers(Id)
        ON DELETE CASCADE     -- xóa khách -> xóa luôn đơn của họ
);

-- Composite primary key: 1 cặp (OrderId, ProductId) là duy nhất
CREATE TABLE OrderItems (
    OrderId   INT NOT NULL,
    ProductId INT NOT NULL,
    Quantity  INT NOT NULL CHECK (Quantity > 0),
    UnitPrice DECIMAL(12,2) NOT NULL,

    PRIMARY KEY (OrderId, ProductId),                 -- composite key
    FOREIGN KEY (OrderId)   REFERENCES Orders(Id),
    FOREIGN KEY (ProductId) REFERENCES Products(Id)
);
⚠️ ON DELETE behavior: CASCADE xóa lan truyền, SET NULL đặt FK về NULL, NO ACTION / RESTRICT chặn xóa nếu còn bản ghi con. Cân nhắc kỹ — CASCADE mạnh nhưng dễ xóa nhầm hàng loạt.

8. Index — Tăng tốc truy vấn

Index giống mục lục sách: thay vì quét toàn bảng (full table scan), database tra cứu nhanh qua cấu trúc B-Tree. Tăng tốc đọc nhưng làm chậm ghi.

LoạiĐặc điểmSố lượng / bảng
ClusteredSắp xếp vật lý dữ liệu theo key. Dữ liệu = chính index. PK thường là clustered.Chỉ 1
Non-clusteredCấu trúc riêng trỏ về hàng dữ liệu (qua row locator / clustered key).Nhiều
Covering indexIndex chứa đủ mọi cột query cần (qua INCLUDE) → không cần "lookup" về bảng.Nhiều
Composite indexIndex trên nhiều cột. Thứ tự cột rất quan trọng (left-most prefix rule).Nhiều
-- Non-clustered index trên cột hay lọc/sắp xếp
CREATE INDEX IX_Orders_CustomerId
    ON Orders(CustomerId);

-- Composite index: tối ưu WHERE CustomerId = ? AND Status = ?
CREATE INDEX IX_Orders_Customer_Status
    ON Orders(CustomerId, Status);

-- Covering index: INCLUDE thêm cột để query không cần đụng vào bảng
CREATE INDEX IX_Orders_Customer_Covering
    ON Orders(CustomerId)
    INCLUDE (Total, OrderDate);

✅ Index giúp khi

  • Cột trong WHERE, JOIN ON, ORDER BY
  • Cột có độ phân tán cao (selectivity tốt)
  • Foreign key (tăng tốc JOIN + tránh lock khi xóa)
  • Bảng đọc nhiều, ghi ít

❌ Index làm hại khi

  • Bảng ghi nhiều (INSERT/UPDATE phải cập nhật index)
  • Cột ít giá trị phân biệt (vd: cột giới tính)
  • Quá nhiều index → tốn dung lượng, chậm ghi
  • Index không dùng tới → chỉ là gánh nặng
💡 Đọc execution plan: dùng EXPLAIN (PostgreSQL/MySQL) hoặc bật "Actual Execution Plan" (SSMS). Thấy Index Seek là tốt; Index Scan / Table Scan trên bảng lớn là dấu hiệu thiếu index phù hợp.

9. Chuẩn hóa (Normalization) — 1NF, 2NF, 3NF

Chuẩn hóa tổ chức lại bảng để giảm trùng lặp dữ liệu và tránh bất thường khi thêm/sửa/xóa (anomalies). Đi từ dạng thô tới 3NF.

1NF — First Normal Form

Mỗi ô chứa một giá trị nguyên tử (atomic), không nhóm lặp lại, không danh sách trong 1 cột.

❌ Trước (vi phạm 1NF)

Orders
Id | Customer | Products
1  | An       | "Bút, Vở, Tẩy"
2  | Binh     | "Sách"

Cột Products chứa danh sách → không query/join được.

✅ Sau (đạt 1NF)

OrderItems
OrderId | Product
1       | Bút
1       | Vở
1       | Tẩy
2       | Sách

Mỗi sản phẩm 1 hàng riêng — atomic.

2NF — Second Normal Form

Đạt 1NF + mọi cột non-key phụ thuộc vào toàn bộ khóa chính (loại bỏ phụ thuộc một phần — partial dependency). Chỉ liên quan khi PK là composite.

❌ Trước (vi phạm 2NF)

OrderItems (PK: OrderId+ProductId)
OrderId | ProductId | ProductName | Qty
1       | 10        | Bút         | 2
2       | 10        | Bút         | 5

ProductName chỉ phụ thuộc ProductId (một phần khóa) → lặp lại.

✅ Sau (đạt 2NF)

OrderItems      Products
OrderId|ProductId|Qty   Id | Name
1      |10       |2     10 | Bút
2      |10       |5

Tên sản phẩm tách ra bảng Products, lưu 1 lần.

3NF — Third Normal Form

Đạt 2NF + không có phụ thuộc bắc cầu (transitive dependency): cột non-key không phụ thuộc vào cột non-key khác.

❌ Trước (vi phạm 3NF)

Products (PK: Id)
Id | Name | CategoryId | CategoryName
10 | Bút  | 3          | Văn phòng phẩm
11 | Vở   | 3          | Văn phòng phẩm

CategoryName phụ thuộc CategoryId (không phải PK) → bắc cầu.

✅ Sau (đạt 3NF)

Products           Categories
Id|Name|CategoryId    Id | Name
10|Bút |3            3  | Văn phòng phẩm
11|Vở  |3

Danh mục tách riêng → sửa tên category 1 chỗ.

Khi nào denormalize? Chuẩn hóa tốt cho tính toàn vẹn nhưng nhiều JOIN có thể chậm. Hệ thống đọc nặng (reporting, analytics) đôi khi cố ý denormalize (lưu dư thừa) để tăng tốc đọc — đánh đổi bằng việc phải đồng bộ dữ liệu khi ghi.

10. Transaction & ACID

Transaction là một nhóm lệnh thực thi "tất cả hoặc không gì cả". Ví dụ kinh điển: chuyển tiền — trừ tài khoản A và cộng tài khoản B phải cùng thành công.

-- Chuyển 100 từ tài khoản 1 sang tài khoản 2
BEGIN TRANSACTION;

    UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
    UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;

    -- Nếu mọi lệnh OK -> lưu vĩnh viễn
COMMIT;

-- Nếu có lỗi giữa chừng -> hủy toàn bộ, quay về trạng thái ban đầu
-- ROLLBACK;
-- Pattern an toàn với TRY...CATCH (SQL Server)
BEGIN TRY
    BEGIN TRANSACTION;
        UPDATE Accounts SET Balance = Balance - 100 WHERE Id = 1;
        UPDATE Accounts SET Balance = Balance + 100 WHERE Id = 2;
    COMMIT;
END TRY
BEGIN CATCH
    ROLLBACK;            -- có lỗi -> hoàn tác
    THROW;               -- ném lại lỗi cho tầng trên xử lý
END CATCH;
Thuộc tính ACIDÝ nghĩa
A — Atomicity (Nguyên tử)Tất cả lệnh trong transaction thành công, hoặc không lệnh nào áp dụng. Không có trạng thái "nửa vời".
C — Consistency (Nhất quán)Database chuyển từ trạng thái hợp lệ này sang trạng thái hợp lệ khác — mọi ràng buộc (constraint, FK) luôn được tôn trọng.
I — Isolation (Cô lập)Các transaction chạy song song không "thấy" dữ liệu dở dang của nhau (tùy isolation level).
D — Durability (Bền vững)Sau khi COMMIT, dữ liệu được ghi bền vững — dù mất điện / crash cũng không mất.

Isolation Levels (sơ lược)

LevelNgăn đượcVẫn có thể gặp
READ UNCOMMITTED(không ngăn gì)Dirty read, non-repeatable, phantom
READ COMMITTED (mặc định nhiều DB)Dirty readNon-repeatable read, phantom
REPEATABLE READ+ Non-repeatable readPhantom read
SERIALIZABLETất cả (cô lập cao nhất)Chậm nhất, dễ deadlock
⚠️ Đánh đổi: isolation càng cao càng an toàn nhưng càng nhiều lock → giảm đồng thời (concurrency), tăng nguy cơ deadlock. Đa số ứng dụng web dùng READ COMMITTED là đủ.

11. SQL Injection & Parameterized Query

SQL Injection là lỗ hổng bảo mật nghiêm trọng bậc nhất: kẻ tấn công chèn SQL độc hại qua input người dùng. Cách phòng chống duy nhất đúng đắn: luôn dùng tham số (parameterized query).

❌ KHÔNG BAO GIỜ — nối chuỗi (vulnerable)

-- Input người dùng: username = "admin"
-- Câu truy vấn build bằng nối chuỗi:
SELECT * FROM Users WHERE Username = 'admin';

-- Kẻ tấn công nhập:  ' OR '1'='1' --
-- Câu lệnh bị bóp méo thành (luôn TRUE, bỏ qua password):
SELECT * FROM Users WHERE Username = '' OR '1'='1' --';

-- Tệ hơn:  '; DROP TABLE Users; --   -> xóa sạch bảng!
// C# — KHÔNG BAO GIỜ viết thế này (lỗ hổng injection)
var sql = $"SELECT * FROM Users WHERE Username = '{username}'";
var cmd = new SqlCommand(sql, conn);   // input chèn thẳng vào SQL

✅ ĐÚNG — parameterized query

-- SQL với tham số (@p hoặc ? tùy provider)
SELECT * FROM Users WHERE Username = @username;
-- Giá trị truyền RIÊNG, DB coi nó là DỮ LIỆU thuần, không phải mã SQL
// C# ADO.NET — tham số hóa an toàn
using var cmd = new SqlCommand(
    "SELECT * FROM Users WHERE Username = @username", conn);

cmd.Parameters.AddWithValue("@username", username);  // truyền giá trị riêng
// Tốt hơn — chỉ định kiểu & độ dài rõ ràng:
cmd.Parameters.Add("@username", SqlDbType.NVarChar, 100).Value = username;

using var reader = await cmd.ExecuteReaderAsync();
// Dapper — tham số hóa tự động qua object ẩn danh
var user = await conn.QueryFirstOrDefaultAsync<User>(
    "SELECT * FROM Users WHERE Username = @Username",
    new { Username = username });   // Dapper tự tạo SqlParameter an toàn
🚫 Tuyệt đối không nối chuỗi input vào SQL — kể cả khi "chắc chắn input an toàn". Tham số hóa vừa chống injection, vừa cho phép DB cache execution plan (tái dùng plan → nhanh hơn). Với ORM như EF Core, LINQ-to-Entities tự tham số hóa; chỉ cẩn thận khi dùng FromSqlRaw với chuỗi nội suy.
💡 Phòng thủ nhiều lớp: tham số hóa (bắt buộc) + validate input + nguyên tắc least privilege cho DB account (app không cần quyền DROP/ALTER) + dùng stored procedure khi hợp lý. Nhưng nhớ: stored procedure vẫn dính injection nếu bên trong nó nối chuỗi động.

12. Thứ tự thực thi logic của một câu SELECT

Bạn viết theo thứ tự này nhưng database thực thi theo thứ tự khác. Hiểu điều này giải thích tại sao alias ở SELECT chưa dùng được trong WHERE.

  1. FROM / JOIN — xác định & ghép các bảng nguồn.
  2. WHERE — lọc hàng đơn lẻ (chưa gom nhóm, chưa có alias của SELECT).
  3. GROUP BY — gom các hàng thành nhóm.
  4. HAVING — lọc các nhóm theo kết quả tổng hợp.
  5. SELECT — chiếu cột, tính biểu thức, đặt alias.
  6. DISTINCT — loại bỏ hàng trùng.
  7. ORDER BY — sắp xếp (lúc này alias SELECT đã dùng được).
  8. LIMIT / OFFSET / TOP — cắt lấy số hàng cuối cùng.
Hệ quả thực tế: không dùng được alias định nghĩa ở SELECT trong WHERE (vì WHERE chạy trước SELECT). Nhưng ORDER BY thì dùng được alias vì nó chạy sau SELECT.

13. Common Pitfalls — Lỗi thường gặp

❌ Dùng = NULL

So sánh với NULL luôn trả về UNKNOWN → không khớp hàng nào.

Fix: dùng IS NULL / IS NOT NULL.

❌ Lọc bảng phải trong WHERE của LEFT JOIN

LEFT JOIN âm thầm biến thành INNER JOIN, mất hàng NULL.

Fix: đặt điều kiện vào mệnh đề ON.

❌ SELECT cột không có trong GROUP BY

Cột không tổng hợp & không nằm trong GROUP BY → lỗi (Postgres) hoặc kết quả không xác định (MySQL cũ).

Fix: mọi cột non-aggregate phải có trong GROUP BY.

❌ Phân trang không ORDER BY

Thứ tự hàng không xác định → trang lặp/sót dữ liệu.

Fix: luôn ORDER BY trên cột duy nhất/ổn định.

❌ Nối chuỗi input vào SQL

Mở toang cửa cho SQL Injection.

Fix: luôn dùng parameterized query.

❌ Index lên mọi cột "cho chắc"

Làm chậm INSERT/UPDATE, tốn dung lượng, có khi không được dùng.

Fix: index theo query thực tế, xem execution plan.

🎯 Checklist nắm vững SQL nền tảng

  • ✅ Viết được SELECT với projection, alias, DISTINCT
  • ✅ Thành thạo WHERE: so sánh, AND/OR, LIKE, IN, BETWEEN, IS NULL
  • ✅ Hiểu & chọn đúng loại JOIN (INNER, LEFT, RIGHT, FULL, CROSS, SELF)
  • ✅ Dùng GROUP BY + aggregate (COUNT/SUM/AVG/MIN/MAX) và phân biệt WHERE vs HAVING
  • ✅ Thiết kế bảng với PK, FK, UNIQUE, composite key, CHECK constraint
  • ✅ Biết khi nào index giúp, khi nào hại; hiểu clustered vs non-clustered & covering index
  • ✅ Chuẩn hóa được dữ liệu tới 3NF và biết khi nào nên denormalize
  • ✅ Dùng transaction đúng (BEGIN/COMMIT/ROLLBACK) và hiểu 4 thuộc tính ACID
  • ✅ Phân trang đúng (OFFSET-FETCH / LIMIT) với ORDER BY ổn định
  • ✅ Luôn dùng parameterized query — không bao giờ nối chuỗi input vào SQL
  • ✅ Đọc được execution plan để chẩn đoán truy vấn chậm
  • ✅ Hiểu thứ tự thực thi logic: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
