Error Handling & Resilience

Xây dựng hệ thống ASP.NET Core "không gãy": chiến lược exception đúng đắn, global exception handler với ProblemDetails (RFC 7807), Result pattern cho lỗi nghiệp vụ, và bộ công cụ resilience Polly v8 — retry với backoff + jitter, circuit breaker, timeout, fallback, graceful degradation. Chính xác cho .NET 8/9.

1. Chiến lược Exception — dùng đúng chỗ

Exception là cơ chế cho những tình huống ngoại lệ thật sự — điều bất thường, không lường trước, không thể xử lý tại chỗ. Đừng dùng exception cho control flow (luồng điều khiển bình thường): nó đắt (capture stack trace, unwind stack), khó đọc và che giấu ý định.

✅ Expected / Business (lỗi nghiệp vụ)

Đoán trước được: email đã tồn tại, số dư không đủ, mã giảm giá hết hạn. Đây là kết quả hợp lệ của nghiệp vụ → nên biểu diễn bằng Result<T>, không throw.

🚫 Unexpected / System (lỗi hệ thống)

Mất kết nối DB, null không lường trước, hết bộ nhớ, config sai. Đây là bug/sự cố hạ tầng → throw để fail fast và để global handler bắt & log.

// ❌ Dùng exception cho control flow — sai
try { var u = ParseUser(input); }
catch (FormatException) { // "kiểm tra input" bằng exception — đắt & khó hiểu }

// ✅ Kiểm tra trước, throw chỉ khi thật sự ngoại lệ
if (!Guid.TryParse(input, out var id))
    return Result.Fail("Id không hợp lệ");   // lỗi dự đoán được

var conn = _factory.Create()
    ?? throw new InvalidOperationException("Không tạo được connection"); // thật sự bất thường → fail fast
Fail fast: với lỗi hệ thống/lập trình (config thiếu, invariant bị vi phạm), hãy throw ngay tại điểm phát hiện thay vì cố "đoán" và chạy tiếp với trạng thái hỏng. Phát hiện sớm → debug dễ, tránh corrupt dữ liệu.

2. Global Exception Handling (.NET 8/9)

.NET 8 giới thiệu IExceptionHandler — cách chính thống, có DI, thay cho việc tự viết middleware. Đăng ký bằng AddExceptionHandler + UseExceptionHandler, trả lỗi chuẩn ProblemDetails (RFC 7807) để client máy đọc được.

// Program.cs — đăng ký handler + ProblemDetails
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddProblemDetails(); // chuẩn hoá body lỗi RFC 7807
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

var app = builder.Build();

app.UseExceptionHandler(); // kích hoạt pipeline bắt exception
app.MapControllers();
app.Run();
// GlobalExceptionHandler.cs — map từng loại exception sang status code
public sealed class GlobalExceptionHandler(
    IProblemDetailsService problemDetailsService,
    ILogger<GlobalExceptionHandler> logger) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext httpContext,
        Exception exception,
        CancellationToken cancellationToken)
    {
        // Log đầy đủ context (kèm TraceId để truy vết)
        logger.LogError(exception,
            "Unhandled exception. TraceId={TraceId}",
            httpContext.TraceIdentifier);

        (int status, string title) = exception switch
        {
            ValidationException      => (StatusCodes.Status400BadRequest, "Dữ liệu không hợp lệ"),
            NotFoundException        => (StatusCodes.Status404NotFound, "Không tìm thấy tài nguyên"),
            UnauthorizedAccessException => (StatusCodes.Status401Unauthorized, "Chưa xác thực"),
            ConflictException        => (StatusCodes.Status409Conflict, "Xung đột dữ liệu"),
            _                          => (StatusCodes.Status500InternalServerError, "Lỗi hệ thống")
        };

        httpContext.Response.StatusCode = status;

        // Trả ProblemDetails — KHÔNG lộ stack trace ra client ở prod
        return await problemDetailsService.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = httpContext,
            Exception   = exception,
            ProblemDetails = new ProblemDetails
            {
                Status = status,
                Title  = title,
                Type   = $"https://httpstatuses.io/{status}",
                Detail = status == 500 ? "Đã xảy ra lỗi không mong muốn." : exception.Message,
                Extensions = { ["traceId"] = httpContext.TraceIdentifier }
            }
        });
    }
}
So với middleware cũ: trước .NET 8 ta thường tự viết ExceptionMiddleware với RequestDelegate + try/catch bao quanh await _next(context). Cách đó vẫn chạy nhưng phải tự lo serialize JSON, content negotiation, ghi ProblemDetails. IExceptionHandler tích hợp DI sạch hơn, có thể đăng ký nhiều handler theo thứ tự (handler nào trả true thì dừng).
⚠️ Tuyệt đối không trả stack trace cho client ở production. Nó lộ cấu trúc nội bộ, đường dẫn file, phiên bản thư viện → hỗ trợ kẻ tấn công. Chỉ bật chi tiết khi app.Environment.IsDevelopment(). Client nhận message chung chung + traceId để báo support tra log.

3. Result Pattern vs Exceptions

Với lỗi nghiệp vụ dự đoán được (validation, vi phạm rule), ném exception là lạm dụng: tốn hiệu năng, ẩn ý định, biến luồng bình thường thành "ngoại lệ". Dùng Result<T> (kiểu Either) để biểu diễn rõ "thành công HOẶC lỗi" ngay trong chữ ký method.

// Result record — biểu diễn thành công/thất bại tường minh
public readonly record struct Error(string Code, string Message);

public class Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public Error? Error { get; }

    private Result(bool ok, T? value, Error? error)
        => (IsSuccess, Value, Error) = (ok, value, error);

    public static Result<T> Success(T value) => new(true, value, null);
    public static Result<T> Fail(Error error)  => new(false, default, error);
}
// Service trả Result thay vì throw cho lỗi nghiệp vụ
public async Task<Result<User>> RegisterAsync(RegisterDto dto, CancellationToken ct)
{
    if (await _db.Users.AnyAsync(u => u.Email == dto.Email, ct))
        return Result<User>.Fail(new("USER_EXISTS", "Email đã được đăng ký"));

    var user = new User(dto.Email);
    _db.Users.Add(user);
    await _db.SaveChangesAsync(ct);
    return Result<User>.Success(user);
}

// Controller map Result -> HTTP response, không cần try/catch nghiệp vụ
[HttpPost]
public async Task<IActionResult> Register(RegisterDto dto, CancellationToken ct)
{
    var result = await _service.RegisterAsync(dto, ct);
    return result.IsSuccess
        ? Ok(result.Value)
        : Conflict(new ProblemDetails { Title = result.Error!.Value.Message });
}
Tình huốngDùng gìVì sao
Validation input, vi phạm business ruleResult<T>Dự đoán được, là kết quả bình thường của nghiệp vụ
Không tìm thấy entity (thường xảy ra)Result<T> / Option"Không có" không phải sự cố
Mất kết nối DB, timeout hạ tầngExceptionBất thường, cần fail fast + log + retry
Vi phạm invariant / bug lập trìnhExceptionKhông thể xử lý tại chỗ, cần crash sớm để lộ bug
Constructor không thể tạo object hợp lệExceptionConstructor không trả Result được
💡 Nguyên tắc: exception cho điều bất thường, Result cho điều dự đoán được. Result làm lỗi nghiệp vụ trở thành phần explicit của API (caller buộc phải xử lý), tránh "exception ngầm" mà người gọi không biết. Cân nhắc thư viện như FluentResults hoặc ErrorOr nếu không muốn tự viết.

4. Polly v8 & Resilience cho HttpClient

Khi gọi service ngoài (HTTP, gRPC), mạng sẽ chắc chắn hỏng đôi lúc: timeout, 503, reset connection. Resilience là khả năng hệ thống chịu lỗi mà không sụp. .NET 8 cung cấp gói Microsoft.Extensions.Http.Resilience (xây trên Polly v8) với AddStandardResilienceHandler — gói sẵn retry + circuit breaker + timeout + rate limiter.

// Program.cs — bật resilience chuẩn chỉ với 1 dòng (đề xuất cho đa số case)
// dotnet add package Microsoft.Extensions.Http.Resilience
builder.Services.AddHttpClient<PaymentApiClient>(c =>
{
    c.BaseAddress = new Uri("https://api.payment.com");
})
.AddStandardResilienceHandler(); // retry + circuit breaker + timeout + rate limiter
// Tuỳ biến từng chính sách của standard handler
builder.Services.AddHttpClient<PaymentApiClient>()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 3;
        o.Retry.BackoffType = DelayBackoffType.Exponential;
        o.Retry.UseJitter   = true;
        o.AttemptTimeout.Timeout    = TimeSpan.FromSeconds(10); // timeout mỗi lần thử
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(30); // timeout toàn bộ
        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        o.CircuitBreaker.FailureRatio     = 0.2;
    });
Polly v8 ResiliencePipeline: Polly v8 thay Policy.Handle<>... (v7) bằng ResiliencePipelineBuilder — API mới, allocation thấp, hỗ trợ ValueTask. AddStandardResilienceHandler bên trong chính là một pipeline được cấu hình sẵn theo best practice của Microsoft.

5. Retry — thử lại thông minh (backoff + jitter)

Nhiều lỗi mạng là transient (tạm thời): 503, timeout, connection reset — thử lại sau chốc lát thường thành công. Nhưng retry sai cách (ngay lập tức, không giới hạn) làm tình hình tệ hơn.

// Polly v8: pipeline retry với exponential backoff + jitter
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddRetry(new RetryStrategyOptions<HttpResponseMessage>
    {
        MaxRetryAttempts = 3,
        Delay        = TimeSpan.FromSeconds(1),
        BackoffType  = DelayBackoffType.Exponential, // 1s, 2s, 4s...
        UseJitter    = true,                          // thêm nhiễu tránh "thundering herd"
        // CHỈ retry lỗi transient — KHÔNG retry 400/401/404
        ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
            .Handle<HttpRequestException>()
            .HandleResult(r => r.StatusCode == HttpStatusCode.ServiceUnavailable
                            || r.StatusCode == HttpStatusCode.TooManyRequests),
        OnRetry = args =>
        {
            Console.WriteLine($"Retry {args.AttemptNumber} sau {args.RetryDelay}");
            return ValueTask.CompletedTask;
        }
    })
    .Build();

var response = await pipeline.ExecuteAsync(
    async token => await _http.GetAsync("/orders", token), ct);
⚠️ Idempotency — cảnh báo sống còn: chỉ retry tự động các thao tác idempotent (GET, PUT, DELETE). Retry một POST /payment không idempotent có thể trừ tiền 2 lần! Với thao tác có hiệu ứng phụ, dùng idempotency key (client gửi key duy nhất, server dedupe) trước khi cho phép retry.
Vì sao cần jitter? Nếu 1000 client cùng retry sau đúng 2s, chúng đập service cùng lúc ("thundering herd") khiến nó tiếp tục sập. Jitter rải ngẫu nhiên thời điểm retry để giãn tải. Luôn dùng UseJitter = true.

6. Circuit Breaker — ngắt mạch bảo vệ

Khi một service phụ thuộc đang "chết", việc cứ gửi request (và retry) chỉ làm nó tệ hơn và khiến caller cũng treo theo. Circuit breaker "ngắt mạch": phát hiện tỉ lệ lỗi cao thì mở mạch, fail nhanh tức thì (không gọi nữa) trong một khoảng, cho service kia thời gian hồi phục.

🟢 Closed (đóng)

Trạng thái bình thường, request đi qua. Đếm tỉ lệ lỗi trong cửa sổ thời gian.

🔴 Open (mở)

Tỉ lệ lỗi vượt ngưỡng → mạch mở. Mọi request fail ngay lập tức (BrokenCircuitException), không gọi service đang chết.

🟡 Half-Open (nửa mở)

Sau thời gian chờ, cho vài request thử. Thành công → đóng lại; thất bại → mở tiếp.

// Polly v8: circuit breaker
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<HttpResponseMessage>
    {
        FailureRatio     = 0.5,                       // 50% request lỗi...
        MinimumThroughput = 10,                       // ...trong tối thiểu 10 request
        SamplingDuration  = TimeSpan.FromSeconds(30),  // cửa sổ quan sát
        BreakDuration     = TimeSpan.FromSeconds(15),  // thời gian mạch mở
        ShouldHandle = new PredicateBuilder<HttpResponseMessage>()
            .Handle<HttpRequestException>()
            .HandleResult(r => (int)r.StatusCode >= 500),
        OnOpened    = _ => { Console.WriteLine("🔴 Circuit MỞ"); return ValueTask.CompletedTask; },
        OnClosed    = _ => { Console.WriteLine("🟢 Circuit ĐÓNG"); return ValueTask.CompletedTask; }
    })
    .Build();
💡 Thứ tự quan trọng: trong pipeline, đặt retry BÊN NGOÀI circuit breaker (retry → circuit breaker → timeout). Như vậy circuit breaker đếm cả các lần retry thất bại, và khi mạch mở thì retry cũng fail nhanh thay vì chờ vô ích.

7. Timeout — đừng chờ vô tận

Một request treo mãi sẽ giữ thread/connection và lan sự chậm chạp ngược lên caller. Phải đặt timeout. Phân biệt rõ hai cấp:

Loại timeoutÝ nghĩa
Per-attempt (mỗi lần thử)Giới hạn thời gian cho 1 lần gọi. Hết giờ → hủy lần đó, để retry thử lại.
Total (tổng)Giới hạn cho toàn bộ thao tác (gồm tất cả lần retry). Bảo vệ caller không chờ quá lâu.
// Polly v8: kết hợp total timeout (ngoài) + per-attempt (trong) + retry
var pipeline = new ResiliencePipelineBuilder<HttpResponseMessage>()
    // 1) Tổng: cả thao tác (kèm retry) không quá 30s
    .AddTimeout(TimeSpan.FromSeconds(30))
    .AddRetry(new() { MaxRetryAttempts = 3, BackoffType = DelayBackoffType.Exponential, UseJitter = true })
    // 2) Mỗi lần thử: tối đa 10s, hết giờ thì hủy lần đó cho retry tiếp
    .AddTimeout(TimeSpan.FromSeconds(10))
    .Build();

// Timeout của Polly tự tạo CancellationToken & ném TimeoutRejectedException
var res = await pipeline.ExecuteAsync(async token => await _http.GetAsync(url, token), ct);
⚠️ Lưu ý: đừng dựa duy nhất vào HttpClient.Timeout (nó là total và ném TaskCanceledException khó phân biệt). Polly timeout strategy ném TimeoutRejectedException rõ ràng và phối hợp đúng với retry/per-attempt. Luôn truyền CancellationToken để timeout thực sự hủy được công việc bên dưới.

8. Fallback — giá trị dự phòng

Khi mọi nỗ lực (retry, circuit) đều thất bại, đôi khi tốt hơn là trả một giá trị dự phòng / response suy giảm thay vì ném lỗi cho người dùng. Ví dụ: API gợi ý sản phẩm chết → trả danh sách "phổ biến" tĩnh.

// Polly v8: fallback trả giá trị dự phòng khi pipeline thất bại
var pipeline = new ResiliencePipelineBuilder<List<Product>>()
    .AddFallback(new FallbackStrategyOptions<List<Product>>
    {
        ShouldHandle = new PredicateBuilder<List<Product>>()
            .Handle<HttpRequestException>()
            .Handle<BrokenCircuitException>()    // mạch đang mở
            .Handle<TimeoutRejectedException>(),
        FallbackAction = _ => Outcome.FromResultAsValueTask(_popularProductsCache),
        OnFallback = _ =>
        {
            _logger.LogWarning("Recommendation service down — trả danh sách phổ biến (degraded)");
            return ValueTask.CompletedTask;
        }
    })
    .AddRetry(new())
    .Build();

var products = await pipeline.ExecuteAsync(async ct => await _recoApi.GetAsync(userId, ct), ct);
💡 Fallback chỉ hợp lý khi có giá trị thay thế chấp nhận được. Đừng fallback bừa cho thao tác ghi quan trọng (vd: thanh toán) — ở đó nên fail rõ ràng. Fallback hợp với dữ liệu đọc / tính năng phụ (gợi ý, banner, thống kê).

9. Graceful Degradation — suy giảm có kiểm soát

Mục tiêu: khi một phần hệ thống hỏng, phần còn lại vẫn phục vụ được — "degraded" còn hơn "down hoàn toàn". Tập hợp kỹ thuật:

🗃️ Serve stale cache

Khi nguồn dữ liệu chết, trả bản cache cũ (stale) kèm header cảnh báo, thay vì lỗi. Người dùng thấy dữ liệu hơi cũ còn hơn trang trắng.

🧩 Partial response

Trang gồm nhiều widget: widget nào lỗi thì ẩn/hiện placeholder, các widget khác vẫn render. Không để 1 service kéo sập cả trang.

🚩 Feature flag

Tắt nhanh tính năng nặng/không ổn định (qua flag) khi hệ thống quá tải, giữ chức năng cốt lõi sống.

🧱 Bulkhead isolation

Cô lập tài nguyên (giới hạn concurrency) cho từng phụ thuộc — như vách ngăn khoang tàu. Một service chậm không nuốt hết thread pool làm chết toàn app.

// Bulkhead bằng RateLimiter (Polly v8) — giới hạn concurrency tới 1 dependency
var pipeline = new ResiliencePipelineBuilder()
    .AddConcurrencyLimiter(permitLimit: 20, queueLimit: 5) // tối đa 20 đồng thời, xếp hàng 5
    .Build();

// Serve stale: thử lấy mới, lỗi thì dùng bản cũ trong cache
try
{
    var fresh = await _api.GetRatesAsync(ct);
    _cache.Set("rates", fresh, TimeSpan.FromMinutes(5));
    return fresh;
}
catch (Exception ex) when (_cache.TryGetValue("rates", out var stale))
{
    _logger.LogWarning(ex, "Dùng tỉ giá cache cũ (degraded)");
    return (Rates)stale!; // suy giảm có kiểm soát thay vì lỗi
}
Kết hợp tất cả: một HttpClient sản xuất thường có pipeline: Timeout(total) → Retry → CircuitBreaker → Timeout(per-attempt), kèm Fallback/serve-stale ở tầng ứng dụng và ConcurrencyLimiter để cô lập. Đó chính là tinh thần của AddStandardResilienceHandler.

10. Do / Don't

❌ Catch-all rồi nuốt exception

try { await DoWork(); } catch { } // nuốt sạch — lỗi biến mất, debug địa ngục

Bắt Exception chung rồi không làm gì che giấu bug. Chỉ catch loại bạn xử lý được, và luôn log (hoặc re-throw). Để global handler lo phần còn lại.

❌ Retry mù thao tác non-idempotent

.AddRetry(...) // áp lên POST /transfer-money → có thể chuyển tiền nhiều lần!

Retry tự động chỉ an toàn với thao tác idempotent. Với ghi có hiệu ứng phụ, bắt buộc dùng idempotency key hoặc không retry.

❌ Lộ stack trace cho client ở production

return StatusCode(500, ex.ToString()); // lộ nội bộ, hỗ trợ attacker

Client chỉ nên nhận message chung + traceId. Chi tiết exception chỉ bật ở Development.

❌ Retry ngay lập tức, không backoff/jitter

.AddRetry(new() { Delay = TimeSpan.Zero }) // đập service đang chết → thundering herd

Luôn exponential backoff + jitter, và giới hạn số lần. Retry vô hạn = tự gây DDoS.

✅ Log có ngữ cảnh

logger.LogError(ex, "Đặt hàng thất bại. OrderId={OrderId}, UserId={UserId}", orderId, userId);

Log structured kèm TraceId, ID nghiệp vụ, input liên quan (không log dữ liệu nhạy cảm). Giúp truy vết & correlate.

✅ Phân biệt expected vs unexpected

return Result.Fail(...);     // lỗi nghiệp vụ
throw new DbException(...);  // sự cố hạ tầng → handler + resilience lo

Result cho lỗi đoán trước, exception cho ngoại lệ thật. Đặt resilience ở ranh giới gọi service ngoài.

🎯 Checklist Error Handling & Resilience

  • ✅ Có GlobalExceptionHandler (IExceptionHandler) + AddProblemDetails, trả ProblemDetails (RFC 7807)
  • ✅ Map từng loại exception sang status code đúng (400/401/404/409/500)
  • ✅ Không bao giờ lộ stack trace cho client ở production; có traceId để truy vết
  • ✅ Lỗi nghiệp vụ dự đoán được dùng Result<T>, không throw để control flow
  • ✅ HttpClient gọi service ngoài bật AddStandardResilienceHandler (hoặc pipeline Polly v8)
  • ✅ Retry chỉ cho lỗi transient, có exponential backoff + jitter, giới hạn số lần
  • ✅ Không retry thao tác non-idempotent nếu chưa có idempotency key
  • ✅ Có circuit breaker để fail fast khi service phụ thuộc chết
  • ✅ Đặt cả per-attempt timeout và total timeout; truyền CancellationToken xuyên suốt
  • ✅ Có fallback / serve-stale cho dữ liệu đọc & tính năng phụ (degraded còn hơn down)
  • ✅ Cô lập tài nguyên bằng concurrency limiter (bulkhead) để tránh thread starvation
  • ✅ Log structured có ngữ cảnh; không catch-all rồi nuốt exception
