System Design cho Scale

Tư duy thiết kế hệ thống phân tán: CAP theorem, load balancing, horizontal scaling, caching nhiều tầng, DB sharding & read replica, mô hình nhất quán, rate limiting, design for failure. Kết thúc bằng một bài thiết kế hoàn chỉnh: URL Shortener.

1. CAP Theorem

Trong hệ phân tán, khi có network partition (P), bạn buộc phải chọn giữa Consistency (C) và Availability (A). Không thể có cả ba cùng lúc khi mạng phân vùng.

Consistency

Mọi node đọc thấy dữ liệu mới nhất, hoặc lỗi.

Availability

Mọi request đều có phản hồi (có thể là data cũ).

Partition tolerance

Hệ vẫn chạy khi message giữa node mất/trễ.

Lựa chọnKhi partitionVí dụ
CPHy sinh availability — từ chối request để giữ nhất quánPostgreSQL (single primary), MongoDB (majority), ZooKeeper, etcd
APHy sinh consistency — trả data có thể cũ, hội tụ sauCassandra, DynamoDB, Riak (eventual consistency)
PACELC mở rộng CAP: Ngay cả khi không có partition (Else), vẫn có trade-off giữa Latency và Consistency. Đọc từ replica gần nhanh hơn nhưng có thể cũ. Thực tế thiết kế là chọn điểm trên một phổ, không phải nhị phân.

2. Load Balancing

Phân phối request tới nhiều instance. LB là cửa ngõ cho horizontal scaling và high availability.

(L4/L7)
→

App 2

Thuật toán phân phối

  • Round-robin — lần lượt từng server
  • Least connections — server ít kết nối nhất
  • Weighted — server mạnh nhận nhiều hơn
  • Consistent hashing — cùng key → cùng server (cho cache/sticky)

L4 vs L7

  • L4 (transport): route theo IP/port, nhanh, không hiểu HTTP
  • L7 (application): route theo path/header/cookie, làm TLS termination, sticky session
  • Health check loại server chết khỏi pool
💡 Stateless app + LB: Để scale ngang dễ, giữ app stateless — session/state ra ngoài (Redis, DB). Khi đó bất kỳ instance nào cũng xử lý được request, không cần sticky session.

⚠️ Scale ngang trước hết phải giải bài toán state. Session in-memory, cache local, file upload lên disk local — tất cả phá vỡ khi nhiều instance. Đẩy state ra Redis/blob storage/DB trước khi scale out.

4. Caching nhiều tầng

Cache giảm tải DB và độ trễ. Mỗi tầng đánh đổi tốc độ vs độ mới của dữ liệu.

1. Browser / Client cache — HTTP Cache-Control, ETag. Nhanh nhất, gần user nhất.
2. CDN — static asset + edge cache. Giảm latency địa lý.
3. Reverse proxy / API gateway — cache response (Varnish, Nginx).
4. Application in-memory — IMemoryCache, rất nhanh nhưng riêng từng instance.
5. Distributed cache — Redis, dùng chung cho mọi instance.
6. Database cache — query cache, buffer pool của chính DB.

Cache-Aside (lazy loading) — phổ biến nhất

public async Task<Product?> GetAsync(int id, CancellationToken ct)
{
    var key = $"product:{id}";

    // 1. Thử đọc cache
    var cached = await _cache.GetStringAsync(key, ct);
    if (cached is not null)
        return JsonSerializer.Deserialize<Product>(cached);

    // 2. Miss → đọc DB
    var product = await _db.Products.FindAsync(new object[] { id }, ct);
    if (product is null) return null;

    // 3. Ghi lại cache với TTL
    await _cache.SetStringAsync(key, JsonSerializer.Serialize(product),
        new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
        }, ct);

    return product;
}

❌ Cache stampede

Key hết hạn → nghìn request cùng miss, cùng đập DB. Fix: lock/single-flight, jitter TTL, refresh-ahead.

❌ Stale data

Quên invalidate khi update. Fix: xoá/ghi cache khi write (write-through hoặc xoá key).

❌ Cache mọi thứ

Cache data đổi liên tục → hit rate thấp, phức tạp. Chỉ cache data đọc nhiều, đổi ít.

5. Database: Read Replica & Sharding

📖 Read Replica (scale read)

Primary nhận write, replicate sang nhiều replica chỉ-đọc. Route query đọc sang replica.

Writes
→
Primary
→
Replica 1 (read)
Replica 2 (read)

Lưu ý: replication lag → replica có thể cũ vài ms-giây (eventual). Read-your-write phải đọc từ primary.

🧩 Sharding (scale write + storage)

Chia dữ liệu thành các shard theo shard key. Mỗi shard là một DB độc lập.

  • Range: theo khoảng (A-M, N-Z) — dễ hot-spot
  • Hash: hash(key) % N — đều nhưng khó re-shard
  • Consistent hashing: thêm/bớt shard ít di chuyển dữ liệu
  • Directory: bảng tra cứu key → shard
Sharding rất đắt về độ phức tạp: mất JOIN cross-shard, transaction phân tán, query fan-out, re-balancing đau đớn. Chỉ shard khi đã hết cách (replica, partition, vertical). Chọn shard key cẩn thận — sai là phải migrate toàn bộ.

7. Rate Limiting

Bảo vệ hệ thống khỏi quá tải/abuse. .NET 8+ có middleware RateLimiter built-in.

Thuật toán

  • Token bucket: bucket nạp token đều, request tiêu token — cho phép burst
  • Fixed window: N request / khoảng — đơn giản, có "boundary spike"
  • Sliding window: cửa sổ trượt, mượt hơn fixed
  • Leaky bucket: xử lý đều theo nhịp cố định

Phân tán

Nhiều instance → counter phải dùng chung (Redis) để giới hạn toàn cục, không phải per-instance. Trả 429 Too Many Requests + header Retry-After.

// Program.cs — ASP.NET Core built-in rate limiter
builder.Services.AddRateLimiter(o =>
{
    o.AddTokenBucketLimiter("api", opt =>
    {
        opt.TokenLimit = 100;             // dung lượng bucket
        opt.TokensPerPeriod = 20;          // nạp 20 token mỗi kỳ
        opt.ReplenishmentPeriod = TimeSpan.FromSeconds(1);
        opt.QueueLimit = 0;
    });
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
});

app.UseRateLimiter();
app.MapGet("/api/data", () => Results.Ok()).RequireRateLimiting("api");

8. Design for Failure

Mọi thứ sẽ hỏng. Thiết kế để hỏng có kiểm soát, không sập dây chuyền. Trên .NET dùng Polly (tích hợp Microsoft.Extensions.Http.Resilience trong .NET 8+).

🔁 Retry + backoff

Thử lại lỗi tạm thời với exponential backoff + jitter. Đừng retry lỗi 4xx.

⚡ Circuit breaker

Service downstream lỗi liên tục → "mở mạch", fail nhanh, không đập service đang chết. Cho nó thời gian hồi phục.

⏱️ Timeout

Mọi call ra ngoài phải có timeout. Không có timeout → thread treo → cạn pool → sập.

🚧 Bulkhead

Cô lập tài nguyên (pool riêng) để một phần lỗi không nuốt hết thread của cả app.

🪂 Graceful degradation

Fallback khi dependency chết: trả cache cũ, giá trị mặc định, tính năng giảm thay vì lỗi trắng.

🩺 Health check + idempotency

/health cho LB/k8s. Idempotency key để retry an toàn không tạo trùng.

// .NET 8+ resilience pipeline (Polly v8) cho HttpClient
builder.Services.AddHttpClient<PaymentClient>()
    .AddResilienceHandler("payment", b =>
    {
        b.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true
        });
        b.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,                          // 50% lỗi
            SamplingDuration = TimeSpan.FromSeconds(10),
            BreakDuration = TimeSpan.FromSeconds(15)
        });
        b.AddTimeout(TimeSpan.FromSeconds(5));
    });

9. Worked Design — URL Shortener

Áp dụng tất cả: thiết kế hệ rút gọn URL (như bit.ly) ở quy mô lớn.

Yêu cầu & ước lượng

Functional

  • POST URL dài → trả short code
  • GET /{code} → redirect 301/302
  • Tuỳ chọn: custom alias, hết hạn, analytics

Ước lượng (back-of-envelope)

  • 100M URL mới/tháng ≈ 40 write/s
  • Đọc:ghi = 100:1 → ~4000 read/s (peak cao hơn)
  • ⇒ read-heavy → ưu tiên cache + replica
  • 5 năm ≈ 6 tỷ URL → cần code đủ dài

Short code: Base62

62 ký tự (a-z A-Z 0-9). 7 ký tự = 62⁷ ≈ 3.5 nghìn tỷ — dư cho 6 tỷ. Sinh từ ID tăng dần (encode counter) thay vì hash để tránh trùng.

public static class Base62
{
    private const string Alphabet =
        "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

    public static string Encode(long id)
    {
        if (id == 0) return "0";
        var sb = new StringBuilder();
        while (id > 0)
        {
            sb.Insert(0, Alphabet[(int)(id % 62)]);
            id /= 62;
        }
        return sb.ToString();
    }
}

Kiến trúc tổng thể

Client
→
CDN + LB
→
API (stateless, N instance)
→
Redis (code→URL)
DB (primary + replica)
  1. Write: API lấy ID từ counter/snowflake → Base62 encode → lưu DB (primary) → trả short URL. Ghi cache.
  2. Read (redirect): tra Redis trước (hit rate rất cao vì read-heavy). Miss → đọc replica → nạp lại Redis → redirect 302 (để đếm được click; 301 bị cache vĩnh viễn ở browser).
  3. Scale: API stateless scale ngang sau LB. DB shard theo code khi vượt một node. Redis cluster cho cache layer.
  4. Analytics: mỗi redirect bắn event async qua message queue (không chặn redirect) → consumer ghi vào kho analytics.
  5. Resilience: Redis chết → fallback DB replica (degradation). Counter dùng nhiều range để tránh single point.
Trade-off đã chọn: Hệ này thiên về AP + eventual consistency cho phần đọc (replica lag chấp nhận được — URL mới tạo trễ vài giây mới redirect được là OK). Phần sinh code cần unique nên counter là CP. Đây là ví dụ thực tế của việc trộn nhiều mô hình theo từng phần.

🎯 Checklist System Design

  • ✅ Hiểu CAP/PACELC — chọn C hay A theo từng phần nghiệp vụ
  • ✅ App stateless để scale ngang sau load balancer
  • ✅ Caching nhiều tầng; có chiến lược invalidation + chống stampede
  • ✅ Read replica trước, sharding chỉ khi bắt buộc
  • ✅ Chọn consistency model đúng nhu cầu (strong vs eventual)
  • ✅ Rate limiting (phân tán qua Redis), trả 429 + Retry-After
  • ✅ Mọi external call có timeout + retry + circuit breaker (Polly)
  • ✅ Graceful degradation + health check + idempotency
  • ✅ Ước lượng QPS/storage trước khi chọn kiến trúc
  • ✅ Ghi rõ trade-off đã chọn — không có thiết kế "đúng tuyệt đối"
