C# Language — Viết Code Đúng Cách

C# rất mạnh, nhưng mạnh cũng đồng nghĩa với dễ dùng sai

NÊN LÀM

Dùng C# features mới — đừng viết code kiểu C# 5 mãi

C# phát triển rất nhanh, mỗi version thêm features giúp code ngắn gọn, an toàn hơn. Nhiều dev mắc kẹt ở C# cũ vì "quen rồi".

❌ Cách cũ (C# 7 trở về trước) 
// Null check verbose
if (user != null)
{
    if (user.Address != null)
    {
        var city = user.Address.City;
    }
}

// String format
var msg = string.Format("Hello {0}, age {1}", name, age);

// Pattern matching không có
if (obj is string)
{
    var s = (string)obj;
}

// Switch cũ
switch (status)
{
    case "active": return true;
    case "inactive": return false;
    default: return false;
}
✅ Cách mới (C# 10+) 
// Null conditional + null coalescing
var city = user?.Address?.City ?? "Unknown";

// String interpolation
var msg = $"Hello {name}, age {age}";

// Pattern matching
if (obj is string s)
{
    // s đã được cast
}

// Switch expression
return status switch
{
    "active" => true,
    "inactive" => false,
    _ => false
};

Đừng bỏ qua Nullable Reference Types

NullReferenceException là bug #1 mọi thời đại. C# 8+ có nullable reference types giúp compiler cảnh báo null từ lúc code.

// Bật nullable trong .csproj
<Nullable>enable</Nullable>

// Compiler cảnh báo: "user" có thể null
string GetName(User? user)
{
    return user.Name; // ⚠️ CS8602: Dereference of possibly null reference
}

// Fix: handle null explicitly
string GetName(User? user)
{
    return user?.Name ?? "Anonymous";
}

// Non-nullable = contract: "parameter này KHÔNG BAO GIỜ null"
string GetName(User user) // Caller phải đảm bảo không null
{
    return user.Name; // Safe — compiler enforce
}
💡 Tip: Bật nullable cho project MỚI ngay từ đầu. Project cũ bật dần per-file bằng #nullable enable.

Dùng record cho DTOs và Value Objects

// ❌ Cũ: DTO class 30 dòng boilerplate
public class UserDto
{
    public string Name { get; set; }
    public string Email { get; set; }
    // Equals, GetHashCode, ToString... manually?
}

// ✅ Mới: 1 dòng, có sẵn equality, ToString, deconstruction
public record UserDto(string Name, string Email);

// Immutable by default — tạo bản sao modify bằng "with"
var updated = user with { Email = "new@email.com" };

// Value equality — so sánh theo VALUE, không phải reference
var a = new UserDto("An", "an@mail.com");
var b = new UserDto("An", "an@mail.com");
Console.WriteLine(a == b); // true! (class thì false)
💡 Khi nào dùng: record cho DTO, API response, events, value objects. class cho entities có identity và mutable state.

Đừng throw Exception cho business logic

// ❌ SAI: Exception cho flow control — chậm, khó handle
public User GetUser(int id)
{
    var user = _repo.Find(id);
    if (user == null)
        throw new UserNotFoundException(id); // Exception = expensive!
}

// ✅ ĐÚNG: Result pattern — explicit success/failure
public Result<User> GetUser(int id)
{
    var user = _repo.Find(id);
    return user is null
        ? Result<User>.Fail("User not found")
        : Result<User>.Ok(user);
}

// Hoặc dùng OneOf library
public OneOf<User, NotFound> GetUser(int id) { ... }

// Caller handle explicitly — không bỏ sót
var result = service.GetUser(1);
return result.Match(
    user => Ok(user),
    error => NotFound(error.Message)
);
📏 Quy tắc: Exceptions cho EXCEPTIONAL situations (DB down, network fail). Business logic (not found, validation fail) → dùng Result pattern, FluentValidation.

BẮT BUỘC HIỂU

Bản đồ .NET — Cái nào là cái nào?

.NET Framework (1.0 → 4.8) ĐÃ CHẾT

Windows-only. Không có version mới. Chỉ security patches. ĐỪNG bắt đầu project mới với .NET Framework.

Nếu đang maintain project cũ → plan migration sang .NET 8+.

.NET Core (1.0 → 3.1) ĐÃ CHẾT

Cross-platform, nhưng đã merge vào .NET 5+. .NET Core 3.1 hết support.

.NET 5, 6, 7, 8, 9... ĐANG DÙNG

Tên chính thức bây giờ chỉ là ".NET". Cross-platform, high performance, unified platform.

  • .NET 6 — LTS, hết support 11/2024
  • .NET 7 — STS, đã hết support
  • .NET 8 — LTS ✅ NÊN DÙNG CHO PRODUCTION
  • .NET 9 — STS, latest features, cho personal/non-critical projects
📏 Quy tắc chọn version: Production = LTS version (.NET 8). Side projects = latest (.NET 9). KHÔNG BAO GIỜ bắt đầu project mới với .NET Framework hoặc .NET Core 3.1.

Đừng tạo abstraction cho mọi thứ

// ❌ Over-abstraction: IRepository wrap EF Core (đã là Repository + UoW)
public interface IRepository<T>
{
    Task<T> GetByIdAsync(int id);
    Task<List<T>> GetAllAsync();
    Task AddAsync(T entity);
    // ... y hệt DbSet<T> methods
}
// Tại sao? EF Core DbContext ĐÃ LÀ Unit of Work + Repository.
// Wrap thêm 1 layer = thêm code, không thêm value.

// ✅ Approach thực tế hơn:
// Option A: Inject DbContext trực tiếp vào Handler
public class CreateOrderHandler
{
    private readonly AppDbContext _db;
    public async Task Handle(CreateOrderCommand cmd, CancellationToken ct)
    {
        var order = new Order(cmd.ProductId, cmd.Quantity);
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
    }
}

// Option B: Repository CHỈ KHI có complex query logic cần reuse
public class OrderRepository : IOrderRepository
{
    // Chỉ methods CỤ THỂ cho business, không phải CRUD generic
    Task<List<Order>> GetPendingOrdersOlderThan(TimeSpan age);
    Task<OrderSummary> GetMonthlySummary(int year, int month);
}
📏 Hỏi trước khi tạo abstraction: "Nếu bỏ layer này đi, code có dễ hiểu hơn không?" Nếu CÓ → đừng tạo.

PHẢI NHỚ

EF Core Pitfalls — Bẫy mà ai cũng mắc

🕳️ Bẫy 1: Tracking queries khi chỉ đọc

// ❌ Mặc định EF track entities — tốn memory, chậm
var users = await _db.Users.ToListAsync();

// ✅ Chỉ đọc? Dùng AsNoTracking
var users = await _db.Users.AsNoTracking().ToListAsync();
// Hoặc global: _db.ChangeTracker.QueryTrackingBehavior = NoTracking;

🕳️ Bẫy 2: ToList() quá sớm

// ❌ Load toàn bộ table rồi filter trên C#
var result = _db.Users.ToList().Where(u => u.Age > 18);
// SQL: SELECT * FROM Users (100K rows loaded!)

// ✅ Filter trên SQL, chỉ load kết quả
var result = _db.Users.Where(u => u.Age > 18).ToList();
// SQL: SELECT * FROM Users WHERE Age > 18

🕳️ Bẫy 3: SaveChanges trong loop

// ❌ 1000 lần roundtrip đến DB
foreach (var item in items)
{
    _db.Orders.Add(new Order(item));
    await _db.SaveChangesAsync(); // 💥 1000 INSERT statements!
}

// ✅ Batch: 1 lần roundtrip
foreach (var item in items)
    _db.Orders.Add(new Order(item));
await _db.SaveChangesAsync(); // 1 transaction, batch INSERT

// ✅✅ .NET 7+: ExecuteUpdate/ExecuteDelete (bulk operations)
await _db.Orders
    .Where(o => o.Status == "expired")
    .ExecuteDeleteAsync(); // 1 DELETE statement, no loading

🕳️ Bẫy 4: Migration conflicts trong team

// Khi 2 devs tạo migration cùng lúc → conflict ModelSnapshot
// Fix: Convention trong team:
// 1. Chỉ 1 người tạo migration tại 1 thời điểm
// 2. Pull latest trước khi tạo migration
// 3. Nếu conflict: xóa migration của mình, pull, tạo lại
// 4. KHÔNG sửa migration đã pushed lên remote

Dapper + EF Core — Không phải chọn 1

// EF Core: cho CRUD, relationships, migrations, change tracking
// Dapper: cho complex queries, reports, khi cần MAX performance

// Cả 2 dùng chung connection:
public class OrderRepository
{
    private readonly AppDbContext _db;

    // CRUD đơn giản → EF Core
    public async Task AddAsync(Order order, CancellationToken ct)
    {
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
    }

    // Report phức tạp → Dapper (viết SQL thuần, nhanh hơn)
    public async Task<IEnumerable<ReportDto>> GetMonthlyReport(int year)
    {
        var conn = _db.Database.GetDbConnection();
        return await conn.QueryAsync<ReportDto>(
            @"SELECT Category, SUM(Total) as Revenue,
                     COUNT(*) as OrderCount
              FROM Orders
              WHERE YEAR(CreatedDate) = @Year
              GROUP BY Category
              ORDER BY Revenue DESC",
            new { Year = year });
    }
}

API Design — Viết API Mà Frontend Dev Yêu Quý

API là contract. Design tốt = ít meeting, ít bug, ít drama.

BEST PRACTICE

API Response Consistency — Luôn cùng 1 format

// ❌ Mỗi API trả format khác nhau = Frontend phát điên
// GET /users → [{ name: "An" }]
// GET /orders → { data: [{ id: 1 }], total: 50 }
// POST /users → { success: true, user: { ... } }
// Error → { error: "Something wrong" } hoặc plain string

// ✅ Consistent wrapper cho TẤT CẢ responses:
public class ApiResponse<T>
{
    public bool Success { get; init; }
    public T? Data { get; init; }
    public string? Message { get; init; }
    public List<string>? Errors { get; init; }
}

// Paged response:
public class PagedResponse<T> : ApiResponse<List<T>>
{
    public int Page { get; init; }
    public int PageSize { get; init; }
    public int TotalCount { get; init; }
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);
}

// Mọi API:
// Success → { success: true, data: { ... } }
// Error   → { success: false, errors: ["..."], message: "..." }
// Paged   → { success: true, data: [...], page: 1, totalCount: 100 }

Performance — Đo Trước Khi Optimize

"Premature optimization is the root of all evil" — Donald Knuth

NGUYÊN TẮC #1

Đo trước. Optimize sau. Đo lại.

1

KHÔNG optimize nếu không có vấn đề

API response 50ms? Đừng tốn 2 ngày giảm còn 30ms. Spend time đó viết tests.

2

Bottleneck 90% ở database, KHÔNG phải code C#

Trước khi optimize code → kiểm tra SQL queries. Thêm index >> refactor code.

3

Profile trước khi fix

dotTrace, BenchmarkDotNet, Application Insights, SQL Execution Plans. Đừng đoán.

4

Caching là vũ khí mạnh nhất... và nguy hiểm nhất

"There are only two hard things in CS: cache invalidation and naming things." Sai cache = stale data = bugs khó debug.

QUICK WINS

// 5. Pagination — KHÔNG BAO GIỜ trả toàn bộ data
public async Task<PagedResult<T>> GetPagedAsync(int page, int size)
{
    var query = _db.Set<T>().AsNoTracking();
    var total = await query.CountAsync();
    var items = await query.Skip((page-1) * size).Take(size).ToListAsync();
    return new PagedResult<T>(items, total, page, size);
}

Career Path — Từ Junior Đến Lead

Kiến thức kỹ thuật chỉ là 1 phần. Mindset mới quyết định.

MINDSET

Mỗi level cần gì? (Thật sự, không phải JD)

Junior (0-2 năm)
  • Viết code chạy được theo spec
  • Biết dùng framework cơ bản
  • Biết Google + Stack Overflow hiệu quả
  • Cần người review code, hướng dẫn

Focus: Viết nhiều code. Đọc nhiều code (của team). Hỏi nhiều. Đừng sợ sai.

Mid (2-5 năm)
  • Tự hoàn thành feature end-to-end
  • Biết TẠI SAO dùng pattern/tool nào đó
  • Review code cho junior
  • Debug production issues
  • Viết tests, CI/CD cơ bản

Focus: Hiểu WHY, không chỉ HOW. Đọc source code libraries. Ownership.

Senior (5+ năm)
  • Design system/architecture
  • Dự đoán vấn đề TRƯỚC khi xảy ra
  • Mentor mid/junior developers
  • Đưa ra technical decisions
  • Biết trade-offs, không cuồng tín
  • Nói "KHÔNG" khi cần

Focus: Impact. Multiply team's output. Simplify complexity.

Tech Lead
  • 50% code, 50% people/process
  • Shield team khỏi noise bên ngoài
  • Technical estimation + planning
  • Hiring, 1-on-1, career development
  • Architecture decisions + ADRs
  • Production incidents: calm + systematic

Focus: Team success > individual output. Your code IS the team's code quality.

Làm Lead — Bài Học Sống Còn

Chuyển từ "giỏi nhất team" sang "làm team giỏi nhất"

MINDSET SHIFT

Lead ≠ Dev giỏi nhất. Lead = người làm team giỏi lên.

Dev: "Mình code nhanh nhất"
→
Lead: "Team ship nhanh nhất"
Dev: "Mình fix bug này"
→
Lead: "Tại sao bug này xảy ra? Làm sao prevent?"
Dev: "Code mình clean nhất"
→
Lead: "Coding standards cho team đã có chưa?"
Dev: "Mình biết cách giải quyết"
→
Lead: "Ai trong team phù hợp nhất để giải quyết?"
NÊN LÀM

Code Review — Cách review đúng

✅ NÊN

  • Focus vào logic & design, không nitpick formatting (dùng linter)
  • Giải thích TẠI SAO suggest thay đổi, không chỉ nói "sai"
  • Khen code tốt — "Nice approach!" tăng morale
  • Dùng "Nit:" prefix cho minor suggestions (không block merge)
  • Review trong < 24h — don't be bottleneck
  • Dùng PR template với checklist

❌ ĐỪNG

  • "Sai rồi, sửa lại đi" — không giải thích
  • Rewrite nguyên PR theo style mình — đó là gatekeeping
  • Review 2000 lines trong 1 PR — yêu cầu split
  • Comment mỉa mai / passive-aggressive
  • Block merge vì style preference
  • Để PR pending 3 ngày mới review
PHẢI LÀM

Technical Standards — Set up NGAY khi nhận team

1

.editorconfig + Code Analyzers

Enforce coding style tự động. Không ai tranh cãi tabs vs spaces nữa.

2

PR Template + Branch naming

feature/ABC-123-add-order-api, fix/ABC-456-null-exception. PR description phải có: What, Why, How to test.

3

CI Pipeline chạy tự động

Build → Tests → Code Analysis trên MỌI PR. Fail = không merge. Không exceptions.

4

Architecture Decision Records (ADRs)

Mỗi decision quan trọng: WHY chọn X over Y. 6 tháng sau không ai nhớ tại sao chọn RabbitMQ thay vì Kafka.

5

Documentation = code comments + README + ADR

KHÔNG viết novel. Chỉ document: WHY (không phải WHAT), architecture overview, onboarding guide, API docs (Swagger).

SỰ THẬT

Production Incident — 2h sáng, server down

00:00

Alert fires → Stay calm

Panic = sai lầm thêm. Hít thở. Mở runbook. Communicate: "Tôi đang xem, update 15 phút."

00:05

Triage: Impact? Scope?

Bao nhiêu users affected? Partial hay total outage? Revenue impact?

00:15

Mitigate first, root cause later

Rollback deploy? Scale up? Toggle feature flag? FIX SYMPTOMS TRƯỚC. Tìm root cause KHI ĐÃ STABLE.

Next day

Blameless Post-mortem

Timeline + Root cause + Action items. KHÔNG blame cá nhân. "Hệ thống cho phép deploy broken code" chứ không phải "An deploy sai".

📏 Rule of thumb: Nếu 1 người có thể gây sập hệ thống → đó là lỗi của HỆ THỐNG (thiếu review, thiếu tests, thiếu safeguards), không phải lỗi của NGƯỜI.
