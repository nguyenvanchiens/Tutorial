Tư Duy Nền Tảng — Trước Khi Bắt Đầu Mọi Thứ

Kỹ thuật có thể học, nhưng tư duy quyết định bạn đi được bao xa

⭐

Bạn không cần biết hết — bạn cần biết cách tìm

Không ai nhớ hết mọi thứ. Senior developers giỏi không phải vì biết hết API — mà vì biết cách tìm, cách đọc docs, cách debug. Đầu tư vào khả năng tự giải quyết vấn đề, không phải khả năng thuộc lòng.

"The best developers I know Google things every day. The difference is they know WHAT to Google." — Staff Engineer tại Shopify
🔄

Học sâu 1 thứ tốt hơn biết sơ 10 thứ

Pareto 80/20: 20% kiến thức giải quyết 80% vấn đề. Thay vì chạy theo mọi framework mới, hãy master C#, hiểu sâu .NET runtime, nắm chắc SQL. Nền tảng vững thì học gì cũng nhanh.

Hành động: Chọn 1 topic, đào sâu đến khi có thể giải thích cho người khác hiểu.
📐

Code hoạt động ≠ Code tốt

"It works" chỉ là bước đầu. Code tốt = dễ đọc, dễ test, dễ thay đổi. Bạn viết code 1 lần nhưng người khác (và bạn tương lai) đọc nó 100 lần. Viết cho người đọc, không phải cho compiler.

"Any fool can write code that a computer can understand. Good programmers write code that humans can understand." — Martin Fowler
🏗️

Hiểu WHY quan trọng hơn HOW

Biết dùng Entity Framework là HOW. Hiểu tại sao cần ORM, khi nào KHÔNG nên dùng ORM — đó là WHY. WHY giúp bạn đưa ra quyết định đúng khi gặp tình huống mới mà tutorial không dạy.

Hành động: Mỗi khi học tool/pattern mới, tự hỏi: "Nó giải quyết vấn đề gì? Có alternative nào? Trade-offs?"
🎯

Consistency beats intensity

Học 1 giờ/ngày mỗi ngày > học 10 giờ cuối tuần rồi nghỉ 2 tuần. Não bộ cần thời gian consolidate kiến thức. Compound effect: 1% tốt hơn mỗi ngày = 37x tốt hơn sau 1 năm.

Hành động: Đặt lịch cố định mỗi ngày, dù chỉ 30 phút code/đọc. Không cần motivation — cần discipline.
🚀

5 Giai Đoạn Sự Nghiệp — Mỗi Giai Đoạn Cần Gì

Biết mình đang ở đâu, biết cần làm gì tiếp theo — đó là lợi thế lớn nhất

GIAI ĐOẠN 1

Fresher (0-1 năm)

"Xây móng thật chắc — đừng vội lên cao"

📚 Nên học gì

  • C# fundamentals — value/reference types, OOP thật kỹ, collections, LINQ cơ bản
  • SQL cơ bản — SELECT, JOIN, WHERE, GROUP BY. Viết tay, không dùng tool generate
  • Git — commit, branch, merge, resolve conflict. Dùng command line, đừng chỉ dùng GUI
  • HTTP & REST — status codes, GET/POST/PUT/DELETE, request/response lifecycle
  • 1 project hoàn chỉnh — từ database đến API đến deploy. Nhỏ nhưng XONG.

✅ Nên làm gì

  • Code mỗi ngày — dù chỉ 30 phút. Giải LeetCode easy, làm mini projects
  • Đọc code người khác — open source projects, xem cách senior viết
  • Viết blog/note — giải thích lại những gì đã học bằng lời của mình
  • Đừng sợ sai — break things, debug, learn. Sai ở giai đoạn này là rẻ nhất
  • Tìm mentor — 1 người guide đúng hướng = tiết kiệm hàng năm trời

⚠️ Đừng làm gì

  • Đừng học nhiều framework cùng lúc — master 1 cái trước (ASP.NET Core)
  • Đừng copy-paste không hiểu — nếu paste từ StackOverflow, phải hiểu TỪNG DÒNG
  • Đừng so sánh với người khác — mỗi người có tốc độ riêng
  • Đừng bỏ qua fundamentals — đừng nhảy vào microservices khi chưa vững OOP
Dấu hiệu sẵn sàng lên Junior: Tự build được CRUD API với EF Core, hiểu DI container, biết viết unit test cơ bản, tự debug được lỗi thường gặp mà không cần hỏi.
GIAI ĐOẠN 2

Junior Developer (1-3 năm)

"Học cách viết code mà người khác muốn đọc"

📚 Nên học gì

  • ASP.NET Core sâu — middleware pipeline, DI lifetimes, configuration, logging
  • EF Core nâng cao — migrations, tracking, query optimization, N+1 problem
  • Unit Testing — xUnit, Moq, test doubles. Viết test TRƯỚC khi fix bug
  • Design Patterns cơ bản — Repository, Strategy, Factory, Observer. Hiểu KHI NÀO dùng
  • Docker cơ bản — Dockerfile, docker-compose. Containerize được app của mình
  • Clean Code — đọc sách Uncle Bob, áp dụng ngay vào code hàng ngày

✅ Nên làm gì

  • Code review tích cực — review code người khác, học từ feedback nhận được
  • Viết documentation — README, API docs. Nếu bạn rời team, người mới có hiểu không?
  • Xây side projects có chiều sâu — không phải TODO app. Build cái gì có auth, caching, background jobs
  • Tham gia community — meetup, online forums, contribute open source (dù nhỏ)
  • Học cách estimate — task này mất bao lâu? Tập estimate rồi so sánh thực tế

⚠️ Đừng làm gì

  • Đừng over-engineer — YAGNI. Đừng build "framework" cho 1 feature đơn giản
  • Đừng làm việc im lặng — stuck 2 giờ? Hỏi. Đừng để stuck cả ngày vì sĩ diện
  • Đừng chỉ biết code — hiểu business context, tại sao feature này cần?
  • Đừng ignore tech debt — ghi lại, propose fix. Đừng chỉ nói "tôi biết code xấu"
Dấu hiệu sẵn sàng lên Mid: Tự hoàn thành feature end-to-end không cần guidance, code review comments giảm dần, bắt đầu có ý kiến về architecture, team members hỏi bạn kỹ thuật.
GIAI ĐOẠN 3

Mid-Level Developer (3-5 năm)

"Không chỉ giải quyết vấn đề — mà giải quyết ĐÚNG vấn đề"

📚 Nên học gì

  • System Design — caching strategies, load balancing, message queues, database scaling
  • Architecture Patterns — Clean Architecture, CQRS, Event Sourcing. Hiểu trade-offs, không cargo cult
  • Security — OWASP Top 10, JWT/OAuth2, encryption, input validation
  • Performance — profiling, benchmarking, memory management, async patterns
  • CI/CD — build pipelines, automated testing, deployment strategies
  • Cloud basics — Azure/AWS core services, IaC concepts

✅ Nên làm gì

  • Own toàn bộ feature — từ design → implement → test → deploy → monitor
  • Viết RFC/Technical proposals — đề xuất giải pháp, document decision rationale
  • Mentor junior — dạy người khác là cách học tốt nhất cho chính mình
  • Tham gia on-call — hiểu production, biết cảm giác khi alert 3h sáng
  • Đọc case studies — Netflix, Uber, Shopify tech blogs. Học cách họ solve problems at scale
  • Build portfolio kỹ thuật — blog, talks, open source contributions

⚠️ Đừng làm gì

  • Đừng "resume-driven development" — chọn tech vì CV, không vì phù hợp project
  • Đừng sợ production — production problems = learning goldmine
  • Đừng chỉ là "coder" — hiểu metrics, KPIs, business impact
  • Đừng toxic về tech choices — "X tệ, Y mới tốt" → thay bằng "X phù hợp khi..., Y phù hợp khi..."
Dấu hiệu sẵn sàng lên Senior: Team tin tưởng giao bạn technical decisions, bạn có ý kiến có weight trong architecture discussions, bạn identify problems trước khi chúng xảy ra, juniors tìm bạn khi stuck.
GIAI ĐOẠN 4

Senior Developer (5-8 năm)

"Multiply your impact — make everyone around you better"

📚 Nên học gì

  • Distributed Systems — CAP theorem, eventual consistency, saga pattern, event-driven architecture
  • Observability — structured logging, distributed tracing, metrics, alerting strategies
  • Advanced .NET — runtime internals, GC tuning, Span<T>, source generators, AOT
  • Cross-domain knowledge — networking, OS, databases internals. Deep fundamentals
  • Tech strategy — build vs buy, migration planning, tech debt prioritization

✅ Nên làm gì

  • Lead by influence — không cần title. Đưa ra technical direction qua proposals, demos, evidence
  • Write Architecture Decision Records (ADR) — document WHY, không chỉ WHAT
  • Build internal tools & libraries — multiply productivity cho cả team
  • Cross-team collaboration — hiểu systems beyond your team, find integration points
  • Invest in people — 1 giờ mentor junior = tiết kiệm hàng chục giờ cho team
  • Speak at meetups/conferences — teaching solidifies knowledge, builds network

⚠️ Đừng làm gì

  • Đừng hoarding knowledge — share mọi thứ. Bus factor = 1 là nguy hiểm
  • Đừng làm hero — nếu bạn là người duy nhất fix production → team có vấn đề
  • Đừng dismiss junior ideas — fresh eyes thấy things bạn đã blind spot
  • Đừng stop coding — Senior vẫn phải code. Mất touch = mất credibility
Dấu hiệu sẵn sàng lên Lead: Bạn đã define technical direction cho 1+ projects lớn, team members grow visibly dưới sự guidance của bạn, stakeholders tìm bạn cho technical opinions, bạn biết khi nào KHÔNG code mà nên delegate.
GIAI ĐOẠN 5

Tech Lead / Architect (7+ năm)

"Your code is your team's output — your impact is measured in people"

📚 Nên học gì

  • System thinking — how components interact, failure cascades, emergent behaviors
  • Organization design — Conway's Law, team topologies, platform engineering
  • Product thinking — user needs, business metrics, ROI of technical decisions
  • Communication & negotiation — stakeholder management, technical writing, presentations
  • Financial awareness — cloud costs, build vs buy TCO, headcount planning

✅ Nên làm gì

  • Define technical vision — 6-12 months roadmap, alignment với business goals
  • Build engineering culture — code review standards, blameless postmortems, learning budget
  • Remove blockers — 80% job là unblock team. Meetings, decisions, resources
  • Hire & develop talent — interview, onboard, career development plans
  • Balance tech debt vs features — negotiate 20-30% capacity cho technical health
  • Stay technical — vẫn code 30-40% time, review critical PRs, prototype new approaches

⚠️ Đừng làm gì

  • Đừng micromanage — trust team. Set direction, not instructions
  • Đừng optimize cho bản thân — optimize cho team throughput
  • Đừng avoid difficult conversations — performance issues, tech direction disagreements
  • Đừng quên IC track — không phải ai cũng muốn/nên manage. Respect that
Dấu hiệu thành công: Team deliver consistently, members grow và get promoted, technical quality tăng, bạn có thể đi vacation 2 tuần mà team vẫn chạy tốt. Đó là leading.
📖

Cách Học Hiệu Quả — Không Phải Cứ Học Nhiều Là Giỏi

Phương pháp học quyết định 80% kết quả. Học sai cách = lãng phí thời gian

01

Active Recall > Passive Reading

Đọc xong = quên 80% sau 1 ngày. Thay vì đọc lại, hãy tự kiểm tra: đóng tài liệu, viết lại những gì nhớ được. Đau đớn hơn nhưng hiệu quả gấp 3 lần.

Áp dụng: Sau mỗi chapter/bài học, đóng laptop, lấy giấy viết lại 3 điểm chính. Nếu không viết được → chưa hiểu.
02

Spaced Repetition — Ôn đúng lúc sắp quên

Não bộ quên theo đường cong (Ebbinghaus). Ôn lại sau 1 ngày, 3 ngày, 7 ngày, 30 ngày — mỗi lần ôn, ký ức mạnh hơn. Dùng flashcards (Anki) cho concepts quan trọng.

Áp dụng: Tạo Anki deck cho: design patterns, SQL queries, C# gotchas. Review 10 phút mỗi sáng.
03

Feynman Technique — Dạy để hiểu

Nếu không giải thích được cho người không biết gì hiểu → bạn chưa thực sự hiểu. Viết blog, giải thích cho đồng nghiệp, rubber duck debugging — dạy là cách học mạnh nhất.

Áp dụng: Mỗi tuần chọn 1 concept, viết giải thích trong 5 phút không nhìn tài liệu. Chỗ nào bí = chỗ cần học lại.
04

Project-Based Learning — Học bằng cách xây

Tutorial hell = xem 100 videos mà không build được gì. Bắt đầu project TRƯỚC khi "đủ kiến thức". Gặp vấn đề → tìm giải pháp → học sâu hơn bất kỳ tutorial nào.

Áp dụng: Chọn project hơi vượt khả năng hiện tại 20%. Đủ khó để challenge, không quá khó để bỏ cuộc.
05

Deliberate Practice — Luyện điểm yếu, không phải điểm mạnh

Viết CRUD 100 lần không giúp giỏi hơn. Tìm điểm yếu → luyện tập có chủ đích. Sợ SQL? Giải 20 bài SQL. Yếu async? Viết 5 ứng dụng async. Uncomfortable = growth.

Áp dụng: List 3 điểm yếu kỹ thuật lớn nhất. Mỗi tháng focus 1 điểm yếu, dành 70% thời gian học cho nó.
06

Read Source Code — Đọc code giỏi hơn đọc docs

Muốn hiểu ASP.NET Core thật sự? Đọc source code trên GitHub. Xem cách Microsoft implement middleware, DI container, routing. Real code > documentation > tutorials.

Áp dụng: Mỗi tuần đọc 1 file source code từ dotnet/aspnetcore hoặc dotnet/runtime. Bắt đầu từ class nhỏ, quen dần.

Kỹ Năng Cần Tích Lũy — Compound Interest Của Developer

Một số kỹ năng tăng giá trị theo thời gian — đầu tư sớm, hưởng lợi cả sự nghiệp

🔍

Debugging & Problem Solving

Kỹ năng #1 mà không trường nào dạy đủ. Đọc error message kỹ, reproduce bug consistently, binary search để narrow down, đọc logs có hệ thống. Debug giỏi = productivity x3.

Thời điểm đầu tư:
Ngay từ đầu — càng sớm càng tốt
✍️

Technical Writing

Code tồn tại vài năm, docs tồn tại lâu hơn. README rõ ràng, commit messages có ý nghĩa, PR descriptions đầy đủ, ADR cho decisions lớn. Dev viết tốt = dev được trọng dụng.

Thời điểm đầu tư:
Từ Junior — bắt đầu viết blog
🏛️

System Design Thinking

Không phải "lên Senior mới cần". Bắt đầu nghĩ: tại sao dùng caching ở đây? Tại sao tách service này? Tư duy hệ thống tích lũy dần, không thể học 1 lần là hiểu.

Thời điểm đầu tư:
Từ Mid — khi đã vững fundamentals
🤝

Networking & Community

80% cơ hội tốt nhất đến từ network, không từ job boards. Đi meetup, contribute open source, viết blog, giúp đỡ trên forums. Mỗi connection = 1 cánh cửa tương lai.

Thời điểm đầu tư:
Ngay từ đầu — đừng đợi "đủ giỏi"
🛡️

Security Mindset

Security không phải afterthought. Mọi input là untrusted, mọi data cần encrypted, mọi endpoint cần auth. 1 security incident = reputation damage không thể undo.

Thời điểm đầu tư:
Từ Junior — OWASP Top 10 là bắt buộc
📊

Data & Metrics Literacy

Nói "app chậm" không đủ. p99 latency là bao nhiêu? Error rate %? Throughput RPS? Decisions dựa trên data = respected. Decisions dựa trên cảm giác = ignored.

Thời điểm đầu tư:
Từ Mid — khi bắt đầu own production
💥

Sai Lầm Phổ Biến — Những Bẫy Mà Ai Cũng Từng Dính

Học từ sai lầm của người khác rẻ hơn rất nhiều so với tự mắc

01

Tutorial Hell — Xem mà không làm

Xem 50 videos về React, ASP.NET, Docker... nhưng không build được gì thực tế. Cảm giác "hiểu" khi xem ≠ thực sự biết làm. Illusion of competence.

Fix: Quy tắc 1:3 — mỗi 1 giờ xem tutorial, code 3 giờ. Hoặc tốt hơn: bắt đầu project → gặp vấn đề → tìm tutorial CỤ THỂ.
02

Shiny Object Syndrome — Chạy theo mọi công nghệ mới

Tuần này Blazor, tuần sau gRPC, tuần sau nữa Kubernetes... không master được gì cả. Kết quả: biết tên 20 technologies nhưng không viết được production code với bất kỳ cái nào.

Fix: Chọn 1 stack, dùng nó build 3 projects từ đầu đến cuối. Rồi mới mở rộng. Depth first, breadth later.
03

Sĩ diện kỹ thuật — Không dám hỏi, không dám nói "tôi không biết"

Sợ bị đánh giá thấp nên giả vờ hiểu, tự mò cả ngày thay vì hỏi 5 phút. Mọi senior đều từng là người không biết gì. Hỏi thông minh = tín hiệu của sự trưởng thành, không phải yếu kém.

Fix: Format hỏi: "Tôi đã thử X và Y, kết quả là Z. Tôi nghĩ vấn đề ở A. Bạn thấy sao?" — Hỏi có context = được tôn trọng.
04

Chỉ focus code, bỏ qua soft skills

"Tôi chỉ cần code giỏi" — sai. Từ Mid trở lên, communication, negotiation, leadership chiếm 50%+ giá trị. Dev code giỏi nhưng không communicate được → luôn bị stuck ở Junior/Mid.

Fix: Mỗi tuần practice: present 1 idea trong meeting, viết 1 email/message rõ ràng, give 1 constructive feedback.
05

Nhảy việc vì lương, không vì growth

Tăng lương 20% nhưng vào công ty không learn được gì → 2 năm sau vẫn same level. Ở giai đoạn đầu, learning rate > salary. 1 năm ở team có senior giỏi = 3 năm tự mò.

Fix: Hỏi khi phỏng vấn: "Team có bao nhiêu senior? Code review process? On-call? Tech stack decisions ai quyết?" — Đó là signals của learning environment.
06

Không track progress — Cảm giác "không tiến bộ"

Làm 2 năm, cảm giác vẫn "bình thường". Thật ra đã tốt hơn rất nhiều nhưng không nhận ra vì không có benchmark. Dẫn đến demotivation.

Fix: Mỗi 3 tháng viết "brag document": tôi đã ship gì, learn gì, solve problem gì, help ai. Review cuối năm sẽ cảm ơn mình.
🗣️

Soft Skills — Kỹ Năng Quyết Định Mức Lương Và Thăng Tiến

Technical skills mở cửa, soft skills quyết định bạn đi bao xa

🎯 Communication

Viết rõ ràng: Email, Slack, PR description — nói đủ ý trong ít chữ nhất. Đừng viết essay, đừng viết 1 dòng.

Nói có cấu trúc: "Vấn đề là X. Tôi đề xuất Y. Vì Z." — 3 câu, rõ ràng, actionable.

Listen actively: Repeat back: "Nếu tôi hiểu đúng, bạn muốn..." — tránh 90% miscommunication.

Bắt đầu practice từ: Fresher

⏰ Time Management

Estimate thực tế: Nhân estimate ban đầu x1.5 (buffer cho unknowns, meetings, bugs). Deliver sớm > deliver trễ.

Prioritize ruthlessly: Eisenhower matrix — Urgent + Important → làm ngay. Important + Not urgent → schedule. Urgent + Not important → delegate.

Deep work blocks: 2-3 giờ không meetings, không Slack. Code quality tăng x2 trong focused sessions.

Bắt đầu practice từ: Junior

🤝 Collaboration

Code review = teaching: "Tại sao không thử X?" tốt hơn "Code này sai". Build up, đừng tear down.

Disagree respectfully: "Tôi thấy approach khác có thể..." tốt hơn "Cách này sai".

Share credit: "Team đã..." thay vì "Tôi đã...". Leaders share credit, take blame.

Bắt đầu practice từ: Junior

📢 Managing Up

Proactive updates: Đừng đợi manager hỏi "xong chưa?". Weekly update: Done, In progress, Blocked, Next week.

Raise issues early: "Tôi thấy risk X, propose mitigation Y" — managers ghét surprises.

Speak business language: "Feature này giảm 30% support tickets" > "Tôi refactor cái service".

Bắt đầu practice từ: Mid
☠️

Lời Khuyên Sống Còn — Backend Dev Phải Khắc Cốt Ghi Tâm

Những bài học mà nếu không biết sớm, bạn SẼ trả giá bằng incident, data loss, và đêm không ngủ

☠️ MỨC CHẾT NGƯỜI

Không bao giờ tin user input — KHÔNG BAO GIỜ

Mọi thứ từ client đều có thể bị giả mạo: form data, headers, cookies, query params, JWT claims. Validate ở server. Sanitize trước khi lưu DB. Escape trước khi render. Quên 1 chỗ = SQL Injection, XSS, hoặc tệ hơn.

Thực tế: Năm 2024, một startup mất toàn bộ DB vì dev tin tưởng input từ mobile app gửi lên — attacker dùng Postman bypass app, inject SQL trực tiếp. Zero validation ở backend.
Quy tắc: Treat every request like it comes from an attacker — because someday, it will.
☠️ MỨC CHẾT NGƯỜI

Database LUÔN là bottleneck — hãy bảo vệ nó

App server scale ngang dễ (thêm instance). Database thì KHÔNG. Mỗi query bạn viết đều ảnh hưởng production. N+1 query, missing index, full table scan — lúc dev chạy ngon, production 10K users thì chết.

Checklist trước khi ship:
  • Mọi WHERE/JOIN column có index chưa?
  • Có N+1 query không? (EF Core: dùng .Include(), check generated SQL)
  • SELECT chỉ lấy column cần, đừng SELECT *
  • Pagination cho mọi endpoint trả list
  • Query lớn có timeout chưa? (CommandTimeout)
☠️ MỨC CHẾT NGƯỜI

Log ĐÚNG CÁCH — không có log = mù trong production

Bug trong production mà không có log = bạn chỉ có thể "đoán". Structured logging (Serilog) + Correlation ID + đúng log level = debug production chỉ mất 5 phút thay vì 5 giờ.

Log gì: Request/Response (trừ sensitive data), External API calls, Business events, Errors + stack trace, Performance (query time > 500ms)
KHÔNG log: Passwords, tokens, credit cards, PII (Personally Identifiable Information)
Quy tắc: Nếu bạn phải debug 1 bug lúc 3h sáng mà chỉ có log — log đó có đủ thông tin không?
⚠️ MỨC NGUY HIỂM

Idempotency — User bấm 2 lần, hệ thống chỉ xử lý 1 lần

Network timeout → client retry → backend xử lý 2 lần → user bị charge tiền 2 lần, đơn hàng tạo 2 cái, email gửi 2 lần. Đây là bug classic mà dev nào cũng mắc ít nhất 1 lần.

Cách phòng tránh:
  • API tạo resource: dùng Idempotency Key (client gửi unique key, server check trùng)
  • Payment: luôn kiểm tra trạng thái trước khi charge
  • Email/Notification: dedup bằng message ID
  • Database: dùng UNIQUE constraint + upsert thay vì insert blind
⚠️ MỨC NGUY HIỂM

Không deploy chiều thứ 6 — và luôn có rollback plan

Deploy chiều thứ 6 = bug phát hiện lúc cuối tuần = không ai fix = Monday disaster. Mọi deployment đều có thể fail. Câu hỏi không phải "có fail không?" mà là "khi fail thì rollback thế nào?"

Deployment checklist:
  • Database migration có backward compatible không? (rollback code cũ vẫn chạy)
  • Có feature flag không? (tắt feature mà không cần redeploy)
  • Health check endpoint hoạt động?
  • Rollback procedure documented + tested?
  • Monitoring alerts đã setup cho key metrics?
⚠️ MỨC NGUY HIỂM

Race condition — Kẻ giết người thầm lặng

2 requests đến cùng lúc, cùng đọc balance = 100, cùng trừ 80, cùng lưu = 20. Thực tế phải là -60 (âm). Race condition không crash, không log error, không alert — chỉ data sai âm thầm. Phát hiện khi đã quá muộn.

Giải pháp theo context:
• Database: Optimistic Concurrency (RowVersion/ETag) hoặc Pessimistic Locking (SELECT FOR UPDATE)
• Application: Distributed Lock (Redis lock) cho critical section
• Message Queue: Exactly-once processing hoặc idempotent consumer
• Atomic operations: UPDATE accounts SET balance = balance - @amount WHERE balance >= @amount
⚠️ MỨC NGUY HIỂM

Connection pool & Timeout — bỏ qua = production sập

Default connection pool = 100. Default HTTP timeout = ∞ (hoặc rất dài). 1 downstream service chậm → thread bị giữ → pool hết → toàn bộ app đứng. Cascading failure kinh điển.

Phải config:
  • DB Connection Pool: set Max Pool Size phù hợp, monitor Active connections
  • HTTP Client: LUÔN set timeout (5-30s). Dùng IHttpClientFactory, KHÔNG new HttpClient()
  • Circuit Breaker: Polly library — nếu service lỗi 5 lần liên tiếp → ngắt, không gọi tiếp
  • Retry với Exponential Backoff: retry 1s → 2s → 4s, không phải retry ngay lập tức
💡 MỨC QUAN TRỌNG

Cache invalidation — 1 trong 2 bài toán khó nhất CS

"There are only two hard things in CS: cache invalidation and naming things." Cache sai = user thấy data cũ, data người khác, hoặc data không tồn tại. Nhẹ thì UX tệ, nặng thì data corruption.

Nguyên tắc caching:
• Cache data đọc nhiều, ghi ít (product catalog, config, lookup tables)
• Luôn set TTL (Time-To-Live) — không có cache nào nên sống mãi
• Cache-aside pattern: read cache → miss → read DB → write cache → return
• Invalidate cache khi data thay đổi, không đợi TTL hết
• Stampede protection: khi cache expire, chỉ 1 request rebuild cache, còn lại đợi
💡 MỨC QUAN TRỌNG

Distributed Systems — Mọi thứ đều có thể fail

Network bị delay, packet bị mất, server bị restart, clock bị lệch. Trong distributed system, "luôn hoạt động" là ảo tưởng. Design cho failure, không phải cho success.

8 Fallacies of Distributed Computing (phải thuộc):
  • Network KHÔNG reliable — request có thể mất, duplicate, hoặc đến sai thứ tự
  • Latency KHÔNG bằng 0 — gọi service khác = thêm 10-500ms
  • Bandwidth KHÔNG vô hạn — đừng truyền toàn bộ object khi chỉ cần 2 fields
  • Network KHÔNG an toàn — mã hóa mọi thứ, verify mọi token
Quy tắc: Nếu service B down, service A vẫn phải hoạt động (graceful degradation). Nếu không thể — phải timeout + trả lỗi rõ ràng, KHÔNG treo vô hạn.
💡 MỨC QUAN TRỌNG

Monitoring & Alerting — Phải biết trước khi user báo

Không monitor = bạn chỉ biết production lỗi khi user gọi support. Lúc đó đã muộn. 4 Golden Signals: Latency, Traffic, Errors, Saturation — monitor 4 cái này là đủ 90%.

Minimum monitoring:
  • Health check: /health endpoint kiểm tra DB, cache, dependencies
  • Error rate: alert khi > 1% requests lỗi
  • Response time: alert khi p95 > 2 giây
  • Resource: CPU > 80%, Memory > 85%, Disk > 90%
  • Business metrics: đơn hàng/phút đột ngột = 0? Có vấn đề!
💡 MỨC QUAN TRỌNG

Database Migration — Sai 1 bước, mất data thật

Migration trên production không giống development. Table 50 triệu rows + ALTER TABLE = lock table 30 phút = app đứng 30 phút. Và DROP COLUMN là không thể undo.

Migration an toàn:
  • Luôn backward compatible: deploy code mới → chạy migration → cleanup code cũ (3 bước, không phải 1)
  • KHÔNG DROP COLUMN ngay: bước 1: stop đọc/ghi column → bước 2: deploy → bước 3: DROP sau vài ngày
  • Large table: dùng online migration tools (pt-online-schema-change, gh-ost)
  • BACKUP trước MỌI migration: không exception, không "chắc không sao đâu"
  • Test migration trên bản copy production data: không phải trên empty dev DB
📘 MỨC NÊN BIẾT

API Design — Contract giữa bạn và cả thế giới

API published = lời hứa. Thay đổi API = break tất cả client đang dùng. Frontend, mobile app, partners — tất cả đều depend on API contract của bạn. Sai từ đầu = đau mãi mãi.

API Design Rules:
• Versioning từ ngày 1: /api/v1/products — luôn có version
• Consistent naming: camelCase JSON, plural nouns, meaningful HTTP status codes
• Pagination: KHÔNG BAO GIỜ trả list không limit — ?page=1&size=20
• Error format chuẩn: { "error": "...", "code": "...", "details": [...] }
• Breaking changes: thêm field = OK, xóa/đổi field = BREAKING → phải version mới
📘 MỨC NÊN BIẾT

Secret Management — 1 connection string lộ = game over

Connection string, API key, JWT secret commit lên GitHub = bots scan và exploit trong vòng 30 giây. Đây không phải nói quá — có bots chuyên monitor GitHub public repos 24/7.

Quy tắc tuyệt đối:
  • KHÔNG BAO GIỜ hardcode secrets trong code
  • .gitignore: appsettings.Development.json, .env, *.pfx
  • Environment variables cho deployment, User Secrets cho dev local
  • Key Vault (Azure) hoặc Secrets Manager (AWS) cho production
  • Rotate secrets định kỳ — nếu nghi bị lộ, rotate NGAY LẬP TỨC
📘 MỨC NÊN BIẾT

Async & Background Jobs — Không phải cái gì cũng cần response ngay

Gửi email, generate report, resize image — KHÔNG nên làm trong HTTP request. User đợi 30 giây để nhận response "Email đã gửi" = UX tệ + timeout risk + retry disaster.

Pattern đúng:
• API nhận request → validate → đẩy vào message queue → return 202 Accepted ngay
• Background worker đọc queue → xử lý → update status
• Client poll status hoặc nhận webhook/SignalR notification

Tools .NET: Hangfire (simple), MassTransit + RabbitMQ (robust), Azure Service Bus (cloud)
📘 MỨC NÊN BIẾT

Production ≠ Development — Config khác, data khác, scale khác

"Máy tôi chạy được" — câu nói kinh điển nhất ngành. Dev có 10 records, production có 10 triệu. Dev có 1 user, production có 10K concurrent. Mọi assumption đều sai khi lên production.

Bridge the gap:
  • Staging environment: giống production nhất có thể (same config, similar data volume)
  • Load testing: trước khi ship feature mới, chạy k6/Artillery với traffic giả
  • Canary deployment: deploy cho 5% users trước → monitor → 100%
  • Feature flags: tắt/bật feature mà không cần redeploy
  • Observability: logs + metrics + traces — 3 pillars, thiếu 1 = thiếu hết

12 Quy Tắc Vàng — Ghi Nhớ Suốt Sự Nghiệp

Nếu chỉ nhớ được 12 điều, hãy nhớ những điều này

01

Fundamentals > Frameworks

Frameworks đến rồi đi. C#, SQL, HTTP, networking, data structures — ở lại mãi mãi. Đầu tư vào nền tảng.

02

Done > Perfect

"Ship it" beats "perfect it". 80% solution today > 100% solution next month. Iterate, don't overthink.

03

Read more code than you write

Ratio nên là 10:1. Đọc open source, đọc code đồng nghiệp, đọc code chính mình viết 6 tháng trước. Rút kinh nghiệm.

04

Invest in tools mastery

IDE shortcuts, Git commands, CLI tools, debugging tools. 10 phút/ngày luyện tools = tiết kiệm 1000+ giờ trong sự nghiệp.

05

Automate the boring stuff

Làm gì lặp lại 3 lần → automate. Scripts, CI/CD, templates, code generators. Thời gian bạn tiết kiệm = thời gian learn thứ mới.

06

Understand the business

Code tồn tại để giải quyết business problems. Dev hiểu business = dev đưa ra solutions tốt hơn = dev được trả lương cao hơn.

07

Build a personal brand

Blog, GitHub, LinkedIn, speaking. Khi recruiter tìm bạn thay vì bạn tìm việc — bạn đã thắng. Bắt đầu sớm, đừng chờ "đủ giỏi".

08

Take care of yourself

Burnout là real. Ngủ đủ giấc, tập thể dục, có sở thích ngoài code. Bạn không thể sustain 10 năm career nếu cháy hết trong 2 năm đầu.

09

Always have a side project

Side project = playground thử nghiệm không sợ sai. Nơi bạn thử tech mới, build ideas, giữ passion sống. Nhiều career breakthrough đến từ side projects.

10

Be the person who writes things down

Meeting notes, architecture decisions, incident postmortems. Người ghi chép = người được reference = người có influence. Đơn giản nhưng ít ai làm.

11

Make your manager's job easier

Proactive updates, raise risks early, propose solutions (không chỉ nêu problems). Manager thành công → team thành công → bạn thành công.

12

Play long games with long people

Career là marathon, không phải sprint. Đừng đốt cầu. Đồng nghiệp hôm nay = hiring manager, co-founder, partner tương lai. Treat everyone well.

"Sự nghiệp developer không phải đường thẳng — nó là đường xoắn ốc.
Mỗi vòng bạn quay lại những bài học cũ ở level sâu hơn.
Đừng vội. Đừng so sánh. Hãy cứ tiến về phía trước."
