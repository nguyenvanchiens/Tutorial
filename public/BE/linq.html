Truy vấn dữ liệu trong C# với LINQ

Language Integrated Query — viết truy vấn dữ liệu thẳng trong C# với cú pháp gọn, type-safe và IntelliSense đầy đủ. Từ List trong bộ nhớ đến bảng SQL trong database, cùng một ngôn ngữ truy vấn. Bài này đi sâu vào bản chất lazy, IEnumerable vs IQueryable, toàn bộ toán tử cốt lõi và các bẫy hay gặp trong production.

1. LINQ là gì?

LINQ (Language Integrated Query) là tập hợp các tính năng ngôn ngữ + thư viện cho phép truy vấn dữ liệu một cách thống nhất, bất kể nguồn dữ liệu là gì.

📋 LINQ to Objects

Truy vấn trên collection trong bộ nhớ.

  • List<T>, T[]
  • Dictionary, HashSet
  • Bất kỳ IEnumerable<T>

🗄️ LINQ to Entities

Truy vấn EF Core → dịch sang SQL chạy trên DB.

  • DbSet<T>
  • IQueryable<T>
  • Expression tree → SQL

📄 LINQ to XML / khác

Truy vấn XML, JSON provider, nguồn tuỳ biến.

  • XDocument
  • Provider của bên thứ ba
  • Tự viết provider

Ý tưởng cốt lõi: thay vì viết vòng for + if thủ công, ta mô tả "muốn gì" (declarative) thay vì "làm thế nào" (imperative).

// Cách cũ — imperative: mô tả từng bước
var result = new List<string>();
foreach (var u in users)
{
    if (u.Age >= 18 && u.IsActive)
        result.Add(u.Name);
}
result.Sort();

// Cách LINQ — declarative: mô tả kết quả mong muốn
var result = users
    .Where(u => u.Age >= 18 && u.IsActive)
    .OrderBy(u => u.Name)
    .Select(u => u.Name)
    .ToList();
IEnumerable<T> là nền tảng: Hầu hết toán tử LINQ to Objects là extension method trên IEnumerable<T> (namespace System.Linq). Chỉ cần using System.Linq; là mọi IEnumerable đều có .Where(), .Select(), ...

🦥 Bản chất "lazy" (trì hoãn)

Đa số toán tử LINQ không chạy ngay khi gọi. Chúng chỉ dựng nên một "dây chuyền" mô tả truy vấn. Truy vấn chỉ thực sự chạy khi bạn enumerate (duyệt) kết quả — ví dụ qua foreach, .ToList(), .Count().

var numbers = new[] { 1, 2, 3, 4, 5 };

// Dòng này KHÔNG lọc gì cả — chỉ tạo "công thức"
var query = numbers.Where(n =>
{
    Console.WriteLine($"Đang kiểm tra {n}");
    return n % 2 == 0;
});

Console.WriteLine("--- Trước foreach ---");

// CHỈ đến đây predicate mới chạy
foreach (var n in query)
    Console.WriteLine($"Lấy được {n}");
💡 Vì sao lazy lại tốt? Cho phép ghép nhiều toán tử mà chỉ duyệt collection một lần, hỗ trợ chuỗi dữ liệu vô hạn, và với IQueryable thì cho phép gom toàn bộ truy vấn rồi dịch sang một câu SQL duy nhất.

2. Method syntax vs Query syntax

LINQ có hai cách viết tương đương nhau. Trình biên dịch dịch query syntax thành method syntax phía sau hậu trường.

Cùng một truy vấn — viết hai kiểu

// Dữ liệu mẫu
record Product(int Id, string Name, string Category, decimal Price);

List<Product> products = [
    new(1, "Bàn phím", "Phụ kiện", 450_000),
    new(2, "Màn hình", "Thiết bị", 3_200_000),
    new(3, "Chuột",    "Phụ kiện", 280_000),
];
// ① QUERY SYNTAX — giống SQL, dễ đọc khi có join/group
var q1 =
    from p in products
    where p.Category == "Phụ kiện"
    orderby p.Price descending
    select p.Name;

// ② METHOD SYNTAX — dùng lambda, linh hoạt hơn
var q2 = products
    .Where(p => p.Category == "Phụ kiện")
    .OrderByDescending(p => p.Price)
    .Select(p => p.Name);

// q1 và q2 cho kết quả y hệt: ["Bàn phím", "Chuột"]
Tiêu chíQuery syntaxMethod syntax
Hình thứcfrom ... where ... selectChuỗi method .Where().Select()
Dễ đọc khi join/group✅ Rất rõ ràng⚠️ Dài, lồng nhau
Số toán tử hỗ trợMột phần (where, select, join, group, orderby, let)✅ Toàn bộ (Skip, Take, Count, Any, ...)
Lambda phức tạp⚠️ Hạn chế✅ Linh hoạt
Phổ biến trong codebase 2026Ít hơn✅ Đa số dùng cái này
Khuyên dùng: Mặc định dùng method syntax vì nó hỗ trợ đầy đủ toán tử và ghép chuỗi tự nhiên. Chuyển sang query syntax khi truy vấn có nhiều join / group ... by / let — lúc đó nó dễ đọc hơn hẳn.

Có thể trộn lẫn

// Query syntax bọc trong (), rồi gọi method syntax tiếp
var count = (
    from p in products
    where p.Price > 300_000
    select p
).Count();   // Count() chỉ có ở method syntax

3. Toán tử lọc & chiếu — Where, Select, SelectMany

Đây là bộ ba dùng nhiều nhất: lọc phần tử, biến đổi phần tử, và làm phẳng collection lồng nhau.

Where — lọc theo điều kiện

// Lọc đơn giản
var cheap = products.Where(p => p.Price < 500_000);

// Where có overload nhận index
var oddIndexed = products.Where((p, index) => index % 2 == 1);

// Ghép nhiều Where = AND (nhưng nên gộp 1 Where cho gọn)
var filtered = products
    .Where(p => p.Price > 200_000)
    .Where(p => p.Category == "Phụ kiện");

Select — chiếu / biến đổi

// Chiếu sang kiểu khác (projection)
var names = products.Select(p => p.Name);

// Chiếu sang anonymous type
var summary = products.Select(p => new { p.Name, GiaVND = p.Price });

// Chiếu sang DTO (record)
var dtos = products.Select(p => new ProductDto(p.Id, p.Name));

// Select có overload index
var numbered = products.Select((p, i) => $"{i + 1}. {p.Name}");

SelectMany — làm phẳng (flatten)

Khi mỗi phần tử chứa một collection con, SelectMany gộp tất cả thành một chuỗi phẳng.

record Order(int Id, List<string> Items);

List<Order> orders = [
    new(1, ["Bàn phím", "Chuột"]),
    new(2, ["Màn hình"]),
];

// Select → IEnumerable<List<string>> (lồng nhau, KHÔNG mong muốn)
var nested = orders.Select(o => o.Items);

// SelectMany → IEnumerable<string> phẳng: [Bàn phím, Chuột, Màn hình]
var allItems = orders.SelectMany(o => o.Items);

// SelectMany với projection kết hợp cả phần tử cha
var pairs = orders.SelectMany(
    o => o.Items,
    (o, item) => new { o.Id, Item = item });
Mẹo nhớ: Select = 1 phần tử vào → 1 phần tử ra. SelectMany = 1 phần tử vào → nhiều phần tử ra rồi nối lại. Trong query syntax, SelectMany chính là dùng nhiều mệnh đề from liên tiếp.

4. Sắp xếp — OrderBy, ThenBy, Reverse

Sắp xếp theo một hay nhiều khoá. Lưu ý: OrderBy trả về IOrderedEnumerable để có thể nối tiếp ThenBy.

// Sắp xếp tăng dần theo Category, rồi giảm dần theo Price
var sorted = products
    .OrderBy(p => p.Category)
    .ThenByDescending(p => p.Price);

// SAI: gọi OrderBy hai lần = lần sau ghi đè lần trước!
var wrong = products
    .OrderBy(p => p.Category)
    .OrderBy(p => p.Price);   // chỉ còn sắp theo Price

// Đảo ngược thứ tự hiện tại
var reversed = products.Reverse();

// Sắp theo nhiều cấp với comparer tuỳ biến
var byLen = words.OrderBy(w => w.Length).ThenBy(w => w, StringComparer.Ordinal);
⚠️ Bẫy phổ biến: Muốn sắp theo nhiều khoá thì PHẢI dùng OrderBy(...).ThenBy(...). Gọi OrderBy hai lần sẽ khiến lần gọi sau thay thế hoàn toàn thứ tự của lần trước.

5. Nhóm — GroupBy

GroupBy gom các phần tử có chung khoá lại thành các nhóm IGrouping<TKey, TElement>.

// Nhóm sản phẩm theo Category
var groups = products.GroupBy(p => p.Category);

foreach (var g in groups)
{
    Console.WriteLine($"Nhóm {g.Key}: {g.Count()} sản phẩm");
    foreach (var p in g)
        Console.WriteLine($"  - {p.Name}");
}
// GroupBy + chiếu kết quả tổng hợp trong một bước
var stats = products
    .GroupBy(p => p.Category)
    .Select(g => new
    {
        Category   = g.Key,
        SoLuong    = g.Count(),
        TongGia    = g.Sum(p => p.Price),
        GiaTrungBinh = g.Average(p => p.Price),
    })
    .OrderByDescending(x => x.TongGia);

Query syntax cho group

var stats =
    from p in products
    group p by p.Category into g
    orderby g.Count() descending
    select new { Category = g.Key, SoLuong = g.Count() };
⚠️ GroupBy trên EF Core: Một số dạng GroupBy không dịch được sang SQL và EF sẽ throw hoặc đánh giá phía client. Kiểm tra log SQL sinh ra; nếu cần, chỉ GroupBy kèm các hàm tổng hợp đơn giản (Count/Sum/Avg) để EF dịch được thành GROUP BY.

6. Kết hợp dữ liệu — Join & GroupJoin

Ghép hai chuỗi dữ liệu theo khoá chung, giống JOIN trong SQL.

record Customer(int Id, string Name);
record Invoice(int Id, int CustomerId, decimal Amount);

// INNER JOIN — chỉ giữ phần tử khớp ở cả hai phía
var joined = customers.Join(
    invoices,
    c => c.Id,                // khoá phía ngoài
    inv => inv.CustomerId,     // khoá phía trong
    (c, inv) => new            // kết quả
    {
        c.Name,
        inv.Amount
    });
// Query syntax — rõ ràng hơn với join
var joined =
    from c in customers
    join inv in invoices on c.Id equals inv.CustomerId
    select new { c.Name, inv.Amount };

GroupJoin — gom các bản ghi con theo cha (LEFT JOIN)

// Mỗi customer + danh sách invoice của họ (kể cả rỗng)
var grouped = customers.GroupJoin(
    invoices,
    c => c.Id,
    inv => inv.CustomerId,
    (c, invs) => new
    {
        c.Name,
        Total = invs.Sum(i => i.Amount),
        Count = invs.Count()
    });

// Mô phỏng LEFT JOIN: GroupJoin + SelectMany + DefaultIfEmpty
var leftJoin =
    from c in customers
    join inv in invoices on c.Id equals inv.CustomerId into gj
    from inv in gj.DefaultIfEmpty()
    select new { c.Name, Amount = inv?.Amount ?? 0 };
💡 Với EF Core, thường ta KHÔNG viết Join thủ công mà dùng navigation property (customer.Invoices) — EF tự sinh JOIN. Chỉ dùng Join tường minh khi không có quan hệ navigation.

7. Tổng hợp — Aggregate, Sum, Count, Average, Min, Max

Các toán tử này thực thi ngay (immediate) vì phải duyệt hết để trả về một giá trị đơn.

var total   = products.Sum(p => p.Price);
var count   = products.Count();
var active  = products.Count(p => p.Price > 300_000);  // Count có predicate
var avg     = products.Average(p => p.Price);
var min     = products.Min(p => p.Price);
var max     = products.Max(p => p.Price);

// MaxBy / MinBy (.NET 6+): trả về PHẦN TỬ có giá trị lớn/nhỏ nhất
Product? dearest = products.MaxBy(p => p.Price);   // cả object, không chỉ giá
Product? cheapest = products.MinBy(p => p.Price);

Aggregate — gấp (fold) tuỳ biến

// Tự định nghĩa cách tích luỹ
var sum = numbers.Aggregate((acc, n) => acc + n);

// Có seed (giá trị khởi tạo) — an toàn với chuỗi rỗng
var product = numbers.Aggregate(1, (acc, n) => acc * n);

// Seed + bộ chọn kết quả cuối
var csv = names.Aggregate(
    new StringBuilder(),
    (sb, name) => sb.Append(name).Append(", "),
    sb => sb.ToString().TrimEnd(',', ' '));
⚠️ Average / Max / Min trên chuỗi rỗng sẽ throw InvalidOperationException với kiểu giá trị (non-nullable). Dùng overload nullable (vd Average(p => (decimal?)p.Price)) hoặc kiểm tra .Any() trước.

8. Lấy phần tử — First, Single, ElementAt

Phân biệt rõ các biến thể để tránh exception ngoài ý muốn.

First()❌ ThrowTrả phần tử đầuChắc chắn có ≥1
FirstOrDefault()Trả default (null/0)Trả phần tử đầuCó thể rỗng
Single()❌ Throw❌ ThrowPhải đúng 1 (vd theo Id)
SingleOrDefault()Trả default❌ Throw0 hoặc 1

// First/Single có thể nhận predicate luôn
var admin = users.First(u => u.Role == "Admin");          // throw nếu không có
var maybe = users.FirstOrDefault(u => u.Role == "Admin"); // null nếu không có

// Single dùng khi nghiệp vụ yêu cầu đúng 1 — bắt lỗi dữ liệu trùng
var user = users.Single(u => u.Id == 5);  // throw nếu có 2 user trùng Id

// FirstOrDefault với giá trị mặc định tuỳ chọn (.NET 6+)
var name = names.FirstOrDefault(n => n.StartsWith("A"), "(không có)");
Đừng lạm dụng First() không predicate sau Where() rồi quên null-check. Nếu collection rỗng, First() ném exception làm sập request. Dùng FirstOrDefault() + kiểm tra null nếu kết quả có thể rỗng.

9. Kiểm tra & tập hợp — Any, All, Contains, Distinct

// Any — có ÍT NHẤT một phần tử thoả? (dừng ngay khi gặp match)
bool hasExpensive = products.Any(p => p.Price > 1_000_000);
bool hasAny       = products.Any();   // có phần tử nào không

// All — TẤT CẢ đều thoả? (dừng ngay khi gặp phần tử KHÔNG thoả)
bool allActive = products.All(p => p.Price > 0);

// Contains — có chứa giá trị cụ thể
bool has = ids.Contains(42);

// Distinct — loại trùng
var uniqueCats = products.Select(p => p.Category).Distinct();

// DistinctBy (.NET 6+) — loại trùng theo khoá
var onePerCat = products.DistinctBy(p => p.Category);
💡 Dùng Any() thay vì Count() > 0: Any() dừng ngay khi thấy phần tử đầu tiên, còn Count() phải duyệt hết. Trên EF Core, Any() dịch thành EXISTS (nhanh), Count()>0 dịch thành đếm toàn bảng.

Toán tử tập hợp

var union     = listA.Union(listB);        // hợp (loại trùng)
var intersect = listA.Intersect(listB);    // giao
var except    = listA.Except(listB);       // hiệu (A trừ B)
var concat    = listA.Concat(listB);       // nối (GIỮ trùng)

// *By variants (.NET 6+): UnionBy, IntersectBy, ExceptBy
var merged = usersA.UnionBy(usersB, u => u.Email);

10. Phân trang — Take, Skip, Chunk

// Phân trang cơ bản: trang thứ `page` (1-based), mỗi trang `size`
int page = 2, size = 10;
var pageItems = query
    .Skip((page - 1) * size)
    .Take(size);

// TakeWhile / SkipWhile — theo điều kiện (dừng khi điều kiện sai)
var head = numbers.TakeWhile(n => n < 5);
var tail = numbers.SkipWhile(n => n < 5);

// Take với Range (.NET 6+)
var middle = items.Take(2..5);   // phần tử index 2,3,4
var lastThree = items.Take(^3..);

// Chunk (.NET 6+) — chia thành các lô size phần tử
foreach (var batch in items.Chunk(100))
    ProcessBatch(batch);   // xử lý theo lô 100
⚠️ Phân trang trên EF Core PHẢI có OrderBy trước Skip/Take — nếu không thứ tự bản ghi không xác định và kết quả phân trang sẽ không ổn định giữa các lần gọi.

11. Vật chất hoá — ToList, ToArray, ToDictionary, ToHashSet

Các toán tử To... thực thi ngay truy vấn và sao chép kết quả vào một collection mới trong bộ nhớ.

var list  = query.ToList();        // List<T>
var arr   = query.ToArray();       // T[]
var set   = query.ToHashSet();     // HashSet<T> (loại trùng)

// ToDictionary — key + value selector
var byId = products.ToDictionary(
    p => p.Id,         // key
    p => p.Name);      // value

// ToLookup — giống Dictionary nhưng mỗi key map tới NHIỀU value
var byCategory = products.ToLookup(p => p.Category);
var accessories = byCategory["Phụ kiện"];   // IEnumerable
⚠️ ToDictionary ném exception nếu khoá trùng. Nếu dữ liệu có thể có key trùng, dùng ToLookup (1 key → nhiều value) hoặc GroupBy rồi tự xử lý. Tương tự, value selector trả null không sao nhưng key null thì throw.

12. Deferred vs Immediate execution — cái bẫy kinh điển

Hiểu sai điểm này là nguồn gốc của vô số bug "kết quả lúc đúng lúc sai" và "DB bị query nhiều lần".

LoạiToán tử tiêu biểuKhi nào chạy
Deferred (lazy)Where, Select, OrderBy, Take, Skip, GroupBy, Join, DistinctKhi enumerate (foreach / To...)
ImmediateToList, ToArray, Count, Sum, First, Any, Average, MaxNgay lập tức, duyệt collection liền

Bẫy: query được đánh giá LẠI mỗi lần enumerate

var source = new List<int> { 1, 2, 3 };

// query là "công thức", KHÔNG phải kết quả
var query = source.Where(n => n > 1);

Console.WriteLine(query.Count());   // 2  (lần enumerate #1)

source.Add(4);                       // thêm dữ liệu vào NGUỒN

Console.WriteLine(query.Count());   // 3  (!) lần enumerate #2 thấy data mới

// Vì query bám vào `source`, nó chạy LẠI mỗi lần gọi Count()/foreach.
// Muốn "đóng băng" kết quả tại thời điểm này → .ToList()
var snapshot = source.Where(n => n > 1).ToList();  // chụp ảnh ngay
🔥 Hệ quả nghiêm trọng với EF Core: Nếu query là IQueryable bám vào DB, mỗi lần bạn enumerate nó (foreach, Count, ToList) là một lần gọi database. Lặp lại 3 lần = 3 round-trip SQL. Vật chất hoá một lần bằng .ToList() rồi tái sử dụng kết quả trong bộ nhớ. 
// ❌ Query chạy 2 lần xuống DB
var q = db.Orders.Where(o => o.Total > 100);
var count = q.Count();          // SQL #1: SELECT COUNT(*)
var list  = q.ToList();         // SQL #2: SELECT *

// ✅ Một lần xuống DB rồi tính trong bộ nhớ
var list  = db.Orders.Where(o => o.Total > 100).ToList();  // SQL #1
var count = list.Count;          // chỉ đọc property, 0 query

13. IEnumerable vs IQueryable

Hai interface trông giống nhau nhưng hành xử hoàn toàn khác. Nhầm lẫn chúng là nguyên nhân số 1 của các vấn đề hiệu năng trong EF Core.

Tiêu chíIEnumerable<T>IQueryable<T>
NamespaceSystem.Collections.GenericSystem.Linq
Lambda được lưu dưới dạngFunc<T,bool> (delegate đã biên dịch)Expression<Func<T,bool>> (cây biểu thức)
Nơi xử lýTrong bộ nhớ ứng dụng (client)Provider dịch ra ngôn ngữ đích (SQL) — chạy ở DB (server)
Dữ liệu tải vềToàn bộ rồi mới lọc trong RAMChỉ tải về kết quả đã lọc
Dùng choLINQ to Objects (List, mảng...)LINQ to Entities (DbSet), provider remote
Hiệu năng với DB lớn❌ Tải hết → tốn RAM/băng thông✅ Lọc tại nguồn → tối ưu

Expression tree — vì sao IQueryable dịch được sang SQL

Với IQueryable, lambda KHÔNG được biên dịch thành code thực thi mà được lưu thành một cây biểu thức — một mô tả dữ liệu của logic. EF Core đọc cây này và dịch nó thành câu SQL tương ứng.

// IQueryable: lambda là Expression — EF "đọc" được và dịch sang SQL
IQueryable<Order> q = db.Orders.Where(o => o.Total > 100);
// → SELECT * FROM Orders WHERE Total > 100   (lọc ở DB)

// IEnumerable: lambda là Func đã compile — chạy trong RAM
IEnumerable<Order> e = db.Orders.AsEnumerable().Where(o => o.Total > 100);
// → SELECT * FROM Orders   (TẢI HẾT về rồi mới lọc trong app!)
🔥 Vì sao việc "trộn" chúng quan trọng: Khi bạn gọi .AsEnumerable(), .ToList(), hoặc dùng một method C# mà EF không dịch được, query "chuyển" từ IQueryable sang IEnumerable. Mọi toán tử sau điểm chuyển sẽ chạy trong bộ nhớ trên toàn bộ dữ liệu đã tải về — đây gọi là client evaluation và thường âm thầm phá huỷ hiệu năng. 
// ❌ Where THỨ HAI chạy client-side vì đứng sau AsEnumerable()
var bad = db.Orders
    .Where(o => o.Total > 100)   // dịch SQL ✅
    .AsEnumerable()                  // 🚪 cửa chuyển sang RAM
    .Where(o => IsSpecial(o));        // chạy trong app trên TẤT CẢ order >100

// ✅ Giữ mọi thứ trong IQueryable để dịch hết sang SQL
var good = db.Orders
    .Where(o => o.Total > 100 && o.IsSpecialFlag)   // 1 câu SQL
    .ToList();
⚠️ EF Core 3.0+: Mặc định nếu một Where/biểu thức không dịch được sang SQL, EF sẽ throw exception thay vì âm thầm chạy client-side (như EF Core 2.x từng làm). Muốn cố tình đánh giá client phải gọi AsEnumerable() tường minh.

14. Các bẫy thường gặp (Common Pitfalls)

14.1 Multiple enumeration — duyệt nhiều lần

❌ Enumerate cùng một query nhiều lần

Mỗi lần duyệt IEnumerable lazy là một lần chạy lại toàn bộ logic — với EF là một lần xuống DB.

var q = db.Users.Where(u => u.Active);

if (q.Any())                  // SQL #1
{
    foreach (var u in q)     // SQL #2
        Send(u);
    var n = q.Count();        // SQL #3
}

✅ Vật chất hoá một lần

Gọi .ToList() một lần, rồi tái sử dụng list trong bộ nhớ cho mọi thao tác sau.

var users = db.Users
    .Where(u => u.Active)
    .ToList();                // 1 SQL duy nhất

if (users.Count > 0)
{
    foreach (var u in users)
        Send(u);
    var n = users.Count;
}

14.2 N+1 query trong EF Core

❌ Lazy load trong vòng lặp → N+1

1 query lấy danh sách cha + N query lấy con cho từng phần tử = N+1 round-trip xuống DB.

var orders = db.Orders.ToList();   // 1 query

foreach (var o in orders)
{
    // mỗi lần truy cập navigation = 1 query!
    Console.WriteLine(o.Customer.Name);
    // → N query phụ cho N order
}

✅ Eager load với Include / projection

Dùng Include để JOIN sẵn, hoặc Select chỉ lấy field cần — tất cả trong 1 query.

// Eager load: 1 query có JOIN
var orders = db.Orders
    .Include(o => o.Customer)
    .ToList();

// Hoặc projection — chỉ lấy đúng dữ liệu cần
var data = db.Orders
    .Select(o => new { o.Id, Cust = o.Customer.Name })
    .ToList();

14.3 Gọi .ToList() quá sớm

// ❌ ToList() quá SỚM: tải HẾT bảng về RAM rồi mới lọc/phân trang
var page = db.Products
    .ToList()                          // 🔥 SELECT * toàn bảng (có thể triệu dòng)
    .Where(p => p.Price > 100)
    .Skip(20).Take(10)
    .ToList();

// ✅ ToList() đúng lúc: lọc + phân trang ở DB, chỉ tải 10 dòng về
var page = db.Products
    .Where(p => p.Price > 100)
    .OrderBy(p => p.Id)
    .Skip(20).Take(10)
    .ToList();                         // SELECT ... WHERE ... LIMIT 10 OFFSET 20
⚠️ Quy tắc vàng: Với EF Core, giữ truy vấn ở dạng IQueryable càng lâu càng tốt (lọc, sort, phân trang, chiếu), CHỈ gọi .ToList()/.ToArrayAsync() ở bước cuối cùng khi đã thu hẹp dữ liệu xuống đúng những gì cần.

14.4 Client vs Server evaluation

// ❌ Hàm C# tự định nghĩa — EF không dịch sang SQL được
var r = db.Users
    .Where(u => MyHelper.Normalize(u.Email) == "a@b.com")  // throw hoặc client-eval
    .ToList();

// ✅ Dùng biểu thức EF dịch được, hoặc chuẩn hoá trước khi query
string target = "a@b.com".ToLower();
var r = db.Users
    .Where(u => u.Email.ToLower() == target)   // dịch thành LOWER() trong SQL
    .ToList();
Cách kiểm tra: Bật log SQL của EF Core (LogTo(Console.WriteLine) hoặc cấu hình Microsoft.EntityFrameworkCore.Database.Command ở mức Information) và đọc câu SQL sinh ra. Nếu thấy SELECT * không có WHERE bạn mong đợi → logic đang chạy client-side.

15. Async LINQ với EF Core

Với database, luôn dùng các biến thể async để không block thread. Chúng nằm trong namespace Microsoft.EntityFrameworkCore, KHÔNG phải System.Linq.

using Microsoft.EntityFrameworkCore;

var list  = await db.Orders.Where(o => o.Active).ToListAsync();
var first = await db.Orders.FirstOrDefaultAsync(o => o.Id == id);
var count = await db.Orders.CountAsync(o => o.Active);
var exist = await db.Orders.AnyAsync(o => o.Total > 100);
var sum   = await db.Orders.SumAsync(o => o.Total);

// Stream từng bản ghi (không tải hết vào RAM) với IAsyncEnumerable
await foreach (var o in db.Orders.Where(o => o.Active).AsAsyncEnumerable())
    Process(o);
💡 AsNoTracking() cho các truy vấn chỉ-đọc: EF không theo dõi entity → nhanh hơn, ít tốn RAM. Dùng cho mọi query trả dữ liệu ra ngoài (API GET) mà không định cập nhật lại DB.

16. Mẹo viết LINQ sạch

✅ Lọc trước, chiếu sau

Đặt Where sớm nhất để giảm số phần tử trước khi Select/OrderBy phải xử lý.

items
    .Where(x => x.Active)   // giảm tập trước
    .OrderBy(x => x.Name)
    .Select(x => x.Name);

✅ Đặt tên biến trung gian rõ ràng

Tách chuỗi dài thành các bước có tên, dễ debug và đọc hơn lambda lồng nhau.

var active  = users.Where(u => u.Active);
var emails  = active.Select(u => u.Email);
var result  = emails.Distinct().ToList();

❌ Lambda quá dài nhồi trong một dòng

Logic phức tạp nhét hết vào một lambda khiến khó đọc, khó test.

data.Select(x => x.A > 0 ? Calc(x) + Fix(x) - Adj(x) : 0);

❌ Quên OrderBy khi phân trang

Skip/Take không có OrderBy → thứ tự bản ghi không xác định.

db.Items.Skip(20).Take(10);  // không ổn định!

🎯 Checklist nắm vững LINQ

  • ✅ Hiểu LINQ là extension method trên IEnumerable<T>, chỉ cần using System.Linq
  • ✅ Viết được cùng truy vấn theo cả method syntax và query syntax
  • ✅ Phân biệt deferred (Where/Select/OrderBy) vs immediate (ToList/Count/First)
  • ✅ Biết Select vs SelectMany, dùng đúng khi flatten collection lồng nhau
  • ✅ Dùng OrderBy().ThenBy() cho nhiều khoá — KHÔNG gọi OrderBy hai lần
  • ✅ Chọn đúng First / FirstOrDefault / Single theo ngữ cảnh null
  • ✅ Dùng Any() thay cho Count() > 0
  • ✅ Hiểu rõ IEnumerable (client, Func) vs IQueryable (server, Expression tree → SQL)
  • ✅ Tránh multiple enumeration — vật chất hoá .ToList() một lần rồi tái dùng
  • ✅ Tránh N+1 bằng Include hoặc projection Select
  • ✅ Gọi .ToList() ở bước CUỐI, giữ IQueryable càng lâu càng tốt
  • ✅ Đọc log SQL để phát hiện client evaluation ngoài ý muốn
  • ✅ Phân trang luôn kèm OrderBy trước Skip/Take
  • ✅ Dùng các biến thể async (ToListAsync, AnyAsync...) + AsNoTracking() với EF Core
