Caching trong .NET

Tăng tốc và mở rộng ứng dụng ASP.NET Core với caching: IMemoryCache, IDistributedCache + Redis, HybridCache (.NET 9), Output Caching, các pattern cache-aside/write-through, chiến lược TTL + jitter, xử lý cache stampede và bài toán khó nhất — cache invalidation. Chính xác cho .NET 8/9.

1. Tại sao cache & các tầng cache

Cache lưu lại kết quả của một thao tác "đắt" (query DB, gọi API, tính toán nặng) để lần sau trả ngay mà không cần làm lại. Mục tiêu: giảm latency, giảm tải DB/downstream, tăng throughput và tiết kiệm chi phí. Đổi lại, bạn chấp nhận dữ liệu có thể "cũ" (stale) trong một khoảng thời gian.

Cache không phải một chỗ duy nhất — nó là nhiều tầng từ client tới server:

🌐 Client cache (browser)

Trình duyệt cache theo header Cache-Control, ETag, Last-Modified. Rẻ nhất vì request không tới server. Dùng cho asset tĩnh (JS/CSS/ảnh) và response idempotent.

🛰️ CDN / Edge cache

CloudFront, Cloudflare, Azure Front Door cache ở gần user. Giảm round-trip xuyên lục địa. Hợp với nội dung public, ít thay đổi.

⚡ In-memory cache (in-process)

IMemoryCache — nằm ngay trong RAM của process. Nhanh nhất (nano giây) nhưng không share giữa nhiều instance và mất khi restart.

🗄️ Distributed cache (out-of-process)

Redis / SQL Server / NCache. Share giữa tất cả instance, sống sót qua restart app. Chậm hơn in-memory (có network hop) nhưng đồng nhất.

Quy tắc tầng cache: tầng càng gần user càng nhanh và rẻ, nhưng càng khó kiểm soát invalidation. Chiến lược tốt thường kết hợp nhiều tầng (vd: HybridCache = L1 in-memory + L2 Redis).

2. IMemoryCache — cache trong process

Là cache nhanh nhất: dữ liệu nằm thẳng trong heap của process. Đăng ký bằng builder.Services.AddMemoryCache(); rồi inject IMemoryCache. API tiện nhất là GetOrCreateAsync — atomic per-key check-or-load (theo từng key).

// Program.cs
builder.Services.AddMemoryCache();

// Service
public class ProductService(IMemoryCache cache, AppDbContext db)
{
    public Task<Product?> GetAsync(int id, CancellationToken ct = default)
    {
        var key = $"product:{id}";

        return cache.GetOrCreateAsync(key, async entry =>
        {
            // Chỉ chạy khi MISS — nhiều entry options cùng lúc
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);
            entry.SlidingExpiration = TimeSpan.FromMinutes(2);
            entry.Size = 1; // bắt buộc nếu có SizeLimit

            return await db.Products
                .AsNoTracking()
                .FirstOrDefaultAsync(p => p.Id == id, ct);
        });
    }
}

Hoặc cấu hình bằng MemoryCacheEntryOptions rõ ràng:

var options = new MemoryCacheEntryOptions
{
    // Hết hạn tuyệt đối: tối đa sống 10 phút kể từ khi set
    AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),
    // Hết hạn trượt: reset đếm ngược mỗi lần được đọc; idle 2 phút thì xoá
    SlidingExpiration = TimeSpan.FromMinutes(2),
    // Mức ưu tiên khi cache bị nén (memory pressure)
    Priority = CacheItemPriority.High,
    Size = 1
};
options.RegisterPostEvictionCallback((k, v, reason, state) =>
    logger.LogInformation("Evicted {Key} vì {Reason}", k, reason));

cache.Set(key, product, options);
⚠️ Giới hạn bộ nhớ: mặc định IMemoryCache KHÔNG giới hạn dung lượng — cache có thể nuốt hết RAM. Hãy đặt SizeLimit khi AddMemoryCache(o => o.SizeLimit = 1024) và khi đó mọi entry phải khai báo Size, nếu không sẽ ném exception.

Khi nào dùng? App single-instance, hoặc dữ liệu tham chiếu (lookup tables, config, danh mục) chấp nhận lệch nhẹ giữa các node, hoặc làm L1 phía trước Redis.

3. IDistributedCache + Redis

Khi chạy nhiều instance (sau load balancer), bạn cần một cache chia sẻ. IDistributedCache là abstraction chuẩn của ASP.NET Core; provider phổ biến nhất là Redis qua StackExchangeRedis. Lưu ý API chỉ làm việc với byte[]/string → bạn phải tự serialize (thường là JSON).

// Program.cs — đăng ký Redis làm IDistributedCache
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = builder.Configuration.GetConnectionString("Redis");
    options.InstanceName = "devhub:"; // prefix cho mọi key
});
public class UserCache(IDistributedCache cache, AppDbContext db)
{
    private static readonly JsonSerializerOptions _json = new(JsonSerializerDefaults.Web);

    public async Task<User?> GetAsync(int id, CancellationToken ct = default)
    {
        var key = $"user:{id}";

        // 1) Thử đọc từ Redis (trả về byte[]?)
        var bytes = await cache.GetAsync(key, ct);
        if (bytes is not null)
            return JsonSerializer.Deserialize<User>(bytes, _json);

        // 2) MISS → load từ DB
        var user = await db.Users.AsNoTracking()
            .FirstOrDefaultAsync(u => u.Id == id, ct);
        if (user is null) return null;

        // 3) Serialize JSON và set kèm TTL
        var payload = JsonSerializer.SerializeToUtf8Bytes(user, _json);
        await cache.SetAsync(key, payload, new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10),
            SlidingExpiration = TimeSpan.FromMinutes(2)
        }, ct);

        return user;
    }

    public Task InvalidateAsync(int id, CancellationToken ct = default)
        => cache.RemoveAsync($"user:{id}", ct);
}

Đăng ký builder.Services.AddHybridCache(); rồi dùng một API duy nhất cache.GetOrCreateAsync(key, factory, options, ct) — đây là hướng khuyến nghị cho ứng dụng mới. 
// .NET 9 HybridCache — một API, tự lo L1+L2 + chống stampede
builder.Services.AddHybridCache();

public class Catalog(HybridCache cache, AppDbContext db)
{
    public ValueTask<Product?> GetAsync(int id, CancellationToken ct = default)
        => cache.GetOrCreateAsync(
            $"product:{id}",
            id,                                  // state truyền vào factory
            async (id, token) => await db.Products.FindAsync([id], token),
            new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(10) },
            cancellationToken: ct);
}

4. Patterns: Cache-aside / Write-through / Write-behind

PatternCách hoạt độngƯu / Nhược
Cache-aside (lazy)App kiểm tra cache trước; miss thì load từ DB rồi tự ghi vào cache.Phổ biến nhất, đơn giản. Có thể có request miss đầu tiên chậm; dễ stale nếu invalidation kém.
Write-throughMỗi lần ghi DB, ghi luôn vào cache (đồng bộ).Cache luôn tươi sau write. Nhưng mọi write chậm hơn; cache đầy cả dữ liệu ít đọc.
Write-behind (write-back)Ghi vào cache trước, flush xuống DB sau (bất đồng bộ, theo batch).Write rất nhanh, gom batch. Rủi ro mất dữ liệu nếu cache chết trước khi flush; phức tạp.

Cache-aside là mặc định cho hầu hết hệ thống đọc-nhiều-ghi-ít. Mẫu chuẩn:

// CACHE-ASIDE (lazy loading) tổng quát
public async Task<Order?> GetOrderAsync(int id, CancellationToken ct)
{
    var key = $"order:{id}";

    // 1) Đọc cache
    if (cache.TryGetValue(key, out Order? cached))
        return cached;          // HIT

    // 2) MISS → nguồn sự thật (DB)
    var order = await db.Orders.FindAsync([id], ct);

    // 3) Ghi ngược vào cache cho lần sau
    if (order is not null)
        cache.Set(key, order, TimeSpan.FromMinutes(5));

    return order;
}

// WRITE-THROUGH: cập nhật DB rồi đồng bộ cache ngay
public async Task UpdateAsync(Order order, CancellationToken ct)
{
    db.Orders.Update(order);
    await db.SaveChangesAsync(ct);
    cache.Set($"order:{order.Id}", order, TimeSpan.FromMinutes(5)); // cache luôn tươi
}
Cache-aside + write-through kết hợp: đọc theo cache-aside, còn khi update thì hoặc ghi đè cache (write-through) hoặc đơn giản xoá key (để lần đọc sau tự nạp lại). Xoá key thường an toàn hơn vì tránh ghi nhầm dữ liệu chưa commit.

5. Cache invalidation — "một trong hai việc khó nhất"

Phil Karlton: "There are only two hard things in Computer Science: cache invalidation and naming things." Vấn đề: làm sao biết dữ liệu trong cache đã cũ và bỏ nó đi đúng lúc. Dưới đây là các chiến lược, thường kết hợp nhiều cái.

⏱️ TTL-based (hết hạn theo thời gian)

Đặt AbsoluteExpiration — cache tự hết hạn. Đơn giản nhất, chấp nhận stale tối đa = TTL. Không cần biết khi nào dữ liệu đổi.

🗑️ Explicit eviction (xoá chủ động)

Khi ghi/đổi dữ liệu, gọi cache.Remove(key) / RemoveAsync. Chính xác nhưng cần nhớ xoá ở MỌI nơi mutate dữ liệu.

🏷️ Tag / key versioning

Gắn nhiều key vào một "tag" hoặc nhúng số version vào key (product:42:v7). Tăng version = vô hiệu hoá hàng loạt mà không cần biết từng key.

📡 Event-based

Phát sự kiện khi dữ liệu đổi (message bus, Redis pub/sub, domain event) → các node nghe và tự xoá cache. Cần cho invalidate L1 in-memory đa node.

// Key versioning: bump version để vô hiệu hoá hàng loạt
var ver = await cache.GetStringAsync("catalog:ver") ?? "1";
var key = $"catalog:list:v{ver}";
// Khi catalog đổi: tăng version → toàn bộ key cũ trở thành "mồ côi" và tự hết hạn theo TTL
await cache.SetStringAsync("catalog:ver", (int.Parse(ver) + 1).ToString());
⚠️ Stale nguy hiểm nhất khi explicit eviction sót: chỉ cần một đường ghi dữ liệu quên xoá cache là user thấy dữ liệu cũ. Vì vậy nhiều team chọn TTL ngắn làm "lưới an toàn" kết hợp với eviction chủ động — kể cả khi quên xoá, dữ liệu cũng tự tươi lại sau TTL.
💡 Tag-based eviction sẵn có: Output Caching (.NET 8/9) và HybridCache (.NET 9) hỗ trợ tags để evict cả nhóm bằng một lệnh (EvictByTagAsync("products")) — đỡ phải tự xây cơ chế tag.

6. Cache stampede / Thundering herd

Khi một key "nóng" hết hạn, hàng nghìn request đồng thời cùng MISS, cùng lúc đập xuống DB để nạp lại → DB quá tải, có thể sập (cascading failure). Đây gọi là cache stampede (thundering herd).

Giải pháp kinh điển: dùng lock/semaphore để chỉ một request được nạp, các request còn lại chờ và dùng chung kết quả.

// Chống stampede thủ công bằng SemaphoreSlim theo key
private static readonly SemaphoreSlim _lock = new(1, 1);

public async Task<Report> GetReportAsync(CancellationToken ct)
{
    if (cache.TryGetValue("report", out Report? r)) return r!; // fast path

    await _lock.WaitAsync(ct);
    try
    {
        // double-check: có thể request khác đã nạp xong trong lúc chờ lock
        if (cache.TryGetValue("report", out r)) return r!;

        r = await BuildExpensiveReportAsync(ct); // CHỈ 1 request chạy
        cache.Set("report", r, TimeSpan.FromMinutes(5));
        return r;
    }
    finally { _lock.Release(); }
}
💡 .NET 9 HybridCache lo sẵn: với HybridCache.GetOrCreateAsync, nếu nhiều request cùng miss một key, framework đảm bảo factory chỉ chạy một lần trên mỗi node và các request khác chờ kết quả — stampede protection built-in, không cần tự viết semaphore.
Early expiration (làm tươi sớm): thay vì để hết hạn rồi mới nạp lại, một số thư viện chủ động làm mới cache trong nền trước khi hết hạn (vd refresh khi còn 10% TTle), để không có khoảnh khắc nào key vắng mặt → tránh herd ngay từ gốc.

7. Chiến lược TTL & jitter

TTL (time-to-live) là khoảng thời gian dữ liệu được coi là còn "đủ tươi". Chọn TTL theo mức độ dữ liệu được phép cũ:

Loại dữ liệuĐộ tươi yêu cầuTTL gợi ý
Giá tiền tệ / tồn kho real-timeRất caovài giây – không cache
Danh sách sản phẩm, bài viếtTrung bình1 – 10 phút
Config, lookup table, danh mụcThấp30 phút – vài giờ
Dữ liệu gần như bất biến (mã quốc gia)Rất thấpnhiều giờ / tới khi deploy

Nếu nhiều key được nạp cùng lúc với cùng TTL, chúng sẽ hết hạn đồng loạt → tạo ra một đợt stampede đồng bộ. Thêm jitter (ngẫu nhiên hoá nhẹ TTL) để rải thời điểm hết hạn:

// Jitter: cộng ngẫu nhiên 0–60s vào TTL gốc để tránh hết hạn đồng loạt
static TimeSpan WithJitter(TimeSpan baseTtl)
{
    var jitter = TimeSpan.FromSeconds(Random.Shared.Next(0, 60));
    return baseTtl + jitter;
}

cache.Set(key, value, new MemoryCacheEntryOptions
{
    AbsoluteExpirationRelativeToNow = WithJitter(TimeSpan.FromMinutes(5))
});
💡 Kết hợp: AbsoluteExpiration + jitter làm trần tuổi thọ và rải hết hạn; thêm SlidingExpiration để key ít dùng tự rơi sớm, key nóng sống lâu. Đừng đặt sliding mà không có absolute — key cực nóng có thể "bất tử" và không bao giờ tươi lại.

8. Output Caching (.NET 8/9) vs Response Caching cũ

Thay vì cache dữ liệu trong service, bạn có thể cache toàn bộ response của một endpoint. .NET 8 giới thiệu Output Caching — middleware cache server-side mạnh hơn hẳn Response Caching cũ.

// Program.cs
builder.Services.AddOutputCache(options =>
{
    // policy mặc định
    options.AddBasePolicy(b => b.Expire(TimeSpan.FromSeconds(30)));
    // policy đặt tên, vary theo query "page"
    options.AddPolicy("ProductsList", b => b
        .Expire(TimeSpan.FromMinutes(5))
        .SetVaryByQuery("page", "sort")
        .Tag("products"));        // gắn tag để evict nhóm
});

var app = builder.Build();
app.UseOutputCache(); // đặt sau UseRouting

// Áp dụng cho endpoint
app.MapGet("/products", GetProducts).CacheOutput("ProductsList");
app.MapGet("/health", () => "ok").CacheOutput(); // dùng base policy
// Evict theo tag khi dữ liệu đổi (vd sau khi thêm sản phẩm)
app.MapPost("/products", async (Product p, AppDbContext db,
    IOutputCacheStore store, CancellationToken ct) =>
{
    db.Products.Add(p);
    await db.SaveChangesAsync(ct);
    await store.EvictByTagAsync("products", ct); // xoá mọi response gắn tag "products"
    return Results.Created($"/products/{p.Id}", p);
});

9. Khi nào KHÔNG nên cache (Do / Don't)

❌ Dữ liệu thay đổi liên tục

Tồn kho real-time, giá khớp lệnh, số dư ví. TTL phải cực ngắn để đúng → tỉ lệ hit thấp, lợi ích gần như không có mà rủi ro hiển thị sai số liệu rất cao.

❌ Dữ liệu per-user nhạy cảm

Thông tin cá nhân, quyền, số dư riêng. Cache không vary-by-user đúng cách dễ gây rò rỉ dữ liệu giữa các user (user A thấy data user B) — lỗi bảo mật nghiêm trọng.

❌ Dữ liệu nhỏ & rẻ để tính lại

Nếu query đã < 1ms và nhẹ, thêm cache chỉ tăng độ phức tạp, tốn RAM/Redis và sinh nguy cơ stale mà không thực sự nhanh hơn đáng kể.

❌ Cache khi chưa đo

Cache là tối ưu hoá — đừng thêm khi chưa biết nút thắt ở đâu. Cache sai chỗ che giấu vấn đề thật và tạo bug stale khó tái hiện ("máy tôi chạy đúng mà").

✅ Đọc nhiều, ghi ít, chấp nhận stale

Danh mục, bài viết, lookup table, kết quả tổng hợp nặng. Tỉ lệ hit cao, dữ liệu ổn định → cache cho hiệu quả rõ rệt.

✅ Thao tác đắt & lặp lại

Report tổng hợp, gọi API bên thứ ba có rate limit, tính toán nặng. Cache giảm tải downstream và latency một cách thực chất.

🎯 Checklist Caching

  • ✅ Đã đo và xác định cache đúng nút thắt (đọc nhiều, đắt, chấp nhận stale)
  • ✅ Single-instance hoặc dữ liệu tham chiếu → IMemoryCache; đa instance → IDistributedCache (Redis) hoặc HybridCache (.NET 9)
  • ✅ Mọi entry có AbsoluteExpiration làm trần tuổi thọ (không sliding mà thiếu absolute)
  • ✅ Thêm jitter vào TTL để tránh hết hạn đồng loạt
  • ✅ Có cơ chế invalidation rõ ràng: TTL + explicit Remove / tag / version / event
  • ✅ Chống cache stampede: semaphore/lock hoặc dùng HybridCache (stampede protection built-in)
  • ✅ Distributed cache: serialize JSON nhất quán, đặt InstanceName prefix cho key
  • ✅ IMemoryCache có SizeLimit + khai báo Size cho mọi entry
  • ✅ Cache cả response bằng Output Caching (.CacheOutput(), tag, vary-by) thay cho Response Caching cũ
  • ✅ KHÔNG cache dữ liệu per-user nhạy cảm nếu chưa vary-by-user đúng (tránh rò rỉ)
  • ✅ Có log/metric cho cache hit/miss để theo dõi hiệu quả thực tế
