OOP trong C# — Lập trình hướng đối tượng

Nắm vững 4 trụ cột OOP, sự khác biệt class vs struct, interface vs abstract class, access modifiers, properties hiện đại, đa hình và nguyên tắc "composition over inheritance" — chuẩn .NET 8/9 (2026). Đây là nền tảng cốt lõi để viết code C# sạch, dễ bảo trì và mở rộng.

1. OOP là gì & tại sao quan trọng

OOP (Object-Oriented Programming) tổ chức chương trình quanh các đối tượng — đơn vị gói chung dữ liệu (state) và hành vi (behavior). C# là ngôn ngữ OOP từ gốc rễ: mọi thứ kế thừa từ System.Object.

🎯 Mục tiêu của OOP

  • Mô hình hoá thế giới thực thành code
  • Giảm trùng lặp (reuse qua kế thừa/composition)
  • Cô lập thay đổi — sửa 1 chỗ không vỡ chỗ khác
  • Dễ test, dễ mở rộng, dễ đọc

🏛️ 4 trụ cột (4 Pillars)

  • Encapsulation — đóng gói
  • Inheritance — kế thừa
  • Polymorphism — đa hình
  • Abstraction — trừu tượng hoá
// Một class C# điển hình: gói state (fields/properties) + behavior (methods)
public class BankAccount
{
    private decimal _balance;                  // state — được bảo vệ
    public string Owner { get; }            // dữ liệu chỉ đọc

    public BankAccount(string owner, decimal opening)
        => (Owner, _balance) = (owner, opening);

    public void Deposit(decimal amount)    // behavior
    {
        if (amount <= 0) throw new ArgumentException("Số tiền phải > 0");
        _balance += amount;
    }

    public decimal GetBalance() => _balance;
}
Nền tảng .NET: mọi type trong C# (kể cả int, struct) đều bắt nguồn từ object. Hiểu OOP đúng giúp bạn dùng tốt toàn bộ BCL (Base Class Library), EF Core, ASP.NET Core — vì chúng đều thiết kế theo OOP.

2. Trụ cột 1 — Encapsulation (Đóng gói)

Encapsulation = che giấu chi tiết bên trong, chỉ public ra một contract an toàn. State không bị thay đổi tuỳ tiện từ bên ngoài; mọi thay đổi đi qua method/property có kiểm soát (invariant).

// ❌ KHÔNG encapsulation — field public, ai cũng sửa được state vô lý
public class BadAccount
{
    public decimal Balance;   // account.Balance = -9999; vẫn hợp lệ!
}

// ✅ Encapsulation đúng — bảo vệ invariant "balance không bao giờ âm"
public class Account
{
    private decimal _balance;                  // backing field, ẩn

    public decimal Balance => _balance;        // đọc được, không ghi trực tiếp

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > _balance)
            throw new InvalidOperationException("Số dư không đủ");
        _balance -= amount;                       // invariant luôn được giữ
    }
}
💡 Quy tắc vàng: field nên là private. Public ra ngoài bằng property (có thể thêm validate, log, raise event). Đừng public field — bạn sẽ mất khả năng kiểm soát và không break được binary compatibility khi đổi sang property sau này.

3. Trụ cột 2 — Inheritance (Kế thừa)

Inheritance cho phép một class (derived/con) tái sử dụng và mở rộng class khác (base/cha). Quan hệ "is-a": Manager là một Employee. C# chỉ cho kế thừa đơn (single inheritance) đối với class.

// Base class
public class Employee
{
    public string Name { get; set; } = "";
    public decimal BaseSalary { get; set; }

    public virtual decimal CalculatePay() => BaseSalary;

    protected void Log(string msg)         // chỉ derived gọi được
        => Console.WriteLine($"[{Name}] {msg}");
}

// Derived class — kế thừa + mở rộng
public class Manager : Employee
{
    public decimal Bonus { get; set; }

    public override decimal CalculatePay()
    {
        Log("Tính lương có bonus");
        return base.CalculatePay() + Bonus;     // gọi logic của cha
    }
}
⚠️ Đừng lạm dụng kế thừa: kế thừa tạo ràng buộc chặt (tight coupling) giữa cha-con. Cây kế thừa sâu (>2-3 tầng) rất khó bảo trì. Nhiều trường hợp nên dùng composition (xem mục 10). Quy tắc: chỉ kế thừa khi quan hệ "is-a" thực sự đúng và ổn định.

sealed — chặn kế thừa tiếp

// sealed class: không thể kế thừa nữa (vd: type bất biến, type tối ưu hiệu năng)
public sealed class AuditLog { /* ... */ }

// sealed override: cho phép override 1 lần rồi khoá lại ở tầng dưới
public class SalesManager : Manager
{
    public sealed override decimal CalculatePay() => base.CalculatePay() * 1.1m;
}

4. Trụ cột 3 — Polymorphism (Đa hình)

Polymorphism = "nhiều hình thái". Cùng một lời gọi method, hành vi khác nhau tuỳ runtime type của object. Đây là cơ chế giúp viết code dựa trên abstraction thay vì concrete type.

public abstract class Shape
{
    public abstract double Area();        // abstract: BẮT BUỘC override
    public virtual string Describe()       // virtual: CÓ THỂ override
        => $"Hình có diện tích {Area():F2}";
}

public class Circle : Shape
{
    public double Radius { get; init; }
    public override double Area() => Math.PI * Radius * Radius;
}

public class Rectangle : Shape
{
    public double Width { get; init; }
    public double Height { get; init; }
    public override double Area() => Width * Height;
    public override string Describe() => $"Chữ nhật {Width}x{Height}";
}

// Đa hình ở chỗ này: vòng lặp không quan tâm concrete type
Shape[] shapes = [new Circle { Radius = 2 }, new Rectangle { Width = 3, Height = 4 }];
foreach (var s in shapes)
    Console.WriteLine(s.Describe());           // gọi đúng override của từng type

virtual / override / new — phân biệt rõ

Từ khoáÝ nghĩaDùng khi
virtualKhai báo ở base, cho phép derived override. Vẫn có implementation mặc định.Có default behavior nhưng muốn cho override
abstractKhai báo ở base, KHÔNG có body, BẮT BUỘC derived override.Base không có cách mặc định hợp lý
overrideThay thế hẳn method virtual/abstract của base. Late-binding (runtime).Cung cấp logic riêng cho derived
new (method hiding)Che (hide) member của base, KHÔNG phải override. Early-binding (compile-time).Hiếm dùng — thường là dấu hiệu thiết kế sai
sealed overrideOverride rồi khoá, derived sâu hơn không override tiếp được.Khoá behavior, tối ưu hiệu năng
public class Base { public virtual string Who() => "Base"; }

// override: theo runtime type
public class A : Base { public override string Who() => "A"; }

// new: che, theo compile-time type — DỄ GÂY BUG
public class B : Base { public new string Who() => "B"; }

Base a = new A();  Console.WriteLine(a.Who()); // "A"  — đa hình hoạt động
Base b = new B();  Console.WriteLine(b.Who()); // "Base" — new KHÔNG đa hình!
🚫 Tránh new (method hiding): nó phá vỡ tính đa hình — kết quả phụ thuộc kiểu biến khai báo, không phải object thật. Trình biên dịch cảnh báo nếu bạn quên new; đó là tín hiệu nên dùng override hoặc thiết kế lại.

5. Trụ cột 4 — Abstraction (Trừu tượng hoá)

Abstraction = chỉ phơi bày cái gì (what) cần làm, ẩn đi làm thế nào (how). Code phụ thuộc vào abstraction (interface / abstract class) chứ không phụ thuộc chi tiết cụ thể → dễ thay thế, dễ test (Dependency Inversion).

// Abstraction: contract — KHÔNG nói gì về cách lưu trữ
public interface INotificationSender
{
    Task SendAsync(string to, string message);
}

// Các implementation cụ thể — ẩn sau abstraction
public class EmailSender : INotificationSender
{
    public Task SendAsync(string to, string msg)
        => SmtpClientWrapper.SendAsync(to, msg);   // chi tiết SMTP ẩn ở đây
}

public class SmsSender : INotificationSender
{
    public Task SendAsync(string to, string msg)
        => TwilioApi.SendAsync(to, msg);
}

// Service chỉ biết abstraction — không quan tâm Email hay Sms
public class OrderService(INotificationSender sender)
{
    public async Task PlaceOrderAsync(Order o)
    {
        // ... xử lý đơn hàng ...
        await sender.SendAsync(o.CustomerPhone, "Đơn hàng đã được đặt");
    }
}
💡 Abstraction vs Encapsulation: Encapsulation ẩn dữ liệu (state, ở mức object). Abstraction ẩn độ phức tạp của implementation (ở mức thiết kế). Hai khái niệm bổ trợ nhau chứ không trùng nhau.

6. Class vs Struct — reference type vs value type

Lựa chọn sai giữa class và struct gây bug khó tìm (copy ngầm) hoặc tốn hiệu năng (boxing, GC pressure). Hiểu rõ cơ chế bộ nhớ là bắt buộc.

Tiêu chíclass (reference type)struct (value type)
Lưu ởHeap (biến giữ tham chiếu)Stack hoặc inline trong object chứa nó
Gán / truyền tham sốCopy tham chiếu — cùng trỏ 1 objectCopy toàn bộ giá trị — bản sao độc lập
So sánh == mặc địnhSo sánh reference (cùng object?)So sánh từng field (value equality)
Giá trị mặc địnhnullTất cả field = 0/null (không bao giờ null trừ ?)
Kế thừaCó (single inheritance)KHÔNG (chỉ implement interface)
GCBị thu gom bởi GCKhông tạo gánh nặng GC (nếu trên stack)
// class — gán = copy tham chiếu
var p1 = new PointClass { X = 1 };
var p2 = p1;          // p2 và p1 cùng trỏ 1 object
p2.X = 99;
Console.WriteLine(p1.X);   // 99  — bị ảnh hưởng!

// struct — gán = copy giá trị
var s1 = new PointStruct { X = 1 };
var s2 = s1;          // s2 là BẢN SAO độc lập
s2.X = 99;
Console.WriteLine(s1.X);   // 1   — không bị ảnh hưởng

Khi nào dùng struct?

✅ Dùng struct khi

  • Đại diện 1 giá trị nhỏ, bất biến (vd: Point, Money, DateTime, Color)
  • Kích thước nhỏ (≤ ~16-24 bytes thường khuyến nghị)
  • Logic value-equality tự nhiên (2 điểm bằng nhau khi X,Y bằng)
  • Sống ngắn, tạo nhiều — tránh áp lực GC

❌ Tránh struct khi

  • Type lớn (copy tốn kém mỗi lần truyền)
  • Cần kế thừa hoặc identity (cùng object)
  • Có nhiều mutable state — dễ gây bug copy ngầm
  • Boxing thường xuyên (gán vào object/interface non-generic)

readonly struct & record struct (hiện đại)

// readonly struct — bất biến hoàn toàn, compiler tối ưu copy (không defensive copy)
public readonly struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }
    public Money(decimal amount, string currency)
        => (Amount, Currency) = (amount, currency);

    public Money Add(Money other) => new(Amount + other.Amount, Currency);
}

// record struct (C# 10+) — value type + value equality + ToString tự sinh + with-expression
public readonly record struct Point(double X, double Y);

var a = new Point(1, 2);
var b = a with { Y = 5 };       // tạo bản sao đổi Y → (1, 5)
Console.WriteLine(a == new Point(1, 2)); // True — value equality tự động
⚠️ Mutable struct là cái bẫy: struct có field thay đổi được dễ gây bug vì mỗi lần copy là một bản riêng — sửa bản sao không ảnh hưởng bản gốc, ngược với kỳ vọng. Hãy luôn dùng readonly struct trừ khi có lý do hiệu năng rất cụ thể.

7. Interface vs Abstract Class

Cả hai đều là abstraction, nhưng dùng cho mục đích khác nhau. Chọn sai dẫn đến thiết kế cứng nhắc. Đây là câu hỏi phỏng vấn kinh điển — cần nắm chắc.

Tiêu chíinterfaceabstract class
Quan hệ mô hình"can-do" / khả năng (IDisposable, IComparable)"is-a" / quan hệ phân loại
Đa kế thừa✅ implement nhiều interface❌ chỉ kế thừa 1 class
State (field)❌ không có instance field✅ có field, constructor
Constructor❌ không✅ có (gọi từ derived)
Access modifier cho memberpublic mặc định (từ C# 8 có thể private/protected)mọi modifier (public/protected/private...)
Implementation mặc định✅ default interface method (C# 8+)✅ method thường + virtual
Phiên bản hoá (versioning)Thêm method = breaking trừ khi có default implThêm method không break derived
// interface: định nghĩa khả năng, một class có thể có nhiều khả năng
public interface IExportable { byte[] Export(); }
public interface IPrintable  { void Print(); }

public class Invoice : IExportable, IPrintable  // nhiều interface — OK
{
    public byte[] Export() => Encoding.UTF8.GetBytes(ToString()!);
    public void Print() => Console.WriteLine("Đang in hoá đơn...");
}

// abstract class: chia sẻ state + behavior chung cho 1 họ type "is-a"
public abstract class Document
{
    protected DateTime Created { get; } = DateTime.UtcNow;  // state chung
    public abstract string Render();                       // con phải định nghĩa
    public string Header() => $"Tạo lúc {Created:u}";          // dùng chung
}

Default interface methods (C# 8+)

public interface ILogger
{
    void Log(LogLevel level, string message);

    // default method: thêm API mới mà KHÔNG break các implementation cũ
    void LogError(string message) => Log(LogLevel.Error, message);
    void LogInfo(string message)  => Log(LogLevel.Info, message);
}

// Implementer chỉ cần định nghĩa Log; LogError/LogInfo dùng default
public class ConsoleLogger : ILogger
{
    public void Log(LogLevel level, string msg)
        => Console.WriteLine($"[{level}] {msg}");
}
Chọn cái nào? Mặc định ưu tiên interface (linh hoạt, hỗ trợ DI, dễ mock khi test, cho phép đa "khả năng"). Dùng abstract class khi cần chia sẻ state + code chung và quan hệ "is-a" rõ ràng. Default interface methods là để versioning, KHÔNG phải để thay thế abstract class.

✅ Dùng interface khi

  • Định nghĩa contract cho DI / mocking
  • Nhiều type không liên quan cùng có 1 khả năng
  • Cần "đa kế thừa" hành vi

✅ Dùng abstract class khi

  • Có state/field chung cần chia sẻ
  • Có logic mặc định + bắt buộc override một phần
  • Quan hệ phân loại "is-a" chặt chẽ, ổn định

8. Access Modifiers — phạm vi truy cập

Encapsulation thực thi qua access modifier. C# có đầy đủ các mức từ rộng đến hẹp. Nguyên tắc: luôn dùng mức hẹp nhất có thể (least privilege).

ModifierTruy cập được từDùng khi
publicMọi nơi, mọi assemblyAPI công khai của thư viện/module
privateChỉ trong chính class/struct đóMặc định cho field, helper nội bộ
protectedTrong class đó + class kế thừa (kể cả khác assembly)Member cho derived dùng lại
internalTrong cùng assemblyAPI nội bộ của project, ẩn với bên ngoài
protected internalCùng assembly HOẶC derived ở assembly khácMở cho derived bên ngoài + nội bộ
private protected (C# 7.2+)Derived VÀ phải cùng assemblyMember nội bộ chỉ cho derived trong cùng lib
file (C# 11+)Chỉ trong cùng 1 file sourceType sinh bởi source generator, helper riêng file
public class Repository
{
    private DbConnection _conn;             // chỉ class này
    protected internal ILogger Logger;       // derived ngoài + nội bộ
    private protected void Trace() { }     // derived TRONG assembly này
    internal int CacheSize() => 100;       // chỉ assembly này thấy
    public Task SaveAsync() => Task.CompletedTask; // API công khai
}

// file-scoped type — không lộ ra ngoài file, dù trùng tên cũng không xung đột
file class InternalParser { /* chỉ file này dùng */ }
💡 Nguyên tắc: bắt đầu bằng private, chỉ mở rộng khi thực sự cần. Mức truy cập càng hẹp, "bề mặt" có thể bị lạm dụng càng nhỏ, refactor càng an toàn. Đối với class top-level: mặc định là internal nếu không ghi modifier.

9. Properties — đầy đủ các kiểu

Property là "mặt tiền" của encapsulation trong C#: trông như field nhưng thực chất là cặp method get/set. C# hiện đại có nhiều cú pháp ngắn gọn cho từng tình huống.

public class Product
{
    // 1. Auto-property — compiler tự tạo backing field ẩn
    public string Name { get; set; } = "";

    // 2. Get/set với backing field thủ công (validate / raise event)
    private decimal _price;
    public decimal Price
    {
        get => _price;
        set
        {
            if (value < 0) throw new ArgumentOutOfRangeException(nameof(value));
            _price = value;
        }
    }

    // 3. Init-only (C# 9) — chỉ gán lúc khởi tạo, sau đó bất biến
    public string Sku { get; init; } = "";

    // 4. Required member (C# 11) — BẮT BUỘC set khi tạo object
    public required string Category { get; init; }

    // 5. Computed / read-only — tính toán, không lưu
    public bool IsExpensive => Price > 1_000_000m;

    // 6. Expression-bodied get/set
    private string _slug = "";
    public string Slug
    {
        get => _slug;
        set => _slug = value.Trim().ToLowerInvariant();
    }

    // 7. Private setter — đọc public, chỉ class này ghi được
    public int StockCount { get; private set; }
    public void Restock(int qty) => StockCount += qty;
}

// required ép buộc khởi tạo đầy đủ:
var p = new Product { Category = "Sách" }; // OK
// var bad = new Product();  // ❌ COMPILE ERROR: thiếu 'Category'
init vs set: init cho phép gán trong object initializer rồi "đóng băng" — kết hợp tốt với immutability mà vẫn dùng được cú pháp { }. Kết hợp required + init là pattern phổ biến cho DTO/model bất biến trong .NET hiện đại.

10. Composition over Inheritance

Nguyên tắc thiết kế quan trọng nhất của OOP hiện đại: ưu tiên kết hợp (has-a) hơn kế thừa (is-a). Kế thừa tạo coupling chặt và cây phân cấp cứng nhắc; composition linh hoạt, dễ thay đổi runtime, dễ test.

❌ Vấn đề với kế thừa sâu

// Cây kế thừa cứng — "bùng nổ tổ hợp" (class explosion)
public class Vehicle { public virtual void Move() { } }
public class Car : Vehicle { }
public class FlyingCar : Car { public void Fly() { } }
// Cần AmphibiousFlyingCar? ElectricFlyingCar? → nổ class, không tái dùng được hành vi
// Mỗi khả năng mới (bay, lội nước, chạy điện) lại phải tạo nhánh kế thừa mới

✅ Refactor sang composition

// Mỗi khả năng là 1 thành phần độc lập, "cắm" vào khi cần
public interface IMover  { void Move(); }
public interface IFlyer  { void Fly(); }
public interface ISwimmer { void Swim(); }

public class RoadMover : IMover  { public void Move() => Console.WriteLine("Chạy đường bộ"); }
public class JetEngine : IFlyer  { public void Fly()  => Console.WriteLine("Bay bằng động cơ phản lực"); }

// Vehicle KẾT HỢP các khả năng (has-a) thay vì kế thừa (is-a)
public class Vehicle
{
    private readonly IMover _mover;
    private readonly IFlyer? _flyer;

    public Vehicle(IMover mover, IFlyer? flyer = null)
        => (_mover, _flyer) = (mover, flyer);

    public void Travel()
    {
        _mover.Move();
        _flyer?.Fly();              // chỉ bay nếu có khả năng bay
    }
}

// Lắp ráp linh hoạt — không cần class mới cho từng tổ hợp
var car      = new Vehicle(new RoadMover());
var flyingCar = new Vehicle(new RoadMover(), new JetEngine());
💡 Tại sao composition tốt hơn? (1) Linh hoạt — đổi hành vi lúc runtime bằng cách truyền component khác. (2) Tái dùng — JetEngine dùng được cho mọi vehicle. (3) Dễ test — mock từng component. (4) Tránh "fragile base class" — sửa base không làm vỡ hàng loạt derived. Đây cũng là tinh thần của Strategy Pattern và Dependency Injection.

❌ Kế thừa để tái dùng code

Kế thừa chỉ vì muốn dùng lại vài method của base → coupling chặt, dễ vi phạm LSP (Liskov), cây phân cấp phình to khó kiểm soát.

Khi nào kế thừa OK: quan hệ "is-a" thật sự + base ổn định + cần đa hình.

✅ Composition cho khả năng

Tách mỗi hành vi thành interface + implementation, inject vào. Lắp ghép tự do, thay thế runtime, test độc lập.

"Favor object composition over class inheritance" — Gang of Four.

11. record class — tham chiếu nhưng value equality

Bổ sung quan trọng cho OOP hiện đại: record (C# 9) là reference type nhưng có value equality, immutability tiện lợi và with-expression — lý tưởng cho DTO, model bất biến, message.

// record class — compiler tự sinh: Equals, GetHashCode, ToString, Deconstruct, with
public record Customer(int Id, string Name, string Email);

var c1 = new Customer(1, "Chien", "chien@a.com");
var c2 = c1 with { Email = "new@a.com" };   // bản sao đổi 1 field

Console.WriteLine(c1 == new Customer(1, "Chien", "chien@a.com")); // True (value eq)
Console.WriteLine(c1);   // Customer { Id = 1, Name = Chien, Email = chien@a.com }

12. Một ví dụ tổng hợp 4 trụ cột

Ghép tất cả lại trong một mini-domain: hệ thống thanh toán có nhiều phương thức.

// ABSTRACTION — contract cho mọi phương thức thanh toán
public interface IPaymentMethod
{
    Task<PaymentResult> ChargeAsync(decimal amount);
}

// ENCAPSULATION — base giữ state chung, ẩn chi tiết
public abstract class PaymentBase : IPaymentMethod
{
    private int _attempts;                      // state ẩn
    protected ILogger Logger { get; }

    protected PaymentBase(ILogger logger) => Logger = logger;

    // POLYMORPHISM — template method gọi bước trừu tượng
    public async Task<PaymentResult> ChargeAsync(decimal amount)
    {
        _attempts++;
        Logger.LogInformation("Lần thử #{N}", _attempts);
        if (amount <= 0) return PaymentResult.Invalid;
        return await ExecuteAsync(amount);       // con quyết định cách thực thi
    }

    protected abstract Task<PaymentResult> ExecuteAsync(decimal amount);
}

// INHERITANCE + POLYMORPHISM — mỗi phương thức override cách thực thi
public class CreditCardPayment : PaymentBase
{
    public CreditCardPayment(ILogger l) : base(l) { }
    protected override async Task<PaymentResult> ExecuteAsync(decimal a)
        => await CardGateway.ChargeAsync(a);
}

public class WalletPayment : PaymentBase
{
    public WalletPayment(ILogger l) : base(l) { }
    protected override Task<PaymentResult> ExecuteAsync(decimal a)
        => Task.FromResult(Wallet.Deduct(a));
}

// Caller chỉ phụ thuộc abstraction — đa hình hoàn toàn
public class Checkout(IPaymentMethod payment)
{
    public Task<PaymentResult> PayAsync(decimal total) => payment.ChargeAsync(total);
}
Quan sát: Checkout không biết và không quan tâm đang dùng thẻ hay ví — nó chỉ làm việc với IPaymentMethod (abstraction). Thêm phương thức mới (vd CryptoPayment) chỉ cần tạo class mới, không sửa Checkout. Đây là Open/Closed Principle nhờ đa hình.

13. Pitfalls thường gặp về OOP

❌ Anemic model — class chỉ toàn property

Class chỉ có get/set, mọi logic nằm ở "service" bên ngoài → mất encapsulation, dữ liệu không tự bảo vệ invariant.

Fix: đặt hành vi cạnh dữ liệu (rich domain model).

❌ God class — một class làm mọi thứ

Class hàng nghìn dòng, vi phạm Single Responsibility, không test nổi.

Fix: tách thành nhiều class nhỏ, mỗi class 1 trách nhiệm.

❌ Public field thay vì property

Mất khả năng validate, không break binary compat khi đổi sang property sau này.

Fix: luôn dùng property cho dữ liệu public.

❌ Kế thừa vi phạm LSP

Derived không thay thế được base (vd Square : Rectangle với set Width đổi cả Height).

Fix: kiểm tra "derived dùng được ở mọi nơi base dùng được" hay không.

❌ Mutable struct

struct có field set được → bug copy ngầm, sửa bản sao không ảnh hưởng gốc.

Fix: dùng readonly struct / record struct.

❌ Dùng new để hide method

Phá vỡ đa hình, kết quả phụ thuộc kiểu biến khai báo.

Fix: dùng virtual/override hoặc thiết kế lại.
