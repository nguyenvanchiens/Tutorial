Evaluation — Kiểm chứng output AI nghiêm túc

"Chạy thử thấy ổn" KHÔNG phải là đo lường. Khi xây sản phẩm AI thật, bạn cần eval harness: dataset chuẩn, chấm điểm có rubric, regression test cho prompt & agent, và cổng pass/fail. Đây là kỹ năng tách biệt người làm demo với người làm production.

01
Vì sao "chạy thử thấy ổn" là không đủ
LLM không tất định — một mẫu không nói lên gì

Vibe-check không phải là đo lường

LLM có tính ngẫu nhiên: cùng một prompt có thể cho output khác nhau. Bạn chỉnh prompt, thử 2-3 lần thấy "đẹp hơn" rồi deploy — đó là cảm tính, không phải bằng chứng. Khi lên production với hàng nghìn input đa dạng, prompt "nghe hay" đó có thể tệ hơn bản cũ ở 30% case mà bạn không hề biết.

Định nghĩa Evaluation: Đo lường chất lượng output AI một cách có hệ thống, lặp lại được, định lượng — trên một tập input đại diện, với tiêu chí rõ ràng, cho ra con số so sánh được giữa các phiên bản.

Eval là "unit test cho hệ thống AI"

Code thường: input cố định → output cố định → assert bằng nhau. Hệ thống AI: input đa dạng → output không tất định → cần chấm theo tiêu chí. Eval chính là tầng test cho phần "mềm" này — giúp bạn biết một thay đổi (đổi prompt, đổi model, thêm tool) là TIẾN BỘ hay THỤT LÙI.

02
Golden dataset — nền móng của mọi eval
Không có dữ liệu chuẩn thì không có gì để đo

Module 2.1: Xây golden dataset

Advanced

Golden dataset = tập các case {input, output mong muốn / tiêu chí} được chọn kỹ và (lý tưởng) được con người duyệt. Đây là "sự thật" bạn đo model dựa vào.

Nguyên tắc xây dataset tốt:
  • Đại diện: phản ánh phân bố input THẬT của production, không chỉ case dễ.
  • Có case khó: cố tình thêm biên, mơ hồ, đối nghịch — đó là nơi model hay vỡ.
  • Bắt đầu nhỏ, tăng dần: 30-50 case chất lượng tốt hơn 1000 case rác.
  • Nuôi từ production: mỗi lần model sai thật → thêm case đó vào dataset (regression chống tái phát).
  • Có nhãn người duyệt: với case quan trọng, đáp án chuẩn phải do người xác nhận.
Mẹo khởi động: Có thể dùng model (vd claude-opus-4-8) sinh nháp case đa dạng, nhưng PHẢI có người duyệt đáp án chuẩn — đừng để AI vừa sinh đề vừa chấm chính nó mà không kiểm soát.

03
LLM-as-judge pattern
Dùng một LLM để chấm output của LLM khác — mạnh nhưng phải kiểm soát

Khi nào cần LLM làm giám khảo?

Nhiều output không thể so khớp chính xác (so sánh chuỗi). "Câu trả lời này có hữu ích, đúng sự thật, đúng giọng không?" là phán đoán chất lượng — đây là lúc dùng LLM-as-judge: một model mạnh đọc input + output + tiêu chí và trả về điểm/nhãn.

# Judge prompt — chấm theo tiêu chí rõ ràng, trả JSON Bạn là giám khảo nghiêm khắc. Chấm câu trả lời theo 3 tiêu chí (0-5): - factual: có đúng so với tài liệu tham chiếu không? - relevant: có trả lời đúng câu hỏi không? - safe: có nội dung không phù hợp không? CÂU HỎI: {question} TÀI LIỆU THAM CHIẾU: {reference} CÂU TRẢ LỜI CẦN CHẤM: {answer} Trả về JSON: {"factual": n, "relevant": n, "safe": n, "lý_do": "..."}
Cảnh báo bias của judge: LLM-judge có thiên kiến — thích câu dài, thích văn phong giống nó, đôi khi "thiên vị" output của chính họ model. Phải hiệu chuẩn (calibrate) judge với nhãn người trên một tập con, và đo độ khớp giữa judge và người.

Module 3.1: Làm judge đáng tin

Advanced
  • Dùng model mạnh làm judge: judge nên ngang/mạnh hơn model bị chấm (vd claude-opus-4-8 chấm output claude-haiku-4-5).
  • Tiêu chí cụ thể, không hỏi chung "tốt không": chia nhỏ thành các trục đo được.
  • Buộc giải thích trước, điểm sau: tăng độ ổn định (chain-of-thought cho judge).
  • So sánh cặp (pairwise): "A hay B tốt hơn?" thường ổn định hơn chấm điểm tuyệt đối.
  • Đo agreement với người: nếu judge khớp người > 85%, mới tin được để chạy tự động.

04
Chấm điểm theo rubric
Biến "chất lượng" mơ hồ thành con số lặp lại được

Rubric: thang đo rõ ràng cho từng tiêu chí

Rubric mô tả CỤ THỂ mỗi mức điểm nghĩa là gì. Có rubric tốt, dù người hay LLM chấm cũng ra kết quả nhất quán. Đừng dùng thang "1-10" trống rỗng — hãy định nghĩa từng bậc.

ĐiểmTiêu chí "Tính đúng đắn"
0Sai hoàn toàn hoặc bịa thông tin (hallucination)
1Đúng một phần, có lỗi quan trọng
2Phần lớn đúng, sai chi tiết nhỏ
3Hoàn toàn đúng, bám sát tài liệu tham chiếu
Phân loại tiêu chí eval: Tiêu chí khách quan (đúng JSON schema? có chứa số đúng? code có chạy?) nên chấm bằng code/assertion — nhanh, rẻ, tất định. Chỉ dùng LLM-judge cho tiêu chí chủ quan (giọng, độ hữu ích, mạch lạc).
05
Xây eval harness
Hệ thống chạy toàn bộ dataset, chấm, ra báo cáo — tự động

Module 5.1: Kiến trúc một eval harness

Expert

Eval harness = vòng lặp: nạp dataset → chạy hệ thống AI trên từng case → chấm bằng (assertion + LLM-judge) → tổng hợp số liệu → so với baseline → quyết định pass/fail.

// TypeScript — eval harness tối giản với Agent SDK import { query } from "@anthropic-ai/claude-agent-sdk"; import { dataset } from "./golden.json"; let pass = 0; for (const c of dataset) { const out = await runSystem(c.input); // hệ thống cần đánh giá const objective = c.mustContain.every(s => out.includes(s)); // check khách quan const judged = await llmJudge(c.input, out, c.reference); // judge chủ quan if (objective && judged.score >= 3) pass++; } const score = pass / dataset.length; console.log(`Eval score: ${(score*100).toFixed(1)}%`); if (score < 0.85) process.exit(1); // pass/fail gate cho CI
Số liệu harness nên xuất: điểm tổng, điểm theo từng tiêu chí, danh sách case fail (để debug), cost & latency trung bình, so sánh với lần chạy trước.

06
Regression eval & pass/fail gate
Mỗi thay đổi prompt/agent phải chứng minh không làm tệ đi

Prompt & agent cần regression test như code

Sửa một dòng trong system prompt có thể cải thiện case A nhưng phá case B, C, D. Không có regression eval, bạn sẽ không bao giờ biết. Quy tắc: mọi thay đổi prompt, model, tool, hay logic agent phải chạy qua eval harness TRƯỚC khi merge.

Eval-driven development: Coi điểm eval như test suite. Sửa prompt → chạy eval → điểm tăng hoặc giữ thì merge, điểm giảm thì revert hoặc bổ sung case. Biến việc cải tiến prompt từ "đoán mò" thành "đo lường".

Module 6.1: Thiết kế pass/fail gate

Expert
  • Ngưỡng tuyệt đối: điểm tổng phải ≥ X% (vd 85%) mới qua CI.
  • Không thụt lùi (no regression): không case nào đang pass được phép chuyển sang fail.
  • Gate an toàn tuyệt đối: 0 case vi phạm safety — fail ngay dù điểm tổng cao.
  • Ngân sách cost/latency: nếu chậm/đắt hơn ngưỡng → fail dù chất lượng tốt.
  • Chạy nhiều lần: vì LLM ngẫu nhiên, chạy mỗi case 3-5 lần, lấy trung bình + đo độ ổn định.

07
Đo độ tin cậy của agent
Agent nhiều bước → lỗi tích luỹ, phải đo cả quá trình

Reliability = đúng một cách nhất quán, không chỉ đúng một lần

Agent chạy chuỗi nhiều bước (gọi tool, đọc kết quả, quyết định tiếp). Nếu mỗi bước đúng 95% nhưng có 10 bước, xác suất cả chuỗi đúng chỉ còn ~60%. Vì vậy đo agent khác đo một câu trả lời đơn lẻ — phải đo cả kết quả cuối lẫn quỹ đạo (trajectory).

Chỉ sốĐo gì
Task success rate% nhiệm vụ hoàn thành đúng đến cùng
Pass^k (đúng k lần liên tiếp)Độ ổn định — chạy lại nhiều lần vẫn đúng?
Tool-call accuracyGọi đúng tool, đúng tham số không?
Trajectory qualityĐường đi có hợp lý, không lặp vô ích?
Cost / số bướcHiệu quả — không "đốt" token để ra kết quả
Mẹo đo agent: Phân biệt outcome eval (kết quả cuối có đúng không) và process eval (đường đi có đúng không). Một agent đôi khi ra kết quả đúng nhờ may mắn dù đường đi sai — process eval bắt được điều đó.
08
Tránh eval overfitting
Điểm eval cao mà production vẫn tệ — vì bạn đã "học tủ"

Khi eval set trở thành "đề thi bị lộ"

Nếu bạn liên tục tinh chỉnh prompt để vượt qua đúng những case trong eval set, đến lúc nào đó bạn đang tối ưu cho bộ test chứ không phải cho chất lượng thật. Điểm eval đẹp nhưng gặp input mới ngoài đời lại vỡ — đây là overfitting.

  • Tách held-out set: giữ một phần dataset KHÔNG dùng khi tinh chỉnh, chỉ để kiểm tra cuối.
  • Làm mới dataset định kỳ: liên tục bổ sung case mới từ production để eval không "đứng yên".
  • Cảnh giác điểm gần tuyệt đối: 99% trên eval thường nghĩa là eval quá dễ, không phải hệ thống quá tốt.
  • Đo ngoài đời: kết hợp eval offline với metric production thật (phản hồi user, tỉ lệ escalate).
  • Đa dạng người chấm: đừng để một judge/một người định nghĩa toàn bộ "đúng".
Sự thật cuối cùng: Eval là bản đồ, không phải lãnh thổ. Mục tiêu là chất lượng THẬT cho người dùng, không phải con số đẹp. Eval tốt giúp bạn tiến nhanh và an toàn — nhưng đừng bao giờ tôn thờ chính con số đó.

Tổng kết — quy trình Evaluation chuẩn

# EVALUATION WORKFLOW 1. Xây golden dataset đại diện (có case khó, có nhãn người) 2. Chia tiêu chí: khách quan → assertion; chủ quan → LLM-judge (đã calibrate) 3. Viết rubric rõ ràng cho từng tiêu chí 4. Dựng harness: chạy toàn bộ dataset → chấm → ra số liệu 5. Đặt pass/fail gate trong CI (ngưỡng + no-regression + safety) 6. Mọi thay đổi prompt/agent → chạy eval TRƯỚC khi merge 7. Giữ held-out set + làm mới dataset từ production (chống overfit) 8. Kết hợp eval offline + metric production thật
