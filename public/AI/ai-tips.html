TIPS & TRICKS

Dùng AI coding đúng cách

Cùng một con AI, người dùng giỏi cho ra gấp đôi kết quả với một nửa số token. Đây là tập hợp các mẹo cụ thể, đã được kiểm chứng, để làm việc với công cụ AI coding (đặc biệt là Claude Code) một cách năng suất, tiết kiệm và an toàn.

01
Vệ sinh context — giữ ngữ cảnh gọn
Context dài và bẩn làm chất lượng đi xuống, không phải đi lên

Vì sao context dài lại làm AI kém đi

Trực giác sai phổ biến nhất: "nhồi càng nhiều thông tin càng tốt". Thực tế, một cửa sổ context đầy ắp tool output cũ, file không liên quan và các nhánh hội thoại đã chết khiến model khó tìm ra thứ thực sự quan trọng — nó bị nhiễu. Một phiên làm việc sạch và tập trung gần như luôn cho kết quả tốt hơn một phiên kéo dài 3 tiếng đủ thứ chuyện.

Quy tắc 1 phiên = 1 nhiệm vụ: Xong một việc thì gõ /clear trước khi sang việc mới. Đừng để phần fix bug lúc sáng còn lẩn quẩn trong context khi bạn đang viết feature buổi chiều.

Module 1.1: Thói quen giữ context lean

Cơ bản
  • /clear giữa các task — reset hội thoại, giải phóng toàn bộ context cũ.
  • Chỉ tham chiếu file cần thiết — đừng bảo AI "đọc cả thư mục" nếu chỉ cần 2 file.
  • Tách nhiệm vụ lớn thành phiên nhỏ — mỗi phiên một mục tiêu rõ ràng.
  • Để AI tự quản lý context — Claude Code tự nén (compaction) khi gần đầy; đừng cố nhồi thủ công.
/clear Compaction Scoped reads
02
Làm chủ CLAUDE.md
File hướng dẫn dự án — ngắn, đậm tín hiệu, AI đọc trong MỌI phiên

CLAUDE.md là gì và vì sao quan trọng

CLAUDE.md ở gốc dự án được nạp vào context tự động ở đầu mỗi phiên. Đây là nơi bạn dạy AI những thứ nó không thể tự suy ra: lệnh build, quy ước code, kiến trúc tổng thể, các "bẫy" của codebase. Viết tốt một lần, hưởng lợi mãi mãi.

Nên đưa vào:
  • Lệnh hay dùng: npm run dev, npm test, npm run lint, cách chạy 1 test riêng lẻ.
  • Quy ước: style code, naming, dùng tabs hay spaces, không dùng thư viện X.
  • Kiến trúc: module nào làm gì, dữ liệu chảy thế nào, file nào là trung tâm.
  • Gotchas: "đừng sửa file generated", "luôn chạy migration trước khi test".
Ngắn và đậm tín hiệu: CLAUDE.md tốn context mỗi phiên. Một file 5000 từ lan man còn hại hơn 30 dòng cô đọng. Cắt mọi câu không thay đổi hành vi của AI.

Module 2.1: Khung CLAUDE.md gọn

Trung cấp
# CLAUDE.md — ví dụ cô đọng, đậm tín hiệu ## Commands - npm run dev # chạy dev server - npm test # chạy toàn bộ test - npm test -- auth.spec.ts # chạy 1 file test ## Conventions - React 19, JSX thuần (KHÔNG TypeScript) - State-driven, không dùng router ## Gotchas - File trong public/ là HTML tĩnh, KHÔNG phải component React - Nội dung viết bằng tiếng Việt có dấu
Mẹo cập nhật: Khi AI hiểu sai một điều gì đó lặp lại, đừng sửa thủ công mỗi lần — thêm một dòng vào CLAUDE.md. Trong Claude Code, gõ # để ghi nhanh một ghi nhớ vào file này.
CLAUDE.md # memory /init
03
Mẫu prompt hiệu quả
Cụ thể, có ví dụ, tham chiếu file bằng đường dẫn, xin kế hoạch trước

Cụ thể đánh bại mơ hồ — mọi lúc

"Sửa bug login" là prompt tệ. "Trong src/auth/login.ts, hàm validateToken trả về true cả khi token hết hạn — sửa để nó kiểm tra expiresAt so với thời gian hiện tại, và thêm test cho case hết hạn" là prompt tốt. Càng cụ thể, AI càng ít phải đoán, và càng ít đoán sai.

  • Tham chiếu file bằng đường dẫn — src/components/Sidebar.jsx, không phải "cái sidebar đó".
  • Đưa ví dụ input/output — cho AI thấy đúng cái bạn muốn thay vì mô tả.
  • Nêu rõ ràng buộc — "đừng thêm thư viện mới", "giữ API cũ tương thích".
  • Xin kế hoạch trước với việc lớn — "Đề xuất cách làm trước, đừng viết code vội" (xem mục 04).

Module 3.1: Khung prompt "việc khó"

Trung cấp
# Khung prompt cho task phức tạp Bối cảnh: Đây là API thanh toán, dùng cho khách doanh nghiệp. Mục tiêu: Thêm retry với exponential backoff cho hàm chargeCard trong src/billing/charge.ts Ràng buộc: Tối đa 3 lần retry; KHÔNG retry khi lỗi 4xx; dùng thư viện sẵn có, đừng cài mới. Yêu cầu: Đề xuất kế hoạch trước. Sau khi tôi duyệt mới viết code. Viết kèm test cho cả case thành công và case hết retry.
Vì sao đưa "lý do": Nói cho AI biết vì sao bạn cần việc đó ("API này cho khách doanh nghiệp, lỗi tốn tiền thật") giúp nó đưa ra quyết định tốt hơn nhiều so với chỉ đưa mệnh lệnh khô khan.

04
Plan mode & thinking
Bắt AI nghĩ và lập kế hoạch TRƯỚC khi nó đụng vào code

Lập kế hoạch trước = sửa rẻ

Với task lớn hoặc rủi ro, sai lầm đắt nhất là để AI lao vào sửa 15 file ngay lập tức theo một hướng tiếp cận sai. Plan mode trong Claude Code cho AI khảo sát codebase và đề xuất kế hoạch mà không chỉnh sửa gì — bạn duyệt kế hoạch (giai đoạn rẻ nhất để bắt lỗi hiểu sai) rồi mới cho thực thi.

Khi nào dùng plan mode: task chạm nhiều file, refactor kiến trúc, hoặc khi bạn chưa chắc cách làm đúng. Với việc nhỏ rõ ràng (sửa 1 dòng) thì không cần — chỉ tốn thời gian.

Module 4.1: "Plan first" và mức độ suy nghĩ

Nâng cao

Các model Claude đời mới (như claude-opus-4-8) suy nghĩ sâu hơn ở mỗi bước. Với agentic/coding, đặt mức effort cao (high/xhigh) và đưa toàn bộ yêu cầu rõ ràng ngay từ lượt đầu tiên cho kết quả tốt nhất — model lên kế hoạch tốt hơn và thường tốn ÍT token hơn nhờ ít phải làm lại.

Mẫu xin kế hoạch:
# Bắt AI lập kế hoạch trước khi code Hãy KHẢO SÁT codebase và đề xuất kế hoạch chi tiết để [mô tả task]. Liệt kê các file sẽ sửa và thứ tự thực hiện. ĐỪNG viết code cho tới khi tôi duyệt kế hoạch.
Đưa mục tiêu lên đầu: Một lượt đầu tiên đặc tả đầy đủ (mục tiêu, ràng buộc, tiêu chí "xong") thắng xa việc nhỏ giọt yêu cầu qua nhiều lượt. Trong Claude Code có thể dùng /goal để đặt định hướng cho cả phiên dài.
Plan mode effort: high/xhigh /goal
05
Slash command tùy biến & Skills
Tự động hóa các prompt lặp đi lặp lại

Đóng gói prompt lặp lại thành lệnh

Nếu bạn gõ cùng một đoạn prompt dài lần thứ ba ("review diff này tìm bug, kiểm tra cả null check và race condition..."), đã đến lúc biến nó thành lệnh. Custom slash command trong Claude Code là file Markdown trong .claude/commands/ — gõ /tên-lệnh là nạp lại nguyên prompt đó.

# .claude/commands/review.md — gọi bằng /review Review diff hiện tại tìm bug đúng/sai (correctness): - Kiểm tra null/undefined chưa xử lý - Kiểm tra biên (off-by-one, mảng rỗng) - Kiểm tra race condition và double-submit Báo cáo theo mức độ nghiêm trọng, kèm số dòng.

Module 5.1: Skills — chuyên môn nạp khi cần

Nâng cao

Skills là các thư mục chứa SKILL.md đóng gói quy trình/chuyên môn cho một loại task (ví dụ: tạo file Excel, quy ước viết tài liệu). Phần mô tả ngắn nằm sẵn trong context; AI chỉ đọc toàn bộ nội dung khi task thực sự cần — giữ context gốc nhỏ mà vẫn có chuyên môn sâu khi đụng việc.

Khác biệt với prompt: Prompt là chỉ dẫn cho một lần. Slash command và Skills là tài sản tái sử dụng — viết một lần, dùng mọi phiên, chia sẻ cho cả team qua git.
/custom-command SKILL.md .claude/commands
06
Kiểm chứng, đừng tin lời
Bắt AI chạy test / hiện output thật; tự review diff

"Đừng nói nó chạy — CHẠY nó và cho tôi xem output"

Code AI sinh ra trông đúng không có nghĩa là chạy đúng. Khác biệt giữa người dùng nghiệp dư và pro: pro không bao giờ chấp nhận "code này sẽ chạy được". Với agent có quyền chạy lệnh (như Claude Code), hãy bắt nó thực sự chạy test, build, hoặc một đoạn console.log rồi dán output thật làm bằng chứng.

Luôn đọc diff trước khi merge: AI có thể "tiện tay" sửa thứ bạn không yêu cầu, xóa code, hoặc đổi hành vi ngầm. Review diff không phải tùy chọn — đó là rào chắn cuối cùng giữa code AI và nhánh main.

Module 6.1: Vòng lặp tự chứng minh

Trung cấp
  • Bắt chạy test sau mỗi lần sửa — "sửa xong PHẢI chạy npm test và dán output".
  • Dùng hook để tự động — cấu hình hook chạy test/lint mỗi khi agent sửa file, để nó không thể "quên".
  • Hiểu trước khi chấp nhận — nếu bạn không hiểu một đoạn code, đừng merge; hỏi AI giải thích.
  • Cảnh giác câu "Done!" — "xong" mà không có output xác nhận chỉ là lời hứa.
Run tests Hooks Diff review
07
Refactor lớn & nhiều file
Giới hạn phạm vi, checkpoint bằng git, đi từng bước nhỏ

Chia nhỏ, không "big bang"

Yêu cầu AI "refactor toàn bộ codebase sang pattern mới" trong một lượt là công thức cho thảm họa: nửa chừng nó lạc hướng, để lại trạng thái dở dang khó hồi phục. Thay vào đó, chia thành các bước nhỏ kiểm chứng được, và commit sau mỗi bước xanh.

Bẫy "context rot" khi refactor dài: Một lượt sửa quá nhiều file khiến AI quên trạng thái ban đầu và mâu thuẫn với chính nó. Đi từng module một, /clear giữa các module độc lập.

Module 7.1: Quy trình refactor an toàn

Nâng cao
# Refactor lớn — đi từng bước, checkpoint bằng git 1. git commit / git stash # lưu trạng thái sạch trước khi bắt đầu 2. Yêu cầu AI lập kế hoạch chia bước (plan mode) 3. Làm BƯỚC 1 → chạy test → commit 4. Làm BƯỚC 2 → chạy test → commit 5. Lạc hướng? git reset về checkpoint gần nhất, thử lại nhỏ hơn
Worktree cho việc rủi ro: Với thay đổi lớn/mạo hiểm, làm trong một git worktree riêng (xem mục 08) để nhánh chính luôn nguyên vẹn và dễ vứt bỏ nếu hỏng.
Small steps git checkpoint git reset
08
Git workflow với AI
Commit thường xuyên, worktree cho việc song song/rủi ro, review trước commit

Git là lưới an toàn cho code AI

Khi để AI sửa code tự động, git là cứu cánh. Commit thường xuyên tạo các điểm hồi phục; mỗi commit nhỏ giúp dễ git diff, dễ git revert đúng phần hỏng mà không mất phần tốt.

  • Commit nhỏ và thường xuyên — mỗi đơn vị công việc xanh là một commit.
  • Luôn review diff trước khi commit — đọc git diff, không commit mù.
  • Đừng để AI tự push lên main — tạo nhánh trước; chỉ push/commit khi bạn chủ động yêu cầu.

Module 8.1: Worktree cho việc song song & mạo hiểm

Nâng cao

Git worktree cho phép checkout nhiều nhánh ra các thư mục riêng cùng lúc — lý tưởng để chạy nhiều phiên AI song song hoặc thử một thay đổi rủi ro mà không động đến working directory chính.

# Tạo worktree riêng cho một thử nghiệm mạo hiểm git worktree add ../proj-experiment -b experiment # Cho AI làm trong ../proj-experiment; nhánh main vẫn nguyên # Hỏng thì xóa sạch, không ảnh hưởng gì: git worktree remove ../proj-experiment
Mẹo: Mỗi worktree là một context cô lập. Chạy 2 phiên AI ở 2 worktree để xử lý 2 feature độc lập song song mà không giẫm chân nhau.
git worktree feature branch git revert
09
Chọn model & tiết kiệm token
Dùng đúng model cho đúng việc; giữ phiên gọn để giảm chi phí

Không phải việc gì cũng cần model mạnh nhất

Mỗi model có điểm cân bằng riêng giữa trí tuệ, tốc độ và chi phí. Dùng model mạnh cho việc khó (refactor lớn, gỡ bug hóc búa, agentic dài hơi); dùng model nhanh/rẻ cho việc đơn giản (phân loại, tóm tắt, sửa lặt vặt). Chỉ dùng đúng các ID model thật bên dưới.

Module 9.1: Giảm chi phí mà không giảm chất lượng

Trung cấp
  • Giữ phiên gọn — /clear giữa task; context ngắn = ít token đầu vào mỗi lượt.
  • Đặc tả đầy đủ từ đầu — ít vòng làm-lại nghĩa là ít token tổng, và thường chất lượng cao hơn.
  • Tận dụng prompt caching — phần ngữ cảnh ổn định (như CLAUDE.md) được cache, đọc lại rẻ hơn nhiều.
  • Chỉnh effort theo việc — high/xhigh cho coding/agentic; medium/low cho việc thường để tiết kiệm.

10
Bẫy thường gặp & anti-pattern
Những thói quen âm thầm phá hỏng năng suất của bạn

Các sai lầm kinh điển khi dùng AI coding

  • Copy-paste không hiểu: dán code AI vào dự án mà không hiểu nó làm gì — nợ kỹ thuật trá hình, không debug nổi khi hỏng.
  • Quá tin AI: nhận "nó sẽ chạy được" mà không kiểm chứng; bỏ qua review diff.
  • Prompt mơ hồ: "làm cho nó tốt hơn" — AI buộc phải đoán ý bạn, và đoán sai.
  • Để context thối (context rot): phiên kéo dài nhiều giờ đủ thứ chuyện, AI lẫn lộn nhiệm vụ.
  • Big-bang refactor: sửa cả codebase trong một lượt, không checkpoint git.
  • Bịa ID model / API: dùng tên model không có thật thay vì các ID thật ở mục 09.

11
Prefix Command & Trigger Word — "mã lệnh" đặt trước prompt
Sự thật đằng sau các mã kiểu /Ghost <prompt>, Scaffold <prompt> bạn thấy share trên mạng
Đọc cái này trước: Những "mã thần kỳ" như L99 <prompt>, /Ghost <prompt>, Scaffold <prompt> KHÔNG phải lệnh có sẵn (built-in) của Claude hay Claude Code. Gõ /Ghost vào một phiên Claude trống thì không có gì xảy ra. Chúng "chạy được" với người share vì họ đã tự định nghĩa trước (custom command), hoặc đó chỉ là câu "mồi" persona/mode. Hiểu đúng cơ chế thì bạn tự tạo được bộ của riêng mình — mạnh hơn nhiều việc copy mã của người khác.

Vì sao "prefix một mã" lại cho output chuẩn hơn?

Vì cái prefix đó bung ra (expand) thành một prompt dài có cấu trúc mà bạn đã soạn sẵn: vai trò, ràng buộc, định dạng đầu ra, checklist... Thay vì gõ lại đoạn dài đó mỗi lần, bạn gói nó vào 1 từ khoá ngắn. Bản chất là tái sử dụng prompt tốt, không phải phép thuật.

Module 11.1: Cơ chế THẬT #1 — Custom Slash Command

Cách tự tạo

Đây chính là thứ đứng sau các ví dụ /Ghost, /scaffold. Trong Claude Code, tạo file Markdown trong .claude/commands/ — tên file thành tên lệnh. Dùng $ARGUMENTS để chèn phần prompt bạn gõ sau lệnh.

# .claude/commands/scaffold.md # → tạo ra lệnh /scaffold Bạn là senior engineer. Scaffold một feature hoàn chỉnh cho yêu cầu sau: $ARGUMENTS Yêu cầu bắt buộc: - Đề xuất cấu trúc file trước, chờ xác nhận nếu thay đổi lớn. - Viết code + test đi kèm, theo convention trong CLAUDE.md. - Chạy test, dán output thật để chứng minh.

Giờ gõ /scaffold form đăng ký có validate email → Claude bung nguyên template trên với $ARGUMENTS = "form đăng ký...". Đó đúng là trải nghiệm "mã + prompt" bạn thấy.

Module 11.2: Cơ chế THẬT #2 — Trigger word có sẵn (dùng được ngay)

Built-in thật

Khác với mã tự chế, đây là từ khoá thật sự được Claude Code nhận diện, không cần cài gì:

  • think → think hard → think harder → ultrathink: tăng dần "ngân sách suy nghĩ" của model trước khi trả lời. Dùng cho bài toán khó (thiết kế, debug rối). Đây là cái gần nhất với "mã làm output chuẩn hơn" mà có thật.
  • Plan mode: bắt model lập kế hoạch trước, không sửa file cho tới khi bạn duyệt — lý tưởng cho task lớn.
// Dùng trực tiếp, không cần định nghĩa gì: ultrathink: thiết kế schema DB cho hệ thống đặt vé có chống overbooking // càng "nặng" từ khoá, model suy nghĩ càng kỹ (và tốn token hơn)
Mẹo: chỉ dùng ultrathink khi thật sự cần — nó tốn token hơn nhiều. Việc đơn giản thì think hoặc không cần là đủ.

12.1 · Subagent chạy song song

Đòn mạnh nhất

Claude Code có thể bung nhiều agent con cùng lúc, mỗi agent có context riêng → không làm "thối" context chính. Lý tưởng cho việc fan-out: đọc nhiều subsystem, review nhiều khía cạnh, viết nhiều file.

// Ví dụ thật: "Spawn 5 agent song song, mỗi agent rà 1 thư mục (BE, FE, infra, tests, docs) và báo về các bug tìm được." // Mỗi agent làm độc lập → gộp kết quả → nhanh gấp nhiều lần
Mẹo: nói rõ "song song" / "parallel" và chia việc theo ranh giới rõ ràng (theo thư mục, theo khía cạnh) để các agent không giẫm chân nhau.

13.1 · Hooks — tự động theo sự kiện

Do harness chạy, chắc chắn

Hook là lệnh tự chạy khi có sự kiện (trước/sau khi sửa file, trước khi commit...). Khác với "nhờ Claude nhớ làm" — hook do harness thực thi nên luôn chạy.

  • PostToolUse: tự dotnet format / prettier sau mỗi lần sửa file.
  • PreToolUse: chặn ghi vào file nhạy cảm, chặn commit chứa secret.
  • Stop / Notification: báo khi Claude làm xong (chuông, thông báo).
Mẹo: muốn một hành vi "luôn luôn xảy ra tự động" thì phải dùng hook, không phải ghi vào CLAUDE.md — vì model có thể quên, còn hook thì không.
PostToolUsePreToolUseauto-format / lint

13.2 · MCP servers — cắm thêm "giác quan" cho Claude

Kết nối hệ thống ngoài

MCP cho Claude thao tác trực tiếp với công cụ ngoài. Vài cái hữu ích cho dev .NET/React/AI:

  • Playwright MCP: Claude mở trình duyệt thật, click/chụp màn hình → tự kiểm chứng UI sau khi sửa.
  • Database/Postgres MCP: truy vấn DB trực tiếp để hiểu schema, kiểm tra dữ liệu.
  • Code-graph MCP (vd codegraph): index codebase thành đồ thị → Claude tra cứu thay vì đọc mò file, đỡ tốn token với repo lớn.
  • GitHub MCP: đọc/tạo PR, issue, review.
An toàn: MCP là bên thứ ba — ưu tiên loại chạy local, mã nguồn mở, ít quyền. "Năm server chọn kỹ hơn hai mươi server cài bừa."
