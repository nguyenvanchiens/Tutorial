Testing với AI

Code AI sinh ra trông đúng — không có nghĩa là chạy đúng. Bài này dạy bạn dùng test như một cơ chế kiểm chứng: bắt AI tự viết test, tự chạy, tự chứng minh code làm đúng việc bạn cần.

01
Vì sao test là vũ khí chống AI ảo
LLM tối ưu cho "trông hợp lý", test tối ưu cho "thật sự đúng"

Vấn đề cốt lõi: AI tự tin kể cả khi sai

Một model như claude-opus-4-8 hay claude-sonnet-4-6 sinh code rất nhanh và trôi chảy. Nhưng nó tối ưu cho việc tạo ra văn bản plausible (nghe hợp lý), không phải văn bản verified (đã kiểm chứng). Kết quả: off-by-one, sai biên, sai giả định business logic — tất cả đều được viết với giọng văn rất tự tin.

Test là cầu nối giữa "trông đúng" và "chạy đúng". Khi có test xanh + bạn đã đọc test đó kỹ, niềm tin vào code AI sinh ra chuyển từ cảm tính sang bằng chứng.

Nguyên tắc nền tảng: Không bao giờ merge code AI sinh ra chỉ vì "đọc thấy ổn". Phải có test chứng minh — và bạn phải hiểu test đó kiểm tra cái gì.

Test biến AI thành một hệ thống tự sửa

Khi AI có thể chạy test và đọc output thất bại, nó có vòng phản hồi để tự sửa: viết code → chạy test → đọc lỗi → sửa → lặp lại. Không có test, AI chỉ đoán. Có test, AI có "sự thật khách quan" để hội tụ về.

02
Test-first prompting (TDD với AI)
Viết test trước, dùng test làm spec để AI implement theo

Module 2.1: Test là bản đặc tả chính xác nhất

Intermediate

Mô tả bằng lời dễ mơ hồ. Test là spec có thể chạy được — AI không thể "diễn giải sai" một test cụ thể. Quy trình: bạn (hoặc AI dưới sự duyệt của bạn) viết test mô tả hành vi mong muốn TRƯỚC, rồi yêu cầu AI implement cho test xanh.

Prompt mẫu (đưa cho Claude Code):
# Test-first prompt — viết test trước, KHÓA test lại Đây là test cho hàm `parseInvoiceTotal`. ĐỪNG sửa test. Viết implementation để toàn bộ test PASS. Sau khi viết xong, CHẠY test và dán output. Nếu fail, sửa code (không sửa test) rồi chạy lại. describe("parseInvoiceTotal", () => { it("cộng các dòng item", () => expect(parseInvoiceTotal([10, 20])).toBe(30)); it("trả 0 khi rỗng", () => expect(parseInvoiceTotal([])).toBe(0)); it("ném lỗi với số âm", () => expect(() => parseInvoiceTotal([-5])).toThrow()); });
Mẹo khoá test: Câu "ĐỪNG sửa test" cực kỳ quan trọng. Nếu không, AI hay "sửa test cho khớp code sai" thay vì sửa code cho khớp test đúng.
TDD Red-Green-Refactor Spec-as-code

Module 2.2: Để AI đề xuất test, BẠN duyệt

Intermediate

Với tính năng mới, hãy bắt AI liệt kê các case test (happy path, biên, lỗi) trước khi viết code. Bạn review danh sách đó — đây là lúc rẻ nhất để phát hiện AI hiểu sai yêu cầu. Khi danh sách case đã đúng, mới cho AI viết test + code.

03
Bắt AI viết test cho legacy code
Characterization test — chốt hành vi hiện tại trước khi đụng vào

Vấn đề: code cũ không test, sửa là vỡ

Với code legacy, bạn không có spec. Chiến lược: dùng AI sinh characterization test — test ghi lại hành vi HIỆN TẠI (kể cả bug), tạo lưới an toàn trước khi refactor.

Bẫy nguy hiểm: Characterization test chốt hành vi hiện có, kể cả khi hành vi đó SAI. Đừng để AI tự quyết "đúng/sai" — hỏi nó đánh dấu rõ test nào đang chốt một hành vi đáng ngờ để bạn xem lại.

Module 3.1: Quy trình bọc test cho legacy

Advanced
Các bước:
  • 1. Sinh test mô tả hành vi hiện tại — chạy hàm với nhiều input, ghi output thật làm assertion.
  • 2. Chạy test trên code GỐC — phải xanh 100% (vì nó mô tả chính code gốc).
  • 3. Đánh dấu hành vi đáng ngờ — bắt AI comment // TODO: hành vi này có thể là bug ở các case lạ.
  • 4. Refactor — giờ mới cho AI sửa code; test gốc làm lưới an toàn.
  • 5. Sửa bug có chủ đích — đổi assertion một cách CÓ Ý THỨC, ghi rõ lý do trong commit.

04
Coverage-driven & Mutation-driven loop
Đo độ phủ là sàn, mutation testing mới đo chất lượng test

Coverage không phải mục tiêu — chỉ là tín hiệu

Bắt AI chạy coverage, tìm dòng/nhánh chưa được test, viết bổ sung. Nhưng cảnh giác: 100% coverage không nghĩa là code đúng — chỉ nghĩa là mọi dòng đã được chạy qua, không phải mọi dòng đã được kiểm chứng.

# Coverage-driven loop với AI Chạy: npm run test -- --coverage Liệt kê các nhánh chưa phủ. Với MỖI nhánh, giải thích nó xử lý case gì, rồi viết test ý nghĩa cho nó (KHÔNG viết test rỗng chỉ để tăng %). Chạy lại coverage và dán bảng kết quả.

Module 4.1: Mutation testing — test cho chính test

Advanced

Mutation testing cố tình "gài bug" vào code (đổi + thành -, > thành >=, xoá dòng). Nếu test của bạn KHÔNG đỏ khi code bị gài lỗi, test đó vô dụng. Đây là cách thật sự đo chất lượng test — quan trọng hơn coverage rất nhiều.

Loop với AI: chạy mutation tool → tìm "surviving mutants" (đột biến sống sót) → bắt AI viết test để giết chúng → lặp đến khi mutation score đủ cao.

05
"Make the AI prove it works"
Không tin lời AI nói — bắt nó chạy và dán output thật

Đòi bằng chứng, không đòi lời hứa

Khác biệt lớn nhất giữa người dùng AI nghiệp dư và pro: pro không bao giờ chấp nhận "code này sẽ chạy được". Họ bắt AI THỰC SỰ chạy test và dán output. Với agent có quyền thực thi (Claude Code, Agent SDK), điều này khả thi và bắt buộc.

Câu thần chú: "Đừng nói với tôi nó chạy — CHẠY nó và cho tôi xem output." Một mệnh đề console.log hay một dòng test xanh thật giá trị hơn cả đoạn văn AI tự tin giải thích.

Module 5.1: Agent SDK loop tự chứng minh

Advanced

Với @anthropic-ai/claude-agent-sdk (TypeScript) hoặc claude-agent-sdk (Python), bạn cấp cho agent công cụ chạy lệnh và bắt nó lặp đến khi test thật sự xanh.

06
Sinh edge case có hệ thống
AI giỏi liệt kê biên — nếu bạn hỏi đúng cách

Bắt AI nghĩ như kẻ phá hoại

Happy path thì ai cũng viết được. Giá trị của AI nằm ở chỗ liệt kê nhanh các biên mà con người hay quên. Đừng hỏi "viết test" chung chung — hãy yêu cầu theo từng nhóm biên cụ thể:

  • Biên giá trị: 0, -1, MAX_INT, số rất lớn, số thập phân, số âm.
  • Biên rỗng/null: chuỗi rỗng, mảng rỗng, null, undefined, khoảng trắng.
  • Biên Unicode: emoji, ký tự có dấu (tiếng Việt!), RTL, ký tự zero-width.
  • Biên thời gian: đổi múi giờ, năm nhuận, DST, timestamp âm.
  • Biên đồng thời: race condition, gọi lại nhiều lần, double-submit.
  • Đầu vào độc hại: chuỗi cực dài, payload SQL/script, ký tự điều khiển.
Mẹo tiếng Việt: Luôn thêm 1 case test với chuỗi tiếng Việt có dấu ("Nguyễn Đệ", "phố Huế") — AI hay quên test encoding/normalize và đây là nguồn bug kinh điển ở app Việt.
07
Verify test không bị "tautological"
Test AI viết có thể xanh mà chẳng kiểm tra gì cả

Test tautological — cái bẫy nguy hiểm nhất khi AI viết cả code lẫn test

Khi AI viết cả code và test cùng lúc, nó dễ tạo ra test chỉ phản chiếu lại implementation (kể cả implementation sai), thay vì kiểm chứng yêu cầu thật. Test xanh nhưng vô nghĩa.

// ❌ Test tautological — mock chính thứ đang test it("tính thuế", () => { calc.computeTax = jest.fn().mockReturnValue(100); expect(calc.computeTax(1000)).toBe(100); // luôn xanh, vô nghĩa }); // ❌ Assert lại đúng code, không phải yêu cầu it("giảm giá", () => { // code: return price * 0.9; test: expect(...).toBe(price * 0.9) // Cả hai sai cùng nhau (đáng lẽ giảm 20%) → vẫn xanh });
Dấu hiệu test rỗng: không có giá trị kỳ vọng cụ thể (dùng lại biểu thức của code), mock chính unit đang test, assertion kiểu toBeDefined() chung chung, hoặc test vẫn xanh khi bạn cố tình phá code.

Module 7.1: Kiểm chứng test bằng giá trị độc lập

Advanced
  • Hard-code kỳ vọng: tự tính tay kết quả đúng và viết toBe(180), đừng để AI viết toBe(price*0.9).
  • Test sanity "phải đỏ": cố tình phá code → chạy test → nó PHẢI đỏ. Nếu vẫn xanh, test vô dụng.
  • Tách người viết: để model này (vd claude-sonnet-4-6) viết code, model/lần khác viết test — giảm việc cùng-sai-một-kiểu.
  • Cấm mock unit đang test: chỉ mock dependency ngoài (DB, HTTP), không mock chính hàm đang kiểm.
Independent oracle Sanity-fail check No self-mock
08
Tích hợp vào dev loop
Biến "AI tự chứng minh" thành thói quen, không phải nỗ lực một lần

Vòng lặp phát triển chuẩn với AI

# Dev loop bền vững với AI coding agent 1. Viết/duyệt test mô tả hành vi mong muốn (bạn nắm spec) 2. AI implement → AI chạy test → dán output (bằng chứng, không lời hứa) 3. Test đỏ? AI đọc lỗi, sửa code (không sửa test), chạy lại 4. Test xanh? Bạn review test có ý nghĩa không (chống tautological) 5. Chạy mutation/coverage định kỳ để đo chất lượng test 6. CI gate: test + lint + coverage tối thiểu phải xanh mới merge
Tự động hoá bằng hook: Cấu hình hook để mỗi lần agent sửa file là test tự chạy — agent không thể "quên" chứng minh. Test trở thành rào chắn tự động, không phụ thuộc kỷ luật con người.

Tổng kết — 5 luật vàng Testing với AI

  • 1. Test xanh + bạn đã đọc test = bằng chứng. Còn lại chỉ là cảm tính.
  • 2. Khoá test, bắt AI sửa code cho khớp test — đừng để nó sửa ngược.
  • 3. "Chạy nó và cho tôi xem output", không bao giờ nhận "nó sẽ chạy được".
  • 4. Cảnh giác test tautological — luôn làm phép thử "phải đỏ".
  • 5. Mutation score > coverage %. Đo sức mạnh test, không đo số dòng.
