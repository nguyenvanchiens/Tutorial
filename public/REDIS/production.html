Persistence, Replication, Sentinel, Cluster, Memory, Security, Monitoring — chạy Redis thật với hàng triệu request/ngày.

1. Persistence — Không mất data khi restart

Redis nằm trong RAM, restart = mất hết. 2 cơ chế persistence: RDB (snapshot) và AOF (append log). Dùng cả hai cho an toàn tối đa.

📸 RDB — Snapshot

Định kỳ dump toàn bộ dataset ra file dump.rdb.

  • File nhỏ gọn, load cực nhanh khi restart
  • Backup & clone dễ (chỉ copy 1 file)
  • Chạy nền, không block
Nhược: mất data giữa 2 snapshot (vd mỗi 5 phút). Nếu Redis sập lúc 4:59 sau snapshot lúc 4:55 → mất 4 phút.
# redis.conf
save 3600 1       # ≥1 change trong 1h
save 300 100      # ≥100 changes trong 5min
save 60 10000     # ≥10k changes trong 1min
dbfilename dump.rdb
dir /var/lib/redis

📜 AOF — Append Only File

Ghi mọi write command vào file appendonly.aof. Khi restart, replay lại.

  • Mất data tối đa 1s (hoặc 0s với always)
  • File lớn hơn RDB, Redis tự rewrite định kỳ
  • Restart chậm hơn (phải replay)
# redis.conf
appendonly yes
appendfsync everysec    # khuyên dùng
# appendfsync always — an toàn tuyệt đối, chậm
# appendfsync no — OS tự flush, nhanh nhưng risky

auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
Khuyên dùng: Bật cả RDB + AOF. RDB để backup & restart nhanh, AOF để giảm data loss khi crash. Redis load AOF trước (mới hơn).

2. Replication — Master-Replica

1 master + N replica đọc. Failover thủ công, đọc scale ngang, backup không ảnh hưởng master.

# Trên replica — trỏ về master
replicaof master.redis.local 6379
replica-read-only yes
masterauth <password>

# Hoặc runtime
REPLICAOF master.redis.local 6379

# Kiểm tra trạng thái
INFO replication
Dùng khi: cần scale read (analytic query chạy trên replica), backup định kỳ (dump RDB trên replica để không ảnh hưởng master), disaster recovery (replica ở vùng khác).
Replication không phải HA: master chết → replica không tự động lên master. Cần Sentinel (mục 3) để tự failover.

3. Sentinel — High Availability

3+ sentinel node giám sát master, tự promote replica thành master khi master chết. Client hỏi sentinel để biết master hiện tại.

# sentinel.conf
port 26379
sentinel monitor mymaster master.redis.local 6379 2
# 2 = quorum, cần ≥2 sentinel đồng ý là master chết mới failover

sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
// Client (C#) connect qua sentinel
var config = new ConfigurationOptions {
    ServiceName = "mymaster",
    EndPoints = { "sentinel1:26379", "sentinel2:26379", "sentinel3:26379" },
    CommandMap = CommandMap.Sentinel,
    Password = "...",
};
var sentinel = ConnectionMultiplexer.SentinelConnect(config);
var redis = sentinel.GetSentinelMasterConnection(...);
Kiến trúc Sentinel chuẩn:
  • 3 Redis nodes: 1 master + 2 replica
  • 3 Sentinel nodes (số lẻ để quorum)
  • Mỗi node ở 1 máy khác nhau (AZ khác nhau nếu cloud)

4. Redis Cluster — Sharding ngang

Khi 1 node không đủ RAM/throughput → chia keyspace thành 16384 slots trên nhiều master, mỗi master có replica riêng.

Hoạt động

  1. Key → hash(key) mod 16384 = slot số
  2. Slot nằm trên node nào → route tới node đó
  3. Client (smart client) cache slot→node map
  4. Node di chuyển slot → trả MOVED/ASK, client update map

Kiến trúc tối thiểu

  • 3 master (mỗi master giữ ~5461 slots)
  • 3 replica (1 replica / master)
  • Tổng 6 node, chia 3 máy
# Tạo cluster
redis-cli --cluster create \
  10.0.0.1:7000 10.0.0.2:7000 10.0.0.3:7000 \
  10.0.0.1:7001 10.0.0.2:7001 10.0.0.3:7001 \
  --cluster-replicas 1
Hạn chế Cluster:
  • Multi-key command chỉ chạy nếu các key cùng slot → dùng {tag}: user:{5}:profile, user:{5}:sessions → cùng hash
  • Transaction (MULTI/EXEC) chỉ trong 1 slot
  • Select DB (SELECT 1) không dùng được, chỉ có DB 0
  • Pub/Sub hoạt động toàn cluster nhưng tốn bandwidth
Khi nào cần Cluster? Chỉ khi 1 node đơn thực sự không đủ — RAM >100GB hoặc throughput >100k ops/s. Hầu hết app nhỏ/vừa, 1 master + Sentinel là đủ.

5. Memory Management & Eviction

Khi Redis đầy RAM, phải quyết định: từ chối write mới, hay xoá key cũ? Cấu hình maxmemory + maxmemory-policy.

# redis.conf
maxmemory 4gb
maxmemory-policy allkeys-lru
PolicyHành viDùng khi
noevictionTừ chối write khi đầy. Read vẫn OK.Redis là DB (không được mất)
allkeys-lruXoá key ít dùng nhất (LRU)Cache — mặc định
allkeys-lfuXoá key ít access nhất (LFU) — chính xác hơn LRUCache với skew rõ
volatile-lruLRU chỉ xoá key có TTLMix cache + persistent data
volatile-ttlXoá key sắp hết TTL trướcKhi TTL = priority
allkeys-randomRandomHiếm dùng
Ước lượng maxmemory: tổng RAM máy × 75%. Chừa 25% cho OS + buffer + RDB fork (snapshot cần copy-on-write, có thể gấp đôi RAM tạm thời).

Giám sát RAM

INFO memory
# used_memory           — RAM hiện dùng
# used_memory_peak      — peak từ lúc start
# used_memory_rss       — RAM OS cấp (có thể lớn hơn used_memory vì fragmentation)
# mem_fragmentation_ratio — rss/used. >1.5 là fragment nặng

MEMORY USAGE user:5
# Bytes 1 key tiêu

6. Security

🔑 Authentication

# redis.conf
requirepass your-strong-password-here

# Redis 6+ — ACL chi tiết theo user
ACL SETUSER readonly on >readonly_pass ~* &* +get +mget +scan -@all
ACL SETUSER admin on >admin_pass ~* &* +@all

ACL pattern: ~keys_pattern giới hạn key, +command -command giới hạn lệnh.

🔒 TLS

# redis.conf
tls-port 6380
port 0              # tắt plaintext
tls-cert-file /etc/redis/redis.crt
tls-key-file /etc/redis/redis.key
tls-ca-cert-file /etc/redis/ca.crt
tls-auth-clients yes   # yêu cầu client cert

🛡️ Network

  • Bind private IP: bind 10.0.0.5 — không expose 0.0.0.0
  • Firewall: chỉ mở port 6379 từ app server IP
  • VPC/VPN: Redis trong private subnet
  • protected-mode yes — block connect không auth

⚠️ Rename lệnh nguy hiểm

# Đổi tên để attacker khó gọi
rename-command FLUSHDB ""              # vô hiệu
rename-command FLUSHALL ""
rename-command CONFIG "CFG_xyz123"     # chỉ admin biết
rename-command KEYS ""
rename-command DEBUG ""
Cảnh báo thực tế: Shodan thường xuyên tìm thấy Redis expose public không auth. Attacker dùng CONFIG SET dir + SAVE để ghi SSH key lên server. Không bao giờ expose Redis ra internet.

7. Monitoring & Troubleshooting

📊 INFO — số liệu tổng

INFO
# Key sections:
# server        — version, uptime
# clients       — connected, blocked
# memory        — used, peak, fragmentation
# stats         — ops/sec, hits/misses
# replication   — role, slaves
# cpu           — used_cpu_sys/user
# commandstats  — calls per command
# keyspace      — số key mỗi DB

🐌 SLOWLOG — lệnh chậm

# Cấu hình ngưỡng 10ms
CONFIG SET slowlog-log-slower-than 10000
CONFIG SET slowlog-max-len 128

# Xem 10 lệnh chậm gần nhất
SLOWLOG GET 10

# Clear
SLOWLOG RESET

🔎 MONITOR — realtime command

MONITOR
# In ra mọi command realtime
# ⚠️ CHỈ dùng debug ngắn, ảnh hưởng perf

📈 Metrics quan trọng

  • ops/sec — throughput
  • keyspace_hits / (hits + misses) — hit ratio, target >0.9 cho cache
  • used_memory_rss / maxmemory — đầy RAM chưa?
  • instantaneous_input_kbps — băng thông
  • blocked_clients — có client bị block lâu?
  • evicted_keys — đang xoá key vì đầy RAM
  • latency — dùng LATENCY LATEST

8. Benchmarking

# redis-benchmark đi kèm Redis
redis-benchmark -h localhost -p 6379 -n 100000 -c 50
# -n 100000 = 100k request, -c 50 = 50 client concurrent

# Test 1 command cụ thể
redis-benchmark -t set,get -n 1000000

# Với pipeline
redis-benchmark -t set -n 1000000 -P 16
# -P 16 = pipeline 16 command
Baseline: 1 Redis instance trên AWS t3.small handle ~80-100k ops/s GET/SET đơn giản. Nếu số bạn thấp hơn rất nhiều → kiểm tra network latency, single-command workload, hot key.

9. Deployment Checklist

✅ Trước khi go-live

  • Bật persistence (RDB + AOF)
  • Set maxmemory + eviction policy
  • Auth password hoặc ACL
  • Bind private IP + firewall
  • Rename lệnh nguy hiểm
  • TLS nếu qua internet
  • Sentinel hoặc Cluster nếu cần HA
  • Backup RDB định kỳ sang S3
  • Monitoring: ops/s, memory, hit ratio, slowlog
  • Alert: memory >80%, master down, replication lag

🚫 Tránh

  • Chạy KEYS *, FLUSHALL trên prod
  • Dùng DB 1-15 cho tách data (không tương thích Cluster)
  • Để Redis swap sang disk (RAM cạn = chậm thảm)
  • Chạy Redis chung server với app-CPU nặng
  • Không backup (hoặc backup nhưng chưa test restore)
  • 1 client per request — dùng shared connection

Tốt cho: cần latest features, modules RediSearch/JSON.

Tốt cho: đã all-in 1 cloud, cần VPC peering.
