Redis Internals & Consistency

Bên trong cỗ máy: memory encodings, expiration chủ động/thụ động, mô hình single-thread & event loop, replication bất đồng bộ & mất data lúc failover (WAIT), client-side caching RESP3, và cục diện Redis vs Valkey năm 2026.

1. Memory Encodings — Cùng một type, nhiều cách lưu

Mỗi data type có nhiều biểu diễn nội bộ. Redis tự chọn encoding gọn nhẹ khi nhỏ, và "nâng cấp" sang encoding tổng quát khi vượt ngưỡng. Hiểu điều này = tiết kiệm RAM khổng lồ.

> RPUSH mylist a b c
> OBJECT ENCODING mylist
"listpack"            # nhỏ → đóng gói liền mạch, tiết kiệm
> HSET h f1 v1
> OBJECT ENCODING h
"listpack"
> SADD nums 1 2 3
> OBJECT ENCODING nums
"intset"             # set toàn số nguyên → mảng int gói chặt
> SET n 12345
> OBJECT ENCODING n
"int"

Lịch sử tên gọi: listpack là kế thừa của ziplist cũ (thay từ Redis 7.0, fix lỗi tràn của ziplist). Nếu thấy ziplist trong tài liệu cũ → giờ là listpack. quicklist là linked list của các listpack node.
Tuning thực chiến: Nếu bạn lưu hàng triệu hash nhỏ (vd shard user thành user:{1000} chứa nhiều field), giữ chúng dưới ngưỡng listpack để tiết kiệm tới 5-10× RAM so với hashtable. Đây là kỹ thuật "hash sharding" kinh điển của Instagram. Đừng nâng ngưỡng quá cao — listpack lớn thì thao tác O(n).

2. Expiration — Active vs Passive

Key có TTL không bị xoá đúng từng mili-giây. Redis dùng kết hợp 2 chiến lược để cân bằng CPU và độ chính xác.

🐢 Passive (lazy)

Khi một client truy cập key, Redis kiểm tra TTL — nếu hết hạn thì xoá ngay rồi trả nil. Không tốn CPU nếu key không bao giờ bị đụng tới... nhưng key "chết" vẫn chiếm RAM cho tới khi có người gọi.

⚡ Active (chủ động)

10 lần/giây, Redis lấy mẫu ngẫu nhiên 20 key có TTL trong mỗi DB. Xoá những cái đã hết hạn. Nếu >25% mẫu hết hạn → lặp lại ngay (vì có vẻ nhiều key chết). Cơ chế xác suất, giữ tỉ lệ key hết hạn còn sống ở mức thấp.

Hệ quả vận hành: RAM có thể cao hơn dự kiến vì key hết hạn chưa kịp xoá. Nếu bạn set hàng loạt key cùng TTL ngắn, active expiration có thể gây spike CPU/latency khi chúng đồng loạt hết hạn. Thêm jitter ngẫu nhiên vào TTL để rải đều. 
# Replica KHÔNG tự xoá key hết hạn (chờ DEL từ master)
# → đọc trên replica vẫn trả nil cho key đã hết hạn (logic đúng),
#   nhưng key vẫn chiếm RAM trên replica tới khi master gửi DEL.

3. Single-thread model & Event loop

"Redis chạy 1 thread mà sao nhanh thế?" — vì thao tác in-memory và một event loop tối ưu (ae) ghép kênh I/O. Đây là gốc rễ của tính atomic.

Vòng lặp xử lý

  1. epoll/kqueue chờ socket sẵn sàng
  2. Đọc request từ các client
  3. Thực thi command tuần tự, từng cái một
  4. Ghi reply trở lại socket
  5. Chạy background task (expire, rehash...)

Vì command chạy nối tiếp → không có lock, không race → mọi command (và script Lua) đều atomic.

Không hẳn "1 thread"

Phần thực thi command là single-thread. Nhưng từ Redis 6 có I/O threads (đọc/ghi socket song song) và nhiều task chạy thread riêng:

  • BGSAVE / AOF rewrite → fork tiến trình con
  • UNLINK, FLUSHALL ASYNC → lazy-free thread giải phóng RAM nền
  • I/O threads (io-threads) cho network
Hệ quả #1 cần nhớ: một lệnh O(n) chậm chặn toàn bộ server. KEYS *, SMEMBERS trên set 10 triệu phần tử, HGETALL hash khổng lồ, hay script Lua nặng — tất cả làm đơ mọi client khác. Đây là vì sao trang Cơ Bản nhắc dùng SCAN thay KEYS. 
# Xoá key lớn không block: UNLINK thay DEL
UNLINK huge:key        # giải phóng RAM ở background thread
DEL huge:key           # giải phóng ngay → block nếu key cực lớn

4. Async Replication & mất data lúc failover

Replication của Redis là bất đồng bộ mặc định: master ack write cho client trước khi replica nhận được. Điều này nhanh, nhưng mở ra cửa sổ mất data khi failover.

Kịch bản mất data:
  1. Client SET x 1 → master ack OK
  2. Master chết trước khi kịp gửi write này sang replica
  3. Sentinel promote replica thành master mới
  4. Master mới không có x=1 → write đã "thành công" với client nhưng biến mất

WAIT — đợi replica xác nhận

WAIT numreplicas timeout chặn cho tới khi write trước đó được ít nhất numreplicas replica nhận (hoặc hết timeout). Đẩy độ bền lên gần đồng bộ.

> SET payment:1001 "confirmed" OK > WAIT 1 500 # đợi ≥1 replica ack, tối đa 500ms (integer) 1 # số replica đã xác nhận;
WAIT KHÔNG phải là transaction phân tán. Nó chỉ tăng xác suất bền vững — vẫn có thể mất data trong các kịch bản network partition hiếm. Để đảm bảo mạnh hơn, Redis Enterprise/Cluster có WAITAOF (đợi fsync xuống AOF) và quorum-based config. Với tiền bạc thật sự critical, đừng coi một Redis đơn là source of truth. 
WAITAOF 1 1 1000   # đợi 1 local fsync + 1 replica fsync, timeout 1s
                  # yêu cầu appendonly=yes; bền hơn WAIT (chống mất khi cả cụm restart)

5. Client-side Caching — RESP3 CLIENT TRACKING

Cache phía client (in-process) cho latency gần như 0, nhưng làm sao biết khi data đổi để invalidate? Redis 6 giải quyết bằng server-assisted client-side caching: server chủ động báo client khi key bị thay đổi.

🔔 Default mode (RESP3)

Client bật CLIENT TRACKING ON. Server nhớ các key client đã đọc. Khi key đó bị sửa/xoá, server đẩy thông điệp invalidation (push type > của RESP3) tới đúng client đó. Client xoá entry khỏi cache local.

> HELLO 3
> CLIENT TRACKING ON
OK
> GET user:5     # server bắt đầu "theo dõi" key này cho ta
# khi ai đó SET user:5 → ta nhận push invalidate

📢 Broadcast mode (BCAST)

Đăng ký theo prefix. Server gửi invalidation cho mọi key khớp prefix mà không cần nhớ từng client đọc gì → tốn ít bộ nhớ server hơn, nhưng nhận cả thông báo không liên quan.

> CLIENT TRACKING ON BCAST PREFIX user:

RESP2 client dùng được qua chế độ redirect (gửi invalidation tới 1 connection Pub/Sub riêng).

Trong code — StackExchange.Redis

// StackExchange.Redis hỗ trợ tracking qua tích hợp; nhiều team
// dùng lớp cache 2 tầng (L1 in-memory + L2 Redis) tự invalidate.
// ioredis: dùng client.subscribe('__redis__:invalidate') ở chế độ redirect.
var sub = mux.GetSubscriber();
sub.Subscribe("__redis__:invalidate", (ch, key) => localCache.Remove(key));
Khi nào dùng: dữ liệu đọc cực nhiều / ghi ít (config, feature flag, profile). Cho hit ratio L1 cao mà vẫn nhất quán nhờ invalidation đẩy. Cẩn thận memory phía client và "thundering herd" khi invalidate hàng loạt.

6. Redis vs Valkey — Cục diện 2024 → 2026

Tháng 3/2024, Redis Inc. đổi license từ BSD sang RSALv2/SSPLv1 (không còn open source theo định nghĩa OSI). Cộng đồng + các nhà cung cấp cloud phản ứng bằng cách fork.

Cloud mặc địnhRedis CloudElastiCache, MemoryDB, Memorystore đã chuyển sang Valkey
Trạng thái 2026: Đáng chú ý, tháng 5/2025 Redis 8 thêm lại tùy chọn AGPLv3 — một phần để đáp lại đà tăng của Valkey. Hai dự án giờ phát triển song song và đang dần phân kỳ tính năng. Với code ứng dụng thông thường, cả hai vẫn tương thích lệnh: StackExchange.Redis và ioredis chạy với cả hai mà không sửa gì.
Chọn thế nào? Cần license open source thuần / đang dùng AWS-GCP managed → Valkey là đường mặc định, miễn phí license. Cần module đặc thù của Redis Inc. (vector search tích hợp, RedisJSON cao cấp, hỗ trợ thương mại) → Redis. Kiểm tra license version cụ thể trước khi nhúng vào sản phẩm bán lại (SSPL ràng buộc khi cung cấp như dịch vụ).
