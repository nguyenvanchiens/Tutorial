Lua Scripting trong Redis

Gói nhiều lệnh thành một thao tác nguyên tử chạy server-side. EVAL / EVALSHA / Functions, KEYS vs ARGV, rate limiter thật, và khi nào nên dùng thay cho MULTI/EXEC.

1. Vì sao cần Lua? — Atomicity + Round-trip

Redis thực thi script Lua như một lệnh duy nhất: không client nào xen vào giữa chừng. Đó là chìa khoá giải bài toán "read-modify-write" mà nếu làm bằng nhiều lệnh rời sẽ dính race condition.

❌ 3 round-trip — có race

val = redis.get("stock:42")   # RTT 1
if val > 0:
    redis.decr("stock:42")       # RTT 2 — client khác đã mua giữa chừng!
    redis.lpush("orders", id)   # RTT 3

Giữa GET và DECR, client khác có thể chen vào → bán âm kho (oversell).

✅ 1 script Lua — nguyên tử

-- Toàn bộ logic chạy không gián đoạn, 1 round-trip
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock and stock > 0 then
  redis.call('DECR', KEYS[1])
  redis.call('LPUSH', KEYS[2], ARGV[1])
  return 1
end
return 0
3 lý do dùng Lua: (1) Atomicity — không race vì single-thread chạy hết script mới qua client khác; (2) Giảm round-trip — logic chạy ngay tại server; (3) Logic có điều kiện — if/loop mà MULTI/EXEC không làm được.

2. EVAL — chạy script

Cú pháp: EVAL script numkeys key [key ...] arg [arg ...]. numkeys nói cho Redis biết bao nhiêu tham số đầu là KEY.

> EVAL "return 'Hello ' .. ARGV[1]" 0 Chien "Hello Chien" > EVAL "return redis.call('SET', KEYS[1], ARGV[1])" 1 mykey hello OK > EVAL "return redis.call('GET', KEYS[1])" 1 mykey "hello" > EVAL "return {1, 2, 3, 'foo'}" 0 1) (integer) 1 2) (integer) 2 3) (integer) 3 4) "foo"

📡 redis.call vs redis.pcall

redis.call — lỗi sẽ abort script, trả error lên client. redis.pcall — bắt lỗi thành table, script chạy tiếp. Dùng call trừ khi bạn chủ động xử lý lỗi.

🔢 Chuyển kiểu

Redis trả string. Muốn so sánh số phải tonumber(). Trả về số thì Lua number bị cắt phần thập phân thành integer khi sang RESP — trả string nếu cần float chính xác.

3. KEYS vs ARGV — Quy tắc bắt buộc

Đây là điểm hay sai nhất. Mọi key bạn truy cập phải đi qua KEYS[], mọi tham số khác qua ARGV[].

KEYS[]ARGV[]
Chứa gìTên các key RedisTham số/giá trị tuỳ ý

Vì sao quan trọngĐể Redis Cluster route đúng slot & kiểm tra cùng nodeKhông ảnh hưởng routing
Index1-based: KEYS[1]1-based: ARGV[1]
🚫 Đừng hardcode tên key trong script! Viết redis.call('GET', 'user:5') sẽ vỡ trên Cluster vì Redis không biết script chạm key nào → không route được. Luôn truyền key qua KEYS[]. 
-- ❌ SAI
redis.call('GET', 'user:5')
-- ✅ ĐÚNG
redis.call('GET', KEYS[1])

4. EVALSHA & SCRIPT LOAD — Cache script

Gửi cả script qua mạng mỗi lần là phí băng thông. Nạp 1 lần lấy SHA1, sau đó chỉ gửi SHA.

> SCRIPT LOAD "return redis.call('GET', KEYS[1])" "a5260dd66ce02462c5b5231c727b3f7772c0bcc5" > EVALSHA a5260dd66ce02462c5b5231c727b3f7772c0bcc5 1 mykey "hello" > SCRIPT EXISTS a5260dd66ce02462c5b5231c727b3f7772c0bcc5 1) (integer) 1 > SCRIPT FLUSH # xoá cache script (vd sau deploy) OK
Pattern chuẩn của client lib: thử EVALSHA trước; nếu Redis trả NOSCRIPT (sau restart/flush) thì fallback sang EVAL (tự nạp lại) rồi cache SHA. StackExchange.Redis & ioredis làm việc này tự động giúp bạn.

5. Worked example — Sliding-window Rate Limiter

Đếm request trong cửa sổ thời gian, atomic. Đây là use case kinh điển của Lua vì cần "check + incr + set TTL" không gián đoạn.

-- rate_limit.lua
-- KEYS[1] = rate key (vd: ratelimit:user:5)
-- ARGV[1] = limit (số request tối đa)
-- ARGV[2] = window (giây)
local current = redis.call('INCR', KEYS[1])
if current == 1 then
  -- request đầu tiên: đặt TTL = window
  redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
  return 0            -- vượt giới hạn → từ chối
end
return 1              -- cho qua
> EVAL "<script trên>" 1 ratelimit:user:5 10 60 # Cho phép 10 request / 60 giây cho user:5 (integer) 1 # 9 lần đầu trả 1 (integer) 0 # lần 11 trả 0 → block

Gọi từ C# — StackExchange.Redis

const string RateScript = @"
  local current = redis.call('INCR', KEYS[1])
  if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
  if current > tonumber(ARGV[1]) then return 0 end
  return 1";

// ScriptEvaluate tự dùng EVALSHA + fallback EVAL
var allowed = (int)await db.ScriptEvaluateAsync(
    RateScript,
    keys: new RedisKey[] { "ratelimit:user:5" },
    values: new RedisValue[] { 10, 60 });

if (allowed == 0) return Results.StatusCode(429);  // Too Many Requests

Gọi từ Node.js — ioredis defineCommand

// Đăng ký script như 1 method tuỳ chỉnh — ioredis lo EVALSHA/cache
redis.defineCommand('rateLimit', {
  numberOfKeys: 1,
  lua: `
    local current = redis.call('INCR', KEYS[1])
    if current == 1 then redis.call('EXPIRE', KEYS[1], ARGV[2]) end
    if current > tonumber(ARGV[1]) then return 0 end
    return 1`,
});

const allowed = await redis.rateLimit('ratelimit:user:5', 10, 60);
if (allowed === 0) res.status(429).send('Rate limited');
Biến thể hay gặp: đổi sang conditional update (chỉ SET nếu version khớp — optimistic lock), atomic dequeue (RPOP + ghi vào processing list, an toàn hơn BRPOP trần), hoặc token bucket (tính token còn lại theo timestamp). Cùng một khuôn: read → tính → write, tất cả trong 1 script.

7. Debug, giới hạn & best practices

🐞 Debug

-- Ghi log từ trong script
redis.log(redis.LOG_WARNING, "current=" .. current)

# LDB — Lua debugger tương tác
redis-cli --ldb --eval rate_limit.lua \
  ratelimit:user:5 , 10 60
# dấu ',' phân tách KEYS với ARGV trong --eval

⛔ Giới hạn cứng

  • Script phải tất định (deterministic) — không dùng os.time(), random tự do; truyền timestamp qua ARGV
  • Không I/O ngoài, không network
  • Block cả server khi chạy → giữ script ngắn & nhanh
  • busy-reply-threshold (mặc định 5s) → script lâu bị báo BUSY
Script chạy quá lâu chặn toàn bộ Redis! Vì single-thread, một vòng lặp Lua nặng làm đơ mọi client. Nếu lỡ chạy script vô tận: 
SCRIPT KILL      # dừng script đang chạy (nếu chưa ghi gì)
SHUTDOWN NOSAVE  # biện pháp cuối nếu script đã ghi và không kill được
Best practices: giữ script nhỏ và đơn nhiệm; truyền mọi key qua KEYS và mọi biến động (time, random seed) qua ARGV để tất định; ưu tiên EVALSHA; test kỹ trên staging vì lỗi script ảnh hưởng toàn cluster.

Redis Functions — kế thừa Lua, lưu bền

#!lua name=mylib
redis.register_function('rate_limit', function(keys, args)
  local current = redis.call('INCR', keys[1])
  if current == 1 then redis.call('EXPIRE', keys[1], args[2]) end
  if current > tonumber(args[1]) then return 0 end
  return 1
end)
$ redis-cli -x FUNCTION LOAD < mylib.lua "mylib" > FCALL rate_limit 1 ratelimit:user:5 10 60 (integer) 1 > FUNCTION LIST # liệt kê library đã nạp
Chọn cái nào (2026): MULTI/EXEC cho gom lệnh đơn giản không cần điều kiện; Lua EVAL vẫn là lựa chọn phổ biến nhất, client lib hỗ trợ tốt; Functions khi muốn quản lý logic như "stored procedure" bền vững, dùng lại giữa nhiều app — nhưng tooling client còn ít hơn Lua.

💡 Bài tập

  1. Atomic GETDEL có điều kiện: viết script lấy giá trị rồi xoá key chỉ khi nó khớp ARGV (nền tảng của unlock distributed lock an toàn).
  2. Token bucket: rate limiter mượt hơn — lưu tokens + last_refill, tính token bù theo thời gian truyền qua ARGV.
  3. Atomic dequeue + ack: RPOP từ queue và LPUSH sang processing list trong 1 script.
  4. Chuyển sang Functions: đóng gói 3 script trên thành 1 library mylib, gọi bằng FCALL.
