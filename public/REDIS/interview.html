Phỏng vấn Redis

Câu hỏi thường gặp ở phỏng vấn .NET/Backend có Redis. Đáp án ngắn nhưng đầy đủ ý. Đọc xong tự nói lại bằng lời mình.

🟢 Junior (L1-L2)

JR1. Redis là gì? Khác gì với DB truyền thống?

Redis là in-memory key-value store mã nguồn mở. Dữ liệu nằm chủ yếu trong RAM → đọc/ghi <1ms. Hỗ trợ 9 data types, persistence (RDB/AOF), replication, pub/sub, cluster.

Khác DB SQL: không có schema, không query SQL, không transaction phức tạp. Nhanh gấp 10-100 lần, nhưng không thay thế DB chính — dùng để bổ trợ (cache, session, queue).

JR2. Tại sao Redis nhanh?
  • Data trong RAM (không disk I/O)
  • Single-threaded cho command — không lock/context switch
  • Network I/O non-blocking (epoll)
  • Cấu trúc dữ liệu viết riêng, tối ưu (hash table, skiplist)
  • Protocol RESP đơn giản, parse nhanh
JR3. Kể tên các data types Redis?

9 kiểu: String, List, Hash, Set, Sorted Set, Stream, Bitmap, HyperLogLog, Geo. Ngoài ra còn module: RedisJSON, RediSearch, RedisTimeSeries, RedisBloom.

JR4. Khi nào dùng Hash thay vì String JSON?
  • Hash: khi cần đọc/ghi từng field riêng lẻ (vd: HINCRBY user:5 age 1)
  • Hash: tiết kiệm RAM hơn JSON string cho object nhỏ (<100 field) vì Redis nén tự động
  • String JSON: khi luôn đọc/ghi toàn object, hoặc có nested phức tạp mà ORM app-side dễ map
JR5. TTL là gì? Cách set?

TTL (Time To Live) = thời gian sống của key. Hết TTL, Redis tự xoá. Cách set:

SET key val EX 60       # 60 giây ngay khi SET
SET key val PX 60000    # millisecond
EXPIRE key 60           # cho key đã tồn tại
PERSIST key             # gỡ TTL
TTL key                 # xem còn bao lâu
JR6. Redis có thread-safe không? Nhiều client cùng INCR 1 key có race condition?

Redis xử lý command single-threaded. 1000 client cùng gọi INCR → Redis xếp hàng, chạy tuần tự. Kết quả đúng, không race condition. Đây là lý do INCR dùng cho counter rất an toàn.

JR7. Dùng Redis làm cache thường xuyên — nói 1 ví dụ cụ thể.

Ví dụ: API GET /users/5. Thay vì query DB mỗi lần:

  1. Check GET user:5 từ Redis
  2. Có → return JSON
  3. Không → query DB, SET user:5 {...} EX 300 (TTL 5 phút), return

Khi update user → DEL user:5 để tránh stale. Đây là pattern cache-aside.

JR8. SCAN khác KEYS thế nào? Dùng cái nào?
  • KEYS pattern: trả về TẤT CẢ match trong 1 call. Với 1M key → block Redis vài giây. Cấm dùng production.
  • SCAN cursor MATCH pattern COUNT 100: cursor-based, trả từng batch. An toàn vì Redis vẫn phục vụ request khác giữa các batch.
JR9. Pipeline và MULTI/EXEC khác nhau?
  • Pipeline: gửi nhiều command không đợi reply → giảm round-trip. Các command không chạy atomic, client khác có thể xen vào giữa.
  • MULTI/EXEC: transaction — các command queue, chạy tuần tự không bị xen. Cũng có lợi ích giảm round-trip giống pipeline.
JR10. Persistence trong Redis có những option nào?
  • RDB: snapshot toàn dataset ra file theo định kỳ. Nhỏ gọn, restart nhanh, mất data giữa 2 snapshot.
  • AOF: append log mọi write. Mất tối đa 1s data, file lớn, restart chậm hơn.
  • Cả hai (khuyên production): RDB cho backup + AOF cho safety.
  • No persistence: khi Redis chỉ làm cache thuần, mất không sao.

🟠 Middle (L3)

MID11. Cache Stampede là gì? Cách xử lý?

Khi cache hết TTL và nhiều request cùng miss đồng thời → tất cả query DB → DB overload.

Giải pháp:

  • Single-flight lock: chỉ 1 request được query DB, số còn lại đợi rồi đọc cache
  • Probabilistic early refresh: random refresh cache trước khi TTL hết
  • Stale-while-revalidate: serve stale data, refresh nền
  • Pre-warm: cron job refresh key nóng trước khi hết TTL
MID12. Hot key là gì? Tác hại và cách xử lý?

1 key bị truy cập nhiều hơn các key khác đáng kể. Ví dụ: page:home 10k req/s, trong khi các page khác vài req/s.

Tác hại: single-thread Redis → hot key bão hoà CPU. Trong Cluster, key chỉ nằm 1 shard → shard đó kẹt, shard khác nhàn.

Giải pháp:

  • Client-side LRU cache (caffeine/memory-cache) — giảm hit Redis
  • Shard hot key bằng suffix random: page:home:0, page:home:1, ..., page:home:9, client random 1 trong 10
  • Read replica → scale đọc
MID13. Distributed lock với Redis — viết pseudo code.
// Acquire
const token = uuid();
const ok = await redis.set(lockKey, token, 'NX', 'EX', 30);
if (!ok) throw 'busy';

try {
    await doWork();
} finally {
    // Release — chỉ xoá nếu token vẫn là của mình (Lua atomic)
    await redis.eval(`
      if redis.call('GET', KEYS[1]) == ARGV[1]
        then return redis.call('DEL', KEYS[1])
        else return 0 end
    `, 1, lockKey, token);
}

Tại sao SET NX EX: NX để atomic acquire, EX để auto-release nếu process chết. Tại sao check token: tránh xoá nhầm lock của worker khác nếu job của mình quá TTL.

MID14. Pub/Sub vs Stream — chọn khi nào?
  • Pub/Sub: fire-and-forget, subscriber offline lúc publish = mất message. Dùng cho: notification real-time, presence, broadcast nhẹ.
  • Stream: persistent log, consumer group, ack/retry. Giống Kafka mini. Dùng cho: queue jobs, event sourcing, cần đảm bảo delivery.
MID15. Leaderboard top 100 — dùng gì?

Sorted Set. ZADD lb <score> <user> để add/update, ZREVRANGE lb 0 99 WITHSCORES để lấy top 100 (tất cả O(log N)). Rank của 1 user: ZREVRANK lb <user>.

MID16. Rate limit sliding window bằng Sorted Set — ý tưởng?
  1. Với mỗi request: ZADD rate:{user} <now_ms> <now_ms:random>
  2. Xoá entry cũ: ZREMRANGEBYSCORE rate:{user} 0 (now - window)
  3. Đếm: ZCARD rate:{user}
  4. Nếu > limit → reject
  5. EXPIRE key để auto-clean
MID17. Tại sao không nên dùng FLUSHDB trên production?

Xoá toàn bộ DB, không thu hồi được. Với dataset lớn, thao tác này chặn Redis vài giây/phút. Khuyên: rename lệnh FLUSHDB thành empty hoặc tên bí mật trong redis.conf.

MID18. Redis có hỗ trợ transaction ACID đầy đủ không?

Không đầy đủ:

  • Atomicity: có — tất cả command trong MULTI/EXEC chạy liên tục, không bị xen.
  • Consistency: có ở mức state được giữ hợp lệ.
  • Isolation: có — single-threaded.
  • Durability: tuỳ persistence. AOF always mới thật sự durable.

Khác DB SQL: không có rollback nếu 1 lệnh fail logic. Nếu INCR 1 key không phải số → lệnh đó fail nhưng các lệnh còn lại trong tx vẫn chạy.

MID19. WATCH dùng để làm gì?

Optimistic locking: WATCH key → nếu key đó bị thay đổi bởi client khác giữa WATCH và EXEC, transaction bị huỷ (EXEC trả nil). Dùng cho: check-and-set patterns, ví dụ trừ số dư tài khoản chỉ khi số dư ≥ amount.

MID20. Eviction policy — khi nào dùng cái nào?
  • noeviction: Redis là source of truth, không được mất data (session quan trọng).
  • allkeys-lru: cache thuần — default tốt nhất.
  • allkeys-lfu: cache với access pattern skew rõ (1 số key cực nóng, số còn lại nguội hẳn).
  • volatile-lru/ttl: mix cache + persistent — chỉ evict key có TTL.

🔴 Senior (L4)

SR21. Sentinel và Cluster khác nhau thế nào?
  • Sentinel: giải quyết HA — 1 master + N replica, sentinel tự failover khi master chết. Data vẫn nằm trên 1 master duy nhất (không shard).
  • Cluster: giải quyết scale ngang — chia keyspace thành 16384 slot trên nhiều master, mỗi master có replica. Vừa HA vừa scale.

Hầu hết app không cần Cluster — 1 master mạnh + Sentinel là đủ. Chỉ cần Cluster khi RAM >100GB hoặc throughput >100k ops/s.

SR22. Cluster có những giới hạn gì?
  • Multi-key command chỉ chạy nếu các key cùng slot. Dùng hash tag: user:{5}:profile và user:{5}:sessions cùng slot.
  • MULTI/EXEC chỉ trong cùng slot.
  • Chỉ DB 0 (không dùng được SELECT 1).
  • Pub/Sub broadcast qua tất cả node → tốn bandwidth.
  • Resharding (thêm/xoá node) phức tạp hơn.
SR23. Làm sao debug Redis chậm?
  1. SLOWLOG GET 100 — lệnh >10ms gần nhất.
  2. LATENCY LATEST, LATENCY HISTORY event — latency spike.
  3. INFO commandstats — lệnh gọi nhiều nhất, avg time.
  4. MONITOR ngắn 5-10s để xem realtime (cẩn thận perf).
  5. CLIENT LIST — client nào ngủ lâu, blocked.
  6. Network RTT từ app server.
  7. CPU/memory máy Redis — có bị swap không?

90% case chậm = KEYS, hot key, object lớn, hoặc round-trip không pipeline.

SR24. Cache invalidation strategy — so sánh
  • TTL-only: chấp nhận stale ≤ TTL. Đơn giản nhất, ưu tiên availability.
  • Write-through: write app → DB + Redis cùng lúc. Cache luôn mới nhưng mọi write tốn 2 hop.
  • Write-around + DEL: write → DB, xoá cache, lần đọc kế refresh. Đơn giản, phổ biến.
  • Write-behind: write → Redis, worker flush sang DB async. Nhanh nhất nhưng nguy hiểm (mất data nếu crash).
  • Event-driven (CDC): DB publish event → worker invalidate cache. Ổn định nhất, phức tạp setup.
SR25. Thiết kế cache cho hệ thống 10M user

Nhiều tầng:

  • L1 — In-process cache (Caffeine/MemoryCache): TTL 10-30s, giảm 90% hit Redis.
  • L2 — Redis: TTL phút → giờ, xử lý đa instance app.
  • L3 — CDN: cho public GET (product page). TTL phút-ngày.
  • DB read replica: phòng khi cache miss burst.

Invalidation: DB → emit event → worker DEL cache, app-local cache TTL ngắn tự tan.

SR26. Redis memory usage đột nhiên tăng cao — debug ra sao?
  1. INFO memory — used_memory, rss, fragmentation ratio.
  2. redis-cli --bigkeys — tìm key to nhất mỗi type.
  3. MEMORY USAGE key — bytes của 1 key cụ thể.
  4. SCAN MATCH prefix:* COUNT 100 + MEMORY USAGE — tổng theo prefix.
  5. Kiểm tra client nào đang write bất thường (CLIENT LIST, app log).
  6. Eviction counter tăng? (info stats → evicted_keys)

Cause phổ biến: không set TTL, lưu object khổng lồ, leak key (mỗi request tạo key mới mà không xoá).

SR27. Lua script — khi nào dùng? Ưu/nhược?

Dùng khi: cần nhiều lệnh chạy atomic mà MULTI/EXEC không đủ (có điều kiện logic), vd rate limit token bucket (check + update trong 1 đơn vị atomic).

Ưu: atomic, giảm round-trip, chạy server-side.

Nhược: block Redis (vì single-thread) → script dài = gây latency spike; không gọi command blocking (BRPOP); khó debug.

Best practice: script ngắn, không có loop vô hạn, cache bằng EVALSHA thay vì gửi script mỗi lần.

SR28. Redis vs Memcached — khi nào chọn Memcached?

Memcached chỉ thắng khi:

  • Cache duy nhất string đơn giản, không cần data type khác
  • Workload write-heavy đơn giản, cần squeeze performance (Memcached multi-thread)
  • Không cần persistence, replication

Còn lại Redis thắng: nhiều data types, persistence, pub/sub, scripting, ecosystem. 90% team chọn Redis.

SR29. Trong microservice, mỗi service nên có Redis riêng hay dùng chung?

Tuỳ ngữ cảnh:

  • Redis riêng / service: isolation tốt, 1 service có bug không ảnh hưởng service khác, scale độc lập. Trade-off: vận hành nhiều cluster.
  • Shared Redis: đơn giản, ít overhead. Trade-off: noisy neighbor, 1 service ăn hết RAM thì các service khác bị ảnh hưởng.

Best practice: dùng namespace (prefix key) + ACL để limit từng service. Shared Redis với namespace là đủ cho hầu hết team vừa. Chỉ tách riêng khi 1 service có workload đặc biệt (vd: rate limit cho API gateway).

SR30. Tình huống: cache hit ratio đột nhiên tụt từ 95% xuống 40%. Hướng điều tra?
  1. Có deploy code mới? Query pattern đổi → key cache khác cũ → miss tăng.
  2. Có FLUSHDB hoặc restart Redis không có AOF?
  3. Eviction — INFO stats → evicted_keys tăng vọt? Memory đầy?
  4. TTL set sai — key đang expire quá nhanh? SCAN vài key xem TTL.
  5. Traffic pattern mới — user mới nhiều, cold start → cache chưa warm up.
  6. Bug code: DEL không đúng chỗ, hoặc key format đổi giữa write và read.

🧠 System Design với Redis

SD-1: Thiết kế URL shortener (bit.ly)

Redis lưu mapping short_code → long_url (string), counter atomic cho INCR counter:clicks:{code}. DB chính (Postgres) lưu lịch sử/user. Cache-aside khi lookup.

SD-2: Online status / "Active users in last 5 min"

Sorted Set ZADD online now user_id. Cron xoá cũ: ZREMRANGEBYSCORE online 0 (now-300s). Count: ZCARD online. Hoặc dùng HyperLogLog cho số xấp xỉ.

SD-3: Chat app real-time

Pub/Sub: channel room:{id}. Persist lịch sử: Stream XADD room:{id}. Presence: Set. Read receipt: Hash.

SD-4: Rate limit API gateway

Sliding window Sorted Set hoặc Lua token bucket. Key theo user/IP/endpoint. Global limit + per-user limit riêng.

SD-5: Auction sniper (trả giá cuối cùng thắng)

WATCH auction:{id}:highest, MULTI, check bid > current, SET, EXEC. Lock không cần vì atomic qua WATCH.

SD-6: Newsfeed cache

Feed của user = List feed:{user_id} chứa post IDs, LPUSH khi có post mới từ following, LTRIM feed:{user_id} 0 999 giữ 1000 gần nhất. Client lấy 20 bằng LRANGE 0 19.

🎯 Tips phỏng vấn

Khi được hỏi lý thuyết

  • Trả lời định nghĩa → ví dụ cụ thể → trade-off
  • Nhắc đến data type phù hợp khi giải scenario
  • Luôn nhắc đến "single-threaded" — nó giải thích nhiều thứ

Khi thiết kế hệ thống

  • Đừng mọi thứ bỏ vào Redis — nhắc nó là cache/bổ trợ
  • Nêu invalidation strategy
  • Nêu TTL cụ thể, không nói "cache forever"
  • Nêu cách failover/disaster recovery

Warning signs trong interview

  • Interviewer hỏi "dùng Redis làm DB chính" — điểm gài, trả lời tại sao không
  • Hỏi tại sao Redis nhanh hơn DB — nhắc RAM, single-thread, data structure tối ưu
