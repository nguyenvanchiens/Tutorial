Redis Cơ Bản

9 data types, lệnh thiết yếu, TTL, transaction, pipelining — tất cả những gì bạn cần để dùng Redis trong 99% use case.

1. Mental Model — Hiểu trước khi dùng

🗝️ Key-Value, không phải Table

Quên schema đi. Redis chỉ có key (string) → value (1 trong 9 kiểu). Không có row, column, index, foreign key, join.

# SQL
SELECT * FROM users WHERE id = 5;

# Redis — bạn thiết kế key
GET user:5          # string JSON
HGETALL user:5      # hash

⏱️ Tất cả đều có thể có TTL

Bất kỳ key nào có thể set thời gian sống. Hết hạn → Redis tự xoá. Đây là nền tảng của cache.

SET session:abc123 "user_5" EX 3600
# Key này sẽ bị xoá sau 1 giờ

TTL session:abc123
(integer) 3600

EXPIRE user:5 300    # set TTL cho key đã tồn tại
PERSIST user:5       # gỡ TTL

⚛️ Mọi command là Atomic

Redis single-threaded → mọi lệnh chạy tuần tự, không race condition. INCR 1000 client gọi đồng thời vẫn đúng.

💾 Naming convention

Key là string bất kỳ, nhưng quy ước chuẩn: dùng : làm phân tách tầng.

# Tốt
user:5:profile
user:5:sessions
product:42:stock
cache:api:/users/5

# Tránh — không có pattern
usr5profile
u_5_session_data

2. String — Đơn giản nhất, dùng nhiều nhất

Lưu text, số, JSON, binary (tối đa 512MB / key). 70% use case Redis chỉ cần string.

> SET name "Chien" OK > GET name "Chien" > SET counter 10 OK > INCR counter # +1, atomic (integer) 11 > INCRBY counter 5 (integer) 16 > DECR counter (integer) 15 > APPEND name " Dev" > GET name "Chien Dev" > STRLEN name (integer) 9 > SET cache:result "{...}" EX 60 # TTL 60s ngay khi SET > SETNX lock:job "worker1" # SET if Not eXists → distributed lock (integer) 1 > SETNX lock:job "worker2" # worker1 đã giữ → fail (integer) 0
Idiomatic: INCR cho view counter, SET key val EX 3600 cho cache, SET key val NX cho lock nhẹ.

3. List — Hàng đợi & stack

Doubly-linked list. Thêm/lấy 2 đầu O(1). Dùng làm queue, recent activity, stream đơn giản.

> LPUSH queue "job1" "job2" "job3" (integer) 3 > RPUSH queue "job4" # push bên phải > LRANGE queue 0 -1 # xem toàn list 1) "job3" 2) "job2" 3) "job1" 4) "job4" > LPOP queue # lấy từ trái, FIFO queue "job3" > RPOP queue # lấy từ phải, LIFO stack "job4" > LLEN queue (integer) 2 > BRPOP queue 10 # BLOCKING pop, đợi 10s nếu empty
Pattern queue đơn giản: producer LPUSH, worker BRPOP với timeout. Không mất message nếu worker chết trước khi ack — nên thay bằng Redis Stream hoặc RabbitMQ cho production quan trọng.

4. Hash — Object có nhiều field

Thay vì lưu JSON lớn, dùng hash khi cần đọc/cập nhật field riêng lẻ. Tiết kiệm RAM hơn string JSON.

> HSET user:5 name "Chien" age 30 email "a@b.com" (integer) 3 > HGET user:5 name "Chien" > HGETALL user:5 1) "name" 2) "Chien" 3) "age" 4) "30" 5) "email" 6) "a@b.com" > HINCRBY user:5 age 1 # tăng age field, atomic (integer) 31 > HDEL user:5 email # xoá 1 field > HEXISTS user:5 name (integer) 1 > HMGET user:5 name age # lấy nhiều field 1 lần

✅ Dùng Hash khi

  • Object <100 field
  • Hay update 1 field riêng lẻ
  • Cần tiết kiệm RAM (nhỏ hơn JSON string)

❌ Dùng String JSON khi

  • Chỉ đọc/ghi toàn bộ object
  • Có nested object phức tạp
  • App-side dùng ORM map object dễ hơn

5. Set — Tập hợp không trùng

Unique members, O(1) check membership. Dùng cho: tags, friends, unique visitors, permission.

> SADD tags:post:1 "redis" "cache" "database" (integer) 3 > SADD tags:post:1 "redis" # duplicate → ignored (integer) 0 > SMEMBERS tags:post:1 1) "redis" 2) "cache" 3) "database" > SISMEMBER tags:post:1 "redis" # check có trong set? (integer) 1 > SADD tags:post:2 "redis" "nosql" > SINTER tags:post:1 tags:post:2 # giao 2 set 1) "redis" > SUNION tags:post:1 tags:post:2 # hợp > SDIFF tags:post:1 tags:post:2 # hiệu (có ở 1, không ở 2) > SRANDMEMBER tags:post:1 2 # lấy 2 member random

6. Sorted Set — "Leaderboard built-in"

Giống Set nhưng mỗi member có score (number). Tự động sort. Dùng: leaderboard, priority queue, time-series nhẹ.

> ZADD leaderboard 1500 "alice" 2100 "bob" 1800 "charlie" (integer) 3 > ZRANGE leaderboard 0 -1 WITHSCORES # tăng dần 1) "alice" 2) "1500" 3) "charlie" 4) "1800" 5) "bob" 6) "2100" > ZREVRANGE leaderboard 0 2 WITHSCORES # top 3 giảm dần 1) "bob" 2) "2100" 3) "charlie" 4) "1800" 5) "alice" 6) "1500" > ZINCRBY leaderboard 300 "alice" # +300 điểm, atomic "1800" > ZRANK leaderboard "bob" # hạng bob (0-indexed) (integer) 2 > ZSCORE leaderboard "alice" "1800" > ZRANGEBYSCORE leaderboard 1500 2000 # range theo score
Siêu tiện: viết 1 leaderboard game top 1 triệu user chỉ cần ZADD + ZREVRANGE 0 99. Tất cả O(log N).

7. Các data types đặc biệt

🔢 Bitmap

String nhưng thao tác từng bit. Memory siêu nhẹ.

Use case: track 1M user đã login hôm nay — chỉ tốn 128KB.

SETBIT login:2026-04-19 100005 1
GETBIT login:2026-04-19 100005
BITCOUNT login:2026-04-19       # đếm số user login

🎯 HyperLogLog

Đếm unique xấp xỉ (sai số 0.8%) tốn chỉ 12KB cho hàng tỷ item.

Use case: unique visitors / unique queries.

PFADD visitors:daily user:1 user:2 user:1
PFCOUNT visitors:daily    # ~2
PFMERGE visitors:week visitors:mon visitors:tue

🌍 Geo

Toạ độ + tìm kiếm theo bán kính. Nội bộ là Sorted Set với geohash.

Use case: "quán cafe gần tôi 2km".

GEOADD cafes 106.70 10.77 "BeanCafe"
GEOSEARCH cafes FROMLONLAT 106.69 10.77 BYRADIUS 2 km

🌊 Stream

Append-only log như Kafka nhỏ. Có consumer group, ack, retry.

Use case: event log, message queue bền bỉ.

XADD events * type login user 5
XREAD COUNT 10 STREAMS events 0
XGROUP CREATE events workers $
XREADGROUP GROUP workers w1 STREAMS events >

9. Transaction — MULTI/EXEC

Gom nhiều lệnh chạy tuần tự không bị xen vào. Khác SQL transaction: không có rollback nếu 1 lệnh fail logic.

> MULTI OK > INCR balance:user:5 QUEUED > INCR total_transactions QUEUED > EXEC 1) (integer) 101 2) (integer) 4582

Optimistic locking với WATCH

WATCH account:5
val = GET account:5
if val >= 100:
  MULTI
  DECRBY account:5 100
  EXEC    # fail nếu ai đó đã thay đổi account:5 giữa chừng

10. Pipelining — Batch để tăng tốc 10×

Gửi nhiều lệnh không đợi reply từng cái. Giảm round-trip, đặc biệt khi client ở xa Redis.

❌ Không pipeline — 100 RTT

for i in range(100):
    redis.set(f"key:{i}", i)
    # Mỗi lệnh = 1 round-trip
    # Với RTT 10ms → 1s total

✅ Pipeline — 1 RTT

pipe = redis.pipeline()
for i in range(100):
    pipe.set(f"key:{i}", i)
pipe.execute()
# 1 round-trip, ~10-20ms

11. Kết nối từ code

C# / .NET — StackExchange.Redis

// dotnet add package StackExchange.Redis
using StackExchange.Redis;

var redis = await ConnectionMultiplexer.ConnectAsync("localhost:6379");
var db = redis.GetDatabase();

// String
await db.StringSetAsync("user:5", "Chien", TimeSpan.FromMinutes(10));
var name = await db.StringGetAsync("user:5");

// Hash
await db.HashSetAsync("user:5", new[] {
    new HashEntry("name", "Chien"),
    new HashEntry("age", 30)
});

// Sorted Set — leaderboard
await db.SortedSetAddAsync("leaderboard", "alice", 1500);
var top10 = await db.SortedSetRangeByRankAsync(
    "leaderboard", 0, 9, Order.Descending);

Node.js — ioredis

// npm install ioredis
import Redis from 'ioredis';
const redis = new Redis(process.env.REDIS_URL);

await redis.set('user:5', 'Chien', 'EX', 3600);
const name = await redis.get('user:5');

// Hash
await redis.hset('user:5', { name: 'Chien', age: 30 });
const user = await redis.hgetall('user:5');

// Pipeline — batch
const pipe = redis.pipeline();
for (let i = 0; i < 100; i++) pipe.set(`k:${i}`, i);
await pipe.exec();
Connection tip: app server nên có 1 connection dùng chung (singleton). StackExchange.Redis & ioredis đều dùng connection multiplexing — không cần connection pool.

💡 Bài tập

  1. Counter visit: tạo trang web đếm lượt view bằng INCR page:home:views. Dùng Express/ASP.NET.
  2. Cache 5 phút: wrap DB query — nếu có cache → return, không có → query DB rồi SET ... EX 300.
  3. Session store: sau login lưu user info vào session:{token} với TTL 1 giờ, check trên mỗi request.
  4. Leaderboard game: mỗi trận xong gọi ZINCRBY, trang top 10 gọi ZREVRANGE.
  5. Unique visitor hôm nay: dùng HyperLogLog — PFADD visitors:2026-04-19 {user_id}, cuối ngày PFCOUNT.
