Redis Patterns

10 pattern thực tế: cache-aside, rate limit, distributed lock, leaderboard, queue, pub/sub, session, counter. Code C# + Node.js, cái bẫy thường gặp.

1. Cache-Aside (Lazy Loading) — 90% use case

Pattern phổ biến nhất. App check cache trước → miss → query DB → lưu cache → trả về.

Flow

  1. Client gọi GetUser(5)
  2. App GET user:5 từ Redis
  3. Nếu có → return luôn
  4. Nếu không → query DB
  5. SET user:5 {...} EX 300 (TTL 5 phút)
  6. Return user

Invalidation

Khi update user trong DB, nhớ DEL user:5. Nếu không: cache stale, user thấy data cũ.

  • Write-around: update DB, DEL cache
  • TTL-only: chấp nhận stale ≤ TTL
  • Event-driven: DB CDC → publish invalidate
// C# — cache-aside pattern
async Task<User> GetUserAsync(int id) {
    var key = $"user:{id}";
    var cached = await _db.StringGetAsync(key);

    if (cached.HasValue)
        return JsonSerializer.Deserialize<User>(cached!);

    var user = await _dbContext.Users.FindAsync(id);
    if (user != null) {
        await _db.StringSetAsync(key,
            JsonSerializer.Serialize(user),
            TimeSpan.FromMinutes(5));
    }
    return user;
}

async Task UpdateUserAsync(User user) {
    _dbContext.Users.Update(user);
    await _dbContext.SaveChangesAsync();
    await _db.KeyDeleteAsync($"user:{user.Id}");  // invalidate
}
🐛 Bẫy: Cache Stampede. Khi cache hết TTL và 1000 request đồng loạt miss → 1000 query DB cùng lúc → DB sập. Giải pháp: single-flight lock, hoặc pre-warm cache, hoặc stale-while-revalidate.

Giải pháp stampede: lock + fallback stale

async Task<User> GetUserSafeAsync(int id) {
    var key = $"user:{id}";
    var lockKey = $"lock:user:{id}";

    var cached = await _db.StringGetAsync(key);
    if (cached.HasValue) return Deserialize(cached);

    // Chỉ 1 request được quyền query DB
    if (await _db.StringSetAsync(lockKey, "1", TimeSpan.FromSeconds(10), When.NotExists)) {
        try {
            var user = await QueryDbAsync(id);
            await _db.StringSetAsync(key, Serialize(user), TimeSpan.FromMinutes(5));
            return user;
        } finally {
            await _db.KeyDeleteAsync(lockKey);
        }
    }

    // Các request khác: đợi 50ms rồi retry cache
    await Task.Delay(50);
    return await GetUserSafeAsync(id);
}

2. Rate Limiting

Chặn user/IP spam API. 3 thuật toán phổ biến, chọn theo nhu cầu.

Fixed Window

Đơn giản nhất: đếm request trong mỗi phút. Vấn đề: burst ở rìa phút có thể 2× limit.

const key = `rate:${ip}:${Math.floor(Date.now()/60000)}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 60);
if (count > 100) throw new Error('Rate limit');

Sliding Window (Sorted Set)

Chính xác hơn. Lưu timestamp từng request, đếm trong cửa sổ trượt.

const now = Date.now();
const window = 60_000;
const key = `rate:${ip}`;

await redis.zremrangebyscore(key, 0, now - window);
const count = await redis.zcard(key);
if (count >= 100) throw new Error('Rate limit');

await redis.zadd(key, now, `${now}:${Math.random()}`);
await redis.expire(key, 60);

Token Bucket

Mỗi user có "xô" chứa N token, refill r token/s. Gọi API = tiêu 1 token. Tốt cho burst vừa phải.

→ Dùng Lua script để atomic. Code trong mục "Lua" bên dưới.

Token bucket atomic với Lua

-- rate_limit.lua
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local refill = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

local data = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts = tonumber(data[2]) or now

-- Refill theo thời gian trôi qua
local elapsed = (now - ts) / 1000
tokens = math.min(capacity, tokens + elapsed * refill)

if tokens < 1 then
  return 0  -- rejected
end

tokens = tokens - 1
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, 3600)
return 1  -- allowed
// C# gọi Lua script
var script = File.ReadAllText("rate_limit.lua");
var result = (int)await _db.ScriptEvaluateAsync(
    script,
    keys: new RedisKey[] { $"rl:{userId}" },
    values: new RedisValue[] { 100, 10, DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() }
);
if (result == 0) throw new Exception("Rate limit exceeded");

3. Distributed Lock

Đảm bảo chỉ 1 worker xử lý 1 resource tại 1 thời điểm. Ví dụ: cron job chạy trên 3 server, chỉ muốn 1 cái thực thi.

Simple lock — SET NX EX

// Acquire
const token = crypto.randomUUID();  // unique per process
const ok = await redis.set(
    `lock:send-email-job`,
    token,
    'NX',     // chỉ set nếu chưa tồn tại
    'EX', 30  // auto-release sau 30s (nếu process chết)
);
if (!ok) return;  // worker khác đã giữ lock

try {
    await doJob();
} finally {
    // Release — CHỈ xoá nếu token còn là của mình (dùng Lua)
    await redis.eval(`
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        end
        return 0
    `, 1, `lock:send-email-job`, token);
}
Tại sao phải check token khi release? Nếu job của bạn chạy quá TTL (30s) → lock expire, worker B giành. Bạn xong việc mà vô tình DEL sẽ xoá lock của B. Check token = "chỉ xoá lock nếu còn là của tôi".
Redlock: để đảm bảo an toàn hơn khi có nhiều Redis node, dùng thuật toán Redlock — acquire trên đa số nodes. Cài library redlock (Node) hoặc RedLock.net (C#).

4. Leaderboard — Game rank top 100

Sorted Set giải quyết đẹp. Thêm/đọc/rank đều O(log N).

// Khi user thắng trận, +100 điểm
await redis.zincrby('leaderboard:global', 100, `user:${userId}`);

// Top 10
const top10 = await redis.zrevrange(
    'leaderboard:global', 0, 9, 'WITHSCORES'
);
// [ 'user:5', '8400', 'user:2', '7650', ... ]

// Rank của 1 user
const rank = await redis.zrevrank('leaderboard:global', `user:${userId}`);
// 0-indexed, null nếu chưa có trong leaderboard

// Score của 1 user
const score = await redis.zscore('leaderboard:global', `user:${userId}`);

// Leaderboard hàng tuần — dùng key khác
const week = getISOWeek(new Date());
await redis.zincrby(`leaderboard:week:${week}`, 100, `user:${userId}`);
await redis.expire(`leaderboard:week:${week}`, 60 * 86400);  // 60 ngày
Giảm độ to: 10 triệu user trong 1 sorted set ăn ~500MB RAM. Nếu chỉ cần top 1000 — ZREMRANGEBYRANK xoá phần dưới định kỳ.

5. Queue đơn giản — List

Producer LPUSH, worker BRPOP. Đủ cho hầu hết background task. Production nên dùng Stream hoặc RabbitMQ.

// Producer — khi có email cần gửi
await redis.lpush('queue:email', JSON.stringify({
    to: 'user@example.com',
    template: 'welcome',
    data: {...}
}));

// Worker — loop vô hạn
while (true) {
    const result = await redis.brpop('queue:email', 10);  // đợi 10s
    if (!result) continue;
    const [, payload] = result;
    const job = JSON.parse(payload);
    try {
        await sendEmail(job);
    } catch (err) {
        // Retry queue hoặc DLQ
        await redis.lpush('queue:email:dlq', payload);
    }
}
Hạn chế List-queue:
  • Không có ack → worker chết giữa chừng = mất job
  • Không có consumer group → khó scale nhiều worker
  • Không có delayed message
Dùng Redis Stream + XGROUP (ack, retry, consumer group) hoặc BullMQ / Hangfire khi production.

6. Redis Stream — Kafka mini

Append-only log + consumer group + ack. Giải quyết mọi hạn chế của List-queue.

# Producer
XADD events * type "order.created" userId 5 amount 99.99

# Consumer group — worker group lấy mỗi message 1 lần
XGROUP CREATE events order-processors $ MKSTREAM

# Worker lấy message chưa xử lý
XREADGROUP GROUP order-processors worker-1 COUNT 10 BLOCK 5000 STREAMS events >

# ACK khi xử lý xong
XACK events order-processors 1678901234-0

# Xem message chưa ack (pending) của worker
XPENDING events order-processors
Ưu điểm: retry tự động (worker không ack → message quay lại), scale ngang (thêm worker cùng group = tự chia load), replay history (dùng ID cụ thể thay $).

7. Pub/Sub — Real-time notification

Publisher gửi message lên channel, tất cả subscriber đang connect nhận được. Fire-and-forget — không persist.

// Subscriber (WebSocket server, worker)
const sub = new Redis();
await sub.subscribe('notifications:user:5');
sub.on('message', (channel, message) => {
    ws.send(message);  // push xuống browser
});

// Publisher (API server)
await redis.publish('notifications:user:5', JSON.stringify({
    type: 'new_message',
    from: 'admin'
}));
Giới hạn Pub/Sub: nếu subscriber offline lúc publish → mất message. Dùng Pub/Sub cho notification không quan trọng (toast, presence). Cần persist → dùng Stream.

8. Session Store — Multi-instance app

App chạy trên 3 server load-balanced → session không thể ở memory từng server. Redis là session store mặc định.

// Express + connect-redis
import session from 'express-session';
import RedisStore from 'connect-redis';
import Redis from 'ioredis';

const redis = new Redis();
app.use(session({
    store: new RedisStore({ client: redis, prefix: 'sess:' }),
    secret: process.env.SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: { maxAge: 3600_000 },  // 1h
}));

// Trong handler
req.session.userId = 5;  // tự lưu vào Redis

.NET Core:

// Program.cs
builder.Services.AddStackExchangeRedisCache(o => {
    o.Configuration = "localhost:6379";
    o.InstanceName = "sess:";
});
builder.Services.AddSession(o => {
    o.IdleTimeout = TimeSpan.FromHours(1);
    o.Cookie.HttpOnly = true;
});

app.UseSession();

9. Counter — View count, like count

INCR atomic. Nhưng tạo 1M row DB mỗi lần like = chết. Redis buffer rồi flush định kỳ xuống DB.

// Khi user like
await redis.hincrby('post:likes:pending', `post:${postId}`, 1);

// Cron job mỗi 1 phút: flush vào DB
const pending = await redis.hgetall('post:likes:pending');
for (const [key, count] of Object.entries(pending)) {
    const postId = key.split(':')[1];
    await db.query(
        'UPDATE posts SET likes = likes + $1 WHERE id = $2',
        [count, postId]
    );
}
await redis.del('post:likes:pending');
Trade-off: chấp nhận mất tối đa 1 phút data nếu Redis crash. Đa số use case (like, view count) có thể chấp nhận. Tiền bạc → không.

10. Full-page Cache — Giảm 99% tải

Cache HTML hoặc JSON response nguyên trang. Key theo URL + query.

// Middleware Express
function cachePage(ttl = 60) {
    return async (req, res, next) => {
        if (req.method !== 'GET') return next();

        const key = `page:${req.originalUrl}`;
        const cached = await redis.get(key);
        if (cached) {
            res.setHeader('X-Cache', 'HIT');
            return res.json(JSON.parse(cached));
        }

        // Intercept res.json
        const orig = res.json.bind(res);
        res.json = (body) => {
            redis.set(key, JSON.stringify(body), 'EX', ttl);
            orig(body);
        };
        next();
    };
}

app.get('/api/products', cachePage(120), productsHandler);
Invalidation: khi admin update product → SCAN MATCH page:/api/products* rồi DEL. Hoặc đơn giản: tag cache bằng SADD tag:products key, khi invalidate thì SMEMBERS tag:products → DEL.

🚫 5 Anti-pattern cần tránh

❌ Dùng KEYS trong production

Chặn Redis single-thread. Dùng SCAN với cursor.

❌ Lưu object khổng lồ trong 1 key

1 key 100MB → network slow, block Redis khi GET. Chia nhỏ.

❌ Không set TTL cho cache

Không TTL + không xoá → memory đầy → eviction ép buộc → miss tăng.

❌ Dùng Redis thay DB chính

Persistence Redis không mạnh bằng DB truyền thống. Mất data = thảm hoạ.

❌ Round-trip không pipeline

10,000 GET riêng lẻ = 10,000 RTT = 10s+. Pipeline = 1 RTT.

❌ Hot key — 1 key chịu 99% traffic

Ví dụ page:home bị request 10k/s. Cluster cũng không cứu vì 1 shard. Giải pháp: client-side LRU cache, hoặc shard key theo user.
