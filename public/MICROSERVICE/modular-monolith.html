Làm chủ Modular Monolith trước

Trước khi tách 1 dòng code ra network, hãy xây ranh giới module sạch trong một deployable duy nhất. Đây là cách 90% hệ thống nên bắt đầu — và là bước chuẩn bị bắt buộc để sau này extract service không đau.

Vì sao "Monolith-first" gần như luôn đúng

Martin Fowler & Sam Newman đều khuyến nghị: đừng bắt đầu bằng microservices. Bạn chưa hiểu domain đủ rõ để vẽ ranh giới đúng — và ranh giới sai trong distributed system thì cực kỳ đắt để sửa.

❌ Bắt đầu bằng microservices

  • Ranh giới đoán sai → service "chatty", gọi nhau loạn xạ
  • Refactor cross-service = đổi API + deploy nhiều service + version
  • Distributed transaction, eventual consistency ngay từ ngày 1
  • Cần CI/CD, observability, service mesh trước khi có doanh thu
  • 1 team 4 người gánh 12 repo, 12 pipeline

✅ Bắt đầu bằng Modular Monolith

  • Refactor ranh giới = di chuyển code trong cùng repo, compiler bắt lỗi
  • Transaction ACID thật, không cần Saga
  • 1 deploy, 1 pipeline, debug bằng stack trace
  • Domain dần lộ ra → ranh giới module hội tụ về đúng
  • Khi module nào thực sự cần scale/độc lập → extract module đó thôi
📐 Nguyên tắc: Microservices giải bài toán tổ chức & scale, không phải bài toán code sạch. Một modular monolith tốt cho 80-90% lợi ích kiến trúc với 10% chi phí vận hành.

Module boundary trong một deployable

Modular monolith = nhiều module độc lập, mỗi module là 1 bounded context, giao tiếp qua public contract rõ ràng — nhưng tất cả chạy trong cùng process.

Public API mỏng

Mỗi module phơi ra 1 interface contract (vd ISalesModuleApi). Module khác chỉ gọi qua đây, không chạm internal type.

Internal đóng kín

Entity, repository, handler để internal. Không module nào reference được implementation.

Không chia sẻ DbContext

Mỗi module có DbContext riêng, schema riêng. Không join chéo bảng của module khác.

Cấu trúc một .NET Modular Monolith cụ thể

Bố cục project điển hình (.NET 9). Mỗi module là 1 thư mục/assembly với cấu trúc giống nhau.

ShopApp.sln
├── src/Bootstrapper/
│   └── ShopApp.Api            // host duy nhất: Program.cs, middleware, đăng ký module
│
├── src/Modules/Sales/
│   ├── ShopApp.Sales.Public         // CONTRACT: interface + DTO + integration event
│   ├── ShopApp.Sales.Core           // internal: domain, handler, business logic
│   └── ShopApp.Sales.Infrastructure // internal: EF DbContext, repo (schema "sales")
│
├── src/Modules/Catalog/
│   ├── ShopApp.Catalog.Public
│   ├── ShopApp.Catalog.Core
│   └── ShopApp.Catalog.Infrastructure
│
├── src/Modules/Billing/  ...
│
└── src/Shared/
    ├── ShopApp.Shared.Abstractions  // IEventBus, IModule, marker — KHÔNG có business
    └── ShopApp.Shared.Infrastructure

Quy tắc reference vàng: module chỉ được phép reference assembly .Public của module khác — không bao giờ .Core hay .Infrastructure.

// ShopApp.Sales.Public/ISalesModule.cs — contract duy nhất Sales phơi ra
namespace ShopApp.Sales.Public;

public interface ISalesModule
{
    Task<OrderSummaryDto?> GetOrderAsync(Guid orderId, CancellationToken ct);
    Task<Guid> PlaceOrderAsync(PlaceOrderRequest req, CancellationToken ct);
}

public record OrderSummaryDto(Guid Id, string Status, decimal Total);
public record PlaceOrderRequest(Guid CustomerId, IReadOnlyList<OrderLineDto> Lines);
// ShopApp.Sales.Core/Orders/PlaceOrderHandler.cs — INTERNAL, không ai ngoài Sales thấy
internal sealed class SalesModule(SalesDbContext db, IEventBus bus) : ISalesModule
{
    public async Task<Guid> PlaceOrderAsync(PlaceOrderRequest req, CancellationToken ct)
    {
        var order = Order.Place(req.CustomerId, req.Lines);
        db.Orders.Add(order);
        await db.SaveChangesAsync(ct);  // transaction ACID thật — chưa cần Outbox

        // domain event in-process: module Billing/Shipping sẽ nghe
        await bus.PublishAsync(new OrderPlaced(order.Id, order.Total), ct);
        return order.Id;
    }
}

Ép buộc ranh giới (đừng tin vào thiện chí)

Convention sẽ bị phá sau 6 tháng dưới áp lực deadline. Phải để compiler / CI chặn vi phạm tự động.

1. internal + assembly tách rời

Để type là internal trong .Core/.Infrastructure. Module khác không reference được → compiler error. Đây là hàng rào mạnh nhất, miễn phí.

2. Architecture test (NetArchTest / ArchUnitNET)

[Fact]
public void Sales_should_not_depend_on_Billing_internals()
{
    var result = Types.InAssembly(typeof(SalesModule).Assembly)
        .ShouldNot()
        .HaveDependencyOn("ShopApp.Billing.Core")
        .GetResult();
    Assert.True(result.IsSuccessful);
}
💡 Mẹo: Đặt 1 file ArchitectureTests chạy trong CI. Vi phạm ranh giới = build đỏ. Đây chính là thứ giữ monolith ở trạng thái "extract được" mãi mãi.

In-process domain events

Module giao tiếp lỏng lẻo qua event ngay trong process — y hệt mô hình bạn sẽ dùng sau này với message broker, nhưng giờ chỉ là method call. Sau này đổi implementation IEventBus từ in-memory sang RabbitMQ là xong.

// Shared.Abstractions — interface không đổi dù monolith hay microservice
public interface IEventBus
{
    Task PublishAsync<T>(T @event, CancellationToken ct) where T : IIntegrationEvent;
}

// Bootstrapper: giai đoạn monolith — bus chạy in-memory (MediatR/Wolverine)
// Billing module đăng ký handler:
internal sealed class OnOrderPlaced(BillingDbContext db) : IIntegrationEventHandler<OrderPlaced>
{
    public async Task HandleAsync(OrderPlaced e, CancellationToken ct)
    {
        db.Invoices.Add(Invoice.For(e.OrderId, e.Total));
        await db.SaveChangesAsync(ct);
    }
}
⚠️ Bẫy: In-process event mặc định chạy trong cùng transaction của caller. Quyết định sớm: handler chạy đồng bộ trong transaction (mạnh nhất quán) hay sau commit (giống async broker). Chọn "sau commit" nếu bạn dự tính extract — nó mô phỏng đúng eventual consistency tương lai.

Shared schema vs separate schema

Phương ánMô tảKhi nào dùng
Shared schema, no boundaryTất cả bảng chung 1 schema, join tự do❌ Không dùng — đây là "big ball of mud", không bao giờ extract được
1 DB, schema/prefix riêng/moduleCùng database nhưng sales.*, billing.*; cấm join chéo schema✅ Mặc định nên dùng. Vận hành 1 DB nhưng ranh giới rõ, dễ tách sau
DB riêng / moduleMỗi module 1 database/connection stringKhi đã chắc sẽ extract, muốn mô phỏng "database per service" sớm
📦 Thực tế: Bắt đầu bằng 1 DB + schema riêng/module + cấm join chéo. Đây là sweet spot: chi phí vận hành 1 DB, nhưng dữ liệu đã phân vùng sẵn theo ranh giới service tương lai.

Khi nào & cách extract module thành service (Strangler Fig)

Đừng tách vì "thấy ngầu". Tách khi có lý do cụ thể: module cần scale độc lập, deploy theo nhịp khác, team riêng sở hữu, hoặc cần stack công nghệ khác.

  1. Tín hiệu cần tách: module bị deploy chặn vì module khác; nó là bottleneck scale; có team riêng muốn release độc lập; SLA/bảo mật khác biệt.
  2. Đảm bảo ranh giới đã sạch: module chỉ giao tiếp qua .Public contract + integration event. Nếu còn join chéo schema → sửa trước khi tách.
  3. Đổi transport, giữ contract: thay implementation ISalesModule từ in-process sang HTTP/gRPC client; đổi IEventBus in-memory → RabbitMQ/Kafka. Code gọi không đổi.
  4. Tách dữ liệu: di chuyển schema sales.* sang database riêng. Bỏ mọi FK chéo (đã không có nếu làm đúng).
  5. Đặt proxy/gateway trước: route các call của module Sales sang service mới; phần còn lại vẫn ở monolith. Roll out dần (canary).
  6. Thêm hạ tầng distributed: giờ mới cần Outbox (thay in-process event), Saga (thay ACID transaction), tracing xuyên service, retry/circuit breaker.
💡 Insight then chốt: Nếu modular monolith làm đúng, "extract 1 service" chỉ là đổi transport + tách DB — không phải viết lại logic. Đó là toàn bộ lý do ta đầu tư vào ranh giới ngay từ đầu.

Checklist — Modular Monolith đạt chuẩn "extract-ready"

✅ Ranh giới & code

  • Mỗi module có assembly .Public / .Core / .Infrastructure
  • Domain/repo/handler đều internal
  • Module chỉ reference .Public của module khác
  • Architecture test chạy trong CI, vi phạm = build đỏ
  • Giao tiếp chéo module qua interface contract + integration event

✅ Dữ liệu & sự kiện

  • Mỗi module DbContext riêng, schema riêng
  • Không join chéo schema, không FK chéo module
  • IEventBus abstraction sẵn (đổi transport không sửa caller)
  • Domain event publish "sau commit" để mô phỏng async tương lai
  • Có thể chỉ tên 1-2 module thật sự nên (và sẽ) tách trước
