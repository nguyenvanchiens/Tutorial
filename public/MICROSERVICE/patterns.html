Microservices · Patterns Thực Chiến

Saga, CQRS, Event Sourcing, Outbox, Circuit Breaker, API Gateway, BFF... Tất cả pattern phải biết khi làm production system.

1. API Gateway

🎯 Vấn đề

Client gọi trực tiếp 10 service → nightmare: CORS, auth, rate-limit, version mismatch, mobile gọi nhiều round trip → battery + latency cao.

💊 Giải pháp

Đặt 1 Gateway ở giữa: client chỉ biết gateway. Gateway lo:

  • Authentication / Authorization
  • Rate limiting, throttling
  • Request/response transformation
  • Aggregation (gộp nhiều API call)
  • Caching, logging, tracing
📦 Tools: Ocelot, YARP (.NET) · Kong, Traefik, Nginx · AWS API Gateway, Azure APIM.

2. BFF — Backend for Frontend

Mỗi loại client có 1 backend "may đo": MobileBFF, WebBFF, AdminBFF. Mỗi BFF gọi nhiều microservice rồi trả response phù hợp client đó.

// Mobile cần ít field, tối ưu battery
GET /mobile/home
  => gọi Catalog + Promotion + User
  => trả: { banner, top10, userName }   // 1 call thay vì 3

// Web có nhiều màn, cần nhiều dữ liệu
GET /web/home
  => gọi Catalog + Promotion + User + Cart + Recommendation
  => trả: { ... đầy đủ ... }
💡 Khi nào cần BFF: client app khác nhau quá nhiều (mobile vs web), hoặc 1 màn cần aggregate > 3 service.

3. Saga — Distributed Transaction

Trong micro, không thể 2PC qua nhiều DB. Saga chia transaction lớn thành chuỗi local transaction + compensating action khi fail.

🎭 Choreography (phân tán)

Service tự lắng nghe event và quyết định bước tiếp theo. Không có "đầu não".

OrderCreated
  → Inventory reserve, publish StockReserved
  → Payment charge, publish PaymentSucceeded
  → Order set CONFIRMED

// nếu Payment fail:
PaymentFailed
  → Inventory release stock
  → Order set CANCELLED

Hợp với: ít bước, ít coupling. Khó với: > 5 bước → khó debug, ai cũng phải biết business flow.

🎬 Orchestration (tập trung)

Có 1 Orchestrator điều phối. Các service "câm" — chỉ làm việc khi được gọi.

OrderSaga:
  step 1: ReserveStock      | compensate: ReleaseStock
  step 2: ChargePayment     | compensate: RefundPayment
  step 3: ConfirmOrder      | compensate: CancelOrder

// nếu step 2 fail → run compensate step 1

Hợp với: flow phức tạp, business logic rõ. Tools: MassTransit Saga, Camunda, Temporal, AWS Step Functions.

⚠️ Lưu ý: Mọi compensating action phải idempotent — vì có thể chạy nhiều lần do retry.

4. Outbox Pattern

Giải quyết bài toán dual-write: lưu DB + publish event không thể atomic vì 2 nơi khác nhau.

❌ Code dễ mất event

db.Orders.Add(order);
await db.SaveChangesAsync();      // ✅ commit
await bus.Publish(new OrderCreated()); // ❌ broker down → mất event

✅ Outbox: ghi event cùng transaction

db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage(OrderCreated));
await db.SaveChangesAsync();   // 1 transaction, atomic

// background worker đọc Outbox → publish → mark sent
💡 Tool có sẵn: Debezium (CDC từ Postgres/MySQL → Kafka), MassTransit Transactional Outbox, NServiceBus Outbox.

5. Inbox Pattern (Idempotent Consumer)

Broker thường at-least-once delivery — message có thể đến 2 lần. Consumer phải idempotent.

async Task HandleAsync(OrderCreated evt) {
    // 1. check inbox xem đã xử lý chưa
    if (await db.Inbox.AnyAsync(x => x.MessageId == evt.Id))
        return;  // đã xử lý — skip

    // 2. xử lý + ghi inbox trong cùng transaction
    ReserveStock(evt.OrderId);
    db.Inbox.Add(new InboxMessage(evt.Id));
    await db.SaveChangesAsync();
}

→ Dù message đến 100 lần, hành động chỉ thực hiện 1 lần.

6. CQRS — Command Query Responsibility Segregation

📝 Vấn đề

Một model lo cả write (validate, business rule) lẫn read (join nhiều bảng, optimize query) → vừa phức tạp vừa chậm.

💊 Giải pháp

Tách 2 phía:

  • Command side: write → validate → save → publish event
  • Query side: subscribe event → cập nhật read model (denormalized) → API đọc nhanh
// Write (Command) — Postgres normalized
OrderService.CreateOrder(cmd) → ghi 5 bảng + publish OrderCreated

// Read (Query) — MongoDB / ElasticSearch denormalized
OrderReadModel.On(OrderCreated) → save 1 document đầy đủ
GET /orders/123  → query 1 document, <5ms
⚠️ Đánh đổi: Read model eventual consistency — có thể trễ vài giây. Không hợp với màn hình "real-time balance".

7. Event Sourcing

Thay vì lưu state hiện tại, lưu chuỗi event đã xảy ra. State = replay event.

// Thay vì lưu:  account.balance = 50

// Lưu:
AccountOpened(id=A1)
Deposited(id=A1, amount=100)
Withdrew(id=A1, amount=30)
Withdrew(id=A1, amount=20)

// Replay → balance = 50
// Lợi: full audit log, time travel, debug được mọi lúc

✅ Phù hợp

  • Domain audit cao (banking, ledger, healthcare)
  • Cần "undo / time travel"
  • Phân tích hành vi user theo thời gian

❌ Không phù hợp

  • CRUD đơn giản
  • Team chưa quen DDD
  • Schema thay đổi liên tục (event versioning đau)

Tools: EventStoreDB, Marten (Postgres), Axon, Kafka như event log.

8. Circuit Breaker — Polly Style

Service A gọi service B. B chậm → A treo → caller A treo → cascade failure. Circuit Breaker là cầu chì.

// .NET — Polly
var policy = Policy
    .Handle<HttpRequestException>()
    .CircuitBreakerAsync(
        exceptionsAllowedBeforeBreaking: 5,
        durationOfBreak: TimeSpan.FromSeconds(30));

await policy.ExecuteAsync(() => httpClient.GetAsync("http://payment/health"));
StateHành vi
ClosedCho phép call, đếm lỗi
OpenSau N lỗi → ngắt mạch, fail nhanh, không gọi B
Half-OpenSau timeout → cho 1 request thử. Nếu OK → Closed; fail → Open lại
📦 Tools: Polly (.NET), resilience4j (Java), gobreaker (Go). Service mesh (Istio) có sẵn ở layer mạng.

9. Retry + Exponential Backoff

Policy
  .Handle<HttpRequestException>()
  .WaitAndRetryAsync(
      retryCount: 5,
      sleepDurationProvider: i => TimeSpan.FromSeconds(Math.Pow(2, i))
      // 2s, 4s, 8s, 16s, 32s + jitter
  );
⚠️ Phải có jitter (random 0-500ms) — nếu không, 1000 client retry cùng lúc → "thundering herd" giết service vừa hồi sinh.

10. Bulkhead — Cô lập tài nguyên

Giống vách ngăn trong tàu thuỷ: 1 ngăn ngập nước, các ngăn khác vẫn nổi.

// Mỗi service downstream có thread pool riêng / connection pool riêng
PaymentClient: max 10 concurrent calls
EmailClient:   max 20 concurrent calls

// Email service chậm → email request bị chặn,
// nhưng Payment vẫn còn đầy slot — không bị "đói" thread.

11. Strangler Fig — Migrate Monolith → Micro

Tên lấy từ cây "siết cổ" trong rừng — bao quanh cây cũ rồi từ từ thay thế. Áp dụng vào software:

  1. Đặt Proxy / Gateway trước Monolith. Mọi request đi qua proxy.
  2. Tách 1 module nhỏ ra thành Microservice. Proxy route module đó về service mới, các module khác vẫn đến Monolith.
  3. Lặp lại từng module một. Có thể mất 1-3 năm cho hệ lớn.
  4. Khi Monolith trống → tắt.
💡 Quy tắc vàng: Đừng "big bang rewrite" — 80% dự án thất bại theo cách này. Migrate từng phần, đo bằng business metric.

12. Sidecar & Service Mesh

Sidecar = 1 container nhỏ chạy cạnh service chính trong cùng pod. Lo các "cross-cutting concerns": mTLS, retry, tracing, rate-limit.

// K8s pod
Pod:
  containers:
    - app          // service của bạn
    - envoy-proxy  // sidecar — Istio đặt vào

// Mọi network in/out đi qua envoy
// → mTLS, tracing, retry tự động — code không cần biết
📦 Service mesh: Istio, Linkerd, Consul Connect. Đáng cân nhắc khi có > 20 service.
