Microservices · Cơ Bản

8 nguyên tắc cốt lõi, 5 bounded context, cách tách service đúng theo domain — tránh sai lầm "tách quá sớm" mà 80% startup mắc phải.

8 Nguyên tắc cốt lõi

1. Single Responsibility

Mỗi service chỉ chịu trách nhiệm một business capability. Order Service chỉ lo order — không xử lý payment, không gửi email.

2. Database per Service

Service không bao giờ truy cập DB của service khác. Muốn dữ liệu? Gọi API hoặc subscribe event.

3. Loose Coupling

Service A đổi schema không làm service B sập. Hợp đồng rõ qua REST/gRPC + versioning.

4. High Cohesion

Code liên quan thuộc cùng service. Đừng vẽ ra "Service Helper" lo nhiều thứ — đó là dấu hiệu chia sai.

5. Independently Deployable

Deploy 1 service không cần build/redeploy service khác. Pipeline riêng, version riêng.

6. Decentralized Data

Không có "Master DB". Eventual consistency > ACID toàn cục.

7. Fail Fast, Fail Independently

Service chết phải bị isolate (Circuit Breaker). Không kéo cả hệ thống xuống.

8. Built for Observability

Mọi service log/metric/trace từ đầu — không phải "thêm sau". Không quan sát được = không debug được.

Bounded Context — Cách tách service đúng

Bounded Context (DDD) là ranh giới ngữ nghĩa: cùng từ "Customer" trong sales nghĩa khác trong logistics. Mỗi bounded context là 1 ứng cử viên service.

❌ Sai: Tách theo layer kỹ thuật

// Phản pattern
UserAPI      // chỉ HTTP layer
UserService  // chỉ business
UserDB       // chỉ data

Tách như vậy chỉ là phân lớp trong Monolith — nhưng đặt qua network. Tệ nhất của 2 thế giới.

✅ Đúng: Tách theo business capability

OrderService      // API + logic + DB của Order
PaymentService    // API + logic + DB của Payment
InventoryService  // API + logic + DB của Stock
NotificationService

Mỗi service đầy đủ stack — autonomous, deploy riêng, scale riêng.

📐 Quy tắc 2 pizza: Một service nên đủ nhỏ để 1 team 6-8 người (ăn hết 2 pizza) sở hữu trọn từ code → deploy → on-call. Lớn hơn → tách. Nhỏ hơn → gộp.

Ví dụ: E-commerce — Tách thành bounded context nào?

Vòng đời 1 request — Customer đặt hàng

  1. Mobile App → API Gateway — POST /checkout. Gateway xác thực JWT, rate-limit, route đến Order Service.
  2. Order Service tạo Order với status PENDING, lưu DB.
  3. Order Service publish event OrderCreated lên RabbitMQ/Kafka.
  4. Inventory Service consume event, reserve stock, publish StockReserved hoặc StockOutOfStock.
  5. Payment Service consume OrderCreated, gọi cổng thanh toán, publish PaymentSucceeded / PaymentFailed.
  6. Order Service consume các event này → cập nhật status CONFIRMED hoặc CANCELLED (Saga).
  7. Notification Service consume OrderConfirmed → gửi email/SMS cho user.
  8. Shipping Service consume OrderConfirmed → tạo shipment, gửi cho đối tác vận chuyển.
💡 Insight: 1 user click "Đặt hàng" → 5 service chạy. Nếu làm Monolith, đó chỉ là 1 transaction. Microservices = nhanh hơn, phân tải tốt hơn, nhưng phải cẩn thận với Saga, Idempotency, Tracing — sẽ học ở các trang sau.

Các thành phần phải có (Building Blocks)

🚪 API Gateway

Cửa ngõ duy nhất từ ngoài vào. Auth, rate-limit, aggregate, transform.

Tools: Ocelot, YARP, Kong, Nginx, AWS API Gateway, Azure API Management.

🔍 Service Discovery

Service tìm nhau bằng tên, không phải IP cứng. K8s tự lo qua DNS.

Tools: Consul, Eureka, K8s Service.

⚙️ Config Server

Config tập trung, đổi không cần redeploy. Hot reload.

Tools: Spring Cloud Config, K8s ConfigMap, AWS AppConfig.

🔐 Secret Manager

API key, DB password — KHÔNG bỏ vào git/env file.

Tools: HashiCorp Vault, AWS Secrets Manager, Azure Key Vault.

📨 Message Broker

Async giữa các service. Decouple producer/consumer.

Tools: RabbitMQ, Kafka, NATS, Azure Service Bus.

🔭 Observability Stack

Log + Metric + Trace tập trung. OpenTelemetry là chuẩn 2026.

Tools: Prometheus, Grafana, Jaeger, Loki, Datadog.

Hello World Microservice (.NET 8)

Một Order Service tối thiểu: REST API + DB + publish event lên RabbitMQ.

// Program.cs
var builder = WebApplication.CreateBuilder(args);

// 1. EF Core với DB riêng cho Order
builder.Services.AddDbContext<OrderDbContext>(opt =>
    opt.UseNpgsql(builder.Configuration.GetConnectionString("OrderDb")));

// 2. MassTransit + RabbitMQ
builder.Services.AddMassTransit(x => {
    x.UsingRabbitMq((ctx, cfg) => {
        cfg.Host("rabbitmq", "/", h => {
            h.Username("guest"); h.Password("guest");
        });
    });
});

var app = builder.Build();

// 3. POST /orders
app.MapPost("/orders", async (CreateOrderDto dto, OrderDbContext db, IPublishEndpoint bus) => {
    var order = new Order(dto.UserId, dto.Items);
    db.Orders.Add(order);
    await db.SaveChangesAsync();

    // publish event để Inventory + Payment xử lý
    await bus.Publish(new OrderCreated(order.Id, order.Total));

    return Results.Ok(order);
});

app.Run();

→ Service này tự lo DB riêng, publish event, không gọi trực tiếp Inventory hay Payment. Đó là nguyên tắc loose coupling.

⚠️ Vấn đề ở code trên: SaveChanges + Publish không atomic. Nếu DB save xong nhưng RabbitMQ down → mất event → Inventory không reserve. Giải pháp: Outbox Pattern (xem trang Patterns).

Checklist trước khi viết service đầu tiên

✅ Nắm chắc

  • HTTP status codes, REST best practices
  • JSON serialization & versioning (v1, v2)
  • Async/await, Task, goroutine — tuỳ ngôn ngữ
  • SQL transaction, isolation level
  • Docker: build, run, multi-stage, compose
  • Linux permissions, port, network
