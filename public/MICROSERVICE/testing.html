Testing Hệ Phân Tán

Trong microservices, "tất cả unit test xanh" không có nghĩa hệ thống chạy. Học test pyramid đúng cho distributed system: Testcontainers, contract testing với Pact, test Saga & idempotency, test luồng event bất đồng bộ.

Test Pyramid cho Microservices

Nhiều test nhanh & rẻ ở đáy, ít test chậm & đắt ở đỉnh. Microservices thêm 1 tầng quan trọng mà monolith không có: contract test.

🔺 E2E (rất ít, chậm, dễ vỡ)

Unit vs Component — ranh giới

Unit test — domain thuần

[Fact]
public void Place_order_with_no_lines_throws()
{
    var act = () => Order.Place(
        Guid.NewGuid(), Array.Empty<OrderLine>());

    act.Should().Throw<DomainException>();
}

Không DB, không HTTP. Test business rule của aggregate. Phải cực nhanh, cực nhiều.

Component test — cả service in-process

// WebApplicationFactory: chạy API in-memory
[Fact]
public async Task Post_order_returns_201()
{
    var client = _factory.CreateClient();
    var resp = await client.PostAsJsonAsync(
        "/orders", new PlaceOrderRequest(...));

    resp.StatusCode.Should().Be(HttpStatusCode.Created);
}

Test cả pipeline HTTP→handler→domain, nhưng mock Payment/broker bên ngoài.

Integration Test với Testcontainers

Đừng test với SQLite in-memory rồi prod dùng Postgres — hành vi khác nhau (JSON, ngày giờ, lock). Testcontainers spin up Postgres/RabbitMQ/Kafka thật trong Docker cho mỗi test run, rồi dọn sạch.

// Testcontainers.PostgreSql + Testcontainers.RabbitMq (2026)
public class OrderIntegrationFixture : IAsyncLifetime
{
    private readonly PostgreSqlContainer _db = new PostgreSqlBuilder()
        .WithImage("postgres:17-alpine")
        .WithDatabase("orders")
        .Build();

    private readonly RabbitMqContainer _mq = new RabbitMqBuilder()
        .WithImage("rabbitmq:4-management")
        .Build();

    public string DbConnString => _db.GetConnectionString();

    public async Task InitializeAsync()
    {
        await Task.WhenAll(_db.StartAsync(), _mq.StartAsync());
        // chạy EF migration lên DB container thật
    }

    public async Task DisposeAsync() =>
        await Task.WhenAll(_db.DisposeAsync().AsTask(), _mq.DisposeAsync().AsTask());
}

[Fact]
public async Task SaveOrder_persists_to_real_postgres()
{
    await using var ctx = new OrderDbContext(_fixture.DbConnString);
    var order = Order.Place(_customerId, _lines);
    ctx.Orders.Add(order);
    await ctx.SaveChangesAsync();

    var reloaded = await ctx.Orders.FindAsync(order.Id);
    reloaded!.Total.Should().Be(order.Total);  // đúng với DB thật
}
💡 2026 best practice: Dùng respawn để reset state DB giữa các test thay vì restart container (nhanh hơn nhiều). Chạy container 1 lần / test class qua shared fixture.

Consumer-Driven Contract Testing (Pact)

Vấn đề lớn nhất của micro: Provider đổi API → tất cả Consumer vỡ ở production, không ai biết trước. Contract test bắt điều này ở CI, không cần chạy cả 2 service cùng lúc.

Cách hoạt động

  1. Consumer viết test mô tả "tôi mong API trả gì" → sinh ra file pact (contract).
  2. Contract đẩy lên Pact Broker.
  3. Provider chạy verification: replay contract lên API thật của mình, đảm bảo đáp ứng đúng.
  4. can-i-deploy chặn deploy nếu phá vỡ contract của consumer đang chạy.

Consumer side (.NET — PactNet)

_pact.UponReceiving("yêu cầu order theo id")
    .WithRequest(HttpMethod.Get, "/orders/42")
  .WillRespond()
    .WithStatus(HttpStatusCode.OK)
    .WithJsonBody(new {
        id = Match.Type(42),
        status = Match.Regex("Confirmed", "Pending|Confirmed")
    });

// chạy client thật của consumer với mock server Pact dựng
await _pact.VerifyAsync(async ctx => {
    var order = await sut.GetOrderAsync(42);
    order.Status.Should().Be("Confirmed");
});
📦 Async/message contract: Pact cũng test message contract — consumer khai báo nó mong event OrderPlaced có schema gì; provider verify event mình publish khớp. Cực kỳ quan trọng cho hệ event-driven.

Test Saga & Idempotency

Đây là phần dễ vỡ nhất nhưng ít người test: compensating action, retry trùng message, thứ tự event đảo lộn.

Test compensation path

[Fact]
public async Task Payment_fails_releases_stock()
{
    // arrange: Payment trả Failed
    _paymentStub.SetupFail();

    await _harness.Bus.Publish(new OrderPlaced(id, total));

    // assert: stock đã được release (compensate)
    (await _harness.Published
        .Any<StockReleased>()).Should().BeTrue();
    (await _harness.Published
        .Any<OrderCancelled>()).Should().BeTrue();
}

MassTransit InMemoryTestHarness cho phép test Saga state machine không cần broker thật.

Test idempotency — gửi 2 lần

[Fact]
public async Task Duplicate_message_processed_once()
{
    var evt = new OrderPlaced(orderId, total);

    await _handler.HandleAsync(evt);
    await _handler.HandleAsync(evt);  // gửi lại cùng MessageId

    // chỉ tạo 1 invoice dù nhận 2 lần
    (await db.Invoices.CountAsync(
        i => i.OrderId == orderId)).Should().Be(1);
}

Bắt buộc test: broker at-least-once → message lặp là chuyện bình thường, không phải ngoại lệ.

Test luồng bất đồng bộ (async / event flow)

Khó: bạn publish event rồi assert ngay → fail vì handler chưa chạy xong. Đừng dùng Thread.Sleep cứng — dùng polling / await condition.

// ❌ Sai: flaky, chậm
await bus.Publish(evt);
Thread.Sleep(2000);
Assert.True(handled);

// ✅ Đúng: chờ điều kiện với timeout (vd thư viện Polly / AwaitHelpers)
await bus.Publish(evt);
await Wait.UntilAsync(
    condition: async () => await db.Invoices.AnyAsync(i => i.OrderId == id),
    timeout: TimeSpan.FromSeconds(5),
    pollInterval: TimeSpan.FromMilliseconds(100));
⚠️ Test thứ tự & out-of-order: Event có thể đến không đúng thứ tự. Viết test cố tình đảo thứ tự (vd PaymentSucceeded đến trước OrderPlaced) để chắc handler xử lý đúng (buffer/idempotent), không crash.

Chiến lược CI cho microservices

  1. Pipeline mỗi service riêng: chỉ chạy khi code service đó đổi (path filter). Mỗi service deploy độc lập.
  2. Stage nhanh trước: unit + component (in-memory) chạy trên mọi commit, <1 phút. Fail nhanh, feedback nhanh.
  3. Integration với Testcontainers: chạy trên PR. Cần Docker runner. Song song hoá theo service.
  4. Contract verification: consumer publish pact; provider verify; can-i-deploy gate trước khi release.
  5. E2E tối thiểu: chỉ vài happy-path critical (checkout, payment) chạy trên staging sau deploy, không chạy mọi PR.
  6. Quan sát production thay vì test thêm: dùng synthetic monitoring + canary + feature flag. Ở scale lớn, observability bù cho việc không thể E2E mọi thứ.
💡 Quy tắc: Càng lên cao pyramid càng ít test. Nếu thấy mình viết nhiều E2E để bắt bug logic → bug đó đáng lẽ phải bắt ở unit/contract. E2E flaky là thuế, không phải tài sản.

Checklist — Testing hệ phân tán

✅ Coverage đúng tầng

  • Domain logic phủ bằng unit test, không I/O
  • Integration test dùng Testcontainers (DB/broker thật), không SQLite giả
  • Mỗi cặp tương tác service có contract test (Pact)
  • Message/event có schema contract, không chỉ REST
  • E2E giới hạn ở vài luồng business critical

✅ Distributed-specific

  • Test cả compensation path của Saga, không chỉ happy path
  • Test idempotency: gửi message trùng → side-effect 1 lần
  • Test out-of-order event
  • Không Sleep cứng — dùng await-condition với timeout
  • can-i-deploy gate trong CI trước release
