40+ Câu hỏi phỏng vấn Microservices

Câu hỏi thật từ phỏng vấn Mid/Senior tại các công ty Việt Nam & nước ngoài. Câu trả lời ngắn, tới luôn — không lý thuyết suông.

🎯 Khái niệm cốt lõi (8 câu)

Microservices và SOA khác nhau ở đâu?

SOA: nhiều service, dùng ESB (Enterprise Service Bus) tập trung làm điều phối, share data + protocol nặng (SOAP). Microservices: dumb pipes (HTTP/MQ), smart endpoints — service tự lo logic, không phụ thuộc broker thông minh; mỗi service có DB riêng.

Khi nào KHÔNG nên dùng microservices?

Team < 10, MVP, chưa biết K8s/CI-CD, nghiệp vụ đơn giản, latency-sensitive, distributed transaction phức tạp khó tránh. Bắt đầu Modular Monolith — tách dần khi đau thật sự.

Bounded Context là gì? Cách tách service đúng?

Bounded Context (DDD) là ranh giới ngữ nghĩa của domain. Tách theo business capability (Order, Payment, Inventory…) không tách theo layer kỹ thuật (UI/Service/DB). Nguyên tắc 2-pizza team: 1 service đủ nhỏ để 6-8 người sở hữu trọn.

Database per service — tại sao bắt buộc?

Nếu 2 service cùng DB → mọi schema change phải đồng bộ deploy, vẫn là Monolith trá hình. DB riêng đảm bảo loose coupling, deploy độc lập, mỗi team chọn DB phù hợp (Postgres, Mongo, Redis...).

Eventual consistency là gì? Khi nào chấp nhận được?

Sau 1 transaction qua nhiều service, dữ liệu chỉ cuối cùng nhất quán (vài ms - vài giây). Chấp nhận được với 90% nghiệp vụ: gửi email, cập nhật inventory, recommendation. KHÔNG dùng cho: tài khoản ngân hàng số dư, đặt vé số lượng cứng.

CAP theorem áp dụng vào microservices ra sao?

Trong distributed system, khi network partition xảy ra phải chọn Consistency hoặc Availability. Microservices thường chọn AP + eventual consistency. CP chỉ dùng cho ledger, lock, leader election.

Modular Monolith vs Microservices?

Modular Monolith: 1 process, nhiều module ranh giới rõ, không share data layer. Cùng lợi ích về cấu trúc nhưng không có overhead network/deploy/observability. 80% startup nên start ở đây, tách khi có lý do thật.

"12-Factor App" có 12 yếu tố gì?

Codebase, Dependencies, Config (env), Backing services, Build/Release/Run, Processes (stateless), Port binding, Concurrency, Disposability, Dev/prod parity, Logs (stream), Admin processes. Tham khảo: 12factor.net.

🔁 Communication & Patterns (10 câu)

REST vs gRPC vs GraphQL — chọn cái nào khi nào?

REST: public API, web/mobile, tooling tốt. gRPC: service-to-service nội bộ, hiệu năng cao, đa ngôn ngữ. GraphQL: BFF cho UI nhiều màn nhiều shape data khác nhau, giảm over/under-fetching.

Synchronous hay asynchronous nên dùng khi nào?

Sync: UI cần kết quả ngay (validate, query). Async: workflow, notification, integration nhiều service. Mặc định async — coupling thấp hơn, fault isolation tốt hơn.

Saga Choreography vs Orchestration?

Choreography: service tự nghe event, không có "đầu não". Hợp với flow ngắn (≤ 3 bước). Orchestration: 1 service chỉ huy gọi từng bước. Hợp với flow phức tạp, business logic rõ. Tools: Temporal, MassTransit, Camunda.

Distributed transaction xử lý thế nào?

Không 2PC — chậm và mong manh. Dùng Saga + compensating transaction: chuỗi local transaction, mỗi bước có "undo" tương ứng. Kết hợp Outbox để publish event atomic với DB write.

Outbox pattern giải quyết vấn đề gì?

Vấn đề dual-write: SaveDB + PublishEvent không atomic. Outbox: ghi event vào bảng outbox cùng transaction với business data → background worker đọc outbox → publish broker → mark sent. Đảm bảo at-least-once delivery.

Idempotency là gì? Cách triển khai?

Cùng request gửi N lần chỉ tạo ra hiệu ứng 1 lần. Triển khai: Idempotency-Key header + bảng inbox lưu key đã xử lý. Bắt buộc cho POST tài chính, message consumer.

Circuit Breaker hoạt động ra sao?

3 trạng thái: Closed (thường) → khi lỗi vượt ngưỡng (vd 5 lỗi/30s) → Open (fail fast, không gọi) → sau timeout → Half-Open (cho 1 request thử) → OK thì Closed, fail thì Open. Polly (.NET), resilience4j (Java).

CQRS lúc nào nên áp dụng?

Khi read và write có nhu cầu khác nhau lớn: ghi cần validate, đọc cần join 5 bảng / chịu traffic lớn. Tách: write model (normalized) + read model (denormalized, sync qua event). Đừng dùng nếu CRUD đơn giản — over-engineer.

Event Sourcing đáng dùng khi nào?

Domain cần audit log (banking, ledger), undo/time-travel, phân tích hành vi. Tránh khi: schema thay đổi liên tục (event versioning đau), team chưa quen DDD. Tools: EventStoreDB, Marten, Axon.

API Gateway có những trách nhiệm gì?

Auth, rate-limit, request routing, response aggregation, protocol translation, caching, logging, tracing, circuit breaker chung. Tools: Ocelot, YARP, Kong, AWS API Gateway. Tránh nhồi business logic vào gateway.

📨 Message Broker (6 câu)

RabbitMQ vs Kafka — khi nào chọn cái nào?

RabbitMQ: smart broker, routing mạnh, queue ngắn hạn, throughput vừa, dễ học → task/command. Kafka: dumb broker + smart consumer, throughput cao, retention dài, replay được → event sourcing, log streaming, analytics.

At-least-once / At-most-once / Exactly-once?

At-least-once: tối thiểu 1 lần (có thể trùng) — phổ biến nhất. At-most-once: tối đa 1 lần (có thể mất). Exactly-once: chính xác 1 lần — hầu như không tồn tại thực sự, đạt được qua at-least-once + idempotent consumer.

Kafka partition key chọn như thế nào?

Cùng key → cùng partition → giữ thứ tự. Chọn key có cardinality cao và phân bố đều: userId, orderId. Tránh key skew (vd: country=VN chiếm 90% → 1 partition nóng).

Consumer group trong Kafka làm gì?

N consumer cùng group → mỗi partition gán cho 1 consumer (load balance). 2 group khác nhau → cùng đọc full topic (broadcast). Mỗi group có offset riêng — replay được độc lập.

Dead Letter Queue (DLQ) dùng làm gì?

Message xử lý fail N lần → đẩy vào DLQ riêng để không block queue chính. Có thể xem, debug, replay sau khi fix bug. Bắt buộc cho mọi consumer production.

Schema evolution khi đổi event schema?

Backward compatible: thêm field optional, không xoá/đổi tên. Forward compatible: consumer mới đọc được event cũ. Dùng Schema Registry (Confluent, Apicurio) để enforce. Versioning trong type: OrderCreated.v1, v2.

🚀 Deploy & DevOps (8 câu)

K8s Deployment khác Pod ra sao?

Pod: đơn vị chạy 1 hoặc nhiều container, ephemeral. Deployment: quản lý nhiều replica của Pod, hỗ trợ rolling update, rollback. Người ta deploy Deployment, K8s tạo Pod thay bạn.

Liveness vs Readiness probe khác nhau?

Liveness: app còn sống không — fail thì K8s kill & restart. Readiness: sẵn sàng nhận traffic — fail thì K8s không route traffic vào (nhưng không restart). Service mới khởi động cần Readiness chờ DB connect.

HPA scale theo cái gì?

CPU/RAM mặc định. Custom metric: queue length, RPS, latency P95 — qua Prometheus Adapter. Cấu hình minReplicas ≥ 2 để không cold start.

Blue-Green vs Canary deployment?

Blue-Green: 2 môi trường song song, switch traffic 100% qua Green khi sẵn sàng. Canary: 5% → 25% → 50% → 100% từ từ, rollback nếu metric xấu. Canary an toàn hơn nhưng phức tạp hơn — dùng Argo Rollouts/Flagger.

GitOps là gì? Khác CI/CD truyền thống?

Git là single source of truth cho infra/config. CI build artifact + push tag mới vào manifest repo → ArgoCD/Flux phát hiện diff → tự sync vào cluster. Mọi thay đổi auditable, rollback = git revert.

Service mesh có cần thiết?

Khi > 20 service. Lo cross-cutting concerns ở layer mạng: mTLS, retry, timeout, tracing, traffic split — không phải code lại trong từng service. Tools: Istio, Linkerd. Trade-off: thêm complexity + latency.

Helm vs Kustomize?

Helm: package manager, dùng template engine, values.yaml cho từng env. Kustomize: overlay, không template — patch declarative. Kustomize built-in trong kubectl. Helm mạnh khi share chart công khai.

Mỗi service deploy độc lập — version compatibility xử lý sao?

Backward compatible API: version v1, v2 cùng tồn tại 1 thời gian. Consumer-driven contract test (Pact). Schema evolution rule. Feature flag để release dần. Không bao giờ "big bang" deploy nhiều service cùng lúc.

🔭 Observability & Debug (5 câu)

3 trụ cột observability?

Logging (chuyện gì xảy ra), Metrics (hệ thống bình thường không), Tracing (request đi qua đâu, chậm ở đâu). OpenTelemetry là chuẩn 2026 cho cả 3.

Distributed tracing cần thiết cỡ nào?

Khi > 3 service. Mỗi request có trace-id propagate qua mọi service, mỗi đoạn xử lý là 1 span. Khi user complain "chậm", mở Jaeger thấy ngay span nào nuốt thời gian.

Log của microservice nên cấu trúc ra sao?

JSON structured: timestamp, level, service, traceId, spanId, userId, message, exception. Không log password/token. Tập trung qua Loki/ELK. Serilog (.NET), zap (Go), pino (Node).

RED metrics là gì?

Rate (req/s), Errors (% lỗi), Duration (latency P50/P95/P99). Bộ 3 cho mọi service. Cùng cặp với USE (Utilization, Saturation, Errors) cho hạ tầng.

Khi 1 service chậm — debug thế nào?

(1) Mở dashboard service đó: CPU/RAM/GC bình thường? (2) Tracing: span nào chậm? (3) Log: có exception/retry? (4) DB query: thiếu index? (5) Downstream call: gateway/service khác chậm? Quy trình: top-down từ user request.

🛠️ System Design Scenario (5 câu)

Thiết kế hệ thống đặt vé concert (1M user xem cùng lúc)?

CDN cache trang, Redis cache stock, queue (Kafka) cho mọi request đặt vé, Inventory service xử lý theo thứ tự queue (FIFO per show), distributed lock Redis cho seat reservation, idempotency-key cho retry, payment async với Saga, notification qua event. Quan trọng: limit concurrent user vào checkout (virtual queue).

Migration Monolith → Microservices — bắt đầu module nào?

Module có (1) ranh giới rõ ràng nhất, (2) ít coupling với phần còn lại, (3) traffic riêng/nhu cầu scale khác nhau. Vd: Notification, Search, Recommendation. Dùng Strangler Fig: proxy route module mới sang service mới, các phần khác vẫn ở monolith.

Hệ thống thanh toán — đảm bảo không double charge ra sao?

Idempotency-key bắt buộc trong header. Server lưu key + result trong Redis 24h. Request trùng key → trả về kết quả cũ. Bên payment gateway cũng có idempotency. Saga + Outbox cho consistency. Không bao giờ retry blind từ client.

Service A cần data từ Service B — gọi sync hay copy data?

Tuỳ tần suất & data size. Gọi sync: data realtime, ít. Copy qua event: data không cần realtime, A nghe event B publish và lưu read model riêng (CQRS). Tránh "shared database" hoặc "service A query DB của B".

1 service chết kéo theo cả hệ thống — phòng tránh?

Circuit Breaker (Polly), Bulkhead (cô lập thread/connection pool), Timeout (mọi call ngoài), Retry với backoff + jitter, Fallback (degraded mode), Async (Kafka đệm), Health check + auto-restart. Quan trọng: thiết kế cho fault — service ngoài SẼ chết.

💡 Câu hỏi "trick" hay gặp

"Nếu được làm lại từ đầu, bạn vẫn chọn microservices không?"

Trả lời thật lòng — đây là câu test maturity. "Tuỳ team size + nghiệp vụ. Nếu < 10 người, MVP — tôi sẽ chọn Modular Monolith. Microservices không phải silver bullet, nó là trade-off: tăng complexity DevOps để đổi lấy team autonomy & scale độc lập."

"Bạn từng debug 1 incident microservice phức tạp nhất là gì?"

Kể 1 case THẬT: triệu chứng → cách bạn nhìn dashboard / tracing → giả thuyết → cách verify → root cause → fix tạm thời → fix lâu dài + postmortem. Kể quá trình tư duy, không chỉ kết quả.

"Service A có nên gọi DB của Service B không?"

KHÔNG. Đây là phản pattern. Hậu quả: schema lock, deploy phụ thuộc, không thể thay DB type. Đúng: gọi qua API/gRPC, hoặc subscribe event để build read model riêng.
