Architect-level Microservices

Tầng dành cho người thiết kế nền tảng cho hàng trăm service, hàng triệu user, nhiều region. Multi-region, multi-tenancy, service mesh, backpressure, platform engineering, capacity planning — và quan trọng nhất: khi nào microservices là sai lầm.

Multi-region & Geo-distribution

Phục vụ user toàn cầu với độ trễ thấp và sống sót khi cả một region sập. Đây là bài toán đánh đổi giữa latency, consistency và cost.

Mô hìnhMô tảĐánh đổi
Active-Passive1 region chính, region khác standby; failover khi sự cốĐơn giản, RTO/RPO cao hơn; lãng phí capacity dự phòng
Active-ActiveMọi region nhận traffic; route theo địa lý (GeoDNS/Anycast)Latency thấp, kháng lỗi; phải giải xung đột ghi dữ liệu
Cell-basedHệ chia thành "cell" độc lập, mỗi cell phục vụ tập userBlast radius nhỏ, scale tuyến tính; phức tạp routing & vận hành

Dữ liệu xuyên region

  • Data residency: GDPR/luật VN buộc data user ở lại region của họ
  • Conflict resolution: CRDT, last-write-wins, hoặc partition theo region để tránh ghi đồng thời
  • DB toàn cầu: CockroachDB, Spanner, DynamoDB Global Tables, Cosmos DB multi-region

Đo độ sẵn sàng

  • RTO (Recovery Time Objective): bao lâu để khôi phục
  • RPO (Recovery Point Objective): chấp nhận mất bao nhiêu dữ liệu
  • Diễn tập region failover định kỳ (game day), không chỉ trên giấy

Chiến lược Multi-tenancy

SaaS phục vụ nhiều khách hàng (tenant) trên cùng hạ tầng. Chọn mức cô lập là quyết định kiến trúc nền tảng, ảnh hưởng cost, bảo mật và blast radius.

Mô hìnhCô lậpChi phí / Phù hợp
Shared DB, shared schema (TenantId cột)Thấp — chỉ bằng query filterRẻ nhất, dày đặc; rủi ro rò rỉ chéo tenant nếu quên filter
Shared DB, schema/tenantTrung bìnhCân bằng; giới hạn số tenant theo khả năng DB
DB/tenantCaoCô lập tốt, backup/restore riêng; vận hành nhiều DB
Stack/tenant (silo)Cao nhấtCho khách enterprise, compliance; đắt, ít dày đặc
 
// EF Core global query filter — cô lập tenant mức shared schema
protected override void OnModelCreating(ModelBuilder mb)
{
    mb.Entity<Order>()
      .HasQueryFilter(o => o.TenantId == _tenantContext.CurrentTenantId);
    // MỌI query tự thêm WHERE TenantId = @current — chống rò rỉ chéo
}
⚠️ Noisy neighbor: Ở shared model, 1 tenant "ồn ào" có thể ngốn hết tài nguyên của tenant khác. Cần rate-limit & quota theo tenant (xem backpressure bên dưới).

Service Mesh — Istio / Linkerd (hands-on)

Service mesh đẩy các cross-cutting concern (mTLS, retry, traffic shaping, telemetry) xuống tầng hạ tầng qua sidecar proxy — code service không cần biết. 2026: Istio có ambient mode (không sidecar) ngày càng phổ biến.

🔐 mTLS tự động

Mọi traffic service-to-service được mã hoá & xác thực hai chiều, zero-trust, không sửa code.

🚦 Traffic management

Canary, blue-green, traffic splitting theo %, fault injection — khai báo bằng YAML.

📊 Telemetry đồng nhất

Golden metrics (latency, traffic, error, saturation) cho mọi service mà không cần instrument tay.

# Istio: canary 90/10 + retry + timeout — khai báo, không code
apiVersion: networking.istio.io/v1
kind: VirtualService
metadata: { name: orders }
spec:
  hosts: [ orders ]
  http:
  - route:
    - destination: { host: orders, subset: v1 }
      weight: 90
    - destination: { host: orders, subset: v2 }   # canary 10%
      weight: 10
    retries: { attempts: 3, perTryTimeout: 2s, retryOn: 5xx,reset }
    timeout: 10s
📦 Istio vs Linkerd: Linkerd nhẹ, đơn giản, Rust-based proxy, dễ vận hành — hợp đa số. Istio mạnh & nhiều tính năng (multi-cluster, ambient mesh) nhưng phức tạp hơn. Đừng dùng mesh khi <15-20 service — overhead vận hành không xứng.

Backpressure & Load Shedding

Khi tải vượt sức, hệ thống phải chủ động từ chối một phần để phần còn lại sống — thay vì cố nhận hết rồi sập toàn bộ (cascading failure).

Backpressure (đẩy ngược áp lực)

Consumer chậm → báo ngược cho producer chậm lại. Trong .NET dùng System.Threading.Channels bounded, Kafka consumer lag, hoặc gRPC flow control.

// Bounded channel — producer bị chặn khi đầy
var ch = Channel.CreateBounded<Job>(
    new BoundedChannelOptions(1000)
    {
        FullMode = BoundedChannelFullMode.Wait
    });
// queue không phình vô hạn → không OOM

Load shedding (vứt bớt tải)

Khi quá tải, từ chối nhanh request ít quan trọng (HTTP 429/503) để bảo vệ request critical. Ưu tiên theo tier.

// .NET 9 Rate Limiting middleware
builder.Services.AddRateLimiter(o =>
{
    o.AddConcurrencyLimiter("checkout", l =>
    {
        l.PermitLimit = 500;
        l.QueueLimit = 0;  // đầy → 503 ngay, fail fast
    });
    o.RejectionStatusCode = 503;
});
💡 Nguyên tắc: "Fail fast" tốt hơn "fail slow". Một 503 trả trong 5ms tốt hơn vô hạn request treo 30s rồi timeout đồng loạt. Kết hợp với adaptive concurrency (vd thuật toán giống Netflix concurrency-limits) để tự điều chỉnh ngưỡng theo latency thực.

Platform Engineering & Internal Developer Platform (IDP)

Ở quy mô hàng trăm service, bạn không thể bắt mỗi team tự lo K8s, CI/CD, observability. Platform team xây "golden path" để dev tự phục vụ (self-service) — đây là xu hướng chủ đạo 2024-2026.

🛤️ Golden Path

Template + scaffolding cho service mới: repo, pipeline, dashboard, alert đã sẵn. create service → chạy được trong vài phút.

🧰 Self-service IDP

Dev khai báo "tôi cần 1 service + Postgres + topic" → platform tự provision. Tools: Backstage, Port, Humanitec.

📜 Platform as Product

Coi developer là khách hàng. Đo bằng DORA metrics, thời gian onboard, developer satisfaction.

📦 IaC + GitOps: Hạ tầng khai báo bằng Terraform/Pulumi; deploy qua GitOps (ArgoCD/Flux) — git là nguồn sự thật duy nhất. Platform team sở hữu các module này, team sản phẩm chỉ "đặt hàng" qua PR.

Cost & Capacity Planning

Microservices ở cloud dễ "đốt tiền" âm thầm: mỗi service idle vẫn ăn CPU/RAM, traffic chéo region tốn phí egress, over-provision vì sợ.

Tối ưu chi phí

  • Right-sizing: đặt request/limit K8s sát thực tế dựa trên metric, không đoán
  • Autoscaling: HPA theo CPU/RPS, KEDA theo queue length; scale-to-zero cho service ít dùng
  • Spot/preemptible cho workload chịu được gián đoạn
  • Egress cost: giữ traffic trong cùng AZ/region; data transfer chéo region rất đắt
  • FinOps: gán cost theo team/service (tagging), hiển thị showback/chargeback

Capacity planning

  • Load test để biết 1 pod chịu được bao nhiêu RPS (k6, NBomber)
  • Tính headroom cho spike (vd Black Friday = 10x): xác định trước scaling limit
  • Quota & limit để 1 service không ngốn cả cluster
  • Theo dõi saturation (USE method) — phát hiện cạn tài nguyên trước khi sập

Khi nào microservices THẤT BẠI

Phần quan trọng nhất của một architect: biết khi nào không dùng. Phần lớn "thảm hoạ microservices" đến từ áp dụng sai bối cảnh.

🚩 Dấu hiệu tách sai

  • Distributed monolith: service phải deploy cùng nhau, đổi 1 phải đổi tất cả — tệ hơn monolith
  • Chatty services: 1 request user → hàng chục network hop nội bộ → latency & lỗi lan
  • Tách trước khi hiểu domain → ranh giới sai, refactor cực đắt
  • Team nhỏ hơn số service → mỗi người ôm nhiều repo, kiệt sức on-call
  • Shared database giữa các service → coupling ngầm, mất hết lợi ích

✅ Khi nên giữ monolith

  • Startup giai đoạn đầu, domain còn biến động mạnh
  • Team nhỏ (< 15-20 dev), 1-2 team
  • Tải không lớn, không có nhu cầu scale từng phần độc lập
  • Chưa có nền tảng CI/CD, observability, on-call trưởng thành
  • → Dùng Modular Monolith, tách dần khi có lý do rõ ràng
🔥 Sự thật của architect: Microservices là giải pháp cho bài toán quy mô tổ chức & scale độc lập, đánh đổi bằng độ phức tạp vận hành khổng lồ. Nếu bạn không có bài toán đó, bạn chỉ đang mua phức tạp mà không nhận lại lợi ích. "Big enough to need it, mature enough to run it."

Checklist — Tư duy Architect-level

✅ Thiết kế nền tảng

  • Chọn mô hình multi-region khớp RTO/RPO & ngân sách
  • Chiến lược multi-tenancy rõ ràng + chống rò rỉ chéo tenant
  • Service mesh chỉ khi đủ số service để xứng overhead
  • Backpressure + load shedding có chủ đích, fail fast
  • IDP/golden path cho dev self-service, đo bằng DORA

✅ Kỷ luật & chi phí

  • FinOps: cost gán theo service/team, tối ưu egress & right-size
  • Capacity plan có load test & headroom cho spike
  • Game day diễn tập failover định kỳ
  • Luôn hỏi "bài toán này có cần micro không?" trước khi tách
  • Sẵn sàng gộp service lại nếu tách sai (không cố chấp)
