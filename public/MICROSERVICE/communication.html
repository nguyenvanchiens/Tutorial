Giao tiếp giữa các service

REST vs gRPC vs Message Broker vs Event Streaming — chọn đúng kiểu giao tiếp quyết định 70% sự ổn định của hệ thống.

Sync vs Async — Khác biệt cốt lõi

Tiêu chíSynchronous (REST/gRPC)Asynchronous (Broker)
Caller chờ response?Có — block đến khi có kết quảKhông — fire & forget
CouplingTight (caller biết callee tồn tại)Loose (qua broker)
Callee chếtCaller fail / treoMessage ở queue, xử lý sau
LatencyThấp (1 round trip)Cao hơn (qua broker)
Use caseQuery, validate, immediate responseNotification, integration, long task
PatternRequest/ResponsePub/Sub, Queue, Event Streaming
💡 Quy tắc vàng: Mặc định async. Chỉ dùng sync khi UI cần kết quả ngay lập tức (ví dụ: GET data, validate form).

REST — Khi nào dùng

✅ Dùng REST khi

  • Public API cho web/mobile/3rd party
  • Nghiệp vụ đơn giản: CRUD
  • Cần caching HTTP (CDN, ETag)
  • Tooling sẵn (Swagger, Postman)

❌ Tránh REST khi

  • Service-to-service nội bộ tần suất cao → gRPC
  • Streaming (chat, realtime) → WebSocket / gRPC
  • Event-driven → Kafka / RabbitMQ

Best practices REST 2026

// 1. Resource-based URL, không verb
POST /orders                // ✅
POST /createOrder           // ❌

// 2. Status code chuẩn
200 OK              // success
201 Created         // POST tạo mới
204 No Content      // DELETE thành công
400 Bad Request     // validation lỗi
401 Unauthorized    // chưa đăng nhập
403 Forbidden       // đăng nhập rồi nhưng không có quyền
404 Not Found       // resource không tồn tại
409 Conflict        // trùng, version mismatch
429 Too Many        // rate limit
500 Server Error    // bug server
503 Service Unavail.// downstream chết

// 3. Versioning
/v1/orders   /v2/orders   // hoặc header Accept-Version

// 4. Pagination chuẩn
GET /orders?page=1&size=20
GET /orders?cursor=eyJpZCI6MTIzfQ  // cursor-based, ổn định hơn

// 5. Idempotency-Key cho POST tài chính
POST /payments
Idempotency-Key: "abc-123"     // retry không tạo 2 thanh toán

gRPC — Service-to-service nhanh

HTTP/2 + Protobuf binary. Nhanh hơn REST 5-10×, schema mạnh, code-gen đa ngôn ngữ.

✅ Lợi thế

  • Binary & nén → bandwidth thấp
  • Strong typing qua .proto
  • Streaming 4 chiều: unary, server stream, client stream, bidi
  • Code gen tự động cho 10+ ngôn ngữ
  • Built-in deadline, cancel, multiplexing

❌ Hạn chế

  • Browser không gọi trực tiếp (cần grpc-web/proxy)
  • Debug khó hơn REST (binary)
  • Tooling kém JSON
  • Versioning đòi quy ước nghiêm

Định nghĩa contract

// payment.proto
syntax = "proto3";

service PaymentService {
  rpc Charge(ChargeRequest) returns (ChargeResponse);
  rpc StreamStatus(StatusRequest) returns (stream StatusEvent);
}

message ChargeRequest {
  string order_id   = 1;
  int64  amount     = 2;
  string currency   = 3;
  string idempotency_key = 4;
}

→ Chạy protoc sinh stub cho C#, Go, Node, Python... Mọi service nói cùng "ngôn ngữ".

📦 Khi nào dùng gRPC: service-to-service nội bộ, cần performance, đa ngôn ngữ, streaming.

Message Broker — Async Communication

2 mô hình chính:

📬 Queue (Point-to-Point)

1 message → 1 consumer xử lý. Phù hợp command/task: SendEmail, ProcessPayment.

Tools: RabbitMQ, AWS SQS, Azure Service Bus.

📢 Pub/Sub (Topic / Event)

1 event → N subscriber xử lý. Phù hợp event: OrderCreated → Inventory + Payment + Email cùng nhận.

Tools: Kafka, RabbitMQ topic exchange, NATS, Google Pub/Sub.

RabbitMQ vs Kafka — Khi nào dùng cái nào

Tiêu chíRabbitMQKafka
Mô hìnhSmart broker, dumb consumerDumb broker, smart consumer
RoutingMạnh (exchange, routing key)Đơn giản (topic + partition)
Throughput~50k msg/s~1M+ msg/s
Lưu trữNgắn hạn (xử xong → xoá)Dài hạn (giữ N ngày, replay được)
OrderPer queuePer partition
Use caseTask queue, RPC, commandEvent sourcing, log, streaming, analytics
Học ban đầuDễ — quen tay nhanhKhó hơn — partition, offset, consumer group
📌 Quy tắc: Task ngắn, ít data, cần routing → RabbitMQ. Event-driven, data lớn, cần replay → Kafka.

RabbitMQ — Ví dụ thực tế (.NET / MassTransit)

Producer

// Order Service publish event
await bus.Publish(new OrderCreated(
    OrderId: order.Id,
    UserId: order.UserId,
    Total:  order.Total
));

Consumer

// Inventory Service consume
public class OrderCreatedConsumer : IConsumer<OrderCreated> {
    public async Task Consume(ConsumeContext<OrderCreated> ctx) {
        var evt = ctx.Message;
        await _inventory.ReserveAsync(evt.OrderId);
        await ctx.Publish(new StockReserved(evt.OrderId));
    }
}

Cấu hình

builder.Services.AddMassTransit(x => {
    x.AddConsumer<OrderCreatedConsumer>();
    x.UsingRabbitMq((ctx, cfg) => {
        cfg.Host("rabbitmq");
        cfg.ReceiveEndpoint("inventory-queue", e => {
            e.ConfigureConsumer<OrderCreatedConsumer>(ctx);
            e.UseMessageRetry(r => r.Exponential(5, TimeSpan.FromSeconds(2),
                TimeSpan.FromSeconds(30), TimeSpan.FromSeconds(5)));
            e.UseInMemoryOutbox();   // idempotency
        });
    });
});

Kafka — Concept cốt lõi

📋 Topic

Tên kênh logic. Vd: orders, payments.

🔪 Partition

Topic được chia thành N partition để scale. Mỗi partition có order riêng.

👥 Consumer Group

N consumer cùng group → mỗi partition được 1 consumer xử lý → load balance tự động.

📍 Offset

Vị trí đã đọc trong partition. Consumer commit offset → resume được khi restart.

🔁 Replication

Mỗi partition có N replica trên N broker. Leader xử lý, followers đồng bộ.

♻️ Retention

Giữ message N ngày / GB. Replay từ offset = time travel cho data.

Producer .NET

using var producer = new ProducerBuilder<string, string>(config).Build();
await producer.ProduceAsync("orders", new Message<string, string> {
    Key   = order.UserId,   // cùng key → cùng partition → giữ thứ tự
    Value = JsonSerializer.Serialize(order)
});
⚠️ Partition key quyết định message đi vào partition nào. Chọn sai → 1 partition nóng, các partition khác idle. Nguyên tắc: key có cardinality cao và cân bằng (vd: userId).

Event-Driven Architecture (EDA)

Service không "gọi" nhau — mà phát event. Service khác lắng nghe event mình quan tâm.

🎯 3 loại event

  • Domain event — đã xảy ra trong domain: OrderPlaced
  • Integration event — phát ra ngoài bounded context
  • Notification event — chỉ thông báo, ít data

📐 Event schema chuẩn

{
  "id":        "uuid",
  "type":      "OrderPlaced",
  "version":   "v1",
  "timestamp": "2026-04-27T10:00:00Z",
  "source":    "order-service",
  "data": { ... }
}
📦 Chuẩn: CloudEvents (CNCF) — schema chuẩn cho event qua hệ thống.

Schema Registry & Versioning

Khi đổi schema event, làm sao consumer cũ không vỡ?

  • Backward compatible: thêm field optional, không xoá field cũ
  • Forward compatible: consumer mới đọc được event cũ
  • Dùng Schema Registry (Confluent, Apicurio) — broker từ chối publish nếu schema không tương thích
  • Version trong type name: OrderCreated.v1, OrderCreated.v2
