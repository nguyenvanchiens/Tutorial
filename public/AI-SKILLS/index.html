Bước 1: Tạo CLAUDE.md - "Bộ não" của project

Trước khi code bất kỳ thứ gì, hãy tạo file CLAUDE.md ở gốc project. Đây là file quan trọng nhất - mỗi khi Claude Code bắt đầu, nó đọc file này đầu tiên.

Tại sao cần CLAUDE.md?

Không có CLAUDE.md = Claude phải "đoán" về project mỗi lần. Có CLAUDE.md = Claude hiểu ngay lập tức, làm đúng từ lần đầu. Giống như bạn viết tài liệu onboarding cho nhân viên mới: càng rõ, nhân viên càng làm tốt.

CLAUDE.md# Dự Án: TaskFlow - Quản Lý Công Việc

## Tổng quan
Ứng dụng web quản lý công việc cho team nhỏ.

## Tech Stack
- Frontend: React 18 + TypeScript + Tailwind CSS
- Backend: Node.js + Express + Prisma ORM

Bước 3: Verification Loop - Vòng lặp kiểm tra

Đây là khái niệm cực kỳ quan trọng. Verification Loop là quy trình Claude Code tự động kiểm tra và sửa lỗi cho đến khi mọi thứ hoạt động hoàn hảo.

┌─────────────┐ ┌──────────────┐ ┌──────────────┐ │ Claude │────▶│ Chạy code │────▶│ Có lỗi? │ │ viết code │ │ / tests │ │ │ └─────────────┘ └──────────────┘ └──────┬───────┘ ▲ │ │ ┌──────────────┐ Có │ Không │ │ │◀──────┘ │ └──────────────│ Phân tích │ ▼ │ & sửa lỗi │ ┌──────────┐ └──────────────┘ │ DONE! │ └──────────┘

Ví dụ Verification Loop trong thực tế:

Những gì Claude tự động làm1. Viết component TodoList.tsx
2. Chạy: npm run build
3. Lỗi: "Property 'completed' does not exist on type..."
4. Phân tích: Thiếu type definition
5. Sửa: Thêm interface Todo { id: number; title: string; completed: boolean; }
6. Chạy lại: npm run build
7. Lỗi: "Cannot find module './TodoItem'"
8. Sửa: Tạo file TodoItem.tsx
9. Chạy lại: npm run build ✓ Success!
10. Chạy: npm test ✓ All tests passed!
Bạn không cần can thiệp!

Toàn bộ vòng lặp này Claude tự làm. Bạn chỉ cần ngồi xem. Nếu sau 3-4 lần thử mà vẫn lỗi, Claude sẽ hỏi bạn. Nhưng 90% trường hợp, nó tự giải quyết được.

Bài 5

.claude Directory - Kho Vũ Khí Bí Mật

Rules, Memory, Agents, Skills - mà 98% người dùng bỏ qua.

Thư mục .claude là gì?

Ngoài file CLAUDE.md, còn có một thư mục ẩn cực kỳ mạnh mẽ: .claude/. Đây là nơi bạn cấu hình toàn bộ hành vi, khả năng, và "tính cách" của Claude Code cho project.

.claude/ ├── settings.json ← Cấu hình chính: hooks, MCP, permissions ├── commands/ ← Slash commands tự tạo │ ├── deploy.md │ ├── review-pr.md │ └── generate-tests.md └── agents/ ← Agent templates tự tạo ├── code-reviewer.md └── test-writer.md

1. Rules - Quy tắc bất di bất dịch

Rules là những quy tắc mà Claude PHẢI tuân theo, khác với CLAUDE.md (là hướng dẫn chung). Rules được đặt trong settings.json: 

.claude/settings.json{
  "permissions": {
    "allow": [
      "Read",
      "Glob",
      "Grep",
      "Edit",
      "Write"
    ],
    "deny": [
      "Bash(rm -rf *)",
      "Bash(git push --force)"
    ]
  }
}
Quy tắc Allow/Deny

Allow: Các tool Claude được tự động dùng không cần hỏi.
Deny: Các lệnh bị CẤM tuyệt đối. Dù bạn có yêu cầu, Claude cũng không được chạy. Ví dụ: cấm rm -rf, cấm git push --force.

2. Memory - Bộ nhớ dài hạn

Claude Code có hệ thống memory - nhớ thông tin qua các phiên làm việc khác nhau. Khác với context (ngắn hạn, mất khi /clear), memory tồn tại vĩnh viễn.

Các loại memory:

Loại Lưu gì? Ví dụ
User Thông tin về bạn "Tôi là frontend developer, thích Tailwind CSS"
Feedback Những gì bạn sửa Claude "Đừng thêm comments thừa vào code"
Project Tình trạng project "Đang freeze code, chỉ fix bug critical"
Reference Nơi tìm thông tin "Bugs được track trên Linear project INGEST" 
Cách sử dụng Memory# Yêu cầu Claude nhớ:
> Nhớ rằng: tôi thích code ngắn gọn, không thêm comments thừa,
  và luôn dùng arrow functions thay cho function declarations.

# Claude sẽ tạo file memory và nhớ cho các phiên sau.
# Lần sau bạn mở Claude Code, nó đã biết sở thích của bạn.

4. Custom Agents - Tạo agent riêng

.claude/agents/security-reviewer.md---
name: Security Reviewer
description: Kiểm tra bảo mật cho code
---

Bạn là chuyên gia bảo mật. Khi được gọi, hãy:

1. Quét code tìm lỗ hổng OWASP Top 10:
   - SQL Injection
   - XSS (Cross-Site Scripting)
   - CSRF
   - Broken Authentication
   - Sensitive Data Exposure

2. Kiểm tra:
   - Có hardcode secrets không?
   - Input validation đã đủ chưa?
   - API endpoints có rate limiting không?

3. Cho điểm bảo mật: A/B/C/D/F
4. Liệt kê cụ thể từng lỗ hổng và cách sửa
Tại sao 98% bỏ qua?

Hầu hết người dùng chỉ biết gõ chat với Claude Code. Nhưng sức mạnh thực sự nằm ở thư mục .claude/. Khi bạn cấu hình đúng: Rules bảo vệ code, Memory nhớ sở thích, Skills mở rộng khả năng, Agents chuyên biệt hoá - Claude Code trở thành một team AI hoàn chỉnh, không chỉ là 1 chatbot.

Bài 6

Context Management + Plan Mode

Làm chủ "bộ nhớ" của Claude và lên kế hoạch trước khi build.

Phần 1: Context Management

Context Window là gì?

Context window là bộ nhớ ngắn hạn của Claude - chứa TẤT CẢ thông tin trong phiên làm việc hiện tại. Giống như bàn làm việc: càng nhiều giấy tờ, càng khó tìm thứ cần.

┌──────────── Context Window (200K tokens) ──────────────┐ │ │ │ CLAUDE.md + System prompt ~5,000 tokens │ │ Lịch sử hội thoại ~20,000 tokens │ │ File đã đọc ~50,000 tokens │ │ Kết quả lệnh đã chạy ~10,000 tokens │ │ ──────────────────────────────────────── │ │ Còn lại cho phần trả lời ~115,000 tokens │ │ │ └─────────────────────────────────────────────────────────┘ 1 token ≈ 3/4 từ tiếng Anh 1 từ tiếng Việt ≈ 2-4 tokens 1 file 100 dòng ≈ 1,000-2,000 tokens

Khi context đầy, chuyện gì xảy ra?

  • Claude bắt đầu "quên" những gì nói trước đó
  • Phản hồi chậm hơn và có thể kém chính xác
  • Tốn nhiều tiền hơn (nhiều token = nhiều chi phí)

3 công cụ quản lý context

Lệnh Tác dụng Khi nào dùng
/compact Nén lịch sử lại, giữ thông tin quan trọng Mỗi 30-45 phút, hoặc khi Claude bắt đầu quên
/clear Xoá sạch toàn bộ context, bắt đầu mới Khi chuyển sang task hoàn toàn khác
CLAUDE.md Thông tin tồn tại vĩnh viễn qua các phiên Quy tắc, cấu trúc, cách chạy project 
Mẹo dùng /compact thông minh# Khi compact, nói cho Claude biết cần giữ gì:
> /compact Giữ lại: đang làm feature search, đã xong phần UI
  ở file SearchBar.tsx, còn lại phần API integration với endpoint
  GET /api/search?q=keyword

# Claude sẽ tóm tắt mọi thứ nhưng giữ nguyên thông tin bạn chỉ định

Phần 2: Plan Mode - Lên kế hoạch trước khi code

Plan Mode là tính năng cho phép Claude suy nghĩ và lên kế hoạch trước khi bắt tay vào code. Thay vì nhảy vào viết code ngay, Claude sẽ:

  1. Phân tích yêu cầu Hiểu bạn muốn gì, xác định scope, liệt kê assumptions
  2. Khảo sát codebase Đọc code hiện có, hiểu kiến trúc, tìm file liên quan
  3. Đề xuất kế hoạch Trình bày plan chi tiết: thay đổi gì, ở đâu, theo thứ tự nào
  4. Chờ bạn duyệt Bạn xem plan, góp ý, điều chỉnh. Chỉ khi bạn đồng ý, Claude mới bắt đầu code

Cách bật Plan Mode:

Nói với Claude# Cách 1: Yêu cầu lên plan
> Lên kế hoạch chi tiết để thêm hệ thống authentication
  vào app này. CHƯA code gì cả, chỉ plan thôi.

# Cách 2: Dùng shift+tab để vào Plan Mode
# (Trong VS Code, nhấn Shift+Tab trước khi gửi message)

# Cách 3: Nói rõ ràng
> /plan Refactor hệ thống payment từ Stripe sang Paddle

Ví dụ Plan Mode output:

Claude trả lời## Kế hoạch: Thêm Authentication

### Phân tích hiện tại:
- App chưa có auth, tất cả routes đều public
- Đang dùng Express backend, React frontend
- Database: PostgreSQL với Prisma ORM

### Đề xuất approach:
Session-based auth (phù hợp với app nhỏ hơn JWT)

### Các bước thực hiện:

**Bước 1: Database** (ước tính ~50 dòng code)
- Tạo migration: bảng users (email, password_hash, created_at)
- Tạo migration: bảng sessions (token, user_id, expires_at)

**Bước 2: Backend** (ước tính ~150 dòng code)
- POST /auth/register - đăng ký
- POST /auth/login - đăng nhập
- POST /auth/logout - đăng xuất
- Middleware: requireAuth cho protected routes

**Bước 3: Frontend** (ước tính ~200 dòng code)
- Trang Login / Register
- AuthContext cho state management
- ProtectedRoute component
- Cập nhật Navbar hiển thị user info

**Bước 4: Tests** (ước tính ~100 dòng code)
- Unit tests cho auth middleware
- Integration tests cho auth API
- E2E test cho login flow

### Rủi ro & lưu ý:
- Cần hash password với bcrypt (KHÔNG lưu plaintext)
- Session token phải random, đủ dài (256-bit)
- Cần rate limiting cho login endpoint

Bạn đồng ý với plan này không? Tôi sẽ bắt đầu từ Bước 1.
Tại sao Plan Mode quan trọng?

Không có plan → Claude code xong → bạn không hài lòng → phải làm lại → tốn gấp 2-3 lần token và thời gian. Có plan → bạn duyệt trước → điều chỉnh sớm → Claude code 1 lần đúng → tiết kiệm 50-70% thời gian. Với mọi task phức tạp (>30 phút), hãy luôn dùng Plan Mode.

Nhóm 4: Custom Commands - Bạn tự tạo

Đây là nhóm mạnh nhất. Bạn tạo file .md trong .claude/commands/:

.claude/commands/deploy.md# Lệnh deploy toàn bộ ứng dụng

Thực hiện đúng quy trình sau, KHÔNG được bỏ bước:

1. **Kiểm tra code:**
   - `npx tsc --noEmit` → phải 0 errors
   - `npm run lint` → phải 0 warnings
   - `npm test` → phải all passed

2. **Build production:**
   - `npm run build`
   - Kiểm tra output size hợp lý (<5MB)

3. **Git:**
   - Tạo commit với message mô tả changes
   - Push lên remote

4. **Báo cáo:**
   - Liệt kê những gì đã thay đổi
   - Ghi chú nếu có breaking changes
.claude/commands/morning-standup.md# Báo cáo buổi sáng

Phân tích project và tạo báo cáo standup:

1. `git log --oneline --since="yesterday"` → việc đã làm hôm qua
2. Đọc TODO comments trong code → việc cần làm hôm nay
3. `npm test` → có test nào fail không?
4. `git status` → có file nào chưa commit?

Trình bày theo format:
- ✅ Hôm qua đã làm: ...
- 📋 Hôm nay sẽ làm: ...
- ⚠️ Blockers/Issues: ...

Sử dụng: /project:deploy hoặc /project:morning-standup

Bài 8

MCP Tools - Kết Nối Với Thế Giới Bên Ngoài

Email, browser, database, GitHub, Slack - Claude Code làm được tất cả qua MCP.

MCP là gì?

MCP (Model Context Protocol) là giao thức chuẩn cho phép Claude Code kết nối với bất kỳ dịch vụ bên ngoài nào. Giống như cổng USB cho AI - cắm vào là dùng được.

Claude Code │ ┌────────────────────┼────────────────────┐ ▼ ▼ ▼ ▼ ▼ Database GitHub Slack Email Browser │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ PostgreSQL Issues Channels Gmail Web pages MongoDB PRs Messages Outlook Screenshots SQLite Actions Threads Automation

Tại sao MCP thay đổi mọi thứ?

Mặc định Claude Code chỉ có thể đọc file và chạy terminal. Với MCP, nó trở thành trung tâm điều khiển kết nối mọi công cụ bạn dùng hàng ngày:

Cách cài đặt MCP Servers

.claude/settings.json{
  "mcpServers": {

Bài 9

Hooks - Tự Động Hoá Hành Vi

Tự động hoá hành vi trước/sau mỗi hành động của Claude - không cần nhắc nhở.

Hooks là gì?

Hooks là các lệnh shell tự động chạy khi Claude thực hiện 1 hành động. Giống như "quy tắc tự động" - khi X xảy ra → tự động làm Y.

Bạn yêu cầu Claude sửa file │ ▼ ┌─── PreToolUse Hook ───┐ │ Kiểm tra: file này có │ │ nằm trong danh sách │──── Từ chối? → CHẶN hành động │ cấm sửa không? │ └───────────┬────────────┘ │ OK ▼ ┌─── Claude sửa file ───┐ │ (Edit/Write) │ └───────────┬────────────┘ │ ▼ ┌─── PostToolUse Hook ──┐ │ Tự động: │ │ - Format code (Prettier)│ │ - Lint check (ESLint) │ │ - Type check (tsc) │ └────────────────────────┘

4 loại Hooks

Hook Khi nào chạy? Use case phổ biến
PreToolUse TRƯỚC khi Claude dùng tool Chặn sửa file .env, chặn xoá file quan trọng
PostToolUse SAU khi Claude dùng tool Auto format, auto lint, auto type-check
Notification Khi Claude gửi thông báo Gửi alert qua Slack, push notification
Stop Khi Claude hoàn thành task Chạy full test suite, build kiểm tra

Giải thích từng hook:

🛡️

PreToolUse #1: Bảo vệ secrets

Nếu Claude muốn sửa file .env, .key, .pem → CHẶN ngay. Không cho sửa dù bạn yêu cầu.

⛔

PreToolUse #2: Chặn lệnh nguy hiểm

Nếu Claude chạy rm -rf → CHẶN ngay. Bảo vệ bạn khỏi mất dữ liệu.

✨

PostToolUse: Auto format

Mỗi khi Claude sửa file → tự động chạy Prettier + ESLint. Code luôn đẹp, luôn chuẩn.

🧪

Stop: Auto test

Mỗi khi Claude hoàn thành task → tự động chạy tests. Biết ngay có gì bị hỏng.

Hooks = An toàn + Chất lượng tự động

Bạn không cần nhắc "format code đi", "chạy test đi" mỗi lần. Hooks làm tự động. Bạn cũng không cần lo Claude sửa nhầm file quan trọng. Setup 1 lần, yên tâm mãi mãi.

Bài 10

Sub-agents & Agent Teams

Orchestrate đội ngũ AI làm việc song song - từ 1 Claude thành cả team.

Từ 1 Agent thành 1 Team

Khi task phức tạp, 1 Claude không đủ. Giải pháp: tạo đội ngũ agents chuyên biệt, mỗi agent giỏi 1 việc, phối hợp nhau như một team thực sự.

Bạn: "Refactor hệ thống auth" │ ▼ ┌─── Main Agent ───┐ │ (Orchestrator) │ │ Phân tích task │ │ Chia nhỏ công │ │ việc & phân công │ └────────┬─────────┘ ┌──────────────┼──────────────┐ ▼ ▼ ▼ ┌─── Researcher ──┐ ┌── Coder ───┐ ┌── Tester ───┐ │ Quét codebase │ │ Viết code │ │ Viết tests │ │ Tìm tất cả JWT │ │ Session │ │ Unit tests │ │ code, endpoints │ │ auth mới │ │ Integration │ │ liên quan │ │ │ │ E2E tests │ └────────┬─────────┘ └─────┬──────┘ └──────┬──────┘ │ │ │ └────────────────┼───────────────┘ ▼ ┌─── Main Agent ───┐ │ Tổng hợp kết │ │ quả, review, │ │ merge tất cả │ └──────────────────┘

Khi nào Claude tạo sub-agents?

  • Tìm kiếm rộng: Cần quét nhiều file/thư mục cùng lúc
  • Nhiệm vụ độc lập: Nhiều việc có thể làm song song
  • Phân tích sâu: Cần xem xét nhiều khía cạnh (performance, security, UX...)
  • Task lớn: Bài toán có thể chia thành 3-5 phần riêng biệt

Orchestration Patterns

Có 3 cách phổ biến để tổ chức agent teams:

Pattern 1: Fan-out / Fan-in (Phổ biến nhất)

Mô hìnhMain Agent
    ├──▶ Agent A (làm phần 1) ──┐
    ├──▶ Agent B (làm phần 2) ──┼──▶ Main Agent tổng hợp
    └──▶ Agent C (làm phần 3) ──┘

Ví dụ: "Review security cho toàn bộ app"
    ├──▶ Agent A: Kiểm tra SQL injection
    ├──▶ Agent B: Kiểm tra XSS
    └──▶ Agent C: Kiểm tra authentication bypass

Pattern 2: Pipeline (Tuần tự)

Mô hìnhAgent A ──▶ Agent B ──▶ Agent C ──▶ Done
(Research)   (Code)      (Test)

Ví dụ: "Thêm tính năng search"
Agent A: Nghiên cứu codebase, tìm pattern phù hợp
    ↓
Agent B: Viết code search dựa trên kết quả Agent A
    ↓
Agent C: Viết tests cho code Agent B vừa viết

Pattern 3: Supervisor (Giám sát)

Mô hìnhSupervisor Agent (giám sát liên tục)
    ├── Worker Agent 1 (code)
    ├── Worker Agent 2 (code)
    └── Review Agent (kiểm tra output)

Supervisor phân việc → Workers làm → Review kiểm tra
    → Nếu fail → quay lại Worker sửa

  }

// Chạy team song song
async function runTeam(task: string) {
  // Bước 1: Researcher quét codebase
  const research = await callAgent("researcher", task);

  // Bước 2: Coder + Tester làm song song
  const [code, tests] = await Promise.all([
    callAgent("coder", `Dựa trên research:\n${research}\n\nViết code cho: ${task}`),
    callAgent("coder", `Viết tests cho: ${task}`)
  ]);

  // Bước 3: Reviewer kiểm tra tất cả
  const review = await callAgent("reviewer",
    `Review code:\n${code}\n\nTests:\n${tests}`
  );

  return { research, code, tests, review };
}

Agent Teams vs Git Worktrees - Khi nào dùng cái nào?

Đây là câu hỏi rất nhiều người nhầm lẫn. Hai công cụ này phục vụ mục đích khác nhau:

Dùng Agent Teams khi:

  • Task hoàn toàn độc lập về file - như build 3 website khác nhau từ đầu
  • Không quan tâm đến lịch sử code (Git history)
  • Muốn nhanh, không cần setup Git
  • Mỗi agent làm xong → giao kết quả → không cần merge

Dùng Git Worktrees khi:

  • Nhiều agents cùng làm việc trên MỘT project có sẵn
  • Tasks có thể share file (navigation, CSS chung, utils...)
  • Bạn dùng GitHub và cần track lịch sử thay đổi rõ ràng
  • Làm việc nhóm - cần tách biệt để tránh ghi đè nhau
Quy tắc đơn giản để chọn

Agent Teams = Nhiều project riêng, không liên quan → mỗi agent 1 thế giới riêng.
Git Worktrees = 1 project, nhiều nhánh song song → cùng codebase, khác branch.

Ví dụ: Bạn cần build landing page + API + mobile app cùng lúc? → Agent Teams.
Bạn cần thêm feature search + fix bug login + viết tests cho 1 app? → Git Worktrees.

app.pyimport modal
from fastapi import FastAPI, HTTPException
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel
import sqlite3

# ===== Modal Setup =====
app = modal.App("todo-api")
volume = modal.Volume.from_name("todo-data", create_if_missing=True)
image = modal.Image.debian_slim().pip_install("fastapi", "uvicorn")

# ===== FastAPI Setup =====
web_app = FastAPI(title="Todo API", version="1.0")
web_app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_methods=["*"],
    allow_headers=["*"],
)

# ===== Models =====
class TodoCreate(BaseModel):
    title: str
    description: str = ""

class TodoUpdate(BaseModel):
    title: str = None
    completed: bool = None

# ===== Database =====
def get_db():
    conn = sqlite3.connect("/data/todos.db")
    conn.execute("""
        CREATE TABLE IF NOT EXISTS todos (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            title TEXT NOT NULL,
            description TEXT DEFAULT '',
            completed BOOLEAN DEFAULT FALSE,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        )
    """)
    return conn

# ===== Endpoints =====
@web_app.get("/todos")
async def list_todos():
    db = get_db()
    todos = db.execute("SELECT * FROM todos ORDER BY created_at DESC").fetchall()
    return [{"id": t[0], "title": t[1], "description": t[2],
             "completed": bool(t[3]), "created_at": t[4]} for t in todos]

@web_app.post("/todos")
async def create_todo(todo: TodoCreate):
    db = get_db()
    cursor = db.execute(
        "INSERT INTO todos (title, description) VALUES (?, ?)",
        (todo.title, todo.description)
    )
    db.commit()
    return {"id": cursor.lastrowid, "title": todo.title, "completed": False}

@web_app.put("/todos/{todo_id}")
async def update_todo(todo_id: int, todo: TodoUpdate):
    db = get_db()
    updates = []
    values = []
    if todo.title is not None:
        updates.append("title = ?")
        values.append(todo.title)
    if todo.completed is not None:
        updates.append("completed = ?")
        values.append(todo.completed)
    if not updates:
        raise HTTPException(400, "Không có gì để cập nhật")
    values.append(todo_id)
    db.execute(f"UPDATE todos SET {', '.join(updates)} WHERE id = ?", values)
    db.commit()
    return {"updated": True}

@web_app.delete("/todos/{todo_id}")
async def delete_todo(todo_id: int):
    db = get_db()
    db.execute("DELETE FROM todos WHERE id = ?", (todo_id,))
    db.commit()
    return {"deleted": True}

# ===== Deploy lên Modal =====
@app.function(image=image, volumes={"/data": volume})
@modal.asgi_app()
def api():
    return web_app

        os.environ["SLACK_WEBHOOK_URL"],
        json={"text": report}
    )
