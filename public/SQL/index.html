1. SELECT — Nền Tảng Của Mọi Thứ

90% công việc hàng ngày với SQL là SELECT. Nắm chắc phần này = xong nửa SQL.

⚡ THỨ TỰ THỰC THI SQL — Quan trọng nhất!

SQL KHÔNG chạy theo thứ tự bạn viết. Hiểu thứ tự thực thi giúp bạn debug mọi lỗi.

1FROM Chọn bảng nào
2JOIN Nối bảng nào
3WHERE Lọc hàng nào (TRƯỚC group)
4GROUP BY Nhóm theo cột nào
5HAVING Lọc nhóm nào (SAU group)
6SELECT Lấy cột nào
7DISTINCT Loại trùng
8ORDER BY Sắp xếp
9OFFSET/FETCH Phân trang
⚠️ Vì sao quan trọng: Bạn KHÔNG THỂ dùng alias đặt ở SELECT trong WHERE — vì WHERE chạy TRƯỚC SELECT. Đây là lỗi #1 của người mới.

📝 SELECT cơ bản

Lấy tất cả users ở Hà Nội, sắp xếp theo ngày tạo mới nhất
SELECT id, name, email, created_at
FROM Users
WHERE city = N'Hà Nội'
  AND is_active = 1
ORDER BY created_at DESC;
SELECT id, name... — Liệt kê CỤ THỂ cột cần. KHÔNG BAO GIỜ dùng SELECT * trong production.
N'Hà Nội' — Prefix N cho Unicode (tiếng Việt). Không có N → sai dữ liệu.
ORDER BY ... DESC — DESC = giảm dần (mới nhất trước). Mặc định ASC = tăng dần.

🎯 WHERE — Tất cả các toán tử bạn cần

So sánh cơ bản

-- Bằng
WHERE status = 'completed'

-- Khác
WHERE status != 'cancelled'
-- hoặc: WHERE status <> 'cancelled'

-- Lớn hơn, nhỏ hơn
WHERE price >= 100 AND price < 500

BETWEEN — Khoảng

-- Đơn hàng trong tháng 3/2026
WHERE created_at BETWEEN
    '2026-03-01' AND '2026-03-31'

-- ⚠️ BETWEEN bao gồm CẢ HAI đầu
-- Với DATETIME: '2026-03-31' = 00:00:00
-- → mất data ngày 31! Dùng < '2026-04-01'

IN — Nhiều giá trị

-- Thay vì OR dài dòng:
WHERE city IN (N'Hà Nội', N'HCM', N'Đà Nẵng')

-- NOT IN: loại trừ
WHERE status NOT IN ('cancelled', 'refunded')

-- ⚠️ Nếu IN chứa NULL → NOT IN sai!

LIKE — Tìm kiếm pattern

-- Tên bắt đầu bằng "Nguyễn"
WHERE name LIKE N'Nguyễn%'

-- Email chứa "gmail"
WHERE email LIKE '%gmail%'

-- _ = 1 ký tự bất kỳ
WHERE code LIKE 'A_B' -- A1B, A2B...

-- ⚠️ '%abc' = KHÔNG dùng index → chậm!

IS NULL — Kiểm tra NULL

-- NULL không thể so sánh bằng =
WHERE phone IS NULL      -- ✅ Đúng
WHERE phone = NULL       -- ❌ LUÔN false!

-- Có giá trị (không null)
WHERE phone IS NOT NULL

-- COALESCE: giá trị mặc định nếu NULL
SELECT COALESCE(phone, 'Chưa có')

AND / OR — Kết hợp điều kiện

-- AND ưu tiên hơn OR!
-- Ý bạn: (A OR B) AND C
-- SQL hiểu: A OR (B AND C) ← SAI!

-- ✅ Luôn dùng ngoặc cho rõ ràng:
WHERE (city = N'HCM' OR city = N'HN')
  AND is_active = 1

📄 Phân trang — OFFSET / FETCH

Lấy trang 3, mỗi trang 20 bản ghi (SQL Server)
SELECT id, name, email
FROM Users
ORDER BY created_at DESC
OFFSET 40 ROWS           -- Bỏ qua 40 bản ghi đầu (page 1 + 2)
FETCH NEXT 20 ROWS ONLY;  -- Lấy 20 bản ghi tiếp theo
⚠️ OFFSET lớn = CHẬM! OFFSET 10000 = DB phải scan 10000 rows rồi bỏ. Với bảng lớn, dùng Keyset Pagination:
WHERE id > @lastId ORDER BY id FETCH NEXT 20 ROWS ONLY — Nhanh gấp 100x.

🔄 DISTINCT & TOP

DISTINCT — Loại bỏ trùng lặp
-- Danh sách thành phố (không trùng)
SELECT DISTINCT city
FROM Users
WHERE city IS NOT NULL
ORDER BY city;
TOP — Lấy N bản ghi đầu
-- 10 sản phẩm đắt nhất
SELECT TOP 10 name, price
FROM Products
ORDER BY price DESC;

-- MySQL/PostgreSQL dùng LIMIT 10

🔀 CASE WHEN — If/Else trong SQL

Phân loại đơn hàng theo giá trị
SELECT
    id,
    total,
    CASE
        WHEN total >= 10000000 THEN N'VIP'
        WHEN total >= 1000000  THEN N'Lớn'
        WHEN total >= 100000   THEN N'Trung bình'
        ELSE N'Nhỏ'
    END AS order_tier          -- AS = đặt tên alias cho cột
FROM Orders
WHERE status = 'completed';
💡 Mẹo: CASE WHEN dùng được ở SELECT, WHERE, ORDER BY, và cả GROUP BY. Rất linh hoạt — thay thế cho việc tính toán ở application layer.

2. JOIN — Nối Bảng, Kỹ Năng #1

Hầu hết query thực tế đều cần JOIN. Hiểu sai JOIN = data sai = bug nghiêm trọng.

📊 4 loại JOIN — So sánh trực quan

INNER JOIN

Chỉ lấy rows khớp ở CẢ HAI bảng. Không khớp = bỏ.

Dùng khi: chỉ muốn data có đầy đủ ở 2 bên

LEFT JOIN

Lấy TẤT CẢ rows bảng trái + rows khớp bảng phải. Không khớp → NULL.

Dùng khi: muốn giữ tất cả bảng trái dù bảng phải không có

RIGHT JOIN

Lấy TẤT CẢ rows bảng phải + rows khớp bảng trái. Ít dùng — viết ngược LEFT JOIN.

Dùng khi: hiếm — thường đổi thứ tự thành LEFT JOIN cho dễ đọc

FULL OUTER JOIN

Lấy TẤT CẢ rows CẢ HAI bảng. Không khớp bên nào → NULL bên đó.

Dùng khi: so sánh 2 dataset, tìm orphan records

📝 INNER JOIN — Trường hợp phổ biến nhất

Lấy đơn hàng kèm tên khách hàng
SELECT
    o.id        AS order_id,
    u.name      AS customer_name,
    o.total,
    o.status,
    o.created_at
FROM Orders o                          -- o = alias cho bảng Orders
INNER JOIN Users u ON o.user_id = u.id  -- Nối: Orders.user_id = Users.id
WHERE o.status = 'completed'
ORDER BY o.created_at DESC;
FROM Orders o — o là alias (tên ngắn) cho bảng Orders. Giúp viết ngắn gọn.
ON o.user_id = u.id — Điều kiện nối: cột nào ở bảng này liên kết với cột nào ở bảng kia.
o.total — Khi JOIN, PHẢI ghi rõ alias.column nếu 2 bảng có cùng tên cột.

📝 LEFT JOIN — Giữ tất cả bảng trái

Tất cả users + số đơn hàng (kể cả user chưa mua gì)
SELECT
    u.id,
    u.name,
    COUNT(o.id) AS total_orders    -- COUNT(o.id): chỉ đếm khi o.id NOT NULL
FROM Users u
LEFT JOIN Orders o ON u.id = o.user_id
GROUP BY u.id, u.name                 -- Nhóm theo user
ORDER BY total_orders DESC;
LEFT JOIN → User chưa có đơn nào vẫn xuất hiện, với total_orders = 0.
Nếu dùng INNER JOIN → User chưa mua gì sẽ bị MẤT khỏi kết quả!
COUNT(o.id) thay vì COUNT(*) — COUNT(*) đếm cả rows NULL = sai!

📝 Multi JOIN — Nối 3+ bảng

Chi tiết đơn hàng: user + product + category
SELECT
    u.name       AS customer,
    p.name       AS product,
    c.name       AS category,
    oi.quantity,
    oi.unit_price,
    (oi.quantity * oi.unit_price) AS line_total
FROM OrderItems oi
INNER JOIN Orders o    ON oi.order_id = o.id
INNER JOIN Users u     ON o.user_id = u.id
INNER JOIN Products p  ON oi.product_id = p.id
LEFT JOIN  Categories c ON p.category_id = c.id  -- LEFT: product có thể chưa có category
WHERE o.created_at >= '2026-01-01'
ORDER BY o.created_at DESC, oi.id;
💡 Mẹo đọc multi JOIN: Đọc từ FROM xuống — mỗi JOIN = "kết nối thêm 1 bảng". Luôn bắt đầu từ bảng "trung tâm" (ở đây là OrderItems vì nó FK đến cả Orders và Products).

📝 Self JOIN — Bảng nối với chính nó

Category cha-con (parent_id → id)
SELECT
    child.name  AS sub_category,
    parent.name AS parent_category
FROM Categories child
LEFT JOIN Categories parent ON child.parent_id = parent.id
ORDER BY parent.name, child.name;
⚠️ JOIN TRAP — Sai lầm kinh điển:
• Quên ON condition → CROSS JOIN → hàng triệu rows (mọi combo)!
• JOIN sai cột → data nhân bản sai. Luôn kiểm tra COUNT trước và sau JOIN.
• JOIN tạo duplicate → Nếu bảng phải có nhiều rows khớp 1 row bảng trái → kết quả nhân lên. Cần GROUP BY hoặc DISTINCT.

3. GROUP BY & Aggregate — Thống Kê Dữ Liệu

Đếm, tính tổng, tính trung bình — mọi báo cáo đều bắt đầu từ GROUP BY

🔢 5 Hàm Aggregate Bắt Buộc

COUNT()
Đếm số hàng
-- Đếm tất cả orders
SELECT COUNT(*) FROM Orders;

-- Đếm orders có email (bỏ NULL)
SELECT COUNT(email) FROM Users;

-- Đếm city khác nhau
SELECT COUNT(DISTINCT city) FROM Users;
SUM()
Tính tổng
-- Tổng doanh thu
SELECT SUM(total)
FROM Orders
WHERE status = 'completed';

-- ⚠️ SUM(NULL) = NULL, không phải 0
-- Dùng: COALESCE(SUM(total), 0)
AVG()
Trung bình
-- Giá trị đơn hàng trung bình
SELECT AVG(total) AS avg_order
FROM Orders
WHERE status = 'completed';

-- ⚠️ AVG bỏ qua NULL!
-- 10 + NULL + 20 → AVG = 15 (2 rows)
MIN() / MAX()
Nhỏ nhất / Lớn nhất
-- Giá rẻ nhất và đắt nhất
SELECT
    MIN(price) AS cheapest,
    MAX(price) AS most_expensive
FROM Products;

-- Cũng dùng được cho DATE, VARCHAR

📝 GROUP BY — Ví dụ thực tế

Doanh thu theo tháng
SELECT
    YEAR(created_at)  AS [year],
    MONTH(created_at) AS [month],
    COUNT(*)          AS total_orders,
    SUM(total)        AS revenue,
    AVG(total)        AS avg_order_value
FROM Orders
WHERE status = 'completed'
GROUP BY YEAR(created_at), MONTH(created_at)
ORDER BY [year] DESC, [month] DESC;
Top 5 sản phẩm bán chạy nhất
SELECT TOP 5
    p.name,
    SUM(oi.quantity)              AS total_sold,
    SUM(oi.quantity * oi.unit_price) AS total_revenue
FROM OrderItems oi
INNER JOIN Products p ON oi.product_id = p.id
GROUP BY p.id, p.name            -- Nhóm theo product
ORDER BY total_sold DESC;

🔍 HAVING — WHERE cho nhóm

WHERE lọc rows TRƯỚC khi nhóm. HAVING lọc nhóm SAU khi nhóm.

Khách hàng mua trên 5 đơn, tổng trên 1 triệu
SELECT
    u.name,
    COUNT(o.id)  AS total_orders,
    SUM(o.total) AS total_spent
FROM Users u
INNER JOIN Orders o ON u.id = o.user_id
WHERE o.status = 'completed'       -- WHERE: lọc rows trước khi nhóm
GROUP BY u.id, u.name
HAVING COUNT(o.id) > 5            -- HAVING: lọc nhóm sau khi nhóm
   AND SUM(o.total) > 1000000
ORDER BY total_spent DESC;
⚠️ Quy tắc GROUP BY: Mọi cột trong SELECT mà KHÔNG phải aggregate function → BẮT BUỘC phải có trong GROUP BY. Vi phạm = lỗi syntax hoặc data sai.

4. Subquery, CTE & Window Functions

Khi 1 câu SELECT không đủ — nâng cấp lên query phức tạp mà vẫn dễ đọc

📝 Subquery — Query lồng trong query

Subquery trong WHERE
-- Sản phẩm có giá cao hơn trung bình
SELECT name, price
FROM Products
WHERE price > (
    SELECT AVG(price) FROM Products
);

-- Users đã từng mua hàng
SELECT name, email
FROM Users
WHERE id IN (
    SELECT DISTINCT user_id FROM Orders
);
Subquery trong FROM (Derived Table)
-- Thống kê user theo "tier" đơn hàng
SELECT
    tier,
    COUNT(*) AS user_count
FROM (
    SELECT
        user_id,
        CASE
            WHEN SUM(total) >= 5000000 THEN 'VIP'
            WHEN SUM(total) >= 1000000 THEN 'Gold'
            ELSE 'Normal'
        END AS tier
    FROM Orders
    GROUP BY user_id
) AS UserTiers            -- BẮT BUỘC đặt alias
GROUP BY tier;

📝 CTE (Common Table Expression) — Query rõ ràng hơn

CTE = "đặt tên" cho subquery, đặt ở đầu với WITH. Dễ đọc hơn subquery lồng nhau.

Cùng bài toán trên nhưng viết bằng CTE
-- CTE: dễ đọc, dễ debug, reuse được
WITH UserSpending AS (
    SELECT
        user_id,
        SUM(total) AS total_spent,
        COUNT(*)   AS order_count
    FROM Orders
    WHERE status = 'completed'
    GROUP BY user_id
),
UserTiers AS (
    SELECT
        user_id,
        total_spent,
        order_count,
        CASE
            WHEN total_spent >= 5000000 THEN 'VIP'
            WHEN total_spent >= 1000000 THEN 'Gold'
            ELSE 'Normal'
        END AS tier
    FROM UserSpending
)
SELECT
    u.name,
    ut.tier,
    ut.total_spent,
    ut.order_count
FROM UserTiers ut
INNER JOIN Users u ON ut.user_id = u.id
ORDER BY ut.total_spent DESC;
💡 Khi nào dùng CTE thay Subquery: Query dài > 15 dòng, cần reuse subquery, hoặc cần đặt tên cho từng "bước" logic. CTE giống viết code có comment — rõ ý đồ hơn.

🪟 Window Functions — Tính toán KHÔNG mất chi tiết

GROUP BY gộp rows lại. Window Functions tính toán mà giữ nguyên từng row — rất mạnh cho ranking, running total, so sánh.

ROW_NUMBER — Đánh số thứ tự
-- Xếp hạng sản phẩm bán chạy nhất TRONG MỖI category
SELECT
    p.name,
    c.name AS category,
    SUM(oi.quantity) AS total_sold,
    ROW_NUMBER() OVER (
        PARTITION BY c.id        -- Chia nhóm theo category
        ORDER BY SUM(oi.quantity) DESC  -- Sắp xếp trong nhóm
    ) AS rank_in_category
FROM OrderItems oi
INNER JOIN Products p  ON oi.product_id = p.id
INNER JOIN Categories c ON p.category_id = c.id
GROUP BY p.id, p.name, c.id, c.name;
Running Total — Doanh thu lũy kế
SELECT
    created_at,
    total,
    SUM(total) OVER (
        ORDER BY created_at
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM Orders
WHERE status = 'completed';
LAG / LEAD — So sánh với row trước/sau
-- Doanh thu tháng này vs tháng trước
WITH MonthlyRevenue AS (
    SELECT
        FORMAT(created_at, 'yyyy-MM') AS month,
        SUM(total) AS revenue
    FROM Orders WHERE status = 'completed'
    GROUP BY FORMAT(created_at, 'yyyy-MM')
)
SELECT
    month,
    revenue,
    LAG(revenue) OVER (ORDER BY month) AS prev_month,
    revenue - LAG(revenue) OVER (ORDER BY month) AS growth
FROM MonthlyRevenue;

📝 EXISTS — Kiểm tra "có tồn tại không?"

✅ EXISTS (nhanh hơn IN cho dataset lớn)
-- Users ĐÃ mua hàng
SELECT u.name
FROM Users u
WHERE EXISTS (
    SELECT 1 FROM Orders o
    WHERE o.user_id = u.id
);
NOT EXISTS — Users CHƯA mua gì
-- Users CHƯA có đơn hàng nào
SELECT u.name, u.email
FROM Users u
WHERE NOT EXISTS (
    SELECT 1 FROM Orders o
    WHERE o.user_id = u.id
);
💡 EXISTS vs IN: EXISTS dừng ngay khi tìm thấy 1 match → nhanh hơn khi subquery trả về nhiều rows. IN phải load toàn bộ list → chậm hơn với dataset lớn. Rule: EXISTS cho performance.
✏️

5. INSERT / UPDATE / DELETE — Thao Tác Dữ Liệu

Đọc data dễ, SỬA data mới nguy hiểm. 1 câu UPDATE sai = mất data thật.

📝 INSERT — Thêm dữ liệu

Insert 1 row
INSERT INTO Users (name, email, city, is_active)
VALUES (N'Nguyễn Văn A', 'a@email.com',
        N'Hà Nội', 1);

-- Lấy ID vừa insert (SQL Server)
SELECT SCOPE_IDENTITY() AS new_id;
Insert nhiều rows + Insert từ SELECT
-- Nhiều rows 1 lần (nhanh hơn insert từng cái)
INSERT INTO Products (name, price, stock)
VALUES
    (N'Laptop', 15000000, 50),
    (N'Mouse',  200000,   200),
    (N'Keyboard', 500000, 100);

-- Insert từ query khác
INSERT INTO VipUsers (user_id, total_spent)
SELECT user_id, SUM(total)
FROM Orders
GROUP BY user_id
HAVING SUM(total) > 5000000;

📝 UPDATE — Cập nhật dữ liệu

Update cơ bản + Update với JOIN
-- ✅ LUÔN có WHERE khi UPDATE!
UPDATE Users
SET city = N'TP.HCM',
    is_active = 0
WHERE id = 42;

-- Update với JOIN: giảm giá 10% cho sản phẩm category "Clearance"
UPDATE p
SET p.price = p.price * 0.9
FROM Products p
INNER JOIN Categories c ON p.category_id = c.id
WHERE c.name = 'Clearance';
☠️ CẢNH BÁO TỐI QUAN TRỌNG:
UPDATE Users SET is_active = 0; ← KHÔNG CÓ WHERE = CẬP NHẬT TOÀN BỘ BẢNG!
Trước khi UPDATE: luôn chạy SELECT với cùng WHERE trước để kiểm tra sẽ ảnh hưởng bao nhiêu rows.

📝 DELETE — Xóa dữ liệu

-- ✅ LUÔN có WHERE!
DELETE FROM Orders
WHERE status = 'cancelled'
  AND created_at < '2025-01-01';

-- ⚠️ DELETE FROM Orders; ← XÓA TOÀN BỘ! Không undo được!

-- Soft Delete (khuyến khích): không xóa thật, chỉ đánh dấu
UPDATE Users
SET is_active = 0, deleted_at = GETDATE()
WHERE id = 42;
💡 Best Practice: Trong production, hầu như KHÔNG BAO GIỜ dùng DELETE thật. Luôn dùng Soft Delete (thêm cột is_deleted hoặc deleted_at). Data đã xóa = không thể recover nếu không có backup.

📝 MERGE — Upsert (Insert hoặc Update)

Nếu tồn tại → update, chưa có → insert
MERGE INTO Products AS target
USING (
    VALUES ('SKU-001', N'Laptop Pro', 20000000, 30)
) AS source (sku, name, price, stock)
ON target.sku = source.sku
WHEN MATCHED THEN
    UPDATE SET price = source.price, stock = source.stock
WHEN NOT MATCHED THEN
    INSERT (sku, name, price, stock)
    VALUES (source.sku, source.name, source.price, source.stock);

6. Index & Performance — Query Nhanh Gấp 100x

Query chạy 10 giây vs 10ms — khác biệt là INDEX. Hiểu index = hiểu performance.

🔑 Index là gì? — Giải thích đơn giản

📖 Không có Index = Đọc sách từ đầu đến cuối

Tìm từ "SQL" trong sách 500 trang → lật từng trang, đọc từng dòng. Full Table Scan = đọc toàn bộ bảng.

📇 Có Index = Mở phần mục lục (Index) ở cuối sách

Tra "SQL" → mục lục chỉ: trang 42, 156, 301 → nhảy thẳng tới. Index Seek = nhảy thẳng đến row cần.

📊 Các loại Index

Clustered Index

= Thứ tự vật lý của data trên disk. Mỗi bảng chỉ có 1. Thường là Primary Key.

-- Tự tạo khi đặt PRIMARY KEY
CREATE TABLE Users (
    id INT PRIMARY KEY,  -- = Clustered Index
    ...
);
Giống sách xếp theo thứ tự ABC — data SẮP XẾP theo key này

Non-Clustered Index

= Bảng phụ chỉ đường đến data gốc. Có thể tạo nhiều cái. Dùng cho cột WHERE, JOIN, ORDER BY.

-- Tạo index cho cột thường xuyên tìm kiếm
CREATE INDEX IX_Users_Email
ON Users (email);

-- Composite: index nhiều cột
CREATE INDEX IX_Orders_Status_Date
ON Orders (status, created_at DESC);
Giống mục lục cuối sách — bản đồ chỉ trang nào chứa data cần

Covering Index (INCLUDE)

Index kèm thêm cột data → query không cần quay lại bảng gốc. Cực nhanh.

-- Index cho email + include name, city
CREATE INDEX IX_Users_Email_Cover
ON Users (email)
INCLUDE (name, city);

-- Query này dùng index 100%, không đọc bảng
SELECT name, city FROM Users
WHERE email = 'a@email.com';
Giống mục lục có tóm tắt nội dung — không cần mở trang

✅ Khi nào TẠO index / ❌ Khi nào KHÔNG

✅ NÊN tạo index cho:

  • Cột trong WHERE dùng thường xuyên
  • Cột trong JOIN ... ON (Foreign Key)
  • Cột trong ORDER BY
  • Cột có UNIQUE constraint
  • Cột dùng trong GROUP BY

❌ KHÔNG nên tạo index cho:

  • Bảng nhỏ (< 1000 rows) — scan nhanh hơn
  • Cột ít unique (VD: is_active chỉ có 0/1)
  • Bảng INSERT/UPDATE nhiều — index chậm ghi
  • Cột dùng LIKE '%abc' — index không giúp
  • Quá nhiều index — mỗi INSERT phải update TẤT CẢ index

🔍 Execution Plan — "X-ray" cho query

Xem query chạy thế nào (SQL Server)
-- Bật hiển thị Execution Plan
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Hoặc: Ctrl+L trong SSMS = Estimated Plan
-- Hoặc: Ctrl+M trong SSMS = Actual Plan

-- Tìm trong plan:
-- ✅ Index Seek = tốt (nhảy thẳng)
-- ⚠️ Index Scan = OK (đọc toàn bộ index)
-- ❌ Table Scan = tệ (đọc toàn bộ bảng)
-- ❌ Key Lookup = phải quay lại bảng (cần INCLUDE)
💡 Quy trình tối ưu query:
1. Chạy query, ghi nhận thời gian
2. Xem Execution Plan → tìm Table Scan, Key Lookup
3. Tạo index phù hợp
4. Chạy lại → so sánh. Nếu chưa đủ → bước 2.

💀 5 Query Pattern GiẾT Index

❌ 1. Function trên cột WHERE

-- ❌ YEAR() bọc cột → index vô dụng
WHERE YEAR(created_at) = 2026

-- ✅ So sánh khoảng → dùng index
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01'

❌ 2. LIKE bắt đầu bằng %

-- ❌ %abc = scan toàn bộ
WHERE name LIKE '%nguyen'

-- ✅ abc% = dùng index
WHERE name LIKE 'nguyen%'

-- Full-text search cho tìm kiếm phức tạp

❌ 3. Implicit Conversion

-- ❌ Column là VARCHAR, so với INT
WHERE phone = 0901234567
-- SQL convert TOÀN BỘ phone → INT để so!

-- ✅ Đúng type
WHERE phone = '0901234567'

❌ 4. OR trên khác cột

-- ❌ OR = scan cả 2 index hoặc table
WHERE name = 'A' OR email = 'a@b.com'

-- ✅ Tách thành UNION
SELECT * FROM Users WHERE name = 'A'
UNION
SELECT * FROM Users WHERE email = 'a@b.com'

❌ 5. SELECT *

-- ❌ Lấy TẤT CẢ cột → luôn đọc bảng
SELECT * FROM Orders;

-- ✅ Chỉ lấy cột cần → dùng covering index
SELECT id, status, total
FROM Orders;

7. Transaction & ACID — Đảm Bảo Dữ Liệu Luôn Đúng

Chuyển tiền mà trừ bên A rồi không cộng bên B = mất tiền. Transaction ngăn chặn điều đó.

🔐 ACID — 4 Tính Chất Sống Còn

A — Atomicity

Tất cả hoặc không gì cả. 5 câu SQL trong 1 transaction → hoặc TẤT CẢ thành công, hoặc ROLLBACK hết. Không bao giờ "chạy được nửa".

VD: Chuyển tiền: trừ A + cộng B. Nếu cộng B lỗi → trừ A cũng rollback.

C — Consistency

Data luôn hợp lệ. Transaction đưa DB từ trạng thái hợp lệ này → trạng thái hợp lệ khác. Constraints, triggers đảm bảo điều này.

VD: Balance không bao giờ âm → CHECK(balance >= 0)

I — Isolation

Transaction này không thấy data "dở dang" của transaction khác. 2 người chuyển tiền cùng lúc → không "thấy" nhau.

VD: A đang update giá → B query không thấy giá "nửa cũ nửa mới"

D — Durability

Commit rồi = không mất. Dù server crash, mất điện → data đã commit vẫn còn. Ghi vào disk, không chỉ RAM.

VD: "Đặt hàng thành công" hiện ra → order phải tồn tại dù server restart

📝 Transaction — Cú pháp thực tế

Chuyển tiền: trừ A, cộng B, ghi log — tất cả hoặc không gì
BEGIN TRANSACTION;
BEGIN TRY
    -- Trừ tiền người gửi
    UPDATE Accounts
    SET balance = balance - 1000000
    WHERE id = 1 AND balance >= 1000000;  -- Check đủ tiền

    IF @@ROWCOUNT = 0                        -- Không update được = không đủ tiền
        THROW 50001, 'Insufficient balance', 1;

    -- Cộng tiền người nhận
    UPDATE Accounts
    SET balance = balance + 1000000
    WHERE id = 2;

    -- Ghi log giao dịch
    INSERT INTO TransactionLog (from_id, to_id, amount, created_at)
    VALUES (1, 2, 1000000, GETDATE());

    COMMIT;                                  -- ✅ Tất cả OK → lưu vĩnh viễn
END TRY
BEGIN CATCH
    ROLLBACK;                                 -- ❌ Có lỗi → hoàn tác TẤT CẢ
    THROW;                                    -- Re-throw lỗi để app biết
END CATCH;

8. Thiết Kế Database — Đúng Từ Đầu, Đỡ Đau Về Sau

Schema sai → mọi query đều khó, mọi feature đều chậm, mọi bug đều khó fix

🔐 Constraints — Quy tắc bảo vệ data

Tất cả constraints bạn cần biết
CREATE TABLE Products (
    id          INT IDENTITY(1,1) PRIMARY KEY,  -- PK: unique + not null + auto increment
    sku         NVARCHAR(50)  NOT NULL UNIQUE,      -- UNIQUE: không trùng
    name        NVARCHAR(200) NOT NULL,              -- NOT NULL: bắt buộc
    price       DECIMAL(10,2) NOT NULL
                CHECK(price > 0),                     -- CHECK: điều kiện
    stock       INT NOT NULL DEFAULT 0
                CHECK(stock >= 0),                    -- DEFAULT + CHECK
    category_id INT NULL,
    created_at  DATETIME NOT NULL DEFAULT GETDATE(),

    -- FOREIGN KEY: liên kết với bảng khác
    CONSTRAINT FK_Products_Category
        FOREIGN KEY (category_id)
        REFERENCES Categories(id)
        ON DELETE SET NULL               -- Xóa category → product.category_id = NULL
        ON UPDATE CASCADE                -- Update category.id → tự cập nhật FK
);

📐 Normalization — 3 Dạng Chuẩn (đủ dùng)

1NF — Mỗi ô chỉ 1 giá trị

❌ Sai: tags = "react,vue,angular"
✅ Đúng: Tách thành bảng ProductTags (product_id, tag)

Quy tắc: Không lưu list/array trong 1 cột. Mỗi ô = 1 giá trị atomic.

2NF — Mọi cột phụ thuộc TOÀN BỘ PK

❌ Sai: OrderItems có product_name (chỉ phụ thuộc product_id, không phụ thuộc order_id)
✅ Đúng: Lấy product_name bằng JOIN, không lưu trùng

Quy tắc: Nếu dùng composite PK, mọi cột phải phụ thuộc CẢ composite, không chỉ 1 phần.

3NF — Không có phụ thuộc bắc cầu

❌ Sai: Users có city + city_province (province phụ thuộc city, không phụ thuộc user)
✅ Đúng: Tách bảng Cities (id, name, province)

Quy tắc: A → B → C thì C không nên ở cùng bảng với A. Tách B ra bảng riêng.

💡 Thực tế: Normalize đến 3NF là đủ 99% trường hợp. Đôi khi cố tình denormalize (lưu trùng) cho performance — nhưng phải biết trade-off: data inconsistency risk.

📋 Quy Ước Đặt Tên — Consistency > Creativity

Bảng: PascalCase, số nhiều — Users, OrderItems, Categories
Cột: snake_case — created_at, user_id, is_active
PK: luôn là id — đơn giản, nhất quán
FK: {bảng_số_ít}_id — user_id, category_id, order_id
Boolean: prefix is_ hoặc has_ — is_active, has_email
Date: suffix _at — created_at, updated_at, deleted_at
Index: IX_{Bảng}_{Cột} — IX_Users_Email
FK Constraint: FK_{Bảng}_{BảngRef} — FK_Orders_Users

9. Sai Lầm Chết Người — Mỗi Cái Từng Xảy Ra Thật

Không ai nói cho bạn cho đến khi production sập lúc 3h sáng

01

SELECT * trong production

Bảng 50 cột, bạn chỉ cần 3 cột → SELECT * đọc gấp 15x data cần thiết. Network bandwidth, memory, CPU đều bị lãng phí. Covering index vô dụng.

Fix: LUÔN liệt kê cụ thể cột cần: SELECT id, name, email
02

UPDATE / DELETE không có WHERE

UPDATE Users SET is_active = 0; ← Toàn bộ user bị deactivate. Không undo được nếu không có backup.

Fix: Chạy SELECT COUNT(*) ... WHERE ... trước MỌI UPDATE/DELETE. Confirm số rows đúng.
03

N+1 Query — Kẻ giết performance thầm lặng

Lấy 100 orders → mỗi order query user → 101 queries thay vì 1! Ở dev thì nhanh, production 10K records thì chết.

Fix: Dùng JOIN thay vì query trong vòng lặp. Trong EF Core: .Include(o => o.User)
04

Không có Index trên Foreign Key

FK tự tạo constraint nhưng KHÔNG tự tạo index! JOIN mà FK không có index = full table scan bảng con mỗi lần JOIN.

Fix: Tạo index cho MỌI Foreign Key column. CREATE INDEX IX_Orders_UserId ON Orders(user_id);
05

Dùng FLOAT cho tiền

FLOAT 0.1 + 0.2 = 0.30000000000000004 ← Sai số floating point. Tính tiền sai 1 đồng x 1 triệu giao dịch = sai 1 triệu đồng.

Fix: Dùng DECIMAL(10,2) cho tiền. LUÔN. Không exception.
06

NULL trong IN / NOT IN

WHERE id NOT IN (1, 2, NULL) = LUÔN trả về 0 rows! Vì NULL so sánh với bất kỳ gì = UNKNOWN = FALSE.

Fix: Dùng NOT EXISTS thay NOT IN khi subquery có thể trả về NULL.
07

Không backup trước migration

DROP COLUMN, thay đổi data type, delete data — không thể undo. "Chắc không sao đâu" = câu nói trước mọi thảm họa.

Fix: BACKUP DATABASE trước MỌI migration trên production. Không exception. Tự động hóa.
08

Query trong vòng lặp application

foreach(var id in ids) { db.Query("SELECT * WHERE id = @id"); } ← 1000 IDs = 1000 round-trips đến DB.

Fix: Batch: WHERE id IN (@id1, @id2, ...) hoặc dùng Table-Valued Parameter.

10. Lời Khuyên Sống Còn & Con Đường Nâng Cao

Những bài học xương máu từ production thật + lộ trình để đi từ "biết SQL" lên "giỏi SQL"

☠️ LỜI KHUYÊN SỐNG CÒN — Khắc Cốt Ghi Tâm

Không phải kiến thức — đây là bài học máu mà dev nào cũng phải trả giá ít nhất 1 lần.

☠️ CRITICAL

Luôn chạy SELECT trước UPDATE/DELETE

"Tôi chạy UPDATE Users SET role = 'user' lúc 2h sáng — quên WHERE. 50,000 users mất role admin. Backup cuối cùng là 12 tiếng trước."
Quy tắc: Trước MỌI UPDATE/DELETE → viết SELECT với cùng WHERE trước. Xác nhận số rows. Rồi mới đổi thành UPDATE. Không exception.
✓ Viết SELECT ... WHERE ...
✓ Kiểm tra COUNT — đúng số rows mong đợi?
✓ Đổi SELECT → UPDATE/DELETE
✓ Wrap trong BEGIN TRAN ... ROLLBACK trước khi COMMIT
☠️ CRITICAL

KHÔNG chạy script trực tiếp trên Production

"Dev mới connect nhầm prod thay vì staging. Chạy script seed data → 100K records rác vào bảng Orders. Mất 4 tiếng cleanup."
Quy tắc: Luôn kiểm tra SELECT @@SERVERNAME, DB_NAME() trước khi chạy BẤT CỨ THỨ GÌ. Tốt hơn: dùng color-coded connection trong SSMS (đỏ = prod).
☠️ CRITICAL

Backup TRƯỚC migration — Không có ngoại lệ

"ALTER TABLE DROP COLUMN trên bảng 10 triệu rows. Cột hóa ra vẫn có service đang dùng. Không có backup. 2 ngày restore từ log shipping."
Quy tắc: Trước MỌI DDL trên production:
1. BACKUP DATABASE
2. Test script trên staging trước
3. Có rollback script sẵn
4. Chạy ngoài giờ peak
⚠️ DANGER

Transaction phải có timeout

"Long-running transaction lock bảng Orders 45 phút. Toàn bộ checkout trên website bị treo. Revenue mất ~200 triệu."
Quy tắc: Mọi transaction phải ngắn nhất có thể. Không bao giờ để transaction mở chờ user input. Set SET LOCK_TIMEOUT 30000; (30 giây max). Monitor bằng sp_who2 hoặc sys.dm_tran_active_transactions.
⚠️ DANGER

Deadlock — 2 transaction chờ nhau mãi mãi

"API endpoint A lock row 1 rồi cần row 2. API endpoint B lock row 2 rồi cần row 1. Cả 2 chờ nhau → timeout → 500 error hàng loạt."
Quy tắc: Luôn access bảng/rows theo cùng thứ tự trong mọi transaction. Giữ transaction ngắn. Dùng WITH (NOLOCK) cho read-only reports (chấp nhận dirty read). Monitor: sys.dm_tran_locks.
⚠️ DANGER

KHÔNG dùng dynamic SQL trực tiếp

"WHERE name = '" + userInput + "'" → SQL Injection. Hacker drop toàn bộ database. Thật sự xảy ra, không phải chuyện đùa."
Quy tắc: LUÔN dùng parameterized queries. WHERE name = @name. Không bao giờ nối string user input vào SQL. Trong .NET: dùng SqlParameter hoặc Dapper/EF Core — chúng auto parameterize.
⚠️ DANGER

Pagination: OFFSET lớn = Chậm kinh hoàng

"API phân trang OFFSET 500000 FETCH 20 — mỗi request DB scan 500K rows rồi bỏ. CPU 100%. API timeout."
Quy tắc: Bảng > 100K rows → dùng Keyset Pagination:
WHERE id > @lastId ORDER BY id FETCH NEXT 20 ROWS ONLY
Nhanh gấp 100-1000x so với OFFSET lớn.
💡 IMPORTANT

Log mọi thay đổi data quan trọng

"Ai đó update giá sản phẩm từ 100K thành 100. Không biết ai, khi nào, từ đâu. Không có audit log."
Quy tắc: Bảng quan trọng (Users, Orders, Products) → tạo Audit Table hoặc dùng Temporal Table (SQL Server 2016+). Ghi lại: ai, khi nào, thay đổi gì, giá trị cũ/mới.
💡 IMPORTANT

Index không phải thuốc thần — quá nhiều index = chậm write

"Thêm 15 index cho bảng Orders. SELECT nhanh lên. Nhưng INSERT từ 5ms → 200ms. Checkout timeout."
Quy tắc: Mỗi INSERT/UPDATE phải cập nhật TẤT CẢ index. Bảng write-heavy → max 4-5 index. Review index usage: sys.dm_db_index_usage_stats → xóa index không ai dùng.
💡 IMPORTANT

Stored Procedure: lợi và hại

"3000 dòng stored procedure không ai dám sửa vì không có version control, không test được, không biết logic đúng hay sai."
Quy tắc: SP phù hợp cho batch jobs, report phức tạp. Nhưng business logic chính nên ở application code (C#, Go...) — dễ test, dễ debug, có source control. SP > 100 dòng → refactor hoặc chuyển lên app.
📘 GOOD TO KNOW

NOLOCK không phải "miễn phí"

SELECT * FROM Orders WITH (NOLOCK) — đọc nhanh hơn nhưng có thể đọc data đang bị update dở (dirty read). Chỉ dùng cho báo cáo, thống kê — KHÔNG BAO GIỜ dùng cho tính tiền, inventory, xử lý đơn hàng.
📘 GOOD TO KNOW

Connection Pool — hiểu để không bị leak

App mở 1 connection → dùng → trả lại pool. Nếu code quên Close()/Dispose() → connection leak → pool cạn → app không connect được DB. Trong C#: luôn dùng using var conn = new SqlConnection(...); — auto dispose.

🚀 CON ĐƯỜNG NÂNG CAO — Từ "Biết SQL" Lên "Giỏi SQL"

Bạn đã nắm 80% sống còn ở 9 phần trên. Đây là roadmap để chinh phục 20% còn lại và trở thành database expert.

LEVEL 1

Thành Thạo Cơ Bản

1-3 tháng
✅ SELECT, WHERE, ORDER BY, JOIN
✅ GROUP BY, HAVING, Aggregate
✅ INSERT, UPDATE, DELETE an toàn
✅ Subquery, CTE cơ bản
✅ Tạo index cơ bản
Luyện tập: Giải 50 bài trên LeetCode SQL / HackerRank SQL. Viết query cho dự án thật.
LEVEL 2

Intermediate — Query Phức Tạp

3-6 tháng
📌 Window Functions nâng cao (RANK, DENSE_RANK, NTILE, PERCENT_RANK)
📌 Recursive CTE (duyệt tree, hierarchy)
📌 PIVOT / UNPIVOT — chuyển rows ↔ columns
📌 Dynamic SQL an toàn (sp_executesql)
📌 Temp Tables vs Table Variables vs CTE — khi nào dùng cái nào
📌 CROSS APPLY / OUTER APPLY
Ví dụ thực tế: 
-- Recursive CTE: tìm tất cả sub-category
WITH CategoryTree AS (
    -- Anchor: category gốc
    SELECT id, name, parent_id, 0 AS level
    FROM Categories WHERE parent_id IS NULL
    UNION ALL
    -- Recursive: tìm con
    SELECT c.id, c.name, c.parent_id, ct.level + 1
    FROM Categories c
    INNER JOIN CategoryTree ct ON c.parent_id = ct.id
)
SELECT * FROM CategoryTree ORDER BY level, name;
Luyện tập: Viết report phức tạp cho dự án thật. So sánh performance giữa các cách viết query khác nhau.
LEVEL 3

Advanced — Performance & Architecture

6-12 tháng
🔥 Execution Plan chuyên sâu (cardinality estimation, cost analysis)
🔥 Index strategy cho workload cụ thể (OLTP vs OLAP)
🔥 Partitioning — chia bảng lớn thành phần nhỏ
🔥 Columnstore Index — cho analytics/reporting
🔥 Query Store — theo dõi performance qua thời gian
🔥 Temporal Tables — lịch sử thay đổi data tự động
🔥 Database sharding / replication concepts
Ví dụ thực tế: 
-- Partitioning: chia bảng Orders theo năm
CREATE PARTITION FUNCTION PF_OrderDate (DATETIME)
AS RANGE RIGHT FOR VALUES (
    '2024-01-01', '2025-01-01', '2026-01-01'
);

-- Query chỉ scan partition 2026 → cực nhanh
SELECT * FROM Orders
WHERE created_at >= '2026-01-01'
  AND created_at <  '2027-01-01';
Luyện tập: Optimize query thật trên bảng >1 triệu rows. Đọc execution plan cho mọi query quan trọng.
LEVEL 4

Expert — DBA Mindset

1-2 năm+
💎 Backup & Recovery strategy (Full, Differential, Log, Point-in-time)
💎 High Availability (Always On, Failover Cluster, Log Shipping)
💎 Security hardening (Row-Level Security, Dynamic Data Masking, TDE)
💎 Performance tuning hệ thống (memory, TempDB, wait stats)
💎 Migration strategy cho bảng tỷ rows (zero-downtime)
💎 Distributed database (CAP theorem, eventual consistency)

Luyện tập: Quản lý DB production thật. Xử lý incident. Đọc sách: "SQL Server Internals", "Designing Data-Intensive Applications" (Martin Kleppmann).

⚡ MẸO THỰC CHIẾN — Áp Dụng Ngay

01

Viết query từ FROM lên SELECT

Đừng viết SELECT trước — bạn chưa biết data từ đâu. Bắt đầu từ FROM → JOIN → WHERE → GROUP BY → SELECT. Logic hơn, ít lỗi hơn.

02

Alias MỌI THỨ khi JOIN

Luôn dùng alias: FROM Users u, JOIN Orders o. Query 3+ bảng mà không alias = không ai đọc được kể cả bạn tuần sau.

03

Format SQL cho dễ đọc

Mỗi clause xuống 1 dòng. Indent sub-conditions. SQL không quan tâm whitespace — nhưng đồng đội quan tâm. Dùng extension như Poor SQL hoặc SQL Prompt.

04

Comment mọi query phức tạp

Query > 10 dòng → thêm comment giải thích WHY, không phải WHAT. Tương lai bạn sẽ cảm ơn hiện tại bạn.
-- Lấy top 5 sản phẩm bán chạy nhất Q1 2026 cho báo cáo marketing

05

Test với data edge cases

Query chạy đúng với 10 rows ≠ chạy đúng với production. Test với: NULL values, empty strings, duplicate data, 0 rows, 1 triệu rows.

06

Dùng BEGIN TRAN + ROLLBACK để test

Muốn test UPDATE/DELETE trên production mà không sợ?
BEGIN TRAN → chạy query → SELECT kiểm tra → ROLLBACK
Nếu OK → chạy lại với COMMIT.

07

Học cách đọc Execution Plan

Kỹ năng #1 để tối ưu SQL. Đọc từ phải sang trái, từ trên xuống dưới. Tìm: Table Scan → thêm index, Key Lookup → thêm INCLUDE, Sort cost cao → đã có index cho ORDER BY chưa?

08

EF Core ≠ không cần biết SQL

ORM sinh SQL cho bạn — nhưng SQL tệ vẫn tệ dù ORM sinh. Luôn check SQL mà EF Core tạo ra: .ToQueryString() hoặc SQL Profiler. N+1 query hay xảy ra nhất ở đây.

09

Biết khi nào KHÔNG dùng SQL

Full-text search → Elasticsearch. Cache hot data → Redis. Real-time analytics → ClickHouse. Time series → TimescaleDB. Document store → MongoDB. Đừng ép SQL làm mọi thứ.

10

Monitoring là MUST — không phải NICE-TO-HAVE

Setup alert cho: query > 5 giây, deadlock, connection pool > 80%, disk > 85%. Biết vấn đề trước khi user report = chuyên nghiệp.
