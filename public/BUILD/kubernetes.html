11.1 — Tại Sao Cần Orchestration?

Docker giải quyết "đóng gói app". Kubernetes giải quyết "chạy hàng trăm container trên nhiều server"

🐳 Docker là đủ? — Vấn đề khi scale

Bạn có Dockerfile, build image, docker run — ngon. Nhưng production thực tế:

❌ Chỉ có Docker — Đau đầu

Container chết lúc 3h sáng → ai restart? Cần 10 replicas → chạy docker run 10 lần thủ công? Server đầy → di chuyển container sang server khác bằng tay? Deploy version mới → tắt hết rồi bật lại = downtime?

✅ Có Kubernetes — Tự động

Container chết → K8s tự restart (self-healing). Khai báo "muốn 10 replicas" → K8s đảm bảo luôn có 10. Server chết → K8s reschedule container sang node khác. Deploy → rolling update, zero downtime tự động.

💡 Bản chất: Kubernetes là declarative — bạn khai báo "trạng thái mong muốn" (desired state), K8s liên tục so sánh với "trạng thái thực tế" (actual state) và tự động điều chỉnh để khớp. Đây gọi là reconciliation loop.

🧩 Kiến Trúc K8s — Control Plane vs Nodes

🧠
Control Plane

Bộ não cluster: api-server (cổng vào), etcd (DB lưu state), scheduler (xếp pod vào node), controller-manager (reconcile loop).

→
⚙️
Worker Node

kubelet (agent chạy pod), kube-proxy (network/routing), container runtime (containerd). Đây là nơi app của bạn thực sự chạy.

→
📦
Pods

Đơn vị nhỏ nhất K8s quản lý. 1 pod = 1+ container chia sẻ network/storage. App của bạn chạy trong pod.

11.2 — Core Objects — 8 Khái Niệm Phải Biết

Mọi thứ trong K8s đều là "object" khai báo bằng YAML. Đây là 8 object cốt lõi

Pod — đơn vị deploy nhỏ nhất. 1+ container cùng chia sẻ IP, volume. Thường 1 pod = 1 app container. Ephemeral (có thể chết bất kỳ lúc nào).
ReplicaSet — đảm bảo luôn có N pod chạy. Pod chết → tạo pod mới. Ít khi dùng trực tiếp, Deployment quản lý hộ.
Deployment — quản lý ReplicaSet, lo rolling update & rollback. Object bạn dùng nhiều nhất cho stateless app (API, web).
Service — IP/DNS ổn định cho nhóm pod. Pod đổi IP liên tục → Service làm "load balancer nội bộ" ổn định.
Ingress — định tuyến HTTP/HTTPS từ ngoài vào Service theo host/path. Cộng SSL termination. Cần Ingress Controller (nginx, Traefik).
ConfigMap — lưu config dạng key-value (non-secret): connection string, feature flag, app settings. Mount vào pod qua env hoặc file.
Secret — lưu dữ liệu nhạy cảm (password, token, cert). Giống ConfigMap nhưng base64 + RBAC chặt hơn. Nên dùng external secret store cho production.
Namespace — chia cluster thành "phòng" logic: dev, staging, prod. Cô lập resource, RBAC, quota theo team/môi trường.

🔌 Service Types — Phơi App Ra Ngoài Thế Nào

ClusterIP (mặc định)
# Chỉ truy cập trong cluster
# Dùng cho: DB, service nội bộ
type: ClusterIP
NodePort
# Mở port trên mọi node (30000-32767)
# Dùng cho: dev/test, không nên prod
type: NodePort
LoadBalancer
# Cloud LB (Azure/AWS) cấp IP public
# Dùng cho: phơi 1 service ra internet
type: LoadBalancer
Ingress (khuyến nghị)
# 1 LB + route nhiều service theo host/path
# Dùng cho: nhiều app, SSL, prod
kind: Ingress

11.3 — kubectl — Lệnh Cơ Bản Phải Thuộc

kubectl là CLI nói chuyện với api-server. 90% công việc hằng ngày nằm ở vài lệnh này

Xem tài nguyên
kubectl get pods # list pod
kubectl get pods -n prod # theo namespace
kubectl get all # mọi resource
kubectl get pods -o wide # thêm IP/node
kubectl get pods -w # watch realtime
Debug & điều tra
kubectl describe pod my-api # chi tiết + events
kubectl logs my-api # xem log
kubectl logs -f my-api # follow log
kubectl exec -it my-api -- sh # vào shell
kubectl get events --sort-by=.lastTimestamp
Apply & xóa (declarative)
kubectl apply -f deploy.yaml # tạo/cập nhật
kubectl apply -f ./k8s/ # cả thư mục
kubectl delete -f deploy.yaml
kubectl diff -f deploy.yaml # xem sẽ đổi gì
Scale & rollout
kubectl scale deploy my-api --replicas=5
kubectl rollout status deploy/my-api
kubectl rollout undo deploy/my-api # rollback
kubectl rollout history deploy/my-api
kubectl port-forward svc/my-api 8080:80
💡 Mẹo pro: Đặt alias alias k=kubectl và bật autocomplete. Dùng kubectl apply -f (declarative) thay vì kubectl create/run (imperative) để mọi thứ versioned trong Git — đây là nền tảng của GitOps.

11.4 — Manifest Hoàn Chỉnh — Deploy .NET API

Một bộ YAML thực tế production-ready cho ASP.NET Core API: Deployment + Service + Ingress + Config + Secret

📦 deployment.yaml — Deployment + Service

apiVersion: apps/v1
kind: Deployment
metadata:
  name: dotnet-api
  namespace: prod
  labels: { app: dotnet-api }
spec:
  replicas: 3                       # muốn 3 pod chạy
  selector:
    matchLabels: { app: dotnet-api }
  strategy:
    type: RollingUpdate            # cập nhật dần, zero downtime
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  template:
    metadata:
      labels: { app: dotnet-api }
    spec:
      containers:
        - name: api
          image: myregistry.azurecr.io/dotnet-api:1.4.2  # pin tag, không dùng :latest
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_URLS
              value: "http://+:8080"
          envFrom:
            - configMapRef: { name: api-config }
            - secretRef: { name: api-secret }
          resources:                   # luôn đặt requests/limits
            requests: { cpu: "100m", memory: "128Mi" }
            limits:   { cpu: "500m", memory: "256Mi" }
          livenessProbe:             # còn sống không?
            httpGet: { path: /healthz/live, port: 8080 }
            initialDelaySeconds: 10
            periodSeconds: 10
          readinessProbe:            # sẵn sàng nhận traffic chưa?
            httpGet: { path: /healthz/ready, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata: { name: dotnet-api, namespace: prod }
spec:
  selector: { app: dotnet-api }      # khớp pod qua label
  ports:
    - port: 80                       # cổng service
      targetPort: 8080               # cổng container
  type: ClusterIP

🔑 config.yaml — ConfigMap + Secret + Ingress

apiVersion: v1
kind: ConfigMap
metadata: { name: api-config, namespace: prod }
data:
  ASPNETCORE_ENVIRONMENT: "Production"
  Logging__LogLevel__Default: "Information"
---
apiVersion: v1
kind: Secret
metadata: { name: api-secret, namespace: prod }
type: Opaque
stringData:                          # stringData = plaintext, K8s tự base64
  ConnectionStrings__Default: "Server=db;Database=app;User=sa;Password=..."
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: dotnet-api
  namespace: prod
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"  # auto SSL
spec:
  ingressClassName: nginx
  tls:
    - hosts: [api.myapp.com]
      secretName: api-tls
  rules:
    - host: api.myapp.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: dotnet-api, port: { number: 80 } }
⚠️ Secret KHÔNG phải mã hóa: Secret chỉ base64-encode (ai cũng decode được). Production thật phải bật encryption at rest cho etcd + dùng external store: Azure Key Vault / AWS Secrets Manager + External Secrets Operator, hoặc Sealed Secrets. Đừng commit Secret YAML có plaintext vào Git.

11.5 — Health Probes, Scaling & Rolling Update

Self-healing và auto-scaling chỉ hoạt động đúng khi probe được cấu hình chuẩn

🩺 3 Loại Probe — Đừng Nhầm Lẫn

Liveness Probe

"App còn sống không?"

Fail → K8s restart container
Dùng cho: phát hiện deadlock, treo
Endpoint phải nhẹ, không check DB (tránh restart oan khi DB chậm)

Readiness Probe

"Sẵn sàng nhận traffic chưa?"

Fail → K8s ngắt traffic (không restart)
Dùng cho: warmup, chờ DB/cache sẵn sàng
Quan trọng nhất cho zero-downtime deploy

Startup Probe

"App khởi động xong chưa?" — dành cho app khởi động chậm (legacy .NET, JVM)

Trong khi startup chạy, liveness/readiness bị tạm hoãn → tránh K8s giết app đang boot
Đặt failureThreshold cao để cho app đủ thời gian khởi động
💡 ASP.NET Core: Dùng package Microsoft.Extensions.Diagnostics.HealthChecks → app.MapHealthChecks("/healthz/ready") với DB/cache check, và /healthz/live chỉ trả 200 đơn thuần.

📈 HPA — Horizontal Pod Autoscaler

Tự động tăng/giảm số pod theo tải (CPU, memory, hoặc custom metric). Cần Metrics Server cài sẵn.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: dotnet-api, namespace: prod }
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: dotnet-api
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }  # scale khi CPU > 70%
⚠️ HPA cần resource requests: HPA tính % dựa trên resources.requests. Không khai báo requests → HPA không biết tính theo gì → không hoạt động. Đây là lỗi #1 của người mới. Cho scale theo queue length / RPS, dùng KEDA (event-driven autoscaling), 2026 đã là chuẩn cho workload theo sự kiện.

🔄 Rolling Update — Cập Nhật Không Downtime

1

Đổi image tag → apply

kubectl set image deploy/dotnet-api api=...:1.4.3 hoặc sửa YAML rồi kubectl apply.

2

K8s tạo pod mới (maxSurge)

Tạo thêm pod version mới. Chờ readiness probe PASS mới đưa vào Service.

3

Tắt dần pod cũ (maxUnavailable)

Pod mới ready → drain & terminate pod cũ từng cái. Luôn có pod phục vụ traffic.

4

Lỗi? Rollback tức thì

kubectl rollout undo deploy/dotnet-api → quay về ReplicaSet trước đó trong vài giây.

11.6 — Managed K8s, Helm & Học Tập

Đừng tự vận hành control plane — dùng managed. Helm để đóng gói. k3s để học trên laptop

☁️ Managed Kubernetes — Big 3

AKS — Azure Kubernetes Service

Tốt nhất cho: hệ sinh thái .NET / Microsoft
Control plane miễn phí (trả tiền node)
Tích hợp Entra ID, ACR, Key Vault
Workload Identity (OIDC) sẵn
Lựa chọn tự nhiên nếu team đã dùng Azure DevOps + .NET.

EKS — Elastic Kubernetes Service

Tốt nhất cho: hạ tầng đã ở AWS
Control plane ~$0.10/giờ/cluster
IRSA / Pod Identity (OIDC → IAM)
Fargate (serverless node) tùy chọn
Hệ sinh thái rộng nhất, nhiều dịch vụ tích hợp.

GKE — Google Kubernetes Engine

Tốt nhất cho: trải nghiệm K8s mượt nhất
GKE Autopilot — Google lo node hộ bạn
Google là cha đẻ Kubernetes
Auto-upgrade, auto-repair mạnh
Vận hành ít công nhất, đặc biệt với Autopilot.
💡 Đừng dựng K8s thủ công cho production. Tự quản control plane + etcd backup + upgrade = full-time job. Managed K8s lo control plane, bạn chỉ lo workload. Chi phí thêm rất đáng so với rủi ro vận hành.

⎈ Helm — Package Manager cho K8s

Khi có 10 môi trường × 20 microservice, copy-paste YAML là địa ngục. Helm đóng gói YAML thành chart có biến (values), template hóa và versioned.

Lệnh Helm cơ bản
helm repo add bitnami https://...
helm install my-api ./chart \
  -f values.prod.yaml
helm upgrade my-api ./chart --install
helm rollback my-api 1
helm list -n prod
templates/deployment.yaml (template hóa)
spec:
  replicas: {{ .Values.replicas }}
  # values.yaml: replicas: 3
image: {{ .Values.image.repo }}:{{ .Values.image.tag }}
  # 1 chart, nhiều values theo môi trường
