Networking nền tảng cho Deploy

Khi user gõ myapp.com đến lúc thấy trang web, có cả chục bước mạng diễn ra.
Hiểu IP, port, DNS, reverse proxy và firewall sẽ giúp bạn deploy đúng và debug "tại sao site không vào được" trong vài phút thay vì vài giờ.

🌐

1. IP & Cổng (Ports)

Địa chỉ IP = "số nhà" của server. Port = "căn hộ" cụ thể trong nhà đó.

📍 IP Address & Port — Ví Von Đơn Giản

🏠 IP Address

Là địa chỉ duy nhất của một máy trên mạng, vd 203.0.113.10 (IPv4) hoặc dạng dài IPv6. Giống số nhà — để gói tin tìm đúng server.

🚪 Port

Một server chạy nhiều dịch vụ cùng lúc. Port (0–65535) phân biệt chúng. Web HTTP ở 80, HTTPS ở 443. Giống số căn hộ trong toà nhà.

💡 Một địa chỉ đầy đủ là IP:PORT — ví dụ 203.0.113.10:443. Trình duyệt tự ngầm hiểu https:// = port 443 nên bạn không phải gõ.

2. Vòng Đời Một Request HTTP(S)

Chuyện gì xảy ra giữa lúc gõ URL và lúc trang hiện ra — bao gồm cả DNS resolution.

🧭 Hành Trình Của Một Request

1
DNS Resolution

Trình duyệt hỏi: "myapp.com có IP gì?". Hỏi DNS resolver → root server → TLD (.com) → nameserver của domain → trả về 203.0.113.10. Kết quả được cache lại theo TTL.

2
TCP Handshake

Trình duyệt mở kết nối TCP tới 203.0.113.10:443 qua "bắt tay 3 bước" (SYN → SYN-ACK → ACK).

3
TLS Handshake

Với HTTPS, hai bên trao đổi chứng chỉ và thoả thuận khoá mã hoá. Từ đây mọi dữ liệu đều được mã hoá.

4
HTTP Request

Trình duyệt gửi GET / HTTP/1.1 kèm headers (Host, Cookie, User-Agent...).

5
Server xử lý

Reverse proxy (Nginx) nhận request, chuyển tới app backend (vd .NET ở :5000), app truy vấn DB và dựng response.

6
HTTP Response

Server trả status code (200 OK, 404, 500...) kèm HTML/JSON. Trình duyệt render và tải tiếp CSS/JS/ảnh.

🔢 Status Code Cần Nhớ Khi Deploy

3. Reverse Proxy (Nginx)

Cánh cửa đứng trước app của bạn: nhận mọi request từ internet rồi chuyển vào trong.

📖 Reverse Proxy Là Gì & Tại Sao Cần?

App .NET/Node của bạn chạy ở cổng nội bộ như 5000, không nên phơi thẳng ra internet. Đặt một reverse proxy (Nginx) ở cổng 80/443 để làm "lễ tân" tiếp nhận và phân phối.

TLS termination — Nginx lo việc HTTPS/chứng chỉ, app không phải bận tâm.
Định tuyến — /api tới backend, / tới frontend, gom nhiều app sau 1 domain.
Load balancing — chia tải sang nhiều instance app.
Bảo vệ & cache — chặn request xấu, rate limit, phục vụ file tĩnh nhanh.

📝 Cấu Hình Nginx Reverse Proxy — Ví Dụ Thật

/etc/nginx/sites-available/myapp.conf
server {
    listen 80;
    server_name myapp.com www.myapp.com;
    # Ép HTTP → HTTPS
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name myapp.com www.myapp.com;

    ssl_certificate     /etc/letsencrypt/live/myapp.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/myapp.com/privkey.pem;

    # Chuyển mọi request vào app nội bộ ở cổng 5000
    location / {
        proxy_pass         http://127.0.0.1:5000;
        proxy_http_version 1.1;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}
Kích hoạt & nạp lại Nginx
sudo ln -s /etc/nginx/sites-available/myapp.conf /etc/nginx/sites-enabled/
sudo nginx -t            # Kiểm tra cú pháp config — LÀM TRƯỚC KHI reload
sudo systemctl reload nginx   # Áp dụng mà không ngắt kết nối
⚠️ Luôn chạy nginx -t trước khi reload. Một dấu ; thiếu trong config sẽ khiến Nginx không khởi động lại được và toàn bộ site sập. nginx -t bắt lỗi cú pháp an toàn.

4. Firewall, localhost & 0.0.0.0

Hai khái niệm gây bối rối nhất với người mới deploy — và là nguồn gốc của vô số lỗi "không kết nối được".

🔥 Firewall với ufw (Ubuntu)

Firewall quyết định cổng nào được mở ra internet. Mặc định nên chặn hết, chỉ mở cái cần.

Cấu hình ufw an toàn cho web server
sudo ufw default deny incoming    # Chặn mọi kết nối vào theo mặc định
sudo ufw default allow outgoing   # Cho phép server gọi ra ngoài
sudo ufw allow 22/tcp             # SSH — MỞ TRƯỚC kẻo tự khoá mình ra ngoài
sudo ufw allow 80/tcp             # HTTP
sudo ufw allow 443/tcp            # HTTPS
sudo ufw enable                   # Bật firewall
sudo ufw status numbered          # Xem các rule đang áp dụng
⚠️ Mở cổng 22 (SSH) TRƯỚC khi ufw enable. Nếu bật firewall mà chưa allow SSH, bạn sẽ bị đá khỏi server và không vào lại được (trừ khi có console của nhà cung cấp VPS).

🆚 localhost (127.0.0.1) vs 0.0.0.0

🏠 127.0.0.1 / localhost

App chỉ nghe kết nối từ chính máy đó
Bên ngoài KHÔNG truy cập được
Dùng cho: app backend nằm sau reverse proxy — đúng cách an toàn
Nginx ở cùng máy vẫn gọi được qua proxy_pass http://127.0.0.1:5000

🌍 0.0.0.0

App nghe trên mọi network interface
Truy cập được từ bên ngoài (nếu firewall mở)
Dùng cho: app trong container Docker (để host map cổng vào được)
Cẩn thận — phơi app ra mạng, cần firewall che chắn
💡 Lỗi hay gặp: "App chạy trên máy mà gọi từ ngoài không được". Thường vì app bind vào localhost. Trong Docker, set ASPNETCORE_URLS=http://+:8080 hoặc http://0.0.0.0:8080 để nghe mọi interface trong container.

5. Load Balancer & CDN

Khi một server không đủ: chia tải và đưa nội dung tới gần user hơn.

⚖️ Load Balancer — Chia Tải

Khi traffic lớn, bạn chạy nhiều bản (instance) app giống nhau. Load balancer đứng trước, phân phối request đều ra các instance — nếu một con chết, nó tự bỏ qua.

💡 Nginx có thể làm load balancer cơ bản (block upstream). Ở cloud thì dùng dịch vụ chuyên dụng: AWS ALB, Azure Load Balancer, GCP Cloud Load Balancing — tự co giãn và health check.

🌎 CDN — Đưa Nội Dung Tới Gần User

CDN (Content Delivery Network) là mạng máy chủ phân tán khắp thế giới, cache file tĩnh (ảnh, CSS, JS, video) ở "edge" gần user. User ở Việt Nam tải từ server Singapore thay vì bay sang Mỹ → nhanh hơn nhiều và giảm tải cho server gốc (origin).

✅ Lợi ích CDN

Giảm latency — phục vụ từ edge gần nhất
Giảm tải origin server
Chống DDoS, hấp thụ traffic đột biến
Tiết kiệm băng thông origin

🏢 Nhà cung cấp phổ biến

Cloudflare — phổ biến nhất, có free tier mạnh
AWS CloudFront
Fastly, Akamai — enterprise
Vercel/Netlify đã tích hợp CDN sẵn cho frontend
⚠️ Cẩn thận cache: CDN cache file tĩnh nên sau khi deploy bản mới, user có thể vẫn thấy bản cũ. Giải pháp: đặt tên file kèm hash (app.4f8a2.js) hoặc "purge cache" sau mỗi lần deploy.

🛠️ Lệnh Debug Mạng Hữu Ích

Bộ công cụ khi "site không vào được"
ping myapp.com            # Server có sống & phân giải DNS được không
curl -I https://myapp.com   # Xem status code + headers (không tải body)
curl -v http://localhost:5000   # Test app nội bộ từ trên server
dig myapp.com             # Tra cứu DNS records chi tiết
nslookup myapp.com        # Domain trỏ về IP nào
ss -tulpn                 # Liệt kê cổng đang lắng nghe + tiến trình
traceroute myapp.com      # Gói tin đi qua những chặng nào
