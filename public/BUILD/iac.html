12.1 — Tại Sao Cần IaC?

Tạo server bằng click chuột = không tái tạo được, không ai biết ai đổi gì, drift lan tràn

🖱️ ClickOps vs IaC

❌ ClickOps — Click vào portal

Tạo VM bằng tay trên Azure Portal. 6 tháng sau ai nhớ config gì? Server chết → dựng lại mất 2 ngày mò mẫm. Staging khác production vì "ai đó sửa tay". Không audit, không rollback, không review.

✅ IaC — Hạ tầng bằng code

Toàn bộ hạ tầng trong file .tf commit Git. Server chết → terraform apply dựng lại y hệt trong 5 phút. Staging = production vì cùng code (khác variables). Mọi thay đổi qua PR, có review + audit.

💡 "Pets vs Cattle": Server kiểu pet — đặt tên, vuốt ve, chết là khóc, chữa bằng tay. Server kiểu cattle — đánh số, chết là thay con mới từ code. IaC biến hạ tầng từ pet thành cattle. Đây là tư duy cốt lõi của Platform Engineering 2026.

📐 Declarative vs Imperative

Declarative — Khai báo "muốn gì"

Terraform, Bicep, K8s YAML, CloudFormation

Bạn mô tả trạng thái cuối: "tôi muốn 1 VM + 1 network"
Tool tự tính cần làm gì để đạt được
Chạy lại nhiều lần → kết quả như nhau (idempotent)
✅ Chuẩn IaC hiện đại

Imperative — Ra lệnh "làm gì"

Bash script, Azure CLI thuần, Ansible (phần lớn)

Bạn viết từng bước: "tạo VM, rồi tạo network, rồi gắn..."
Bạn tự lo logic "đã tồn tại chưa?"
Chạy 2 lần → có thể tạo trùng / lỗi
⚠️ Hợp cho config/automation hơn provisioning
🌍

12.2 — Terraform — Nền Tảng

Terraform (HashiCorp) là chuẩn de-facto: đa cloud, ngôn ngữ HCL, state-based. Lưu ý license đổi sang BSL 2023 → bản fork OpenTofu (MPL) cũng phổ biến 2026

🧩 4 Khái Niệm Cốt Lõi

Provider — plugin nói chuyện với cloud (azurerm, aws, google). Khai báo provider nào, version nào.
Resource — một thứ hạ tầng (VM, network, DB). Đơn vị xây dựng chính của Terraform.
State — file terraform.tfstate ghi nhớ "đã tạo gì". Terraform so state với code để biết phải thay đổi gì.
Variables / Outputs — tham số hóa input (variable) và xuất giá trị ra (output: IP, connection string).

📄 Ví Dụ Thực Tế — Provision VM + Network trên Azure

# main.tf — Provider
terraform {
  required_providers {
    azurerm = { source = "hashicorp/azurerm", version = "~> 4.0" }
  }
  backend "azurerm" {}    # remote state, cấu hình khi init
}
provider "azurerm" { features {} }

# variables.tf
variable "location"     { default = "southeastasia" }
variable "vm_size"      { default = "Standard_B2s" }
variable "admin_password" { type = string, sensitive = true }  # không log ra

# Resource — Resource Group + Network
resource "azurerm_resource_group" "rg" {
  name     = "rg-webapp-prod"
  location = var.location
}
resource "azurerm_virtual_network" "vnet" {
  name                = "vnet-prod"
  address_space       = ["10.0.0.0/16"]
  location            = azurerm_resource_group.rg.location
  resource_group_name = azurerm_resource_group.rg.name
}
resource "azurerm_subnet" "subnet" {
  name                 = "subnet-web"
  resource_group_name  = azurerm_resource_group.rg.name
  virtual_network_name = azurerm_virtual_network.vnet.name
  address_prefixes     = ["10.0.1.0/24"]
}

# Resource — Linux VM
resource "azurerm_linux_virtual_machine" "web" {
  name                = "vm-web-01"
  resource_group_name = azurerm_resource_group.rg.name
  location            = azurerm_resource_group.rg.location
  size                = var.vm_size
  admin_username      = "azureuser"
  admin_password      = var.admin_password
  network_interface_ids = [azurerm_network_interface.nic.id]
  os_disk { caching = "ReadWrite", storage_account_type = "Premium_LRS" }
  source_image_reference {
    publisher = "Canonical", offer = "ubuntu-24_04-lts"
    sku       = "server",    version = "latest"
  }
}

# outputs.tf — xuất giá trị ra ngoài
output "vm_private_ip" { value = azurerm_network_interface.nic.private_ip_address }
Chạy
terraform init
terraform plan -out=tfplan
terraform apply tfplan
terraform output vm_private_ip
Truyền secret an toàn
# KHÔNG hardcode password trong .tf
export TF_VAR_admin_password=$SECRET
# hoặc đọc từ Key Vault qua data source

📦 Modules — Tái Sử Dụng & Chuẩn Hóa

Module = nhóm resource đóng gói tái dùng. Ví dụ module "network" dùng cho mọi môi trường, chỉ đổi variables.

# Gọi module thay vì copy-paste resource
module "network" {
  source   = "./modules/network"     # local, hoặc registry, hoặc git
  vnet_cidr = "10.0.0.0/16"
  env       = "prod"
}
# Tách môi trường bằng workspace hoặc thư mục riêng + tfvars
#   terraform apply -var-file="prod.tfvars"

12.3 — Bicep & Pulumi — Lựa Chọn Khác

Terraform không phải lựa chọn duy nhất. Tùy hệ sinh thái và sở thích ngôn ngữ

ĐA CLOUD
🌍

Terraform / OpenTofu

Ngôn ngữ HCL khai báo. Đa cloud, hệ sinh thái module khổng lồ. OpenTofu là fork open-source (MPL) sau khi Terraform đổi sang BSL.

✓ Phổ biến nhất, nhiều provider
Đa cloud, team lớn, chuẩn ngành
💪

Bicep (Azure)

DSL của Microsoft, biên dịch ra ARM template. Cú pháp sạch hơn ARM nhiều. Chỉ cho Azure, state do Azure tự quản (không cần file state riêng).

✓ Native Azure, không lo state file
Team thuần Azure / .NET
⚡

Pulumi

Viết hạ tầng bằng ngôn ngữ thật: C#, TypeScript, Python, Go. Có loop, condition, hàm — không học DSL mới. Đa cloud.

✓ Dùng C#/TS, IDE + test thật
Dev thích code hơn DSL, logic phức tạp
💡 Chọn sao? Thuần Azure → Bicep. Đa cloud hoặc chuẩn ngành → Terraform/OpenTofu. Team dev mạnh muốn dùng C#/TypeScript với vòng lặp/test → Pulumi. Đừng trộn nhiều tool trong cùng một dự án.
🔄

12.4 — GitOps — Git Là Nguồn Sự Thật

Đưa IaC lên một tầm cao: Git repo = trạng thái mong muốn, một agent tự đồng bộ cluster theo Git

📖 GitOps là gì?

Thay vì kubectl apply / terraform apply thủ công từ laptop, một operator chạy trong cluster (Argo CD / Flux) liên tục so Git với cluster và tự kéo về cho khớp.

1

Commit thay đổi manifest vào Git

Sửa số replicas / image tag → mở PR → review → merge vào main.

2

Operator phát hiện thay đổi

Argo CD / Flux poll repo (hoặc qua webhook), thấy Git ≠ cluster.

3

Tự động sync về cluster

Operator apply thay đổi. Không ai cần quyền kubectl vào prod nữa.

4

Self-heal & rollback = git revert

Ai sửa tay cluster → operator kéo về đúng Git. Rollback = git revert.

💡 Lợi ích lớn nhất: Mọi thay đổi production đi qua Git → audit hoàn chỉnh (ai, khi nào, vì sao), review qua PR, rollback bằng revert. Không ai cần credential prod trên máy cá nhân. Argo CD và Flux là 2 tool GitOps phổ biến nhất 2026.
💾

12.5 — State & Drift — Best Practices

State file là trái tim của Terraform. Quản sai = mất hạ tầng hoặc lộ secret

🌊 Drift là gì?

Drift = hạ tầng thực tế lệch khỏi code, do ai đó sửa tay trên portal. Code nói "1 VM", thực tế ai đó thêm VM thứ 2 qua portal → state không biết → lần apply tiếp theo gây kết quả bất ngờ.

terraform plan          # phát hiện drift (resource bị sửa ngoài code)
terraform apply         # kéo thực tế về khớp code (xóa thay đổi tay)
terraform import ...    # nhập resource tạo tay vào state để quản lý

✅ Checklist Quản Lý State

🔴
Remote state, KHÔNG local

Lưu state ở Azure Blob / S3 + DynamoDB, không để .tfstate trên laptop. Mất laptop = mất state = không quản được hạ tầng.

🔴
State locking

Bật lock (S3+DynamoDB / Azure Blob lease) để 2 người không apply cùng lúc → corrupt state.

🟡
Đừng commit state vào Git

State chứa secret dạng plaintext (password, key). .gitignore phải có *.tfstate*.

🟡
Đừng sửa tay (no ClickOps)

Mọi thay đổi qua code + PR. Sửa tay tạo drift. Đặt policy chặn quyền write thủ công trên prod.

🔵
plan trong CI, apply có gate

PR chạy terraform plan tự động, comment kết quả vào PR. Apply chỉ sau khi merge + approve gate.

🔵
Pin version provider

version = "~> 4.0" để build tái lập. Provider tự nâng major có thể phá apply.

⚠️ State = secret store ngầm: File tfstate lưu mọi thuộc tính resource ở plaintext, kể cả password DB và key. Bất kỳ ai đọc được state = đọc được hết secret. Mã hóa backend, hạn chế quyền truy cập state nghiêm ngặt như với production database.
